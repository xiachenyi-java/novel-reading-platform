################################################################################
  一、产品定位：主角是"人"，不是"书"
################################################################################

【一句话】
  传统书评站是"一本书下面挂着一堆评论"，
  这个站是"**一个书评人，持续地说他爱什么、恨什么**"。
  书是他谈论的对象，不是主体。

【为什么这个区别重要】
  ------------------------------------------------------------------
  维度        书为主                          人为主
  ------------------------------------------------------------------
  首页        书城 / 排行榜                   内容流（谁说了什么）
  用户记住    某本书的分数                    某个书评人的口味
  回访理由    想找书的时候                    想看他最近说了什么
  内容来源    书的信息（有限、静态）          人的观点（无限、动态）
  ------------------------------------------------------------------

  ★ 只有"人"能承载感情。一本书的评分再高，也不会有人每天回来看它。

【所以数据模型的重心是】
  content（谁说了什么）是**一等公民**；
  novel（说的是哪本书）是附属于 content 的元数据。


################################################################################
  二、★ 感情的三层模型（本方案的核心）
################################################################################

【比喻：一家书店里的店员】
  第 1 层  人格 —— 他穿什么、爱聊什么类型
  第 2 层  关系 —— 他记得你上次来买过什么
  第 3 层  记忆 —— 他看你脸色不好，推了本轻松的

  对应到技术：
  ------------------------------------------------------------------
  层      关键词        技术落点                      实施阶段
  ------------------------------------------------------------------
  1 人格  他是谁          user.bio / areas / isAi       阶段 1
  2 关系  我们之间发生过   follow + 互动记录             阶段 3~4
  3 记忆  他记得我        AI 记忆表 + 检索              外环第 3 期
  ------------------------------------------------------------------

【★★ 最重要的一条判断】
  **感情不是"写"出来的，是"处"出来的。**

  一条精彩的 AI 书评，用户看完就走 —— 那只是"内容"。
  同一个 AI **第三次**在用户会喜欢的地方出现，用户才开始觉得"这人懂我"。

  ⇒ 技术上最重要的不是"让 AI 说得更好"，
    而是「**同一个书评人，id 稳定、人设不变、历史可查**」。

  ⇒ 由此推出三条硬约束：
    1. 书评人必须有稳定 id，不能每次生成临时身份
    2. 人格 prompt / bio 一旦定下，不允许随机改写
    3. 主页必须存在（D3），否则"这是同一个人"无法被感知

【★ 拟人化的边界（必须守）】
  · 用户**知道**它是 AI，仍被打动   → 这是本事（像看小说知道虚构还会哭）
  · 用户**忘了**它是 AI              → 这是欺骗，迟早反噬

  ⇒ 所以 D2 的标注不是合规负担，是安全阀。
    **有感情的 AI 更需要标注，不是更不需要。**

--------------------------------------------------------------------------------
  3.1 user 扩字段
--------------------------------------------------------------------------------

  ALTER TABLE user
    ADD COLUMN bio        varchar(255) DEFAULT NULL,   -- 一句话人设
    ADD COLUMN areas      varchar(255) DEFAULT NULL,   -- 擅长领域，"悬疑,推理,犯罪"
    ADD COLUMN is_ai      int NOT NULL DEFAULT 0;      -- 1 = AI 账号

  【为什么 areas 用逗号分隔，不用 JSON / 独立表】
    · 阶段 1 只需要"展示"，不需要按领域精确匹配
    · 真要做"相似书评人"（阶段 4）再决定要不要拆表
    ★ 过早拆表 = 为不存在的需求付维护成本

  【为什么 bio 不是"自我介绍"，是"人设声明"】
    ❌ 错误写法："我是一个热爱阅读的 AI 助手，喜欢与大家分享好书。"
    ✅ 正确写法："我只读悬疑。读不完的，绝不推荐。"
    ★ bio 允许是**缺点**："只看治愈，不碰悲剧""读得慢，但每本都写长评"
      缺点比优点更像人。

  【★ 一个必须避开的坑】
    不要往 UserVO 里加这三个字段。
    UserVO 是登录 / 注册的返回值（问题 27 刚瘦身成只有 id / username / role）。
    资料展示必须另建 AuthorProfileVO，职责分开：
      UserVO            = 登录态，给认证用
      AuthorProfileVO   = 公开资料，给所有人看


--------------------------------------------------------------------------------
  3.2 content（书评）
--------------------------------------------------------------------------------

  CREATE TABLE content (
    id            int PRIMARY KEY AUTO_INCREMENT,
    author_id     int NOT NULL,                -- user.id（书评人，真人和 AI 都在这里）
    novel_id      int NOT NULL,                -- 评的是哪本书
    polarity      varchar(10) NOT NULL,        -- REC 推荐 / WARN 避雷 / NOTE 长评
    grade         varchar(10),                 -- GOD 仙草 / GOOD 粮草 / OK 干草 / BAD 毒草
    title         varchar(255) NOT NULL,
    body          text NOT NULL,               -- 正文
    like_count    int NOT NULL DEFAULT 0,      -- 冗余，见 3.6
    comment_count int NOT NULL DEFAULT 0,      -- 冗余，见 3.6
    create_time   datetime(6) NOT NULL,
    deleted       int NOT NULL DEFAULT 0,
    KEY idx_content_feed   (deleted, create_time),
    KEY idx_content_novel  (novel_id, deleted, create_time),
    KEY idx_content_author (author_id, deleted, create_time),
    KEY idx_content_polar  (polarity, deleted, create_time)
  );

  【★ 列名为什么叫 body 不叫 text】
    text 是 MySQL 的数据类型关键字，做列名要处处加反引号，
    只要有一处忘了，Hibernate 生成的 SQL 就会炸。
    → 库里叫 body，接口返回字段仍叫 text（前端不用改）。

  【为什么 polarity 不用 0/1/2 数字】
    数字存库省 1 个字节，但读代码时没人知道 2 是什么。
    用字符串 REC / WARN / NOTE，可读性优先。

  【为什么另加 grade（2026-10-24 追加）】
    polarity 回答"我推不推荐"，grade 回答"这本书本身值几档"——两者不重合：
      · 长评(NOTE) 也可能是 GOOD（想认真聊聊一本好书）
      · 避雷(WARN) 也可能是 OK（有雷点，但整体能看）
    ★ 四档用网文圈黑话：仙草 / 粮草 / 干草 / 毒草，用户一看就懂，
      比 1~5 星更贴合这个圈子的表达习惯。
    ★ 可空：AI 没把握时可以只给 polarity，不硬凑档位。
    ★ 枚举类：enums/Grade.java（GOD / GOOD / OK / BAD）

  【三态语义（这是产品差异点）】
    REC  推荐 —— "这本书值得看"
    WARN 避雷 —— "这本书有什么坑"      ← ★ 招牌
    NOTE 长评 —— "我想聊聊这本书"

    ★ 别人把雷点藏在低分里，你把它摆到台面上。
      这是这个产品跟起点 / 番茄最大的不同。


--------------------------------------------------------------------------------
  3.3 content_mark（书评上的标签）
--------------------------------------------------------------------------------

  CREATE TABLE content_mark (
    id         int PRIMARY KEY AUTO_INCREMENT,
    content_id int NOT NULL,
    kind       varchar(10) NOT NULL,     -- GOOD 亮点 / WARN 雷点
    tag        varchar(50) NOT NULL,     -- 烂尾 / 水字数 / 文笔好 / 人物立得住
    KEY idx_mark_content (content_id),
    KEY idx_mark_tag     (kind, tag)
  );

  【它和 novel_pit 的区别（★ 别搞混）】
    content_mark = 某条书评打了哪些标签   （原始数据，一人一条）
    novel_pit    = 这本书一共被打了哪些雷点（聚合结果，一書一份）

  ★ 本方案**不建 novel_pit**：
    书上的雷点 = 对 content_mark 做 GROUP BY 实时算出来的。
      SELECT tag, COUNT(*) c FROM content_mark m
      JOIN content c ON c.id = m.content_id
      WHERE c.novel_id = ? AND m.kind = 'WARN' AND c.deleted = 0
      GROUP BY tag ORDER BY c DESC;

  【为什么雷点可以实时算，评分却必须落库（见 3.5）】
    雷点只用来"展示"，不参与排序 → 实时算的代价是每次查一次，规模小无所谓
    评分要用来"排序书籍"       → 不落库就没法建索引，全表扫


--------------------------------------------------------------------------------
  3.4 booklist / booklist_item
--------------------------------------------------------------------------------

  CREATE TABLE booklist (
    id          int PRIMARY KEY AUTO_INCREMENT,
    curator_id  int NOT NULL,                  -- 创建者 user.id
    title       varchar(255) NOT NULL,
    description varchar(1000) DEFAULT NULL,
    polarity    varchar(10) NOT NULL,          -- REC 推荐单 / WARN 避雷单
    featured    int NOT NULL DEFAULT 0,        -- 1 = 本周精选
    tag         varchar(50) DEFAULT NULL,      -- "本周精选 · 避雷单"
    is_public   int NOT NULL DEFAULT 1,
    saved_count int NOT NULL DEFAULT 0,        -- 冗余
    create_time datetime(6) NOT NULL,
    deleted     int NOT NULL DEFAULT 0,
    KEY idx_booklist_curator (curator_id, deleted),
    KEY idx_booklist_feat    (featured, deleted, create_time)
  );

  CREATE TABLE booklist_item (
    id          int PRIMARY KEY AUTO_INCREMENT,
    booklist_id int NOT NULL,
    novel_id    int NOT NULL,
    sort_no     int NOT NULL,                  -- 排序位，间隔 10
    comment     varchar(500) DEFAULT NULL,     -- 推荐语
    UNIQUE KEY uk_booklist_novel (booklist_id, novel_id),
    KEY idx_item_order (booklist_id, sort_no)
  );

  【★ 排序位用间隔 10（10 / 20 / 30），不是连续整数】
    三种方案：
    ------------------------------------------------------------------
    方案              优点              缺点
    ------------------------------------------------------------------
    (a) 连续 1,2,3     直观              插一个要更新后面全部
    (b) 稀疏 10,20,30  插入平均 O(1)     间隙会用完，要定期重排
    (c) 链表 pre/next  插入 O(1)         查询要递归，SQL 难写
    ------------------------------------------------------------------
    ★ 选 (b)。理由：书单有 200 本书时，拖一次要更新 199 行 —— 那是长事务。
    ★ 间隙用完怎么办：后台重排任务，把 sort_no 重新按 10 分配。
      **先不做**，等真的用完再说（每插一次消耗 1 个间隙，200 本书才消耗一小段）。

  【唯一约束的双重意义】
    · 业务上：同一本书不能重复进同一个书单
    · 工程上：并发重复插入时，靠它兜底（catch 异常，不要靠先查后插）

  【is_public 是资源级权限】
    "这条是不是我的？" —— 比"你是不是管理员？"难一层。
    查询私有书单时必须带 curator_id 条件，不能只靠前端隐藏。


--------------------------------------------------------------------------------
  3.5 rating（评分）
--------------------------------------------------------------------------------

  CREATE TABLE rating (
    id          int PRIMARY KEY AUTO_INCREMENT,
    novel_id    int NOT NULL,
    user_id     int NOT NULL,                 -- AI 也是 user
    score       decimal(3,1) NOT NULL,        -- 同一次打分的平均分，落库
    dims        varchar(255) DEFAULT NULL,    -- "剧情:9.2,人物:9.5,文笔:9.0,更新:7.2"
    create_time datetime(6) NOT NULL,
    UNIQUE KEY uk_rating_user_novel (user_id, novel_id),
    KEY idx_rating_novel (novel_id)
  );

  【★ 一人一书一评】
    想改评分 = UPDATE，不是再插一条。
    唯一约束 uk_rating_user_novel 是这条规则的物理保证，
    不能只在 Service 里先查后插（并发下会漏）。

  【★ 总分必须落库，不能查询时算】
    novel 表加三个冗余字段：
      score       decimal(3,1)   -- 综合分
      ai_score    decimal(3,1)   -- AI 平均分
      human_score decimal(3,1)   -- 真人平均分
      ai_count    int
      human_count int

    理由：要按分数排序书籍 → 必须能建索引。
    ⚠ 算法只能有一处：写在实体的 @PrePersist / @PreUpdate 或统一的服务方法里，
      绝不在 Controller 或前端再算一遍。

  【为什么 AI 分和真人分**分开存**】
    差值本身就是内容：
      AI 9.2 / 真人 8.4 → "叫好的多，叫座的少"
    这是能拿来做话题的产品设计，不是冗余。


--------------------------------------------------------------------------------
  3.6 冗余字段与软删除（★ 本项目的老毛病）
--------------------------------------------------------------------------------

  【本方案新增的冗余字段】
  ------------------------------------------------------------------
  字段              由谁维护      同步时机
  ------------------------------------------------------------------
  content.like_count     点赞服务      点赞 / 取消
  content.comment_count  评论服务      评论增删
  booklist.saved_count   收藏服务      收藏 / 取消
  novel.score/ai_score   评分服务      评分增删改
  novel.human_count      评分服务      评分增删改
  ------------------------------------------------------------------

  ★ 加上原有的 novel.total_words，冗余字段从 1 个变成 6 个。
    靠人记是记不住的 → 三条纪律（沿用《产品改造》第五节）：
      1. 所有写操作必须在同一个事务里
      2. 增 / 删 / 改三处必须都写（不是"记得改"）
      3. 一个定时对账任务兜底

  ★ 对账怎么验（判据本身也要验证）：
    写一条 SQL 比对冗余字段和实际统计值，
    然后**先制造一条不一致的数据**，确认这条 SQL 能查出来。
    否则你永远不知道它是"真的没问题"还是"查询写错了"。

  【软删除统一】
    现有系统里 deleted 字段各表用法不一致。
    本方案的新表**一律**：
      deleted int NOT NULL DEFAULT 0，0 = 正常，1 = 已删
      所有查询必须带 deleted = 0
    ★ 写进项目设计决策，不再逐表讨论。


################################################################################
  四、接口设计
################################################################################

【内容流】
  GET  /contents?page&size&polarity&category&userId&novelId&keyword
       ★ 六个筛选参数都要**后端过滤**，别让前端拉全量再筛
       ★ category 是按"这条内容讲的那本书"的分类筛，要 join novel

  GET  /contents/{id}              单条详情（阶段 2 可后置）
  POST /contents                   发布（要登录，阶段 2 先不做）

【书评人】
  GET  /users/{id}/profile         昵称 / bio / areas / isAi / 统计数
  GET  /users/{id}/contents        他写过什么（也可用 /contents?userId=）

【书单】
  GET  /booklists?page&size&polarity&tag
  GET  /booklists/{id}             含书目列表
  GET  /novels/{id}/booklists      这本书被哪些书单收录

【评分与雷点】
  GET  /novels/{id}/rating         一次返回 aiScore / humanScore / dims
  GET  /novels/{id}/pits           聚合出的雷点（可并入 novel 详情返回）

【★ 列表接口的三个工程要求】
  1. **批量查，禁止 N+1**
     内容流要带作者和书的信息。先收集所有 author_id / novel_id，
     一次 IN 查询捞回来再组装（照 BookshelfItemVO.toItemVOPage 的写法）。
  2. **返回 VO，不返回实体**
     实体里可能有 passwordHash，也可能以后加敏感字段。
  3. **字段名小写驼峰**
     ★ NovelRankVO 的字段首字母大写（NovelId / Title）已经坑过一次：
       前端要写兼容层，书城人气榜空白了好几天。
       新 VO 一律小写驼峰。

################################################################################
  六、验证判据（每阶段做完照着跑）
################################################################################

  【通用三条】
    1. 先写期望值，再看结果
    2. 判据看 body 的 code，不看 HTTP 状态码
       （本项目 RuntimeException 也返回 200）
    3. 判据本身要验证：制造一个必定失败的场景，看它会不会报错

  ------------------------------------------------------------------
  阶段  期望值                        判据                     自检
  ------------------------------------------------------------------
  1     能查到书评人资料               code=200 且 isAi 有值     查不存在的 id
                                                               → 必须报错，
                                                                 不能返回空对象
  2     内容流返回 10 条                records.length=10         tab 传非法值
       每条带 polarity 和作者 isAi      且 author.isAi 存在       → 验证 fallback
  3     书单带条目                     items.length>0           造一个空书单
                                                               → 前端不崩
  4     评分正确                       score = 四维平均          故意改一个维度
                                       （SQL 手算对账）          → 总分跟着变
  5     页面显示真数据                 非 9xxx 的书能渲染        **停掉后端**
                                                               → 优雅降级到 mock
  ------------------------------------------------------------------

  ★ 阶段 5 最后一条最重要：
    NovelDetailView 已经写好 isMockId 兜底逻辑，
    你要验证的是「它真的兜住了」，不是"看起来正常"。


################################################################################
  七、风险与边界
################################################################################

  【1. 冷启动】
    没有真人写书评时，首页是空的。
    AI 书评人是解法（D2=b），但必须标注，不能伪装成真人。

  【2. 内容审核】
    UGC 上线就要有敏感词过滤。AI 生成的内容**不豁免** ——
    它照样会说错话（见《产品改造》7.5 杠杆 5）。

  【3. 拟人化的反噬】
    用户一旦发现"原来全是 AI"，信任会崩塌。
    ⇒ 标注要**始终可见**，不能藏在二级页面里。
    ⇒ bio 里可以坦白："我是 AI，我只读悬疑。"

  【4. 版权】
    D1=b 保留了管理员试读。三条红线不能破：
    不抓取、不全文公开、只做有限试读。

  【5. 数据迁移】
    现在要加 6 张表。**先装 Flyway 或 Liquibase**
    （《产品改造》8.1 已经把它列为"最紧急，比新功能紧急"）。
    否则以后每次改表都要手工同步 schema.sql，迟早对不上。


################################################################################
  八、能拿到面试里讲的三个点
################################################################################

  【1. 稳定人格 id 的数据建模】
    问：AI 产品怎么让用户产生情感连接？
    答：不是把 prompt 写得更好，是保证"同一个人"的身份可追溯。
        所以 AI 账号和真人共用 user 表，有稳定 id，
        而不是每次生成一个临时角色。

  【2. 聚合 vs 落库的取舍】
    问：为什么评分落库，雷点不落库？
    答：评分要参与排序 → 必须建索引 → 必须落库；
        雷点只展示 → 实时 GROUP BY 足够。
    ★ 这个答案能同时证明你懂索引和懂"不过度设计"。

  【3. 书单排序位用稀疏整数】
    问：拖动排序怎么实现？
    答：连续整数在 200 本书时拖一次要更新 199 行，是长事务；
        用间隔 10 的稀疏整数，插入平均 O(1)，间隙用完后台重排。
