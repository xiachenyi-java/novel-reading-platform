################################################################################
  Q1　你怎么验证一个改动真的生效了？★★★　【测试】
################################################################################

- **考点**：★ 这是**方法论题**，也是本类最重要的一题。
  考的是"你有没有把'验证'当成一个需要设计的东西"，
  而不是"改完了跑一下看看"。

- **追问链**：
  Q1「怎么验证？」→ Q2「你怎么知道**判据本身**是对的？」★ 关键
  → Q3「中间态为什么要单独测？」→ Q4「为什么不用前后对比？」
  → Q5「验证工具本身会不会骗你？」（转到 Q3）

- **参考答案**：
  四条原则，都是踩坑踩出来的。

  **第一条：先把期望值写下来，再看结果**
  不写期望值，你会不自觉地把**任何结果都解释成成功**。
  我的实际例子：我以为"接口返回 HTTP 200 就是降级生效了"。
  实际上第一次演练返回的确实是 200 —— 但 body 是
  `{"code":500,"msg":"Redis command timed out"}`。
  如果没提前写下"期望：body.code == 200 且有数据"，
  我就会带着一个没修好的 bug 继续往下走。

  **第二条：判据要选对地方**
  我的 `GlobalExceptionHandler.handleRuntimeException` 没有
  `@ResponseStatus` 注解，所以**所有 RuntimeException 都返回 HTTP 200**。
  → 按"HTTP 200 = 成功"判断，失败会被读成成功，是个**假阳性判据**。
  → 正确判据是看 **body 里的 code 字段**。

  **第三条：故障演练 > 看代码**
  "代码看起来对"和"运行时真的对"是两回事。

  **第四条：用三阶段对比，而不是前后对比**
  我修降级时记录了三组数据，而不是"改前 / 改后"两组：

  | 阶段 | 耗时 | body.code | 接口可用性 |
  |---|---|---|---|
  | ① 改造前 | 60.0s 挂起 | 500 | ❌ |
  | ② 只加超时 | 0.51s | 500 | ❌ |
  | ③ 再加 try-catch | 1.01s | 200 | ✅ |

  ★ 加上中间态 ② 很重要 —— 它证明"只加超时不算修复"。
  如果只记"改前 60s / 改后 1s"，就会误以为"变快 60 倍 = 修好了"。

  ★ **判据本身也要验证**：制造一个**必定失败**的场景，
  看判据会不会报错。我第一次用"Redis 挂掉"就是这个作用 ——
  如果判据说"成功"，那判据就是错的。
  **假阳性判据比没有判据更危险**，因为它让你以为已经验证过了。

- **本项目的证据**：
  · 判据错误导致差点漏掉一个 P0 bug：手动 cacheManager 调用绕过了
    AOP 切面，CacheErrorHandler 静默失效
  · 故障演练命令：
    `docker stop demo2-redis` → `curl /novels/1` → `docker start demo2-redis`
  · 三阶段数据：60.0s 挂起 / 0.51s 快速失败 / 1.01s 真正降级
  · ★ "没有返回值的远程操作，等于没有错误处理" ——
    这是我发现 Lettuce 缓冲写命令后总结的（见 01-缓存体系 Q11）

- **坑**：
  ① 只说"我跑了一下，没问题"
  ② 只看 HTTP 状态码
  ③ 用前后对比而不是三阶段对比 —— 会漏掉"指标变好但问题没解决"的情况

################################################################################
  Q2　压测应该关注哪些指标？为什么不能只看平均值？　【测试】
################################################################################

- **考点**：【测试】标签。考的是"你会不会看数据"，
  而不是"你会不会跑压测工具"。

- **追问链**：
  Q1「看哪些指标？」→ Q2「为什么平均值会骗人？」
  → Q3「你还会额外看什么？」→ Q4「压测怎么保证可信？」

- **参考答案**：
  我关注四个：**最小 / P50 / P95 / 最大**，以及"超过阈值的个数"。

  **为什么平均值会骗人**：

  | 指标 | 值 |
  |---|---|
  | 最小 | 0.503s |
  | P50 | 1.491s |
  | P95 | 2.575s |
  | 最大 | 2.784s |
  | 平均 | 1.526s |

  平均值 1.526s 和 P50 1.491s 看起来很接近，好像"分布很集中"。
  但实际上**最小 0.503s 和最大 2.784s 差了 5.5 倍** ——
  平均值完全掩盖了这个分布。

  平均值的问题是：**它会被两端拉平**。
  一个 60 秒的请求 + 99 个 10ms 的请求，平均值是 610ms ——
  听起来还行，但那 1 个用户已经骂人了。

  **为什么 P95 / 最大 更重要**：
  用户感受到的不是平均值，是**他自己那次**。
  P95 才是"有 5% 的用户比这更慢"的意思。

  ★ **我额外看的一个指标：超过关键阈值的个数**
  "超过 5 秒的: 0 个" / "超过 60 秒的: 0 个"
  这个比 P95 更直白 —— 我能明确说"没有任何一个请求超过 5 秒"。

  ★ **还要对比"不该受影响的接口"**
  级联故障的定义是"**不依赖 Redis 的接口也被拖垮**"，
  所以要同时采样 `/novels` 列表：

  | 指标 | /novels/1 | /novels 列表（不依赖 Redis） |
  |---|---|---|
  | 最小 | 0.503s | 0.006s |
  | P50 | 1.491s | 0.248s |
  | 最大 | 2.784s | 2.162s |
  | HTTP 状态 | 全程 200 | 全程 200 |

  ★ 结论：Redis 挂了不影响不依赖 Redis 的接口，**级联故障被切断**。
  这句话只有在对比了列表接口之后才说得出口。

- **本项目的证据**：
  · 压测配置：500 请求 / 100 并发 / Redis 挂
  · 数据见上表，全部实测
  · ★ 我主动坦白两个**没搞懂的疑点**：
    P50 是单请求的 3 倍（猜测是 Lettuce 共享连接争用 / JVM GC，
    **但我没验证，不敢下结论**）；列表接口最大 2.162s
    （猜测 100 线程高频异常引发小 GC）

- **坑**：
  ① 只报一个"平均响应时间"
  ② 报了 P95 但说不出 P95 的定义
  ③ 只压测目标接口，不测"不该受影响的接口"

- **关联**：docs/实战笔记/05-缓存三大问题实战.txt 4.6 节


################################################################################
  Q3　你的测试脚本本身出过错吗？★　【测试】
################################################################################

- **考点**：【测试】标签。考的是"**验证工具本身也要验证**"这个意识。

- **追问链**：
  Q1「出过错吗？」→ Q2「你怎么发现是脚本的问题？」★ 关键
  → Q3「怎么避免这类问题？」→ Q4「怎么判断一次压测可信？」

- **参考答案**：
  出过，而且差点让我得出错误结论。

  **事故经过**：
  我第一次压测跑出 1000 条记录（应该是 500 条），
  其中 500 条耗时 **0.0003s**。
  我一度以为是"应用存在一条快速失败的路径"——
  这个解释听起来很合理，**差点就写进笔记了**。

  真相是**我的命令写错了**：
  ```bash
  seq 1 100 | xargs -P 100 -n1 curl -s -o /dev/null \
      -w "%{time_total}\n" "http://localhost:8080/novels/1"
  ```
  `xargs -n1` 把序号**追加**到了命令末尾，于是 curl 收到**两个 URL**：
    · `http://localhost:8080/novels/1`（真请求）
    · `1`（被当成 `http://1/`，瞬间失败）
  → 每个 curl 发两次请求、打两行耗时，多出来的 500 行全是噪声。

  ★ **我是靠一个"物理上不可能"的信号发现的**：
  **0.0003 秒完成一次 HTTP 请求** —— 那连 TCP 握手都不够。

  ★ 通用原则：**看到不符合物理常识的数字，先怀疑测量工具，
  再怀疑被测量的系统。**

- **本项目的证据**：
  · 修正写法：`xargs -P 100 -n1 sh -c 'curl ... "URL"'`
    （用 `sh -c` 把序号吃掉，不传给 curl）
  · 修正后样本数变成正好 500 条，最小耗时 0.503s
  · ★ **交叉验证**：单请求 0.51s，并发最小 0.503s，
    两个独立路径的量级一致 → 数据可信

- **坑**：
  ① 把"工具输出的数字"当成事实，不检查工具
  ② 看到一个不合理的数字，第一反应是"系统有问题"而不是"我测错了"

- **关联**：docs/实战笔记/05-缓存三大问题实战.txt 4.6 节末（附带的踩坑）


################################################################################
  Q4　为什么"内存里改的东西"容易被覆盖？★　【其他】
################################################################################

- **考点**：★ 表面问的是一个小事故，实际考的是
  **你能不能识别出同一个模式出现在不同地方**。
  这题答好了，能自然过渡到缓存一致性。

- **追问链**：
  Q1「为什么会被覆盖？」→ Q2「那怎么安全地改这类配置？」
  → Q3「这个模式在别的地方还有吗？」★ 关键
  → Q4「那缓存这边怎么解？」（转到 01-缓存体系 Q10）

- **参考答案**：
  ★ 我遇到过两次，**本质是同一个问题**：

  **案例一：IDE 的配置文件**
  我改 IDE 的 `recentProjects.xml`（清一个残留项目记录），
  改完重启 IDE，发现改动**全没了**。
  原因：IDE 启动时把配置**读进内存**，运行期间只改内存，
  **退出时才整体写回文件**。我在它运行时改文件，
  等于写进了一个马上会被覆盖的地方。

  **案例二：Redis 缓存**
  项目里写数据库后必须 `@CacheEvict`，忘了就会读到旧数据。
  原因：缓存是数据库的副本，数据库改了，副本也要失效。

  **两个是同一个模式**：

  | | IDE 配置 | Redis 缓存 |
  |---|---|---|
  | 真相源 | 内存状态 | MySQL |
  | 副本 | recentProjects.xml | Redis key |
  | 覆盖时机 | 退出时全量写回 | 写库后 evict |
  | 失败模式 | 手改丢失 | 读到旧数据 |

  **本质都是 Lost Update（丢失更新）**：
  两个写者，只有一个知道对方的修改。

  ★ 认识这个模式后，你能**预判"什么时候改会丢"**：
    · 改 IDE / 编辑器的配置文件 → 先关掉它
    · 改 Vim 正在编辑的文件 → 会被 swap 覆盖
    · 改数据库 → 要同步失效缓存
    · 改浏览器 localStorage → 多标签页会互相覆盖

  **认识模式比记住结论有用。**

- **本项目的证据**：
  · IDE 事故：清理一个误存到"最近项目"的 `.bundle` 文件条目时发现
    —— 文件在 IDE 运行时改会被退出时覆盖
  · 缓存侧：全项目 6 个 `@CacheEvict`，就是这个模式的应用
  · ★ 同一次事故还顺带确认了：**改完要验证**
    （重启 IDE 后看列表是不是真的干净了）

- **坑**：
  ① 把这类问题当成"工具的 bug"。它不是 bug，是**设计如此** ——
     内存态 + 退出时落盘是通用做法，关键是你要知道它的存在
  ② 只答 IDE 这一层，说不出和缓存是同一个模式

- **关联**：docs/知识笔记/05-缓存体系.txt 第四节
             docs/面试题库/01-缓存体系.txt Q10


################################################################################
  Q5　你怎么保证改动没有引入回归？　【测试】
################################################################################

- **考点**：【测试】标签。考的是"改动前有没有想过影响面"。

- **追问链**：
  Q1「怎么保证？」→ Q2「测试全绿就够了吗？」★ 关键
  → Q3「那测试覆盖不到的问题怎么办？」
  → Q4「你项目里还有哪些地方可能有类似的隐性依赖？」

- **参考答案**：
  两层：**自动化测试**打底，**副作用清单**查漏。

  **第一层：测试**
  我项目里有 12 个测试用例，`./mvnw test` 连跑两遍全绿。
  ★ 连跑两遍不是仪式感 —— 跑一遍过、第二遍挂，
  说明有**测试间的状态污染**或**执行顺序依赖**，
  这种测试比没有测试更危险（会给你假的安全感）。

  **第二层：副作用清单**（★ 这是踩坑学到的）
  我改缓存的时候，只想着"把缓存实现改好"，
  **完全没意识到这个改动会影响别的功能** ——
  结果把缓存降级打掉了。

  **为什么没意识到**：因为变化发生在**跨切面**的地方。
  我把 `@Cacheable` 换成手写调用，在"缓存功能"这个维度看是对的，
  但在"降级"这个维度看是破坏性的。

  ★ **任何涉及框架注解的改动，都过一遍这张表**：

  | 注解 | 底层切面 | 手写 API 后丢失什么 |
  |---|---|---|
  | `@Cacheable` | CacheInterceptor | 缓存降级 |
  | `@Transactional` | TransactionInterceptor | 事务回滚、传播、隔离 |
  | `@RateLimit`（自定义） | RateLimitAspect | 限流计数 |
  | `@RequireAdmin` | LoginInterceptor | 权限校验 |

  改动前问自己一句："**我是从注解路径换到手写路径了吗？**"
  如果是 → 上表里那一列的能力，我都要自己补回来。

- **本项目的证据**：
  · ★ **测试全绿也抓不到这个 bug** —— 因为测试用的是真实的 Redis，
    Redis 从来没挂过。**测试只能覆盖你想到的场景。**
  · 这个 bug 是**故障演练**发现的，不是测试发现的
  · 12 个测试用例连跑两遍全绿（项目笔记 11）

- **坑**：
  ① 测试全绿就以为没回归
  ② 只测"改动的功能"，不检查"改动会不会影响别的功能"
  ③ 删掉一个东西时不检查谁在用

- **关联**：docs/面试题库/01-缓存体系.txt Q8
             docs/项目笔记/11-测试体系.txt


################################################################################
  Q6　排查问题时，你的思路是什么？　【其他】
################################################################################

- **考点**：考的是**有没有方法论**，而不是"你有没有解决问题"。

- **追问链**：
  Q1「你的思路？」→ Q2「如果日志里一条都没有，你还能怎么查？」
  → Q3「你怎么决定先查哪里？」→ Q4「怎么设计一个有效的实验？」★ 关键

- **参考答案**：
  我的习惯是**先分层定位，再针对性地挖**，而不是一上来就猜原因。

  **这次查降级 bug 的实际路径**：

  **1. 现象层**：Redis 挂 → 接口返回 `code:500`
     → 说明异常没被兜住

  **2. 分界层**：日志里**一条降级 warn 都没有**
     → ★ 关键分叉点。可能两种情况：
       a) 兜底逻辑没执行（代码路径问题）
       b) 异常根本没抛出来（底层行为问题）
     → **区分这两者需要下一步实验**

  **3. 实验层**：重启 Redis，**不发任何新请求**，直接查 key
     → `novel::1` 已经存在 → 排除 a，锁定 b
     → 结论：命令被缓冲了，压根没抛异常

  ★ 第 2 步到第 3 步的跳跃是最关键的：
  "日志一条都没有"这个现象**同时支持两种解释**，
  我必须设计一个能**区分**它们的实验。

  ★ **好实验的标准：能排除至少一种可能**

  | 实验 | 能区分什么 |
  |---|---|
  | 重启 Redis 但不发请求 | 缓冲补发 vs 静默失败 |
  | 只加超时 vs 加 try-catch | 止血 vs 治疗 |
  | 制造必定失败的场景 | 判据本身对不对 |

  **不能"区分可能性"的实验，做了等于没做。**

- **本项目的证据**：
  · 查问题时先确认了三件事：
    ① `application-dev.properties` 里到底有没有配 timeout（没有）
    ② `findDetail` 的代码路径（手动 cacheManager 调用）
    ③ Spring Data Redis 里 `CacheErrorHandler` 由谁调用
       （`AbstractCacheInvoker`，是 AOP 切面的父类）
  · ★ 项目里有一条教训我记住了：
    **"文档和代码不一致时，以代码为准，先去读代码再动手。"**

- **坑**：
  ① 靠猜
  ② 一次改好几个地方 —— 不知道是哪个改动生效了，
     也无法知道哪个引入了新问题

- **关联**：docs/实战笔记/05-缓存三大问题实战.txt 4.5 节
             docs/项目笔记/00-项目总览.txt（文档与代码不一致的教训）


################################################################################
  Q7　有没有你觉得很值的小工具 / 小技巧？　【其他】
################################################################################

- **考点**：考的是"**你有没有自己的工具链**"，
  以及能不能说清每个工具"解决了什么问题"（而不是罗列命令）。

- **追问链**：
  Q1「说几个？」→ Q2「生产环境上你敢 docker stop 吗？」★ 关键
  → Q3「还有什么排查工具？」→ Q4「哪些你只是知道概念，没实际用过？」★ 诚实度

- **参考答案**：

  **1. 故障演练：docker stop / start**
  ```bash
  docker stop demo2-redis
  curl "http://localhost:8080/novels/1"
  docker start demo2-redis
  ```
  一条命令就能验出"依赖挂了会怎样"，比读代码猜强太多。
  ★ 我的降级 bug 就是靠这个发现的。

  **2. 直接查 Redis 验证写入**
  ```bash
  docker exec demo2-redis redis-cli EXISTS "novel::1"
  docker exec demo2-redis redis-cli TTL "novel::1"
  ```
  ★ 验证 TTL 抖动只靠这个 —— 看三个 key 的 TTL 是不是各不相同。
  **绕过应用层，直接看数据层**，比 curl 更直接。

  **3. 用 grep 把日志变成数据**
  ```bash
  grep -c "Redis command timed out" logs/book-manager.log
  grep -c "详情缓存写入失败"      logs/book-manager.log   # 结果 0
  ```
  ★ **"日志里该出现的东西没出现"，和"出现了不该出现的"一样是重要信号。**
  **计数**能让这种"缺席"变得可见。我那次发现 Lettuce 缓冲，起点就是这个 0。

  **4. git bundle：没有网络也能备份 / 迁移仓库**
  ```bash
  git bundle create backup.bundle --all   # 打包整个仓库成一个文件
  git clone backup.bundle my-project      # 从文件克隆
  ```
  用途：内网没有外网时同步代码，或做"整仓快照"归档。
  ★ 但它**不是持续备份** —— 每次提交后都要重新生成才有效。

- **本项目的证据**：
  · 以上四个全部实际用过
  · ★ 降级 bug 的完整发现路径：
    `grep -c "写入失败" → 0` → 设计实验 → 重启 Redis 不发请求
    → `EXISTS novel::1` → 1 → 结论

- **坑**：
  ① 堆砌工具名但说不出什么时候用
  ② ★ **把"知道概念"说成"用过"** —— 面试官一追问就露馅
  ③ 说"生产环境我会 docker stop" —— 生产上不敢，
     要在预发环境或按比例注入故障（混沌工程）

################################################################################
  Q8　你的表结构是怎么跟代码保持一致的？　【其他】
################################################################################

- **考点**：考的是"你知不知道 ORM 的自动建表只是开发期玩具"。
  会写 @Column 的人很多，能说清"这列到底是谁建的、线上怎么办"的人很少。
  追问一定会拐到 migration / Flyway —— 那里是分水岭。

- **追问链**：
  Q1「改实体就能改表？」→ Q2「生产环境也用自动建表吗？」★ 关键
  → Q3「那线上表结构谁负责？」→ Q4「加字段最容易漏哪一步？」
  → Q5「如果约束没生效，代码上会怎么表现？」★ 关键

- **参考答案**：
  "分环境和分层看。

  开发期我用 `ddl-auto=update`，改实体重启就自动加列/建表，图快。
  生产是 `validate` —— **只校验、绝不建表**。这是有意的：
  自动改表在线上等于把 DDL 的执行权交给 ORM，风险不可控。

  所以线上表结构的唯一来源是一份 init 脚本
  （挂在 MySQL 的 `docker-entrypoint-initdb.d` 上），
  作用相当于一个手写的迁移脚本。
  ⇒ 改表结构本质上是**三处同步**：实体 / DTO-VO-Service / 脚本 + 库。

  踩过三个坑，都在同一个下午：
  一是 update 模式**不给已存在的表补约束**；
  二是重新导出脚本时用了追加而不是覆盖，脚本里拼了两份 dump、还漏了新表；
  三是 NOT NULL 列在库里**没有 DEFAULT**，兜底只能写在代码里。"

- **本项目的证据**（★ 最值钱，2026-10-08 全部实测）：

  · **坑 1：约束没进库。** `entity/Bookshelf.java` 声明了
    `@UniqueConstraint(name="uk_bookshelf_user_novel", columnNames="userId,novelId")`，
    但：
    ```sql
    SELECT COUNT(*) FROM information_schema.statistics
    WHERE table_schema='book_db' AND table_name='bookshelf'
      AND non_unique=0 AND index_name<>'PRIMARY';
    -- → 0
    ```
    索引实际只有 PRIMARY + 2 个普通索引。
    ★ 结论：`update` 模式**建新表时会带约束，改已有表时不会补** ——
      "索引定义跟代码走"这句话**只在建表那一刻成立**。

  · ★★ 最狠的是**失败方式**：约束不在，防重复就只剩"先查再插"，
    并发下会真的插进两条。而代码里那段
    `catch (DataIntegrityViolationException) { 复活逻辑 }`
    **永远不会触发** —— 测试全绿，功能是坏的。
    又一个"假阳性判据"：**不报错 ≠ 正确**。

  · **坑 2：脚本被拼成两份。** 189 行的 `docker/mysql/init/01-schema.sql`
    里有两份完整的 mysqldump（`for Linux` + `for Win64`），
    第一份还没有 author 列，新表 bookshelf **两份都没有**。
    ⇒ Bookshelf 实体已在代码里 + prod 是 validate，
      下次 `docker compose down -v && up --build` 会直接启动失败：
      `Schema validation: missing table [bookshelf]`
      （同一个坑 2026-10-07 踩过一次，那次报的是 `missing table [chapter]`）

  · **判据要选硬的**：`grep -c "CREATE TABLE" 01-schema.sql` → 期望 4，
    实际 6（3 张表 × 2 份 dump）。
    ★ 比"文件里搜得到 bookshelf"硬得多 ——
      搜关键词只能证明"有"，证明不了"没有多余的、也没有漏的"。

  · **坑 3：NOT NULL ≠ 有默认值。** 实体写了 `nullable = false`，
    设计文档写了 `DEFAULT '佚名'`，但 `SHOW COLUMNS` 实测 Default 是 **NULL**。
    ⇒ 兜底只能靠 Service 层，数据库这一层会硬拒：
      探针 `INSERT INTO novel (title, author, ...) VALUES ('x', NULL, ...)`
      → `ERROR 1048 (23000): Column 'author' cannot be null`
    ⇒ 同一个字段，"创建"有兜底、"修改"漏了兜底 ——
      **加字段时只改 create 忘了 update**，是这类 bug 的标准形态。

- **坑**：
  ① 说"我用 ddl-auto=update，很方便" —— 面试官下一句必然是"生产呢"
  ② 把 `@Table(indexes=...)` 当成完整的索引管理方案 —— 它管不了已有表
  ③ 说"脚本我已经同步了"，却拿不出**验证脚本本身**的判据
  ④ ★ 最危险的一种：把**"没报错"当成"验证通过"**。
     约束缺失、兜底缺失、脚本缺表 —— 这三样**一个都不报错**
  ⑤ 只盯着"字段加没加"，忘了"改了创建、漏了修改"

################################################################################
  Q9　你踩过哪些"编译通过、能跑，但功能不生效"的坑？★★　【其他】
################################################################################

- **考点**：★ 这是**框架理解深度题**，也是本类最能拉开差距的一题。
  考的是"你知不知道框架的能力是**挂在切面 / 生命周期钩子 / 容器扫描**上的"，
  而不是"注解写上去就生效"。
  能答出**共同规律**（而不是列举现象）才算过关。

- **追问链**：
  Q1「举几个例子？」→ Q2「它们有什么共同点？」★ 关键
  → Q3「怎么提前发现？」→ Q4「那你怎么证明你修好了？」
  → Q5「如果它没生效，编译器和测试为什么都不报？」

- **参考答案**：
  "这类坑的共同特征是：**编译通过、启动不报错、测试可能还是绿的，
  但那段代码根本不参与运行**。我遇到的都是同一类：

  注解要生效，前提是**框架能'看到'它**：
  · `@Component` 忘了加 → 容器扫描不到这个类，它整个是死代码
  · `@Valid` 加在 `@RequestParam Integer` 上 → Integer 没有字段可校验，
    注解在但什么也不做
  · `@Transactional` 加在私有方法上 → AOP 代理拦不住私有调用
  · `@Cacheable` 绕开切面手写 `cacheManager.get()` →
    CacheErrorHandler 的降级能力直接消失
  · `@RequireAdmin` 加在 Service 上 → 拦截器只能拿到 Controller 的
    HandlerMethod，看不到 Service 类上的注解

  所以我的检查动作只有一个：**写完先问一句"它怎么会被调用到？"**
  ——从调用方一路走到这个方法，中间有没有断。

  但"看代码"是查不干净的，因为它的**失败方式是静默的**。
  真正管用的是倒过来验：**制造一个必定失败的场景，看判据会不会报错。**
  比如把 `@Component` 删掉重跑，如果结果没变，说明我的判据测的不是它。"

- **本项目的证据**（★ 2026-10-08 一轮里踩了 9 个，全部可复现）：
  · **Converter 忘加 @Component**（最典型）
    `BookshelfSortConverter implements Converter<String, BookshelfSort>`
    编译通过、启动不报错，但 Spring 根本不知道它存在 ——
    参数转换仍走默认的 `Enum.valueOf`：大小写敏感、非法值直接 400。
    ★ 判据：把 `@Component` 删掉重跑 → 期望 400；
      加上 → 期望 `body.code=200`。**两条都要跑，只跑一条证明不了。**
  · **`@RequestBody @Valid Integer novelId`** ——
    请求体 `{"novelId":123}` 是个对象，反序列化不成 Integer。
    ⇒ 这类"必须建 DTO"的约束，编译器完全看不出来
  · **`@Valid` 加在 `@RequestParam Integer page` 上** ——
    什么也不做。范围校验要用 `@Validated + @Min/@Max`
  · **书架列表第一版漏了 `userId` 过滤** ——
    不报错，只是把**所有人的书架**都查出来了（越权）
  · **漏了 `deleted = 0` 过滤** —— 不报错，已移出的书照样出现
  · **复活分支漏了 `createTime` 重置** ——
    不报错，只是排序排到最后，用户以为系统坏了（语义错）
  · **`@Transactional` 漏加** 在 Service 写方法上
  · ★★ **唯一约束只在实体里声明、库里没有**（问题 21）——
    严格说这不是注解问题，但**共同特征完全一样**：
    约束不在 ⇒ 并发重复插入不会抛异常 ⇒
    代码里那段 `catch (DataIntegrityViolationException)` 永远不触发。
    **功能是坏的，一路不报错。**

  ★ 项目里最早的那一个也是同一类：
    `@RequestParam` 写成了本该是 `@PathVariable` 的地方 ——
    `@RequestParam Integer` 和 `@PathVariable Integer` **类型完全一样**，
    编译通过、IDE 不提示，但取不到路径里的值。

- **坑**：
  ① 只列举现象、说不出共同点 —— 面试官会认为你是"踩过"而不是"懂了"
  ② 说"我代码 review 就能发现" —— 这类坑的失败方式是**静默**的，
     而且类型相同（`Integer` 就是 `Integer`），review 靠不住
  ③ ★ 最要命的：**用"没报错"当验证通过**。
     这 9 个坑里没有一个是靠报错暴露的
  ④ 说"加个注解就行了"，但说不出**为什么**加了才生效
     （答"因为框架靠切面/容器扫描，不是靠注解本身"才是加分项）

================================================================================
  附：这一类的方法论提炼（面试前扫一眼）
================================================================================

  1. 先写期望值，再看结果 —— 否则你会把任何结果解释成成功
  2. 判据本身也要验证 —— 假阳性判据比没有判据更危险
  3. 验证工具本身也要验证 —— 0.0003 秒的 HTTP 请求物理上不可能
  4. 改动前过一遍副作用清单 —— 尤其是涉及框架注解的改动
  5. 设计"能区分可能性"的实验 —— 不能区分的话，做了等于没做
  6. 用计数让"日志里没出现的东西"变得可见
