【Q1：你项目里哪里用到并发了？】
  标准答案（用你自己项目的例子）：
    "有几个地方。
     第一，用户身份识别用的是 ThreadLocal，
     因为 Tomcat 线程池会复用线程，所以在拦截器的 afterCompletion
     里必须 remove()，否则会造成用户串号，这是真实的越权风险。

     第二，限流用的是 Redis 的 INCR，
     因为它是单线程处理命令，天然原子，
     如果用 Java 的 count++ 就要加锁了。

     第三，限流计数如果放在本地 Map 里，多机部署时每台机器各算各的会不准，
     所以必须用 Redis 做集中式计数。"

  ★ 这个回答的威力在于：每一条都来自你真实写过的代码，追问也不怕。

【Q2：单例 Bean 是线程安全的吗？】
  ★ 这是最容易答错的一题。
  标准答案：
    "不是绝对的。单例 Bean 只是'只有一个实例'，是否线程安全取决于它有没有状态。
     我的 Service 是无状态的 —— 所有字段都是 final 的依赖注入，
     没有可变的成员变量，业务数据都是方法内的局部变量，
     所以是线程安全的。
     反过来，如果在 Service 里加一个 private int count 成员变量，多线程下就会出问题。
     这也是为什么 Spring 官方建议 Bean 要设计成无状态的。"

【Q3：ThreadLocal 会内存泄漏吗？】
  标准答案：
    "会。ThreadLocalMap 的 Entry 中，key 是 ThreadLocal 对象的弱引用，
     value 是强引用。当外部不再引用 ThreadLocal 对象时，
     key 会被 GC 回收变成 null，但 value 还被 Entry 强引用着。
     如果线程一直存活（线程池里的核心线程），这个 value 就永远无法回收。
     所以必须在使用完手动 remove()，而且要放在 finally 里。"

【Q4：Redis 为什么能扛并发？】
  标准答案：
    "Redis 处理命令是单线程的，所以每个命令天然是原子的，
     不存在 Java 里 count++ 那种读-改-写的竞态。
     但单线程不等于慢 —— 它是纯内存操作，
     加上 IO 多路复用处理网络，
     瓶颈通常在网络带宽而不是 CPU。"
