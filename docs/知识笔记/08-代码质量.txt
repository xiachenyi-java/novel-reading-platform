【大类 08】代码质量

  对应项目笔记：docs/项目笔记/08-代码质量.txt

################################################################################
  一、判断标准
################################################################################

  · 新同事接手，能不能在 1 小时内看懂你的代码？
  · 三个月后自己回来改，还记不记得当时为什么这么写？
  · 有没有"这段代码删掉好像也没影响"的地方？

  【★ 代码质量的三个层次】

    第一层：消除明显的坏味道
      死代码、重复代码、魔法数字、硬编码、命名不规范

    第二层：提升表达力
      用异常类型表达意图（BusinessException vs RuntimeException）
      用数据结构表达约束（Hash 分组 vs 遍历查找）
      用配置表达环境差异

    第三层：用工具兜底
      静态检查（Alibaba 插件）、SonarLint、代码格式化

  【★ 最好的改进长什么样】
    "代码更短 + 性能更好 + 更安全"三者同时满足。

    例子：把"先判断存在，再查询"合并成一次查询：
      原来 5 行 → 现在 2 行
      原来 2 次 DB 往返 → 现在 1 次
      原来有并发窗口 → 现在没有


################################################################################
  二、代码坏味道清单
################################################################################

--------------------------------------------------------------------------------
2.1 死代码
--------------------------------------------------------------------------------

  【表现】
    · 定义了但从没使用的变量
      String key = "refresh:" + userId;      // ← 后面从没用到
    · 空方法体
      public void setChapters(List<Chapter> chapters) { }
    · 没有任何调用方的私有方法
    · 被注释掉的大段代码

  【为什么是问题】
    会误导后来者："这个方法是不是有什么特殊用途？删了会不会出问题？"
    增加阅读负担，降低代码信噪比。

  【怎么发现】
    IDEA 会灰色标记未使用的变量/方法
    Alibaba 插件也会提示

--------------------------------------------------------------------------------
2.2 重复代码
--------------------------------------------------------------------------------

  【表现】
    两个方法除了第一行参数不同，其余 100% 一样。

  【危害】
    改一处忘了改另一处 → 行为不一致

  【解法】
    提取公共方法：
      private List<XxxVO> doSomething(String key, int top) { ... }

      public List<XxxVO> methodA(int top) {
          return doSomething("key-A", top);
      }
      public List<XxxVO> methodB(int top) {
          return doSomething("key-B", top);
      }

  【★ 什么时候不该提取】
    如果两段代码只是"看起来像"，但业务含义不同、
    未来会朝不同方向演进，就不要强行提取。
    错误的抽象比重复代码更难维护。

--------------------------------------------------------------------------------
2.3 魔法数字与硬编码
--------------------------------------------------------------------------------

  【表现】
    if (top > 100) { top = 100; }                          // 100 是什么？
    .allowedOrigins("http://localhost:5173")               // 上线要改
    if (status.equals("ONGOING"))                          // 状态值散落各处

  【解法】
    · 提取常量
      private static final int MAX_RANKING_TOP = 100;
    · 提取配置
      @Value("${ranking.max-top:100}") private int maxTop;
    · 提取枚举
      public enum NovelStatus { ONGOING, FINISHED }

  【★ 判断标准】
    凡是"换个环境就要改"的值，都不该硬编码。

--------------------------------------------------------------------------------
2.4 命名不规范
--------------------------------------------------------------------------------

  【Java 命名规范】
    ------------------------------------------------------------------
    类型          规范                例子
    ------------------------------------------------------------------
    类            大驼峰              NovelService
    方法          小驼峰              findRanking
    变量          小驼峰              novelId
    常量          全大写下划线        MAX_RANKING_TOP
    包            全小写              com.example.service
    布尔字段      is/has/can 开头     isDeleted
    ------------------------------------------------------------------

  【★ 常见的坑】
    · 字段名首字母大写（NovelId、Title）
      → 违反规范
      → 还会导致 JSON 序列化出的 key 和前端对不上
    · 包名有大写（Entity 而不是 entity）
    · 用拼音命名（yonghu、dingdan）
    · 单个字母的变量名（除了循环变量 i、j）

  【★ 命名要表达意图】
    ✗ List<Novel> list = ...;
    ✓ List<Novel> rankedNovels = ...;
    ✗ int d = 30;
    ✓ int cacheTtlMinutes = 30;

--------------------------------------------------------------------------------
2.5 异常处理不当
--------------------------------------------------------------------------------

  【表现与解法】
    ------------------------------------------------------------------
    坏味道                          正确做法
    ------------------------------------------------------------------
    用裸 RuntimeException           自定义 BusinessException
    异常处理器参数类型不匹配        ★ 必须和声明的类型兼容
    catch (Exception e) { }         至少 log 一下
    log.error(e.getMessage())       log.error("描述", e)  ★ 带堆栈
    业务异常用 error 级别           业务异常用 warn
    兜底异常用 warn 级别            兜底用 error  ★
    直接返回 e.getMessage()         系统异常返回统一话术（防泄露）
    吃掉异常不做任何处理            要么不 catch，要么重新 throw
    ------------------------------------------------------------------

  【★ 为什么兜底异常必须用 error】
    兜底处理器是"不该发生的事发生了"，属于系统故障。
    用 warn 会导致告警规则漏掉真正的线上问题。

  【★ 为什么要区分业务异常和系统异常】
    · 业务异常：可预期，用户操作导致的，不需要堆栈，warn 级别
    · 系统异常：不可预期，代码 bug，需要堆栈，error 级别
    · 系统异常的 message 可能包含表名、SQL 片段 → 不该返回给前端

--------------------------------------------------------------------------------
2.6 破坏框架自动配置
--------------------------------------------------------------------------------

  【★ 典型错误】
    @Configuration
    public class JacksonConfig {
        @Bean
        public ObjectMapper objectMapper() {
            return new ObjectMapper();      // ← 裸的，没注册任何模块
        }
    }

  【问题链】
    ① Spring Boot 的 JacksonAutoConfiguration 带 @ConditionalOnMissingBean
    ② 你自定义了 → Boot 那套配好的 ObjectMapper 就不生成了（"退避"）
    ③ 于是丢掉了：JavaTimeModule（LocalDateTime 序列化）、
       WRITE_DATES_AS_TIMESTAMPS=false、FAIL_ON_UNKNOWN_PROPERTIES=false 等
    ④ 用裸 ObjectMapper 序列化 LocalDateTime 默认会抛异常

  【正确做法（三选一）】
    方案A（推荐）：直接删掉，让 Boot 自动配置生效
    方案B：用 Jackson2ObjectMapperBuilderCustomizer 扩展而不是替换
      @Bean
      public Jackson2ObjectMapperBuilderCustomizer customizer() {
          return builder -> builder
                  .serializationInclusion(JsonInclude.Include.NON_NULL)
                  .failOnUnknownProperties(false);
      }
    方案C：@Bean ObjectMapper objectMapper(ObjectMapper defaultMapper)
          { return defaultMapper.copy().setSerializationInclusion(...); }

  【★ 这是一个通用的规律】
    Spring Boot 的自动配置类大多带 @ConditionalOnMissingBean。
    你一旦自己声明了同类型的 Bean，自动配置就会退避。
    所以自定义时要用 XxxCustomizer 扩展，而不是直接替换。

--------------------------------------------------------------------------------
2.7 其他坏味道
--------------------------------------------------------------------------------

  □ 方法过长（超过 50 行就该拆）
  □ 参数过多（超过 4 个考虑封装成对象）
  □ 嵌套过深（超过 3 层 if，用卫语句提前返回）
  □ 注释写"做了什么"而不是"为什么"
  □ 提交了大段被注释掉的代码
  □ 日志里打印敏感信息（@Data 的 toString 包含所有字段）
  □ 未使用的 import
  □ 测试代码引用已删除的类


################################################################################
  三、设计原则（SOLID）
################################################################################

  ------------------------------------------------------------------
  原则                    含义                          例子
  ------------------------------------------------------------------
  S 单一职责             一个类只做一件事              拆分 God Class
  O 开闭原则             对扩展开放，对修改关闭        用策略模式替代 if-else
  L 里氏替换             子类能替换父类                不要破坏父类契约
  I 接口隔离             接口要小而专                  不要定义胖接口
  D 依赖倒置             依赖抽象而不是实现            Controller 依赖接口
  ------------------------------------------------------------------

  【★ 实际编码中最常用的两条】
    · 单一职责：一个方法只做一件事，一个类只有一个变化的原因
    · 依赖倒置：面向接口编程（Service 抽接口的价值）

  【要避免过度设计】
    SOLID 是指导原则不是教条。
    小项目里"一个接口一个实现"确实有点形式主义，
    但在多人协作的场景里，接口是团队之间的契约。


################################################################################
  四、代码质量工具
################################################################################

  ------------------------------------------------------------------
  工具                              作用
  ------------------------------------------------------------------
  Alibaba Java Coding Guidelines    IDEA 插件，自动扫描规范问题 ★
  SonarLint                         IDEA 插件，实时代码质量检查
  SonarQube                         服务端，团队级代码质量管理
  Checkstyle                        代码风格检查
  SpotBugs                          字节码级 bug 检测
  PMD                               静态代码分析
  ErrorProne                        编译期 bug 检测
  Spotless / .editorconfig          代码格式化
  ------------------------------------------------------------------

  【★ 推荐的上手顺序】
    1. 装 Alibaba Java Coding Guidelines，扫一遍现有代码
    2. 装 SonarLint，看有没有明显的坏味道
    3. 加 .editorconfig 统一格式
    4. 团队协作时再接 SonarQube

  【★ 静态检查的价值】
    能自动抓出：命名不规范、未使用的变量、空 catch、
    魔法数字、重复代码、潜在 NPE……
    这些靠人眼很容易漏。


################################################################################
  五、代码 Review 自查清单
################################################################################

  【分层】
  □ Controller 里有没有直接调 Repository？
  □ Service 里有没有感知 HTTP（HttpServletRequest / ResponseEntity）？
  □ 有没有方法返回 Entity 而不是 DTO/VO？
  □ 依赖的是接口还是实现？

  【参数与校验】
  □ 有没有接口没有加 @Valid？
  □ 校验注解的 message 文案对不对？
  □ 嵌套对象有没有加 @Valid？

  【数据库】
  □ 写操作有没有加 @Transactional？
  □ @Transactional 有没有写 rollbackFor？
  □ 有没有 catch 吃掉异常导致事务不回滚？
  □ 有没有循环里查数据库（N+1）？
  □ 查询条件字段有索引吗？

  【异常与日志】
  □ 兜底异常是不是 error 级别？
  □ log.error 有没有带异常对象？
  □ 日志里有没有打印敏感信息？
  □ catch 块是不是空的？

  【安全】
  □ 有没有校验数据归属（防水平越权）？
  □ 有没有把不该返回的字段返回出去？
  □ 外部输入有没有校验？

  【命名与常量】
  □ 命名符合规范吗？
  □ 有没有魔法数字 / 硬编码路径？

  【死代码】
  □ 有没有未使用的变量 / 方法 / import？
  □ 有没有空方法体？
  □ 有没有被注释掉的大段代码？


################################################################################
  面试会怎么问
################################################################################

  Q1：什么是 Spring Boot 的自动配置？为什么不能随便定义 Bean？
  A： 基于 @Conditional 系列注解的条件装配。
     ★ 结合例子讲：JacksonAutoConfiguration 上有
       @ConditionalOnMissingBean，我自定义 ObjectMapper 后它就退避了，
       结果丢掉了 JavaTimeModule 等预置配置。
       正确做法是用 Jackson2ObjectMapperBuilderCustomizer 扩展而不是替换。

  Q2：@Transactional 默认回滚哪些异常？
  A： 只回滚 RuntimeException 和 Error。受检异常默认不回滚，
     要写 rollbackFor = Exception.class。

  Q3：为什么要自定义业务异常？
  A： 区分业务问题和系统故障。
     业务异常用 warn 级别不带堆栈，系统异常用 error 级别带堆栈，
     方便日志排查和告警分级。
     另外系统异常的 message 可能泄露内部结构，不能直接返回前端。

  Q4：你做过哪些代码优化？
  A： ★ 用"代码更短 + 性能更好 + 更安全"的框架回答：
     · KEYS 改 Hash（消除 Redis 生产阻塞）
     · 路径遍历校验（安全）
     · 两次查询合并成一次（性能 + 消除并发窗口）
     · 自定义业务异常（日志分级）
     · 显式 rollbackFor（数据一致性）
     · 配置文件外化（可维护性）
     · Service 接口层（可测试性）

  Q5：什么是面向接口编程？小项目里是不是形式主义？
  A： 接口的价值在"契约"和"可替换性"，便于 Mock 测试和多人协作。
     小型单人项目里确实有形式大于实质的成分，
     但在多人协作的项目里，接口是团队之间的契约。

  Q6：怎么保证代码质量？
  A： 三层：编码时遵守规范和 SOLID 原则；
     提交前用自查清单过一遍；
     工具兜底（Alibaba 插件 + SonarLint 静态检查）。

  Q7：为什么会写死代码？怎么避免？
  A： 需求变更后忘了删。避免方法：
     用 IDEA 的未使用代码提示、静态检查工具、
     以及代码 Review 时专门关注。
