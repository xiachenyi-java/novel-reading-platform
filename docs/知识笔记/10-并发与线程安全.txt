################################################################################
  10.1 线程基础
################################################################################

【进程 vs 线程】
  ------------------------------------------------------------------
  维度        进程                        线程
  ------------------------------------------------------------------
  定义        操作系统分配资源的基本单位   CPU 调度的基本单位
  资源        独立的内存空间               共享进程的内存空间
  开销        创建/切换开销大              创建/切换开销小
  通信        需要 IPC（管道/消息队列）    直接共享内存
  独立性      一个进程崩溃不影响其他进程   一个线程崩溃可能拖垮整个进程
  ------------------------------------------------------------------

【线程的三种创建方式】
  ------------------------------------------------------------------
  方式                    写法                              返回值
  ------------------------------------------------------------------
  继承 Thread             class T extends Thread            无
  实现 Runnable           class T implements Runnable       无
  实现 Callable           implements Callable<T>            ★ 有
  ------------------------------------------------------------------

  ★ 推荐 Callable + 线程池：
    · Runnable 不能返回结果，也不能抛受检异常
    · 直接 new Thread() 无法管理线程数量

【线程的六种状态】
  NEW（新建）
      ↓ start()
  RUNNABLE（可运行：就绪 + 运行中）
      ↓ 抢不到锁 → BLOCKED
      ↓ wait() / join() / park() → WAITING
      ↓ sleep() / 带超时的 wait() → TIMED_WAITING
      ↓ run() 结束
  TERMINATED（终止）

【★ sleep() vs wait()】
  ------------------------------------------------------------------
  对比项          sleep()                  wait()
  ------------------------------------------------------------------
  所属类          Thread                   Object
  是否释放锁      ✗ 不释放                 ★ 释放
  唤醒方式        时间到了自动醒           需要 notify()/notifyAll()
  使用前提        任意位置                必须在 synchronized 块内
  ------------------------------------------------------------------

【其他常用方法】
  join()      让当前线程等待另一个线程执行完
  yield()     让出 CPU，重新竞争（不保证一定让出）
  interrupt() 中断线程（设置中断标志，不是强制停止）
  守护线程    setDaemon(true)，主线程结束时守护线程也结束

【★ 为什么推荐用线程池而不是 new Thread()】
  · 线程创建/销毁开销大（需要操作系统参与）
  · 无法控制数量，高并发下会创建海量线程导致 OOM
  · 无法管理任务队列和拒绝策略


################################################################################
  10.2 Java 内存模型 JMM
################################################################################

【主内存与工作内存】
  JMM 规定：
    · 所有变量存在主内存（Main Memory）
    · 每个线程有自己的工作内存（Working Memory）
    · 线程对变量的操作必须在工作内存中进行

  所以：线程 A 改了变量 x，线程 B 不一定能立刻看到 → 可见性问题

【三大特性】
  ------------------------------------------------------------------
  特性        含义                        破坏它会怎样
  ------------------------------------------------------------------
  原子性      操作不可分割                i++ 丢更新
  可见性      一个线程的修改其他线程能看到  死循环读不到最新值
  有序性      代码按写的顺序执行          指令重排导致意外结果
  ------------------------------------------------------------------

【★ 实战：线程不安全的例子】
  public class Counter {
      private int count = 0;
      public void increment() { count++; }     // ← 非原子操作！
  }

  100 个线程各加 1000 次，期望 100000，实际每次运行结果都不同。

  【为什么】
    count++ 分三步：
      1. 读取 count 到工作内存
      2. 加 1
      3. 写回主内存
    两个线程可能同时读到 100，各自加 1 后都写回 101 → 少加了一次

  【三种修复方式对比】
    ------------------------------------------------------------------
    方式              性能        适用场景
    ------------------------------------------------------------------
    synchronized      低          临界区代码复杂时
    AtomicInteger     中          一般并发计数
    LongAdder         高          ★ 超高并发计数
    ------------------------------------------------------------------

    ★ LongAdder 的分段累加思想：把计数分散到多个 Cell，
      最后求和。类似 ConcurrentHashMap 的分段思想。

【★ volatile 到底解决什么】

  保证两件事：
    1. 可见性 —— 一个线程修改后，其他线程立刻能看到
    2. 禁止指令重排序

  ★★ volatile 不保证原子性！
    private volatile int count = 0;
    count++;                 // ← 依然是非原子的！

  【正确的使用场景】

    场景1：状态标志位
      volatile boolean running = true;
      // 线程A: while(running) { ... }
      // 线程B: running = false;    ← 能立刻被线程A看到

    场景2：双重检查锁单例（DCL）
      public class Singleton {
          private static volatile Singleton instance;      // ★ 必须加 volatile

          public static Singleton getInstance() {
              if (instance == null) {
                  synchronized (Singleton.class) {
                      if (instance == null) {
                          instance = new Singleton();
                      }
                  }
              }
              return instance;
          }
      }

      【为什么必须加 volatile】
        new Singleton() 分三步：
          1. 分配内存空间
          2. 初始化对象
          3. 把 instance 指向内存地址
        指令重排后可能变成 1→3→2。
        此时另一个线程进来看到 instance != null，
        但对象还没初始化完 → 拿到半成品对象 → 空指针。

【happens-before 原则（8 条，知道前 5 条即可）】
  1. 程序顺序规则：一个线程内，前面的操作 happens-before 后面的
  2. 监视器锁规则：解锁 happens-before 后续的加锁
  3. volatile 规则：volatile 写 happens-before 后续的 volatile 读
  4. 线程启动规则：Thread.start() happens-before 线程内的所有操作
  5. 线程终止规则：线程内所有操作 happens-before 检测到它结束
  6. 线程中断规则
  7. 对象终结规则
  8. 传递性


################################################################################
  10.3 锁机制
################################################################################

【synchronized 的三种用法】
  ------------------------------------------------------------------
  用法                  锁对象              例子
  ------------------------------------------------------------------
  修饰实例方法          this（当前对象）    public synchronized void m()
  修饰静态方法          Class 对象          public static synchronized void m()
  修饰代码块            指定对象            synchronized(obj) { ... }
  ------------------------------------------------------------------

  ★ 锁的是对象，不是代码！
    两个线程用不同的对象实例调用同步方法，不会互斥。

【★ 锁升级过程（面试高频）】
  无锁 → 偏向锁 → 轻量级锁 → 重量级锁

  ------------------------------------------------------------------
  状态        适用场景                  实现方式
  ------------------------------------------------------------------
  偏向锁      只有一个线程访问          对象头记录线程 ID，无需 CAS
  轻量级锁    少量线程竞争，持有时间短  CAS 自旋
  重量级锁    竞争激烈，持有时间长      操作系统互斥量，线程阻塞
  ------------------------------------------------------------------

  ★ 锁只能升级不能降级。
  ★ 为什么要升级？自旋会消耗 CPU，竞争激烈时自旋代价比阻塞还大。

【ReentrantLock vs synchronized】
  ------------------------------------------------------------------
  对比项              synchronized          ReentrantLock
  ------------------------------------------------------------------
  实现层次            JVM 层面              JDK 层面（AQS）
  是否可中断          ✗                     ✓ lockInterruptibly()
  是否可超时          ✗                     ✓ tryLock(timeout)
  是否公平锁          只能非公平            可公平可非公平
  条件变量            单一                  多个（Condition）
  释放锁              自动释放              ★ 必须手动 unlock()（finally）
  性能                优化后差距不大        高竞争下略优
  ------------------------------------------------------------------

  ★ 怎么选？
    一般用 synchronized（简单、不会忘记释放）
    需要超时/可中断/多条件变量时用 ReentrantLock

【★ AQS（AbstractQueuedSynchronizer）原理】
  AQS 是 JUC 里锁和同步器的基石。

  核心三要素：
    1. volatile int state —— 同步状态（0 = 未锁，>0 = 已锁）
    2. CAS 修改 state —— 保证原子性
    3. CLH 双向队列 —— 存放等待的线程

  加锁流程：
    线程尝试 CAS 把 state 从 0 改成 1
      成功 → 拿到锁，继续执行
      失败 → 包装成 Node 加入队列尾部，park 阻塞自己

  解锁流程：
    把 state 改回 0，唤醒队列头部的线程

  ★ 基于 AQS 实现的：
    ReentrantLock、ReentrantReadWriteLock、Semaphore、
    CountDownLatch、CyclicBarrier

【★ 死锁的四个必要条件】
  ------------------------------------------------------------------
  条件        说明                        破坏方法
  ------------------------------------------------------------------
  互斥        资源同一时刻只能被一个线程占用  通常无法破坏
  请求并持有  持有资源的同时请求新资源      一次性申请所有资源
  不可剥夺    已获得的资源不能被强行夺走    允许抢占
  循环等待    形成环形等待链                按固定顺序申请资源 ★ 最实用
  ------------------------------------------------------------------

  【怎么排查死锁】
    jps -l                                    # 找到 Java 进程 PID
    jstack <pid>                              # 打印线程栈
    jstack <pid> | grep -A 30 "deadlock"      # 找死锁
    或者 jconsole / VisualVM / Arthas 的 thread -b

  【最简单的防死锁手段】
    所有线程都按同一个固定顺序申请资源（破坏循环等待）。


################################################################################
  10.4 线程池 ★★ 面试必问第一名
################################################################################

【★ ThreadPoolExecutor 七大参数（必须背下来）】
  public ThreadPoolExecutor(
      int corePoolSize,                   // 1. 核心线程数（常驻，空闲也不销毁）
      int maximumPoolSize,                // 2. 最大线程数
      long keepAliveTime,                 // 3. 非核心线程空闲存活时间
      TimeUnit unit,                      // 4. 时间单位
      BlockingQueue<Runnable> workQueue,  // 5. 任务队列
      ThreadFactory threadFactory,        // 6. 线程工厂（用来命名）
      RejectedExecutionHandler handler    // 7. 拒绝策略
  )

  口诀：核心、最大、存活时间、时间单位、队列、工厂、拒绝策略

【★ 任务提交后的完整流程（面试必考）】

  提交任务
      ↓
  ① 核心线程池满了吗？
     没满 → 创建核心线程执行
     满了 ↓
  ② 队列满了吗？
     没满 → 放进队列等待
     满了 ↓
  ③ 线程数达到 maximumPoolSize 了吗？
     没达到 → 创建非核心线程执行
     达到了 ↓
  ④ 执行拒绝策略

  ★★ 关键点：先排队，再扩容到最大线程数。
    很多人记反，以为"核心满了就直接创建到最大"。
    正确顺序：核心 → 队列 → 最大 → 拒绝

【四种拒绝策略】
  ------------------------------------------------------------------
  策略                        行为                        风险
  ------------------------------------------------------------------
  AbortPolicy（默认）         抛 RejectedExecutionException  调用方要处理
  CallerRunsPolicy            让提交任务的线程自己执行    ★ 降级不丢任务
  DiscardPolicy               静默丢弃，不报错            ✗ 任务静默丢失
  DiscardOldestPolicy         丢弃队列最老的，再提交      ✗ 老任务被丢
  ------------------------------------------------------------------

  ★ 生产推荐 CallerRunsPolicy：
    它会拖慢提交速度，形成"背压"，避免任务被丢弃。

【★ Executors 的四种快捷线程池（不推荐用）】
  ------------------------------------------------------------------
  方法                    特点                    为什么危险
  ------------------------------------------------------------------
  newFixedThreadPool      固定线程数              队列无界 → OOM
  newCachedThreadPool     线程数弹性              最大线程数 Integer.MAX_VALUE → OOM
  newSingleThreadExecutor 单线程                  队列无界 → OOM
  newScheduledThreadPool  定时任务                队列无界 → OOM
  ------------------------------------------------------------------

  ★ 阿里 Java 开发手册明确禁止用 Executors 创建线程池，
    必须手动 new ThreadPoolExecutor，让你清楚每个参数的含义。
    ★ 面试常问："为什么不用 Executors？"—— 这就是答案。

【线程数怎么设】
  ------------------------------------------------------------------
  任务类型              推荐线程数            理由
  ------------------------------------------------------------------
  CPU 密集型            核心数 + 1            线程太多反而增加切换开销
  IO 密集型             核心数 × 2            等待 IO 时不占 CPU，可多开
  ------------------------------------------------------------------

  更理论的公式（Brain Goetz）：
    线程数 = 核心数 × 目标CPU利用率 × (1 + 平均等待时间 / 平均计算时间)

  ★ 实际生产要压测调优，公式只是起点。

  获取核心数：Runtime.getRuntime().availableProcessors()

【线程池的监控与调优】
  · 自定义 ThreadFactory 给线程命名
    executor.setThreadNamePrefix("app-async-");
    ★ 出问题时 jstack 一看就知道是哪个线程池的线程。

  · 继承 ThreadPoolExecutor 覆写 beforeExecute / afterExecute：
    统计已完成任务数、队列积压数、活跃线程数、拒绝任务数

  · 动态调参：
    setCorePoolSize / setMaximumPoolSize 支持运行时调整，
    可以配合配置中心实现动态扩缩容

  · 优雅关闭：
    shutdown()     不再接受新任务，等待已提交的任务执行完
    shutdownNow()  尝试中断正在执行的任务，返回未执行的任务列表
    awaitTermination()  等待终止


################################################################################
  10.5 ThreadLocal ★
################################################################################

【ThreadLocal 是什么】
  每个线程独立的变量副本。线程 A 存进去的值，线程 B 读不到。

【★ 实现原理：数据不在 ThreadLocal 里，而在 Thread 里！】

  public class Thread {
      ThreadLocal.ThreadLocalMap threadLocals = null;    // ← 每个线程一个 Map
  }

  public class ThreadLocal<T> {
      public void set(T value) {
          Thread t = Thread.currentThread();
          ThreadLocalMap map = t.threadLocals;         // ← 拿当前线程的 Map
          map.set(this, value);                        // ← key 是 ThreadLocal 对象自己
      }
      public T get() {
          ThreadLocalMap map = Thread.currentThread().threadLocals;
          return map.get(this);
      }
  }

  结构：
    Thread → ThreadLocalMap → Entry[] → { key: ThreadLocal对象, value: 值 }

【★ 为什么 key 是弱引用、value 是强引用】

  static class Entry extends WeakReference<ThreadLocal<?>> {
      Object value;                          // ← value 是强引用
      Entry(ThreadLocal<?> k, Object v) {
          super(k);                          // ← key 是弱引用
          value = v;
      }
  }

  【为什么 key 用弱引用】
    如果用强引用，即使外部不再使用 ThreadLocal 对象，
    ThreadLocalMap 还持有它 → 无法 GC → 内存泄漏。

【★ 内存泄漏的完整链路】

  1. ThreadLocal 对象被外部置为 null（不再使用）
  2. GC 时，因为 key 是弱引用 → key 被回收 → Entry 的 key 变成 null
  3. 但 value 是强引用，还被 Entry 引用着 → value 无法回收
  4. 如果线程一直存活（线程池里的核心线程），这个 value 就永远无法回收
  5. → 内存泄漏

  ★ ThreadLocalMap 的 set/get/remove 时会"顺手"清理 key 为 null 的 Entry
    （探测式清理），但这不可靠 —— 如果再也不调用这些方法，就永远不会清理。

  ★★ 唯一的正解：用完必须手动 remove()，而且必须放在 finally 里。

    try {
        userContext.set(user);
        // 业务逻辑
    } finally {
        userContext.remove();      // ★ 必须在 finally
    }

【★ 线程池场景下的数据污染】

  Tomcat 用线程池处理请求，一个线程会被反复复用：
    线程 T1 处理用户 A → setUser(A) → 请求结束但没 remove
    → T1 被放回线程池
    → 用户 B 的请求分配到 T1 → getUser() 拿到的是 A 的信息！
    → 用户 B 看到 A 的数据 → 严重的越权漏洞

  ★ 这就是"线程池复用导致的数据污染"，面试常问。

【InheritableThreadLocal】
  可以让子线程继承父线程的 ThreadLocal 值。
  ★ 但线程池场景下会失效（线程是复用的，不会重新创建），
    这时候要用阿里的 TransmittableThreadLocal（TTL）。

【★ @Async 里怎么拿到当前用户】
  问题：@Async 方法执行在新线程里，ThreadLocal 拿不到主线程的值。

  三种解法：
    1. 把用户信息作为方法参数传进去（最简单）
    2. 用 TransmittableThreadLocal（阿里 TTL）
    3. 用 TaskDecorator 手动复制上下文
       @Bean
       public TaskDecorator taskDecorator() {
           return runnable -> {
               UserContextDTO user = UserContext.getUser();   // 主线程里取
               return () -> {
                   try {
                       UserContext.setUser(user);              // 子线程里放
                       runnable.run();
                   } finally {
                       UserContext.remove();
                   }
               };
           };
       }


################################################################################
  10.6 JUC 并发工具
################################################################################

【原子类】
  ------------------------------------------------------------------
  类                      说明
  ------------------------------------------------------------------
  AtomicInteger           原子整型
  AtomicLong              原子长整型
  AtomicBoolean           原子布尔
  AtomicReference         原子引用
  LongAdder               ★ 高并发计数（分段累加）
  AtomicStampedReference  带版本号（解决 ABA 问题）
  ------------------------------------------------------------------

【★ CAS 原理与 ABA 问题】

  CAS = Compare And Swap
    三个参数：内存地址 V、预期值 A、新值 B
    逻辑：如果 V 的值等于 A，就把它改成 B；否则什么都不做

  Java 实现：sun.misc.Unsafe.compareAndSwapInt(obj, offset, expect, update)

  【CAS 的三大问题】
    ------------------------------------------------------------------
    问题          说明                              解决
    ------------------------------------------------------------------
    ABA 问题     值从 A 改成 B 又改回 A，          加版本号
                 CAS 以为没变过                    （AtomicStampedReference）
    自旋开销大    竞争激烈时一直重试，消耗 CPU     自适应自旋 / 改用锁
    只能保证一个  多个变量无法原子更新              AtomicReference
    变量的原子性                                    封装成对象
    ------------------------------------------------------------------

【★ 同步器（面试常问区别）】
  ------------------------------------------------------------------
  工具            作用                          典型场景
  ------------------------------------------------------------------
  CountDownLatch  一个线程等 N 个线程完成        主线程等所有子任务完成
                  （计数减到 0）                 ★ 一次性，不能重置
  CyclicBarrier    N 个线程互相等待，到齐了才走 分批处理
                  （计数加到 N）                 ★ 可以重置
  Semaphore        控制同时访问的线程数量         接口限流、连接池
  Phaser           更灵活的同步器                 多阶段任务
  Exchanger        两个线程交换数据               遗传算法、校对
  ------------------------------------------------------------------

  【CountDownLatch 示例】
    CountDownLatch latch = new CountDownLatch(3);
    for (int i = 0; i < 3; i++) {
        new Thread(() -> {
            try {
                // 做任务
            } finally {
                latch.countDown();      // 计数 -1
            }
        }).start();
    }
    latch.await();                      // 主线程阻塞，直到计数归零

  【实战场景】
    一个页面需要查 ① 基本信息 ② 明细列表 ③ 统计数据，
    这三个操作互相独立，可以并行，用 CountDownLatch 或
    CompletableFuture 加速。

【并发容器】
  ------------------------------------------------------------------
  容器                        特点
  ------------------------------------------------------------------
  ConcurrentHashMap           分段 CAS + synchronized，读完全无锁 ★
  CopyOnWriteArrayList        写时复制，读多写少场景
  CopyOnWriteArraySet         同上
  ConcurrentLinkedQueue       无锁并发队列（CAS）
  ArrayBlockingQueue          有界阻塞队列（数组实现）
  LinkedBlockingQueue         可选有界阻塞队列 ★ 线程池常用
  SynchronousQueue            不存储元素，直接传递
  PriorityBlockingQueue       优先级阻塞队列
  DelayQueue                  延迟队列（定时任务）
  ------------------------------------------------------------------

  【★ 为什么 HashMap 线程不安全】
    多线程 put 可能导致：
      · JDK 7：链表成环 → 死循环 → CPU 100%
      · JDK 8：数据覆盖丢失
    解决：用 ConcurrentHashMap

  【★ ConcurrentHashMap 的实现演进】
    JDK 7：分段锁（Segment），锁的粒度是段
    JDK 8：CAS + synchronized 锁单个桶（Node），粒度更细
           读操作完全无锁（Node 的 val 和 next 用 volatile 修饰）

  【★ HashMap 为什么线程不安全但 ArrayList 也类似】
    ArrayList 多线程 add 会丢元素、size 不准。
    解决：CopyOnWriteArrayList（读多写少）或 Collections.synchronizedList


################################################################################
  10.7 CompletableFuture 异步编排
################################################################################

【Future 的局限】
  · 不能手动完成
  · 不能链式调用（无法在完成后自动执行下一步）
  · 不能组合多个 Future
  · 没有异常处理机制
  · get() 是阻塞的

【CompletableFuture 的常用方法】
  ------------------------------------------------------------------
  方法                    作用
  ------------------------------------------------------------------
  runAsync(Runnable)      异步执行，无返回值
  supplyAsync(Supplier)   ★ 异步执行，有返回值
  thenApply(fn)           上一步结果 → 转换（有输入有输出）
  thenAccept(consumer)    上一步结果 → 消费（有输入无输出）
  thenRun(runnable)       上一步完成 → 执行（无输入无输出）
  thenCompose(fn)         ★ 串行：上一步结果 → 返回新的 CompletableFuture
  thenCombine(other, fn)  ★ 并行：合并两个 Future 的结果
  allOf(futures)          等所有完成
  anyOf(futures)          任一完成即可
  exceptionally(fn)       异常处理
  handle(fn)              无论成功失败都处理
  whenComplete(action)    完成后回调（不改变结果）
  orTimeout(时间)         超时控制
  ------------------------------------------------------------------

  【记忆技巧】
    thenApply   = map（转换）
    thenAccept  = forEach（消费）
    thenRun     = 只关心完成，不关心结果
    thenCompose = flatMap（串行，避免嵌套）
    thenCombine = zip（并行合并）

【★ 实战：并行查询加速】

  串行：
    查 Redis     5ms
    查数据库     20ms
    查其他服务   15ms
    总计：40ms

  并行：
    CompletableFuture<A> f1 = CompletableFuture.supplyAsync(() -> 查A, pool);
    CompletableFuture<B> f2 = CompletableFuture.supplyAsync(() -> 查B, pool);
    CompletableFuture<C> f3 = CompletableFuture.supplyAsync(() -> 查C, pool);

    CompletableFuture.allOf(f1, f2, f3).join();

    总计：约 20ms（取决于最慢的那个）

  ★ 注意：如果 B 依赖 A 的结果，就不能并行。
    只有真正独立的任务才能并行。

【★ 坑】
  · 默认用 ForkJoinPool.commonPool()，生产环境建议传自定义线程池
  · join() 抛的是 CompletionException（非受检），get() 抛 ExecutionException
  · 异常处理要用 exceptionally / handle，否则异常会被吞掉
  · 线程池被打满时，supplyAsync 会阻塞


################################################################################
  10.8 并发设计模式
################################################################################

  ------------------------------------------------------------------
  模式                核心思想                    应用
  ------------------------------------------------------------------
  不可变模式          对象创建后不可修改          String、final
  保护性暂挂          条件不满足就等待            wait/notify、BlockingQueue
  两阶段终止          用标志位优雅停止线程        volatile flag + interrupt
  worker-thread 模式  任务队列 + 工作线程          线程池
  生产者-消费者       阻塞队列解耦                 MQ、线程池
  Future 模式         异步调用，先拿凭证后取结果   CompletableFuture
  线程本地存储        ThreadLocal                 用户上下文
  ------------------------------------------------------------------

  【生产者-消费者手写实现】
    BlockingQueue<Task> queue = new LinkedBlockingQueue<>(100);

    // 生产者
    queue.put(task);        // 队列满时阻塞

    // 消费者
    Task task = queue.take();   // 队列空时阻塞

  ★ 这就是消息队列和线程池的底层模型。


################################################################################
  面试会怎么问
################################################################################

  Q1：线程池的核心参数有哪些？任务提交的流程是什么？
  A： ★ 必背。七个参数 + 「核心 → 队列 → 最大 → 拒绝」的流程图。
     加一句："很多人会记反，以为是核心满了就直接扩到最大，
     实际上是先排队。"

  Q2：为什么不推荐用 Executors 创建线程池？
  A： FixedThreadPool 和 SingleThreadExecutor 的队列长度是
     Integer.MAX_VALUE，会无限堆积任务导致 OOM；
     CachedThreadPool 的最大线程数是 Integer.MAX_VALUE，
     会无限创建线程导致 OOM。
     阿里手册要求手动 new ThreadPoolExecutor。

  Q3：ThreadLocal 原理是什么？会内存泄漏吗？
  A： ★ 数据存在 Thread 的 ThreadLocalMap 里，
       key 是 ThreadLocal 对象的弱引用，value 是强引用。
       key 被 GC 后 value 还被强引用着，
       如果线程一直存活（线程池核心线程）就无法回收。
       ★ 必须手动 remove()，而且要放在 finally 里。
       ★ 不 remove 还会导致线程池复用时的用户串号问题。

  Q4：volatile 的作用是什么？
  A： 保证可见性和禁止指令重排序，★ 不保证原子性。
     典型用法：状态标志位、双重检查锁单例。

  Q5：synchronized 和 Lock 的区别？
  A： 见 10.3 的对比表。重点：Lock 可中断、可超时、可公平、
     多条件变量，但必须手动释放（finally）。

  Q6：synchronized 的锁升级过程？
  A： 无锁 → 偏向锁 → 轻量级锁（CAS 自旋）→ 重量级锁（OS 互斥量）。
     只能升级不能降级。

  Q7：什么是 CAS？有什么问题？
  A： Compare And Swap。问题是 ABA、自旋开销、
     只能保证单个变量的原子性。

  Q8：怎么排查死锁？
  A： jstack <pid>，查找 "deadlock" 关键字。
     预防：按固定顺序申请资源（破坏循环等待）。

  Q9：CountDownLatch 和 CyclicBarrier 的区别？
  A： CountDownLatch 是"一个线程等 N 个"，计数减到 0，不能重置；
     CyclicBarrier 是"N 个线程互相等"，计数加到 N，可以重置。

  Q10：单例 Bean 是线程安全的吗？★ 最容易答错
  A： 不是绝对的。单例 Bean 只是"只有一个实例"，
     是否线程安全取决于它有没有可变状态。
     ★ 无状态的单例（字段全是 final 依赖注入，业务数据都是局部变量）
       是线程安全的。
     ★ 如果有 private int count 这样的可变成员变量，就会出问题。
     这也是 Spring 官方建议 Bean 要设计成无状态的原因。

  Q11：HashMap 为什么线程不安全？
  A： JDK 7 多线程扩容会导致链表成环 → 死循环 → CPU 100%；
     JDK 8 会出现数据覆盖丢失。解决用 ConcurrentHashMap。

  Q12：CompletableFuture 怎么用？
  A： 用 supplyAsync 发起异步任务，thenApply/thenCompose 编排，
     allOf 等全部完成。★ 结合场景讲：把多个独立的查询并行执行，
     耗时从相加变成取最大值。
