################################################################################

    密码怎么存（BCrypt）
        ↓
    登录怎么验（比对指纹）
        ↓

################################################################################
  第 1 部分：密码安全
################################################################################

【存钥匙比喻】
  想象你在小区物业登记家门钥匙：

    明文存储 = 直接把钥匙交给物业保管
               → 员工或黑客看到就能开门

    加密存储 = 把钥匙熔成一把"无法还原的锁模"
               → 下次你来时，物业用同样的模具验证新钥匙是否匹配

【三个环节】
  ------------------------------------------------------------------
  环节            代码                              通俗理解
  ------------------------------------------------------------------
  配置加密器      new BCryptPasswordEncoder()       造一个"熔锁模具"
  注册加密        encoder.encode(password)          把密码熔成印记
  登录验证        encoder.matches(raw, encoded)     用新钥匙比对印记
  ------------------------------------------------------------------

【密码存储方案演进】
  ------------------------------------------------------------------
  方案          安全性    问题
  ------------------------------------------------------------------
  明文          无        拖库即全泄露
  MD5           低        快 → 暴力破解成本低；无盐 → 彩虹表可破
  MD5 + 盐      中        需要自己管理盐值
  SHA-256 + 盐  中        仍然太快，GPU 每秒可算几十亿次
  BCrypt        ★ 高     计算慢（可调 cost）+ 自带随机盐
  Argon2        ★ 最高    抗 GPU/ASIC，密码哈希竞赛冠军
  ------------------------------------------------------------------

【BCrypt 的三个特点】
  1. 不可逆 —— 从哈希推不出原密码
  2. 自带盐值 —— 每个密码的哈希都不同，防彩虹表
  3. 计算慢 —— cost 因子可调（默认 10，表示 2^10 次迭代），
              暴力破解成本极高

【★ 关键认知】
  · 同一个密码每次 encode() 结果都不同（盐值随机）
    → 只能用 matches() 比对，不能用 equals()
  · BCrypt 是单向的，没有"解密"这回事
    → 忘记密码只能重置，不能找回
  · 加盐的目的是让相同的密码产生不同的哈希，
    这样攻击者不能通过"撞库"批量破解

【★ 其他密码安全实践】
  · 密码强度校验（长度、大小写、数字、特殊字符）
  · 登录失败次数限制（防暴力破解）
  · 敏感操作二次验证（改密码、删账号要重新输密码）
  · 密码修改后让所有 token 失效
  · 传输层用 HTTPS（否则密码明文传输）


################################################################################
  第 2 部分：登录认证
################################################################################

【银行柜台取钱比喻】
  核心问题：登录时系统怎么验证"你真的是你"？

    明文比对 = 柜员电脑上直接显示你的密码，你报一个他看一个
               → 旁边人偷看一眼就完蛋

    BCrypt 比对 = 银行只存密码的"指纹档案"，
                  你在密码器上输入后，后台自动比对指纹是否匹配，
                  柜员自己也看不到密码

【四步验身份】
  ------------------------------------------------------------------
  步骤              代码                              银行场景
  ------------------------------------------------------------------
  第一步：查档案    findByUsername().isEmpty()        柜员查有没有这张卡
  第二步：调档案    findByUsername().orElseThrow()    调出开户资料
  第三步：核对密码  encoder.matches(raw, encoded)    后台指纹比对机
  第四步：脱敏返回  setPasswordHash(null)            回单不打印密码档案
  ------------------------------------------------------------------

【★ 安全细节：防账号枚举】

  ✗ 错误做法：
    用户名不存在 → "该用户不存在"
    密码错误     → "密码错误"
    → 黑客用脚本批量测试，快速枚举出系统里有哪些有效账号

  ✓ 正确做法：
    两种情况都返回"用户名或密码错误"
    → 攻击者无法区分

  ★ 面试常问："登录接口怎么防账号枚举？"这就是答案。

【★ 时序攻击（进阶）】
  即使返回同样的文案，如果"用户不存在"时立即返回、
  "密码错误"时因为要跑 BCrypt 而慢 100ms，
  攻击者仍然能通过响应时间差判断账号是否存在。
  防御：用户不存在时也跑一次假的 BCrypt 计算。

【★ 登录接口的其他防护】
  · 限流（IP / 用户名维度）
  · 图形验证码 / 滑块验证
  · 登录失败锁定
  · 异常登录检测（异地、新设备）
  · 登录日志审计


################################################################################
  第 3 部分：会话管理 —— Session vs JWT
################################################################################

【游乐园通票比喻】

  Session = 服务器给每个人建一个小柜子存身份证
            你每次来报柜号（Cookie 里的 SessionID），
            服务器去翻柜子查你是谁
    缺点：服务器有状态，多台机器之间柜子不同步

  JWT = 服务器给你一张自带防伪的通票，你自己揣兜里
        服务器不用存任何信息，看一眼票就知道你是谁

【★ 全面对比】
  ------------------------------------------------------------------
  对比项          Session                JWT
  ------------------------------------------------------------------
  状态           服务端有状态            服务端无状态
  存储位置       服务端（内存/Redis）    客户端
  多机部署       需要共享（Redis）       天然支持
  主动失效       容易（删掉即可）        ★ 困难（需要黑名单）
  体积           小（只有 SessionID）    大（含 Payload）
  跨域           Cookie 有跨域限制       放在 Header 里，无限制
  移动端适配     麻烦                    友好
  安全性          Cookie 可被 CSRF 利用   存 localStorage 有 XSS 风险
  ------------------------------------------------------------------

  【选型建议】
    · 单体应用、需要强控制 → Session
    · 分布式、多端（Web/App/小程序）、开放 API → JWT
    · 两者可以结合：JWT + Redis 白名单（兼顾无状态和可控）

【JWT 的结构】
  xxxxx.yyyyy.zzzzz
    ↑      ↑      ↑
  Header  Payload  Signature

  ------------------------------------------------------------------
  部分        内容                              编码方式
  ------------------------------------------------------------------
  Header      {"alg":"HS256","typ":"JWT"}       Base64URL
  Payload     {"sub":"1001","exp":...,...}       Base64URL
  Signature   HMAC-SHA256(header.payload, secret)  二进制
  ------------------------------------------------------------------

【★ 三个必须知道的坑】

  坑1：Payload 只是 Base64 编码，不是加密！
    把 token 中间那段拿去 base64 解码，就能看到全部内容。
    → 绝对不要在 JWT 里放敏感信息（密码、手机号、身份证号）
    → 面试常问"JWT 安全吗？"
      答："签名保证不可篡改，但内容是可读的。"

  坑2：secret 泄露 = 谁都能造假票
    → 生产环境必须用环境变量注入，不能硬编码
    → 要定期轮换
    → HMAC-SHA256 要求密钥至少 32 字节

  坑3：JWT 无法主动失效
    这是 JWT 最大的缺点 —— 票一旦发出去，在过期前一直有效。
    用户登出怎么办？管理员强制下线怎么办？
    → 需要黑名单机制（见第 5 部分）

【JWT 生成与解析（jjwt 0.12.x）】
  // 生成
  Jwts.builder()
      .subject(String.valueOf(userId))
      .claim("username", username)
      .claim("role", role)
      .issuedAt(now)
      .expiration(expiryDate)
      .signWith(key, Jwts.SIG.HS256)
      .compact();

  // 解析
  Jwts.parser()
      .verifyWith(key)
      .build()
      .parseSignedClaims(token)
      .getPayload();

  ★ 签名不对、过期、格式错误都会抛异常，必须 try-catch。


################################################################################
  第 4 部分：请求拦截与身份注入
################################################################################

【拦截器 vs 过滤器】
  ------------------------------------------------------------------
  对比项        Filter（过滤器）         Interceptor（拦截器）
  ------------------------------------------------------------------
  规范          Servlet 规范             Spring MVC 规范
  作用范围      所有请求                 只拦 Controller 请求
  能否拿到      不能（拿不到 Handler）   能（可拿到方法上的注解）★
  Spring 上下文 不能直接注入 Bean       可以
  执行时机      更早                     更晚
  ------------------------------------------------------------------

  ★ 需要读方法上的注解（如 @RequireAdmin）→ 必须用拦截器。

【拦截器的三态设计（推荐模板）】
  ------------------------------------------------------------------
  情况                              处理
  ------------------------------------------------------------------
  OPTIONS 预检请求                  直接放行（CORS 需要）
  公开路径（白名单）                放行
  游客可访问路径                    有 token 就解析，没 token 也放行
  其他所有路径                      校验 token，失败返回 401
  ------------------------------------------------------------------

【★ 白名单必须包含的路径】
  · 登录、注册、刷新 token 接口
  · 接口文档（swagger-ui / v3/api-docs / doc.html）
  · 静态资源（/uploads/**、favicon.ico、*.html）
  · /error（否则异常时会被拦截器二次拦截）

  ★ 尤其注意：refresh 接口必须放行，
    否则 accessToken 过期后永远刷不了。

【★ 身份上下文：ThreadLocal】

  public class UserContext {
      private static final ThreadLocal<UserContextDTO> holder = new ThreadLocal<>();
      public static void setUser(UserContextDTO user) { holder.set(user); }
      public static UserContextDTO getUser() { return holder.get(); }
      public static void remove() { holder.remove(); }        // ★ 必须调用
  }

  为什么能行：Tomcat 用线程池处理请求，一个请求从头到尾在同一个线程上执行。
             拦截器里 setUser，Service 里 getUser 能读到。

  ★★ 为什么必须在 afterCompletion 里 remove()？
    Tomcat 复用线程：
      线程 T1 处理用户 A → setUser(A) → 请求结束但没 remove
      → 线程 T1 被放回线程池
      → 用户 B 的请求分配到 T1 → getUser() 拿到的是 A 的信息！
      → 用户 B 看到 A 的数据 → 严重的越权漏洞

  ★ 这是并发大类的经典考点，详见 docs/知识笔记/10-并发与线程安全.txt

【★ 拦截器里怎么写 401 响应】
  拦截器里用不了 @RestControllerAdvice（那是给 Controller 用的），
  必须手写：

    private void writeUnauthorized(HttpServletResponse response) throws Exception {
        response.setStatus(401);
        response.setContentType("application/json;charset=UTF-8");
        response.getWriter().write("{\"code\":401,\"msg\":\"未登录或token无效\"}");
        response.getWriter().flush();
    }

【401 vs 403】
  401 Unauthorized —— 你没告诉我你是谁（认证失败）
  403 Forbidden    —— 我知道你是谁，但你没权限（授权失败）


################################################################################
  第 5 部分：Token 生命周期管理
################################################################################

【双 Token 策略】
  ------------------------------------------------------------------
  Token 类型      有效期      存储位置          用途
  ------------------------------------------------------------------
  Access Token    15~30 分钟  客户端            访问受保护接口
  Refresh Token   7~30 天     Redis + 客户端    换新的 Access Token
  ------------------------------------------------------------------

  【为什么要两个】
    · 单个长有效期 Token：被盗后风险窗口太大（7 天随便用）
    · 单个短有效期 Token：用户频繁被踢出登录，体验差
    · 双 Token：短时效保安全 + 长时效保体验

  【为什么 Refresh Token 存 Redis】
    服务端可控 —— 能远程作废（登出、改密码、强制下线）

  【★ 为什么要"双向索引"】

    正向：refresh_token:{token} → userId
          用途：客户端拿 token 来刷新时，查这是哪个用户

    反向：user_refresh:{userId} → token
          用途：用户登出/改密码时，用 userId 查出要删哪个 token

    ★ 两个方向都会用到，所以两个都要存。
      只存正向的后果：登出时找不到要删的 token，
      refreshToken 继续有效 → 登出没登干净。

    ★ 这是"用空间换查询效率"的经典设计，面试可讲。

【★ Refresh Token 轮换】
  每次刷新时，旧 refreshToken 立即失效，发一个新的。
  好处：如果 refreshToken 被盗，攻击者用过一次后，
        真正的用户再用就会失败 → 能及时发现异常。
  ★ 进阶：如果检测到"已使用的 refreshToken 被再次使用"，
    应该把该用户的所有 token 全部作废（说明发生了盗用）。

【黑名单：让 Access Token 提前失效】
  【问题】JWT 无状态，签发了就无法收回。
  【解法】登出时把 token 写进 Redis 黑名单，每次校验先查黑名单。

  【★ 数据结构选型】
    ------------------------------------------------------------------
    方案            结构                          优缺点
    ------------------------------------------------------------------
    Set 方案        blacklist:jti → Set{jti}      没存过期时间，
                                                  不知道何时能清理
    Hash 方案       blacklist:user:{userId}       ★ 推荐
                    → Hash{token: 过期时间戳}     一个结构存两样
                                                  按用户分组
                                                  支持惰性清理
    ------------------------------------------------------------------

  【惰性清理】
    读到黑名单里的 field 时，判断过期时间戳：
      · 还没过期 → 拦截
      · 已过期   → 删掉这个 field，放行

    ★ 优点：不用定时任务，自然清理
    ★ 缺点：如果用户登出后再也不访问，这个 field 会一直留着
            解法：给整个 Hash key 也设一个兜底 TTL

  【★ Redis 生产禁忌：不要用 KEYS】
    KEYS 会遍历整个键空间，O(N) 操作，会阻塞 Redis。
    在有几百万 key 的生产环境执行一次 KEYS 会卡住好几秒。
    替代：SCAN（游标式增量遍历）或直接用 Hash 结构分组。

【远程作废的三种场景】
  ------------------------------------------------------------------
  场景              操作
  ------------------------------------------------------------------
  用户登出          拉黑当前 accessToken + 删除该用户的 refreshToken
  用户修改密码      ★ 删除该用户所有 refreshToken（所有设备强制下线）
  管理员强制下线    直接删 Redis 键
  ------------------------------------------------------------------

  ★ 已颁发的 accessToken 可以不管，等它自己过期（短时效）。
    如果要立刻失效，就要用黑名单。

【★ 进阶：pwdVersion 方案】
  在 JWT 里加一个 pwdVersion 字段，用户表也存一个密码版本号。
  改密码时版本号 +1，校验时比对用户当前的版本号。
  版本号不匹配 → token 失效。
  优点：不用维护黑名单，天然支持"改密码后所有 token 失效"。


################################################################################
  第 6 部分：跨域（CORS）
################################################################################

【同源策略】
  浏览器默认禁止不同源（协议 + 域名 + 端口，任一不同）的页面间请求资源。

【五个关键响应头】
  ------------------------------------------------------------------
  响应头                              作用
  ------------------------------------------------------------------
  Access-Control-Allow-Origin         允许的源
  Access-Control-Allow-Methods        允许的方法
  Access-Control-Allow-Headers        允许的请求头
  Access-Control-Allow-Credentials    是否允许携带 Cookie
  Access-Control-Max-Age              预检结果缓存时间
  ------------------------------------------------------------------

【预检请求（Preflight）】
  对于"非简单请求"（PUT / DELETE / 自定义头如 Authorization），
  浏览器会先发一个 OPTIONS 请求试探，通过后才发真实请求。

  ★ 这就是为什么拦截器第一行要判断 OPTIONS 直接放行。

【简单请求的三个条件】
  1. 方法是 GET / HEAD / POST 之一
  2. 请求头只包含安全首部（Accept、Accept-Language、
     Content-Language、Content-Type 等）
  3. Content-Type 只能是 text/plain、multipart/form-data、
     application/x-www-form-urlencoded

  ★ 带 Authorization 头的请求属于"非简单请求"，会触发预检。

【★ 坑】
  · 生产环境不要用 *，应精确配置白名单
  · Allow-Credentials=true 时，Origin 不能是 *
    （这是浏览器的安全限制）
  · 预检请求不携带 Cookie 和认证信息
  · 网关层统一配置 CORS，避免每个服务重复处理
  · 跨域是浏览器的限制，用 Postman 测不出跨域问题


################################################################################
  第 7 部分：RBAC 权限模型
################################################################################

【模型】
  用户(User) ←→ 角色(Role) ←→ 权限(Permission) ←→ 资源(Resource)

  用户绑定角色，角色拥有权限，权限对应具体的资源/操作。
  解耦"人"和"权"：调整角色即可批量变更权限，无需逐个改用户。

【数据库表设计】
  ------------------------------------------------------------------
  表                      说明
  ------------------------------------------------------------------
  user                    用户
  role                    角色（ADMIN / USER / EDITOR）
  permission              权限（novel:create / novel:delete）
  user_role               用户-角色关联（多对多）
  role_permission         角色-权限关联（多对多）
  ------------------------------------------------------------------

【权限设计的两个维度】
  ------------------------------------------------------------------
  维度        说明              示例
  ------------------------------------------------------------------
  菜单权限    前端可见性        是否显示"用户管理"菜单
  接口权限    后端访问控制      是否能调 DELETE /api/users
  ------------------------------------------------------------------

  ★ 前端权限控制只是"体验优化"，真正的安全必须靠后端控制。
    因为前端代码用户可以看到和修改。

【三种实现方式对比】
  ------------------------------------------------------------------
  方式              实现                              灵活度
  ------------------------------------------------------------------
  硬编码角色判断    if (role.equals("ADMIN"))         低
  注解 + 拦截器     @RequireAdmin / @RequirePermission ★ 推荐
  Spring Security   @PreAuthorize("hasRole('ADMIN')")  高
  ------------------------------------------------------------------

【注解式实现模板】
  1. 定义注解：
     @Target(ElementType.METHOD)
     @Retention(RetentionPolicy.RUNTIME)
     public @interface RequireAdmin { }

  2. 标记在方法上：
     @RequireAdmin
     @PostMapping
     public Result<Novel> add(@RequestBody @Valid NovelDTO dto) { ... }

  3. 在拦截器里检查（★ 必须用拦截器，因为要读方法注解）：
     if (handle instanceof HandlerMethod handlerMethod) {
         if (handlerMethod.hasMethodAnnotation(RequireAdmin.class)) {
             if (!"ADMIN".equals(UserContext.getUser().getRole())) {
                 writeForbidden(response, "权限不足，需要管理员身份");
                 return false;
             }
         }
     }

【★ 越权的两个方向】
  ------------------------------------------------------------------
  类型        含义                          例子
  ------------------------------------------------------------------
  垂直越权    低权限用户访问高权限接口      普通用户调管理员删除接口
  水平越权    同权限用户访问别人的数据      A 用户改 B 用户的订单
  ------------------------------------------------------------------

  【水平越权的防御】
    错误做法：
      public void cancelCollect(Integer collectId) {
          collectService.deleteById(collectId);      // ← 别人能删你的收藏
      }

    正确做法一：先查后判
      Collect c = collectService.findById(collectId);
      if (!c.getUserId().equals(currentUserId)) throw new BusinessException("无权操作");

    正确做法二（★ 更优）：把权限条件写进 SQL
      collectService.deleteByIdAndUserId(collectId, currentUserId);
      → 天然防越权，没有并发窗口，性能也更好

  【★ 通用防御原则】
    · 永远不要相信前端传来的"用户ID"，一律从上下文取
    · 所有涉及"我的数据"的接口，查询条件必须带 userId
    · 优先"把权限条件写进 SQL"，而不是"先查后判"


################################################################################
  第 8 部分：Spring Security
################################################################################

【核心概念】
  ------------------------------------------------------------------
  概念                    说明
  ------------------------------------------------------------------
  Authentication          认证：你是谁
  Authorization           授权：你能干什么
  SecurityContext         安全上下文（存当前认证信息）
  GrantedAuthority        权限标识
  Filter Chain            过滤器链（Security 的核心）
  ------------------------------------------------------------------

【过滤器链的关键过滤器】
  ------------------------------------------------------------------
  过滤器                          作用
  ------------------------------------------------------------------
  SecurityContextPersistenceFilter 恢复/保存 SecurityContext
  UsernamePasswordAuthenticationFilter  表单登录
  BasicAuthenticationFilter        HTTP Basic 认证
  BearerTokenAuthenticationFilter  JWT / OAuth2 Bearer
  ExceptionTranslationFilter       把异常转成 401/403
  FilterSecurityInterceptor        最终鉴权
  ------------------------------------------------------------------

【★ 为什么很多人"用了 Spring Security 但等于没用"】
  常见错误配置：
    .authorizeHttpRequests(auth -> auth.anyRequest().permitAll())
    → 全部放行，Security 只是个摆设

  然后自己写拦截器做鉴权 → 简历上写"Spring Security"会被追问露馅。

  正确姿势：
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/users/login", "/users/register").permitAll()
        .requestMatchers(HttpMethod.GET, "/novels/**").permitAll()
        .requestMatchers(HttpMethod.POST, "/novels/**").hasRole("ADMIN")
        .anyRequest().authenticated()
    )

【Security 的配置要点】
  · 关闭 CSRF（前后端分离 + JWT 场景）
  · 设置 SessionCreationPolicy.STATELESS（无状态）
  · 配置认证入口点（返回 JSON 而不是跳转登录页）
  · 配置异常处理器（401 / 403）
  · 把自定义的 JWT 过滤器加到 UsernamePasswordAuthenticationFilter 之前


################################################################################
  第 9 部分：CSRF
################################################################################

【原理】
  诱导已登录用户在不知情的情况下发出请求。
  例：你登录了银行网站，然后访问了恶意网站，
      它自动向银行发了一个转账请求，浏览器自动带上了 Cookie。

【CSRF 成立的两个前提】
  1. 认证信息由浏览器自动携带（Cookie / Session）
  2. 攻击者能预测请求的全部参数

【★ 为什么用 JWT 就不需要 CSRF 防护】
  传统 Cookie 认证：浏览器自动带 Cookie → 攻击者能借用你的身份
  JWT 认证：token 存在 localStorage，需要 JS 手动加到 Header
           → 攻击者的网站读不到你域名下的 localStorage
           → CSRF 天然不成立

  ★ 结论：前后端分离 + JWT + localStorage 的场景，可以关闭 CSRF。
    但如果改成 Cookie 存 token，就必须重新开启。

【CSRF 的防护手段（如果要用 Cookie）】
  · CSRF Token（服务端下发，请求时必须带上）
  · SameSite Cookie 属性（Lax / Strict）
  · 校验 Referer / Origin
  · 敏感操作二次验证


################################################################################
  面试会怎么问
################################################################################

  Q1：为什么密码要用 BCrypt 而不是 MD5？
  A： MD5 快 → 暴力破解成本低；不带盐 → 彩虹表可破。
     BCrypt 慢（可调 cost）+ 自带随机盐 → 拖库后也难以破解。
     ★ 补充：同一个密码每次 encode 结果不同，所以只能用 matches 比对。

  Q2：JWT 的结构是什么？安全吗？
  A： Header.Payload.Signature 三段。
     ★ 关键：Payload 只是 Base64 编码，不是加密，任何人都能解码。
     签名保证不可篡改，但不保证机密性 —— 不能放敏感信息。

  Q3：JWT 怎么实现主动失效（登出）？
  A： JWT 本身无状态无法失效，需要引入 Redis 黑名单。
     登出时把 token 写进黑名单并设置过期时间（等于 token 剩余有效期）。
     ★ 加分：我用 Hash 结构存，field 是 token，value 是过期时间戳，
       读到时惰性清理过期的 field，避免内存无限增长。

  Q4：为什么用双 Token？
  A： 兼顾安全和体验。Access Token 短时效降低被盗风险，
     Refresh Token 长时效避免频繁登录。
     Refresh Token 存 Redis 所以能远程作废。
     ★ 加分：做双向索引，登出时能用 userId 反查出要删的 token。

  Q5：Session 和 JWT 怎么选？
  A： Session 服务端可控、能主动失效，但多机部署要共享；
     JWT 无状态、天然支持分布式，但无法主动失效、体积更大。
     单体用 Session，分布式/多端用 JWT。

  Q6：什么是水平越权和垂直越权？怎么防？
  A： 垂直 = 低权限访问高权限接口（防法：注解 + 拦截器检查角色）
     水平 = 访问别人的数据（防法：把 userId 作为 SQL 查询条件）

  Q7：ThreadLocal 为什么要在请求结束时 remove？
  A： Tomcat 线程池复用线程，不 remove 会导致下一个请求
     读到上一个用户的身份，造成越权。

  Q8：为什么你的项目关闭了 CSRF？
  A： JWT 存 localStorage，需要 JS 手动加到 Header，
     攻击者网站读不到，CSRF 天然不成立。
     如果改成 Cookie 存 token，就必须重新开启。

  Q9：登录接口怎么防止暴力破解？
  A： 多维度限流（IP / 用户名）+ 失败次数锁定 + 验证码 +
     异常登录检测 + 登录日志审计。

  Q10：怎么防账号枚举？
  A： 用户名不存在和密码错误返回同一句话。
     ★ 进阶：还要防时序攻击，用户不存在时也跑一次假的 BCrypt。
