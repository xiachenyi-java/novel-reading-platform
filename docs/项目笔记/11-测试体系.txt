第 2 步 · 补最有价值的单元测试
--------------------------------------------------------------------------------

  □ 给 NovelServiceIml 写纯单元测试（Mockito，不启动 Spring）
    位置：新建 src/test/java/com/example2/demo2/service/NovelServiceUnitTest.java

    ★ 优先测这三个方法（最容易出 bug 的地方）：

    ① addChapter —— 字数累加
       断言：发布章节后，novel.totalWords 应该增加 chapter.content.length()
       边界：第一章（totalWords 为 null 或 0）、超长正文

    ② updateChapter —— 字数差计算
       断言：新字数 - 旧字数 = totalWords 的变化量
       边界：正文变长、变短、长度不变

    ③ deleteChapter —— 扣减 + 重排
       断言：totalWords 减去被删章节的字数
             剩余章节的 chapterNumber 重排成 1,2,3...
       边界：删除最后一章、删除唯一一章

    ★ 这几个方法的逻辑是"算数 + 状态变更"，
      最容易被忽略、最容易出错，也最适合单元测试。

  □ 给 UserService 写纯单元测试
    ① register
       · 用户名已存在 → 抛 BusinessException("用户名已存在")
       · 正常注册 → 密码被 BCrypt 加密（不是明文）
    ② login
       · 用户名不存在 → 抛"用户名或密码错误"
       · 密码错误 → 抛"用户名或密码错误"（★ 必须和上面同一句话）
       · 正常登录 → 返回 token + refreshToken
    ③ refresh
       · refreshToken 不存在 → 抛"刷新令牌已过期或不存在"

第 3 步 · 接口层测试（★ 最有价值）
--------------------------------------------------------------------------------

  □ 用 MockMvc 写鉴权测试
    这四类测试写完，你的鉴权逻辑就有了保障：

    ① 无 token 访问受保护接口 → 401
       mockMvc.perform(delete("/novels/1")).andExpect(status().isUnauthorized())

    ② 普通用户访问管理员接口 → 403
       先登录拿 token，再带 token 调 DELETE /novels/1

    ③ 游客可以浏览小说列表 → 200
       mockMvc.perform(get("/novels?page=1&size=8")).andExpect(status().isOk())

    ④ 黑名单里的 token → 401
       登录 → 登出（写黑名单） → 再用同一个 token → 401
       ★ 这个测试顺便验证了你的黑名单逻辑是对的

  □ 参数校验测试
    · 用户名长度 2 位 → 返回"用户名长度3-20位"
    · 密码 5 位 → 返回"密码至少6位"
    · 空 body → 400 或校验失败

  □ 业务接口测试
    · 创建小说 → 返回 200 + data.id 不为空
    · 查不存在的小说 → 返回"小说不存在"
    · 分数精度：发布 2 章后，小说 totalWords = 两章字数之和

    目标：先定 40%，覆盖核心业务逻辑即可
    ★ 不要为了数字去测 getter/setter

坑 1 · 测试第一次绿、第二次红（Flaky Test）
--------------------------------------------------------------------------------

  【现象】
    同一个构建，不改变任何代码，连续跑两次结果不同：

      第 1 遍   Tests run: 12, Failures: 0, Errors: 0   BUILD SUCCESS
      第 2 遍   Tests run: 12, Failures: 1, Errors: 2   BUILD FAILURE

    ★ 这叫 Flaky Test（不稳定测试）。
      它比"没有测试"更糟 —— 会让人养成"红了就重跑"的习惯，
      最后整个测试套件失去信任，真出 bug 也没人看。

  【怎么定位的（三步，可复用的排查套路）】
    ① 看错误码：Status expected:<200> but was:<429>
       429 = Too Many Requests → 直觉指向"限流"
    ② 翻日志 logs/book-manager.log，发现 3 条限流 WARN：
         "触发限流: 请求过于频繁，请稍后再试"
       而失败的测试恰好也是 3 个 —— ★ 1:1 对应，锁定根因
    ③ 控制变量法验证：
         等 60 秒再跑 → 绿了
         立刻再跑一遍 → 又红了
       ★ 代码没变、环境没变，只有"时间"变了
         ⇒ 根因一定和"会过期的东西"有关（TTL）

  【根因】
    UserControllerTest 一次运行要登录 4 次：
      testLoginSuccess                  → login #1
      testLoginWithWrongPassword...     → login #2
      testAccessNovelsWithValidToken... → login #3
      testUserCannotDeleteNovel         → login #4

    而登录接口有限流：@RateLimit(key="login", limit=5, window=60)

    三个因素叠加，才酿成这个坑：
      ① 限流计数存在 Redis 里，不在数据库里
      ② 类上的 @Transactional 只能回滚数据库，★ 回滚不了 Redis
      ③ MockMvc 里所有请求的 IP 都是 127.0.0.1 → 共用同一个限流 key

    ⇒ 60 秒内跑第二遍，计数累积超过 5
      → 第 6 次登录开始返回 429
      → 后面的测试拿不到 token，$.data 是 null
      → JsonPath 报 PathNotFound（★ 表象离根因很远，容易查错方向）

  【修法】在 @BeforeEach 里显式重置限流计数（只改测试，不动生产代码）

    @BeforeEach
    void resetRateLimit() {
        Set<String> keys = stringRedisTemplate.keys("rate_limit:*");
        if (keys != null && !keys.isEmpty()) {
            stringRedisTemplate.delete(keys);
        }
    }

  【为什么选这个修法（考虑过三个方案）】
    A. 测试环境关掉限流
       ✗ 测试和生产行为不一致；以后想写限流测试就测不出来了
    B. @BeforeEach 清 key  ← 采用
       ✓ 限流状态本来就在 Redis 里，测试就该显式管理这个状态
    C. 每个测试用不同 IP（request.setRemoteAddr）
       太啰嗦，每个请求都要加

  【验收】
    ./mvnw test && ./mvnw test      → 两遍都 BUILD SUCCESS
    ★ 判据不是"跑通一次"，是"每次都能跑通"（可重复性 / Repeatable）

  【附带收获：错误信息变好了】
    修完之后，Redis 挂掉时的报错从
      "Expected to find an object with property ['token'] in path $['data']"
    变成了
      "RedisConnectionFailure: Unable to connect to Redis"
    ★ 故障从"离根因很远的表象"提前到"离根因最近的地方"，
      排查时间从半小时降到 5 秒 —— 这就是 Fail Fast 的价值。

  【面试怎么讲】
    "我的测试一开始不可重复。原因是登录接口有 Redis 限流，
     @Transactional 能回滚数据库，但回滚不了 Redis ——
     限流计数跨测试运行累加，60 秒内跑第二遍就超限了。
     修法是在 @BeforeEach 里显式重置这个状态。"

    ★ 再补一句更狠的：
      "这个坑还有个变种 —— 测试污染生产。如果测试连的是生产 Redis，
       清理语句会把线上用户的限流计数也清掉。正确做法是测试用
       独立的 Redis DB（比如 database: 1），而不是只加个清理语句。"

坑 2 · 测试方法名说谎
--------------------------------------------------------------------------------

  【现象】三个测试方法名和实际测试内容完全不符：

    方法名                              实际在测什么
    ----------------------------------  ----------------------------------
    testAccessNovelsWithoutToken        密码错误时登录失败
    testAccessNovelsWithToken           不带 token 建小说 → 401（方向正好相反）
    testAccessBooksWithToken            "Books" 是改造成小说项目前的旧名残留

  【为什么要改】
    方法名是唯一不用读代码就能看懂的文档。
    名字说谎 = 文档说谎，而且更危险：
    看测试报告的人会以为某条路径被测过了，其实根本没有
    —— ★ 绿灯给了你虚假的安全感。

  【改成】
    testLoginWithWrongPassword_ShouldReturn500
    testCreateNovelWithoutToken_ShouldReturn401
    testAccessNovelsWithValidToken_ShouldReturn200
    testLogoutThenReuseToken_ShouldReturn401        ← 新增

  【新增的那个测试为什么最值钱】
    它盯着 LoginInterceptor 里"查黑名单"那段逻辑 ——
    也就是刚修过"Redis 挂了要降级"的那段代码。
    ★ 改过的代码，必须有测试盯着，否则下次改动可能悄悄改坏它。

    ★ 为什么用 /users/logout 而不是 /novels 来测：
      拦截器是"三态设计"，GET /novels 属于"游客路径"——
      即使在黑名单里也只是"不设置用户上下文"，仍然放行返回 200。
      要触发 401，必须用一个"严格路径"（非 GET + /novels 开头）。

    改完测试代码跑 ./mvnw test，8 个测试全部报错：

      "确认 MySQL 和 Redis 都在跑（Redis 不在跑的话，
        所有需要登录的接口都会 500，别以为是代码问题）"
