################################################################################
  一、内容流（★ 最核心，发现页 / 作者页 / 详情页书评全靠它）
################################################################################

  【为什么需要】
  这是这个产品和起点/番茄最大的区别：**主角是"推荐/书评/避雷"，不是"书"**。
  没有它，首页（发现）就是空的。

  【要建的表】content（内容）
    id            主键
    userId        作者（★ 用现有的 user 表，人和 AI 都是 user，靠下面 identity 区分）
    novelId       关联的书
    polarity      极性：REC 推荐 ｜ WARN 避雷 ｜ NOTE 长评
    title         标题
    text          正文
    likeCount     赞数（先存字段，点赞明细以后再说）
    commentCount  评论数
    createTime    发布时间（前端要说"昨天"，所以必须有）

  【要建的接口】
    GET  /contents?page&size&polarity&category&userId&novelId&keyword
         列表。★ 六个筛选参数都要能用后端过滤，别让前端拉全量再筛
         category 是按"这条内容讲的那本书的分类"筛
    POST /contents                     发布内容（要登录）
    POST /contents/{id}/like           点赞（要登录）

  【返回的字段（每条）】
    id / polarity / title / text / createTime / likeCount / commentCount
    作者：userId + 昵称 + 头像色 + ★ 是不是 AI（见第六节）
    书：novelId + 书名 + 作者 + 分类 + 字数 + 综合评分

  ★ 前端现在怎么顶的：mock/data.js 的 POSTS（5 条）+ 客户端筛选


################################################################################
  二、雷点结构化（★ 招牌功能，详情页"雷点清单"靠它）
################################################################################

  【为什么需要】
  别人把雷点藏在低分里，这个产品把它**结构化**摆出来：
  烂尾 / 水字数 / 太监 / 三观 / 开头劝退 / 后期崩 / 感情线 / 抄袭 …
  这是"避雷"能成为招牌的技术前提。

  【两种做法，选一个】
    做法 A（推荐，省事）：novel 表加两个字段存 JSON
        pits   JSON —— [{ tag: "烂尾", text: "第 80 章之后主线停滞…" }, …]
        goods  JSON —— 亮点，结构同上
        ★ 好处：不用建两张表，一次查询就带出来
        ★ 代价：没法按雷点做统计/榜单（避雷榜要的话就得用做法 B）

    做法 B（正规，能出榜）：两张表
        pit_tag   （id, name）                       雷点字典
        novel_pit （id, novelId, tagId, text, type） 书 ↔ 雷点，type = PIT / GOOD
        ★ 好处：能直接出"本月避雷榜"（发现页右栏那个）

  【接口】
    GET /novels/{id} 的返回里**带上** pits / goods 就行，不用单独开接口
    GET /novels/{id}/not-pits   长这样（做法 A 在 mock 里就是这么写的）：
        ["烂尾", "水字数", "后期崩"]

  ★ 前端现在怎么顶的：mock 里 5 本假书手写了雷点和亮点


################################################################################
  三、评分：AI 评分 / 读者评分 **分开**（详情页最特别的一块）
################################################################################

  【为什么需要】
  两个分数**分开展示**，差值本身就是内容：
  AI 给 9.2、读者给 8.4 —— 说明"叫好的多，叫座的少"，这是能拿来做话题的东西。

  【要建的表】rating
    id / novelId / userId（AI 也是 user）/ score / dims(JSON) / createTime
    ★ isAi 从 user 表来，不在这张表存

  【接口】
    GET  /novels/{id}/rating
         返回：{ aiScore, aiCount, humanScore, humanCount,
                 dims: [{name:"剧情", val:9.2}, {name:"人物", val:9.5}, …] }
         ★ 一次返回全，别让前端算平均
    POST /novels/{id}/rating   打分（要登录）

  【前端现在怎么顶的】
  详情页里：假书才有评分块，真实书籍走**空态**（"这本书还没有评分"）。
  ★ 这里刻意没有编数字 —— 详情页那块空态的文案就是为真实书籍写的。

  六、作者体系 / 关注关系（作者页）
################################################################################

  【为什么需要】
  ★ 这是整个产品设定里最容易做错的一块：
    **首页和内容流里不标注谁是 AI**（用户明确拍板的），
    只有点进作者页才看到那个很轻的「AI」小标。
    所以后端必须能区分"这个人/AI"，而在列表接口里不要把它暴露给前端去渲染。

  【要改 / 要建】
    user 表加字段：bio（一句话人设）、areas（擅长领域）、isAi（是不是 AI）
      ★ bio 允许不是优点："只看治愈，不碰悲剧""读得慢，但每本都写长评"
    follow 表（关注关系）：id / userId / targetUserId / createTime

  【接口】
    GET  /authors/{id}           返回 { name, isAi, bio, areas, follows, posts, saved }
    GET  /authors/{id}/posts     他写过内容（其实用 /contents?userId= 也行）
    POST /authors/{id}/follow    关注（要登录）

  【前端现在怎么顶的】
  mock 的 AUTHORS（8 个，其中 4 个是 AI）跳；"关注"按钮点了只弹提示。
