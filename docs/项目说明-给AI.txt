################################################################################
  一、项目是什么
################################################################################

【一句话】
  基于 Spring Boot 的小说阅读平台，前后端分离。
  管理员发布小说和章节，读者浏览、搜索、阅读。

【性质】
  个人学习项目 / 简历项目。目标不是上线运营，而是把 Java 后端知识点串成线。

【规模】（★ 2026-10-05 实测核实，旧文档里的 38/2000/19/9 都是错的）
  · 后端：37 个 Java 类，2055 行代码，16 个 REST 接口
  · 测试：12 个测试用例，./mvnw test 连跑两遍稳定全绿（判据 B 已达标）
  · 前端：8 个 Vue 组件
  · 数据库：3 张表（user / novel / chapter）
  · Redis：7 类 key（认证、限流、排行榜、缓存）+ 2 个 Spring Cache 区域
          （novel / novel-null）

  【★ 三个必须知道的版本坑】

  1. Lombok 必须用 1.18.46（Spring Boot 4.1 管理的版本）
     × 1.18.36 及以下不支持 JDK 25，会报：
       ExceptionInInitializerError: com.sun.tools.javac.code.TypeTag :: UNKNOWN
     ★ 最佳做法：pom 里**不要写** <lombok.version>，让 Boot 的 BOM 管理
     ⚠ 现状不一致：pom.xml 第 35 行**确实写了** <lombok.version>1.18.46</lombok.version>。
       值恰好等于 BOM 管理的版本，所以目前无害；但 Boot 升级后它会把 Lombok
       钉死在 1.18.46。建议删掉这一行（annotationProcessorPaths 里的
       ${lombok.version} 仍能从 Boot 的 BOM 解析到）

  2. pom 里必须有 annotationProcessorPaths 配置
     JDK 23+ 默认不再自动运行 classpath 上的注解处理器，
     不配的话 Lombok 完全不生效，报一堆"找不到符号 getXxx()"

  3. 本机 JAVA_HOME 必须指向 JDK 25
     ★ Windows 环境变量改动不会传播到已运行的进程，
       改完要重启终端 / IDEA

################################################################################
  四、关键设计决策（★ 改动前必读，这些是有意为之的）
################################################################################

--------------------------------------------------------------------------------
决策 1：Novel 和 Chapter 用 novelId 手动关联，不用 @OneToMany
--------------------------------------------------------------------------------
  【做法】Chapter 里就一个普通字段 `private Integer novelId;`
  【为什么】用 @OneToMany 的话，查小说时会把所有章节的正文一起加载出来 ——
            一本 500 章的小说正文可能几十 MB
  【代价】失去级联便利，删除小说要手写 chapterRepository.deleteByNovelId(id)
  【改的时候注意】不要"顺手"改成关联注解，会引发性能问题

--------------------------------------------------------------------------------
决策 2：novel.totalWords 是冗余字段
--------------------------------------------------------------------------------
  【做法】总字数单独存一列，而不是每次 SUM(chapter.word_count)
  【为什么】小说列表是最高频接口，实时算要 JOIN + 聚合
  【★ 代价】三个地方必须同步维护，漏一处就数据不一致：
            · addChapter    → totalWords += wordCount
            · updateChapter → totalWords += (新字数 - 旧字数)
            · deleteChapter → totalWords -= wordCount
  【改的时候注意】任何改变章节字数的操作，都要同步改 totalWords

--------------------------------------------------------------------------------
决策 3：Token 黑名单用 Redis Hash，不用 Set
--------------------------------------------------------------------------------
  【结构】blacklist:user:{userId}  →  Hash{ token: 过期时间戳 }
  【为什么不用 Set】Set 只存 token，没存过期时间，不知道何时能清理
  【清理机制】读取时惰性清理过期的 field
  【★ 遗留问题】整个 Hash key 没有兜底 TTL，用户登出后不再访问就永久驻留

--------------------------------------------------------------------------------
决策 4：Refresh Token 做双向索引
--------------------------------------------------------------------------------
  【正向】refresh_token:{token} → userId   用途：刷新时查是哪个用户
  【反向】user_refresh:{userId} → token    用途：登出时查要删哪个 token
  【为什么】两个方向都会用到，只存单向登出就删不掉 Refresh Token
  【★ 遗留问题】String 结构只存一个 token，**多设备登录会互相覆盖**
               （见"已知问题"区）

--------------------------------------------------------------------------------
决策 5：搜索/筛选用 Specification，不用方法名推导
--------------------------------------------------------------------------------
  【做法】NovelSpecifications 里每个条件一个静态方法，
          条件为空返回 null（Spring Data 自动忽略）
  【为什么】3 个可选条件用方法名推导要写 2³ = 8 个方法
  【★ 参数顺序】Controller → Service → Specifications 三处必须一致：
                page, size, category, status, keyword

--------------------------------------------------------------------------------
决策 6：索引用 @Table(indexes=...) 声明，不手写 SQL
--------------------------------------------------------------------------------
  【做法】实体类上 @Table(name="novel", indexes = {@Index(...)})
  【为什么】索引定义跟代码走，换机器 / 重建表会自动创建
  【注意】columnList 写 **Java 属性名**（如 lastUpdateTime），
          Hibernate 会自动翻译成列名（last_update_time）

--------------------------------------------------------------------------------
决策 7：缓存降级（CacheErrorHandler）
--------------------------------------------------------------------------------
  【做法】CacheConfig 实现 CachingConfigurer，自定义 errorHandler
  【为什么】@Cacheable 让 Redis 从"可选依赖"变成"强依赖"，
            Redis 一挂详情页就打不开
  【效果】缓存读写失败只记 warn 日志，请求降级直查数据库
  【★ 局限】CacheErrorHandler 只保护 @Cacheable/@CacheEvict 注解，
            **保护不了手写调用**（stringRedisTemplate 或 cacheManager.getCache()）
            ⇒ 手写的地方必须自己 try-catch

  【✅ 当前状态：已修复（2026-10-06）】
    findDetail 为了做空值缓存（决策 10）改成了手动 cacheManager 调用，
    CacheErrorHandler 因此一度失效。现已用 try-catch 手动补回降级。
    完整修复过程 → docs/实战笔记/05-缓存三大问题实战.txt 第四节

  【★★★ 下面这段是最有价值的教训，别删 —— "改动引入回归"的典型案例】

    ── 为什么 CacheErrorHandler 会失效 ──
      CacheErrorHandler 由 AbstractCacheInvoker 调用，而它是
      CacheAspectSupport（AOP 拦截器）的父类。
      只有**注解驱动**的调用才经过拦截器；
      手动 cache.get() 直接进 RedisCache，没有 try/catch 兜底。
      ★ 一句话：**"注解生效" = "框架的切面拦住了你"。**
        绕开切面（改手写 API），切面提供的所有附加能力都会消失。
      ★ 推广（AOP 通用规律）：
          @Cacheable     → CacheInterceptor       → 丢失：缓存降级
          @Transactional → TransactionInterceptor → 丢失：事务回滚、传播
          @RateLimit     → RateLimitAspect        → 丢失：限流计数
          @RequireAdmin  → LoginInterceptor       → 丢失：权限校验

    ── ★★ 失败方式比"500"更糟：挂起 vs 快速失败 ──
      当时项目没配 spring.data.redis.timeout → 用 Lettuce 默认 60 秒命令超时。
      不是"快速失败"，而是每个请求占着 Tomcat 线程卡满 60 秒。
      Redis 一挂 + 请求量稍大 → 线程池被占满 → 连不依赖 Redis 的
      列表接口也开始排队 → 级联故障。
      ★ 结论：**挂起（hang）几乎总是比报错（fail fast）更危险**，
        因为挂起会消耗资源并向上游传播，报错可以被隔离。

    ── ★★★ 判据修正（旧判据是错的，会给假阳性）──
      旧判据："返回 200 = 降级有效 / 返回 500 = 降级失效"。**这是错的。**
      原因：GlobalExceptionHandler.handleRuntimeException 没有 @ResponseStatus，
      所有 RuntimeException 都返回 HTTP 200。
      ⇒ 按旧判据跑，失败也会被读成"✅ 降级仍然有效"。
      正确判据：看 **body 里的 code 字段**
        · body {"code":200, ...有数据}                        → 降级有效
        · body {"code":500,"msg":"Redis command timed out"}   → 降级失效
      ★ 通用教训：**判据本身也要验证** ——
        假阳性判据比没有判据更危险，因为它会让你以为已经验证过了。

  【✅ 修复方案（已实施）】

    ── 第一级：超时（止血）—— application-dev.properties ──
      spring.data.redis.timeout=500ms
      spring.data.redis.connect-timeout=500ms
      ★ 两个都要配：connect-timeout 管建立 TCP 连接，
        timeout 管命令发出后等响应。Redis 端口不通时走前者。

    ── 第二级：try-catch（治疗）—— NovelServiceIml.findDetail ──
      4 处 Redis 调用各包 try-catch：
        ① nullCache.get()   ② novelCache.get()
        ③ nullCache.put()   ④ novelCache.put()
      · 读失败 → 降级为"缓存未命中"，继续走 DB（**不要 rethrow**）
      · 写失败 → 吞掉异常，不影响主流程（缓存是加速器，不是必需品）
      · catch 里打 log.warn，只打 message 不打堆栈（避免刷屏）

  【✅ 三阶段实测数据（2026-10-06，简历素材）】

    ── 演练方法 ──
       docker stop demo2-redis
       curl "http://localhost:8080/novels/1"
       docker start demo2-redis

    ------------------------------------------------------------------
    阶段                  耗时        HTTP   body.code   接口可用性
    ------------------------------------------------------------------
    ① 改造前（60s 超时）  60.0s 挂起  200    500         ❌ 打不开
    ② 只加超时配置        0.51s       200    500         ❌ 打不开
    ③ 再加 try-catch      1.01s       200    200         ✅ 有数据
    ------------------------------------------------------------------

    ★ ②→③ 才是真正的修复。② 只是 fail fast（快速失败），
      ③ 才是 graceful degradation（优雅降级）。
      ★ 只做 ② 的话，用户体感是"从一直转圈变成立刻报错"，**还是不可用**。

    ── 并发压测（500 请求 / 100 并发 / Redis 挂）──
      /novels/1    ：P50 1.491s，P95 2.575s，最大 2.784s，0 个超 5 秒
      /novels 列表 ：P50 0.248s，全程 200（不依赖 Redis，未被拖垮）
      ⇒ 级联故障被切断

  【★ 附带发现：Lettuce 断连时会缓冲写命令（2026-10-06）】
    演练时发现"详情缓存写入失败"的 warn **一次都没触发**。
    做了个决定性实验：重启 Redis 后**不发任何请求**，直接查
      docker exec demo2-redis redis-cli EXISTS "novel::1"  → 1
    → Lettuce 在断连期间把写命令缓冲了起来，重连后自动补发。

    ★ 影响：
      · 那两个 put 的 catch 在当前场景下永远不会触发
        （保留仍是对的，是防御其他故障模式的安全网）
      · disconnectedBufferSize 默认 64KB，缓冲满了才会真正失败
        → "Redis 挂了"对**写操作**是**延迟暴露**的

    ★ 本质：**同步 API 掩盖了异步现实**。Lettuce 底层是异步的（Netty），
      Spring Data Redis 包了一层同步 API，connection.set() 返回 **void**。
      **"没有返回值的远程调用，等于没有错误处理。"**

决策 8：LoginInterceptor 三态设计
--------------------------------------------------------------------------------
  【第一态】OPTIONS 预检请求 → 直接放行
  【第二态】游客路径（GET + 路径以 /novels 开头）→ 宽松，有 token 就解析
  【第三态】其他所有路径 → 严格，无 token / 解析失败 / 在黑名单 → 401
  【★ 权限检查也在拦截器里】它比过滤器多一个能力：能拿到 HandlerMethod，
                            所以能读方法上的 @RequireAdmin 注解

--------------------------------------------------------------------------------
决策 9：@RequireAdmin 加在 Controller 方法上，不是 Service 上
--------------------------------------------------------------------------------
  【★ 重要】拦截器检查的是 HandlerMethod（Controller 方法），
            Service 方法上的注解它**看不到**。
            所以 Service 层加 @RequireAdmin 是无效的装饰品。

--------------------------------------------------------------------------------
决策 10：空值缓存防穿透（2026-10-05 新增）
--------------------------------------------------------------------------------
  【要解决的问题】
    查询一个不存在的 id（如 /novels/999999）时，缓存永远不命中，
    每次请求都打到数据库 —— 这就是**缓存穿透**。

  【做法】用独立的缓存区域 novel-null 存"查过、但确实没有"的标记：
    · CacheConfig 里给 novel-null 单独设 **5 分钟** TTL
    · NovelServiceIml.findDetail 改成三分支判断：
        ① 命中 novel-null   → 直接抛"小说不存在"，不查库
        ② 命中 novel        → 直接返回
        ③ 都没命中          → 查库；库中也没有就写 novel-null 再抛异常
    · addNovel 上加 @CacheEvict(value = "novel-null", key = "#result.id")
        ★ 为什么需要这一手：空表时查过 /novels/1 会被缓存成 null，
          而新增的第一本小说正好拿到 id=1 —— 不清就会 5 分钟内显示"不存在"

  【为什么用独立区域，不混在 novel 里】
    空值和真实数据的生命周期完全不同：
      · 真实小说：可以缓存 30 分钟
      · 空值：只该缓存几分钟（万一数据后来又真的出现了）

  【★ 三件套完成情况（2026-10-07 更新）】
    · 缓存雪崩（大量 key 同时过期）→ TTL 随机抖动 ✓
      CacheConfig 的 TtlFunction（每次 put 求值），1500~2100 秒
    · 缓存击穿（热点 key 失效瞬间，并发请求同时打 DB）→ 本地互斥锁 ✓
      NovelServiceIml.findDetail：ConcurrentHashMap<Integer,Object> +
      synchronized + 双重检查（锁内重读缓存）
      ★ 遗留：① locks 只增不减（无界增长，内存泄漏隐患）
              ② 这是**单机锁**，多实例部署时每个 JVM 仍各查一次库
    详见 docs/项目笔记/05-缓存体系.txt

  【交互影响】✅ 已处理（2026-10-06）。这次改动把 @Cacheable 换成了手动调用，
              一度打掉了缓存降级（手动调用绕过 AOP 切面）；
              现已用 try-catch 手动补回。
              ★ 完整过程 + 三阶段实测数据见决策 7。

  18. ✅【2026-10-07 实测发现 · 当天已解决】Docker 里的 prod 撞上空库

      ── 现象 ──
      demo2-app 启动即 Exited(1)：
        SchemaManagementException: Schema validation: missing table [chapter]
      ★ 注意：报的是 chapter，但它只是**第一个被检查到的** ——
        三张表其实都缺。

      ── 根因：三件事叠加，缺一不发生 ──
        ① compose 里 SPRING_PROFILES_ACTIVE=prod
        ② prod 的 ddl-auto=validate  → **只校验、绝不建表**（设计正确）
        ③ compose 的 MYSQL_DATABASE   → **只建库、绝不建表**
      ＋ 项目里**没有任何 .sql 文件**（find 过）
      ⇒ 开发库的表是 dev 的 update 模式**悄悄长出来的**，
        只存在于本机硬盘上。**validate 在向一份不存在的合同对账。**
      ⇒ 只要 volume 为空（新机器 / 删过 volume），**100% 复现**，不是偶发。

      ── ✅ 修法（方案 A：MySQL 官方 initdb 机制）──
        ① mysqldump -uroot -p****** --no-data --databases book_db \
             > docker/mysql/init/01-schema.sql
        ② docker-compose.yml 的 mysql 加挂载：
             - ./docker/mysql/init:/docker-entrypoint-initdb.d:ro
        ③ docker compose down -v && docker compose up --build

      ── ★★ 两个必须记住的坑 ──
        · init 脚本**只在数据目录为空时执行一次**。
          不 `down -v` 就 up，脚本根本不会跑，你会得到**一模一样的报错**。
        · 导出的 schema **必须验索引在不在**：
            SHOW INDEX FROM book_db.novel;
          应看到 3 行（PRIMARY + idx_novel_last_update_time
          + idx_novel_category_last_update_time）。
          漏了的话，"索引优化有实测数据"这条简历优势在线上等于零。

      ── ★ 深层认知（面试可讲）──
        **@Table(indexes=...)（决策 6）在 prod 的 validate 模式下
        不产生任何 DDL。** 它在 dev 的 update 下会自动建索引，
        但 prod 只校验不创建 —— 索引必须由 schema.sql / 迁移脚本显式创建。
        ⇒ "索引定义跟代码走"这句话**只在 dev 成立**。

      ── 已实测（2026-10-07）──
        容器 3 个全 Up；GET /novels → body code=200；
        chapter / novel / user 三张表齐全；novel 的 3 个索引齐全。
        ★ 注意 content 为空数组 —— 导出用的是 --no-data，只带结构不带数据。

      ── 遗留待办 ──
        · mysql 仍无 healthcheck（七·二 B1 待办）——
          init 脚本会让 MySQL 首次启动多花 20-40 秒，
          depends_on 只等 service_started ⇒ 更容易撞上"没就绪"
        · 没有 .dockerignore：构建上下文 129M，其中 126M(98%) 是
          novel-frontend/node_modules —— Dockerfile 一个字节都没用到
        · 没有 schema 版本管理（Flyway/Liquibase）—— 第三梯队
        · 前端不在 compose 里（见 七·二 B1：Nginx 托管 dist/）

################################################################################
  十二、不要做的事（约束）
################################################################################

  □ 不要用 @OneToMany 关联 Novel 和 Chapter（会加载正文，性能灾难）
  □ 不要手写 CREATE INDEX —— 用 @Table(indexes=...) 声明
  □ 不要在 Service 方法上加 @RequireAdmin（拦截器看不到）
  □ 不要在 Controller 里直接调 Repository
  □ 不要忘记 @Valid —— 漏了校验完全不生效
  □ 不要忘记 @CacheEvict —— 改了详情字段不清缓存，前端看到旧数据
  □ 不要用 Executors 创建线程池（如果以后加异步）
  □ 不要在日志里打印整个 User 对象（@Data 的 toString 含 passwordHash）
  □ 不要把 passwordHash 返回给前端或写进缓存
  □ 不要提交 application-*.properties 里的真实密码
