  【★ v2 修订 1：去掉 last_read_chapter_number 冗余字段】
  【★ v2 修订 2：索引从 3 个改成 2 个，且带上 is_top/top_time 前缀】

  -- 这是 @Table(indexes = ...) 声明后 Hibernate 生成的等价 DDL
  -- ★ prod 环境不认 @Table，必须同步写进 docker/mysql/init/01-schema.sql
  CREATE TABLE `bookshelf` (
    `id`                        int NOT NULL AUTO_INCREMENT,
    `user_id`                   int NOT NULL,
    `novel_id`                  int NOT NULL,

    -- 阅读进度
    `last_read_chapter_id`      int DEFAULT NULL,
    `last_read_time`            datetime(6) DEFAULT NULL,

    -- 置顶
    `is_top`                    tinyint NOT NULL DEFAULT 0,
    `top_time`                  datetime(6) DEFAULT NULL,

    -- 审计
    `create_time`               datetime(6) NOT NULL,
    `update_time`               datetime(6) NOT NULL,
    `deleted`                   tinyint NOT NULL DEFAULT 0,

    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_bookshelf_user_novel` (`user_id`, `novel_id`),

    -- ★ 排序索引：必须带上 is_top / top_time 前缀，否则排序仍会 filesort
    KEY `idx_bookshelf_top_create`
        (`user_id`, `deleted`, `is_top`, `top_time`, `create_time`),
    KEY `idx_bookshelf_top_read`
        (`user_id`, `deleted`, `is_top`, `top_time`, `last_read_time`)
  ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci;

  ------------------------------------------------------------------
  字段                        说明
  ------------------------------------------------------------------
  last_read_chapter_id       最后读的章节 id，未读为 null
  last_read_time             最后阅读时间，未读为 null
  is_top                     0/1，是否置顶
  top_time                   ★ 多个置顶时按"置顶先后"排
  create_time                收藏时间（复活时重置，见拍板点 2）
  update_time                @PreUpdate 自动维护，零同步成本
  deleted                    软删标记
  ------------------------------------------------------------------

  【★★ v2 修订 1 的完整理由：为什么去掉 last_read_chapter_number】

    v1 草案的原话：
      "冗余的代价是'和 chapter 表可能不一致'，
       但**章节号基本不变，风险低**。"

    ★ 这个前提在本项目**不成立**。代码证据：

      // NovelServiceIml.java:151-156   deleteChapter 的最后一段
      // 重排章节号
      List<Chapter> chapters =
          chapterRepository.findByNovelIdOrderByChapterNumberAsc(novelId);
      for (int i = 0; i < chapters.size(); i++) {
          chapters.get(i).setChapterNumber(i + 1);   // ← 章节号会变！
      }
      chapterRepository.saveAll(chapters);

    ⇒ 管理员删掉第 5 章 → 原来的 6 变成 5、7 变成 6 ……
    ⇒ 用户读到第 8 章，书架显示"读到第 8 章"，删章后他读的
       其实是现在的第 7 章 —— **显示错位**
    ⇒ last_read_chapter_id 甚至可能指向**已被删除的章节**

    ★ 这不是"风险低"，是**必然发生**。
    ★ 而且它是 totalWords 那个病的第三次复发（决策 2）——
      冗余字段要"多处同步维护"，但这个字段**没有任何地方负责同步**。

    【替代方案】不存 number，列表里用 last_read_chapter_id 批量回查。
      成本：**SQL 次数不变** —— 因为本来就要跑"批量查章节统计"那条
      GROUP BY（见第八节）。扩成顺便带回章节号即可。

    【顺带解决】last_read_chapter_id 指向已删章节的问题：
      SQL 里用 LEFT JOIN chapter ON b.last_read_chapter_id = c.id，
      查不到就显示"进度已失效"，前端提示"从第 1 章重新读"。

  【★★ v2 修订 2 的完整理由：为什么索引要带 is_top/top_time 前缀】

    三种排序都是这个形状：
      ORDER BY is_top DESC, top_time DESC, <排序键> DESC, id DESC

    v1 草案配的索引是 (user_id, deleted, last_read_time)。
    ★ 对不上 —— MySQL 用索引避免排序的条件是：
      **ORDER BY 的列顺序必须是索引列顺序的前缀**。
      这里 ORDER BY 第一列是 is_top，而索引第三列才是 last_read_time，
      中间隔着 is_top / top_time。
    ⇒ MySQL 只能用它做 WHERE 过滤，**排序阶段仍然 filesort**。

    修正后的索引：
      idx_bookshelf_top_create (user_id, deleted, is_top, top_time, create_time)
      idx_bookshelf_top_read   (user_id, deleted, is_top, top_time, last_read_time)
      ↑ 等值列 user_id/deleted 后面的部分，正好是 ORDER BY 的前缀
      ↑ InnoDB 会自动在末尾追加主键 id，所以 id DESC 也被覆盖

    ★ novel_update 排序**必然 filesort**，躲不掉 ——
      排序列 n.last_update_time 在另一张表里，任何 bookshelf 上的索引
      都救不了。这不是设计缺陷，是跨表排序的物理限制。
      ⇒ 面试可讲："我为什么接受这个 filesort"

    ★ 为什么是 2 个而不是 3 个：
      既然 novel_update 那个索引救不了排序，它就是纯负担
      （INSERT 时多维护一棵 B+ 树）。

    【★ 待实测】以上是**推理**，不是结论。
      实现后用 EXPLAIN 验证：
        EXPLAIN SELECT ... ORDER BY is_top DESC, top_time DESC,
                last_read_time DESC, id DESC;
        → Extra 列出现 "Using filesort" 就是没生效
        → 出现 "Using index condition" / "Backward index scan" 才算生效
      ★ 这一步别省 —— 推理错在 MySQL 优化器上是很常见的事。

  【唯一索引不带 deleted —— v1 的这个判断是对的，保留】
    复活逻辑走"UPDATE 旧记录"而不是 INSERT 新记录，所以不需要带。
    带上反而会出问题：MySQL 里 NULL 不参与唯一性判断，
    用 NULL 表示"未删除"会导致同一用户能收藏同一本书多次。

1.2 novel 表加 author
--------------------------------------------------------------------------------

  ALTER TABLE `novel` ADD COLUMN `author` varchar(100) NOT NULL DEFAULT '佚名';

  ★ v1 草案写了 "AFTER title 只为字段顺序好看" ——
    实测 mysqldump 导出的列顺序是**字母序**，AFTER 不会保留。
    ⇒ 删掉 AFTER，少一个误导。

  ★ 为什么改字段而不是新建 author 表：
    简单。如果将来要存作者简介、头像，再考虑拆表。

  ★★ 用数据库默认值 DEFAULT '佚名' **救不了你**：
    JPA 会**显式把 NULL 写进 INSERT 语句**，默认值只在"该列不出现在
    INSERT 里"时生效。所以 Service 层必须自己兜底（见 1.2.1）。

1.3 ★★ 建表落地：三个地方都要改（v1 草案完全漏了这节）
--------------------------------------------------------------------------------

  【为什么必须单独讲这一节】
    项目有两种运行模式，建表机制完全不同：

    application-dev.properties:11    spring.jpa.hibernate.ddl-auto=update
    application-prod.properties:8    spring.jpa.hibernate.ddl-auto=validate

  ⇒ 光在实体上声明索引，**prod 环境什么都不会发生**。

  【要改的三个地方】

    │             columnList="userId,deleted,isTop,topTime,createTime"),

    │             columnList="userId,deleted,isTop,topTime,lastReadTime")
    │    })                                                    │
    │  ★ columnList 写 **Java 属性名**，Hibernate 自动翻译成列名 │
    │    （决策 6）                                            │
    │  ★ 唯一索引用 @Table(uniqueConstraints = ...) 声明，       │
    │    不要塞进 indexes 里                                    │
    └──────────────────────────────────────────────────────────┘

    ┌─ ② docker/mysql/init/01-schema.sql（prod 用）────────────┐
    │  加两段：                                                  │
    │    ① ALTER TABLE `novel` ADD COLUMN `author` ...          │
    │    ② CREATE TABLE `bookshelf` (...)  含 2 个 KEY + 1 个 UK │
    │                                                           │
    │  ★★ 怎么改这个文件：不要手写！                             │
    │     在 dev 库跑一次，让 Hibernate 建好表和索引，然后：       │

################################################################################
  二、Redis 进度设计
################################################################################

  Key:   progress:{userId}:{novelId}
  Type:  Hash
  Fields:
    chapterId     → "123"
    chapterNumber → "5"                ← ★ 这里存 number 是安全的（见下）
    updateTime    → "1730000000000"    (毫秒时间戳)
  TTL:   7 天

  【★ 为什么这里可以存 chapterNumber，1.1 却不行？】
    Redis 的 progress 是**短期暂存**（7 天 TTL），刷回 DB 时只用它写
    last_read_chapter_id；而 bookshelf 表的 last_read_chapter_number 是
    **长期存储**，会跨越"管理员删章节"这个事件。
    ⇒ 同样的字段，生命周期不同，结论就不同。
    ★ 判断冗余能不能接受，看的是**它要活多久**，不是它叫什么。

  【写入时机】
    NovelServiceIml.readChapter 里，用户每读一章写一次。
    ★★ 但 readChapter 是**游客接口** —— 见 3.5，必须判空！

  【为什么不直接写 DB】
    快速翻页会打 10+ 次 UPDATE，DB 写压力大。

  【TTL 7 天的理由】
    进度是"活数据"，用户 7 天不看书，进度回 DB 也是准的
    （定时任务已经刷过了），Redis 里留着没意义。

  ------------------------------------------------------------------
  决策点        建议          备选
  ------------------------------------------------------------------
  数据结构      Hash          String 存 JSON（要序列化，且改字段麻烦）
  TTL           7 天          30 天 / 永不过期
  时间戳精度    毫秒          秒（★ 秒级精度下，同一秒内的两次
                              "最后写的赢"判断会失效）
  ------------------------------------------------------------------

3.1 加入书架
--------------------------------------------------------------------------------

  POST /bookshelf
  Body:   { "novelId": 123 }
  返回:   Result<BookshelfItemVO>   ← 返回刚加入的条目，方便前端直接插入列表

  【复活逻辑】
    ① 校验 novel 存在                              ★ v2 新增
         novelRepository.findById(novelId)
             .orElseThrow(() -> new BusinessException("小说不存在"));
       ★ 表间没有外键约束，不校验会产生指向不存在小说的脏记录
    ② 查 (userId, novelId) 的记录
    ③ 不存在          → INSERT
    ④ 存在且 deleted=0 → 幂等返回（已收藏）
    ⑤ 存在且 deleted=1 → UPDATE deleted=0, create_time=now() ★ 复用旧记录

  ★ 第 ⑤ 步 create_time 是否重置 —— 见"十、待拍板点"第 2 条

  【并发双击】
    两个请求同时到、且记录不存在时，都会走 INSERT，
    其中一个会撞 uk_bookshelf_user_novel 抛 DataIntegrityViolationException。
    ⇒ MVP 可以接受（前端按钮置灰即可）；
      要处理的话 catch 后重新查询返回即可。★ 记录在案，本轮不做

3.4 移出
--------------------------------------------------------------------------------

  DELETE /bookshelf/{id}
  POST   /bookshelf/batch-remove      Body: { "ids": [1,2,3] }
  返回:  Result<Void>

  【★ v2 修订：为什么 DELETE /bookshelf/batch 改成 POST】

    ① **DELETE 请求体的语义在 RFC 里是未定义的**，
       实践中有中间件会直接丢弃它（Nginx 默认转发，但某些网关/CDN
       不保证）。本地能跑通，换个环境就 400。
    ② **路由冲突**：DELETE /bookshelf/{id} 和 DELETE /bookshelf/batch
       前缀重叠。现在能work是靠 Spring PathPattern 的"字面量优先于模板"
       规则 —— 能跑 ≠ 设计对。而且 {id} 是 Integer，
       一旦匹配错就是 MethodArgumentTypeMismatchException。
    ③ "批量"是一个**动作**，不是一个资源 —— 本来就不该用 DELETE。

  【★ v2 补充：ids 数量上限】
    @NotEmpty + @Size(max = 100, message = "一次最多移出 100 本")
    ★ 同 3.2 的分页兜底，属于"输入必须有界"

  【★ 必须校验归属】
    批量删的时候要按 (id, userId) 一起删，不能只按 id。
    ★ 建议 SQL：DELETE 改成 UPDATE ...
        WHERE id IN :ids AND user_id = :userId
      这样一次 UPDATE 搞定，且天然免疫越权。

  【★ v2 修订 3 处：fixedDelay / SCAN / 刷完的幂等判断】

  @Component
  @RequiredArgsConstructor
  @Slf4j
  public class ProgressFlushTask {

      private final StringRedisTemplate stringRedisTemplate;
      private final BookshelfRepository bookshelfRepository;

      // ★ r2 修订 A：fixedRate → fixedDelay
      //   fixedRate 不管上一次跑完没有，到点就触发；
      //   若某次刷新超过 5 分钟，会有两个任务同时刷同一批 key。
      @Scheduled(fixedDelay = 300000)   // 上一次结束后再等 5 分钟
      public void flushProgress() {
          // ★ v2 修订 B：KEYS → SCAN
          //   KEYS 是 O(N) 阻塞操作，会卡住整个 Redis。
          //   SCAN 是游标式渐进遍历，不阻塞。
          //   ★ Cursor 必须 close —— 它占着一条 Redis 连接！
          try (Cursor<String> cursor = stringRedisTemplate.scan(
                   ScanOptions.scanOptions().match("progress:*").count(100).build())) {
              while (cursor.hasNext()) {
                  // 解析 key → 读 Hash → 批量收集
              }
          }
          // 批量 UPDATE，见下方幂等判断
      }
  }

  【★★ v2 修订 C：刷完删不删？—— v1 的 TTL 理由和"不删"自相矛盾】

    v1 草案里这两句挨着，但互相打架：
      · "用户 7 天不看书，进度回 DB 也是准的，**Redis 里留着没意义**"
      · "刷完是否删 Redis —— **不删**（会丢'正在读'状态）"

    算一下账：不删的话，每个 key 每 5 分钟被 UPDATE 一次，
    直到 7 天后 TTL 过期：
      7 天 × 24 小时 × 12 次/小时 = 2016 次
    ⇒ **每个 key 白写 2000 次 UPDATE**，且每次写的是同样的值。

    【正确做法：不是"删不删"，而是"要不要写"】
      让 DB 自己挡住重复写 —— 用 last_read_time 做版本号：

        UPDATE bookshelf
           SET last_read_chapter_id = ?,
               last_read_time = ?,
               update_time = ?
         WHERE user_id = ? AND novel_id = ?
           AND (last_read_time IS NULL OR last_read_time < ?)
                                    -- ↑ 只有 Redis 的进度更新时才写

    ⇒ Redis 里留着的 key 不会再产生无效 UPDATE
    ⇒ 也不用删（"正在读"状态得以保留，符合 TTL 7 天的初衷）

    【★★ 为什么版本号必须用 last_read_time，不能用 update_time】
      update_time 会被 @PreUpdate 在任何字段变更时刷新 ——
      包括**置顶、复活、软删**。

      反例：
        ① 用户读书 → Redis 里 updateTime = T
        ② 用户置顶这本书 → DB 的 update_time = now() > T
        ③ 定时任务刷进度 → 判断 "update_time < T" 不成立 → **跳过**
        ⇒ **这次阅读进度永久丢失**

      ★ last_read_time 只在进度变化时改，语义上就是"进度的版本号"。
        选错版本号字段，比不做幂等更危险 —— 它会静默吞掉数据。

  ------------------------------------------------------------------
  决策点        建议          备选
  ------------------------------------------------------------------
  频率          5 分钟        1 分钟（更实时）/ 15 分钟（写压力小）
  遍历方式      SCAN          KEYS（★ 不推荐，会阻塞 Redis）
  幂等          last_read_time 比对  不做（白写 2000 次）
  多实例        单机直接跑    加分布式锁（下一轮）
  ------------------------------------------------------------------

  【★ 多实例问题】
    两个 app 容器会同时扫到同一批 key。
    有了 last_read_time 幂等判断后，重复写**不会导致数据错误**
    （第二次会被 WHERE 挡掉），只是浪费。
    ⇒ 分布式锁的优先级因此降低了 —— 记在"本轮不做"里即可。

  【要改的地方】
    · Demo2Application 加 @EnableScheduling   ← 已核对：当前没有这个注解
    · 新建 task/ProgressFlushTask.java
    · flushProgress 加 @Transactional(rollbackFor = Exception.class)

  【★ Spring 默认调度器只有 1 个线程】
    现在只有一个任务，无所谓。将来加第二个定时任务时要注意排队问题。

--------------------------------------------------------------------------------
① 索引数量：3 个 → 2 个
--------------------------------------------------------------------------------
  建议：2 个（各带 is_top/top_time 前缀）
        idx_bookshelf_top_create / idx_bookshelf_top_read
  理由：3 个里有 1 个（novel_update 用的）**永远不会被用于排序** ——
        跨表排序必然 filesort，索引救不了。它是纯负担
        （INSERT 时多维护一棵 B+ 树）。
  备选：只留 1 个 (user_id, deleted, is_top, top_time, create_time)，
        recent_read 会 filesort（数据量小无所谓）
  权衡：多索引 → 写变慢；少索引 → 排序慢
  ★ 无论选哪个，都要用 EXPLAIN 实测验证，别停在推理。

--------------------------------------------------------------------------------
② 复活时 create_time 是否重置
--------------------------------------------------------------------------------
  建议：重置 → "最近添加"按最新加入时间排（符合直觉）
  备选：不重置 → 保留第一次加入的时间（历史更真实）
  ★ 想两个都要的话要再加 first_add_time 字段 —— **不要，过度设计**

--------------------------------------------------------------------------------
③ last_read_time = NULL 排序
--------------------------------------------------------------------------------
  建议：排后（不加特殊处理，MySQL 默认）
  备选：排前（加 ISNULL(last_read_time) DESC）
  ★ 注意：加了 ISNULL() 是函数运算，**索引会失效** —— 见修订 2

--------------------------------------------------------------------------------
④ "共 Y 章" 计算
--------------------------------------------------------------------------------
  建议：A. 批量 COUNT chapter 表（和步骤 3 合并，多花 0 次 SQL）
  备选：B. novel 表冗余 chapter_count 字段（★ 这将是第 4 个冗余字段，别加）
        C. 用 latestChapterNumber 当总数（不准，章节可能被删）

--------------------------------------------------------------------------------
⑤ ChapterRepository 返回类型
--------------------------------------------------------------------------------
  建议：接口投影，类型安全且**可单测**
        interface NovelChapterStat {
            Integer getNovelId();
            Integer getMaxNumber();
            Long    getTotal();       // ★ COUNT 是 Long
        }
  备选：List<Object[]>（简单但类型不安全，要手动转，且测起来脆）
  ★ 见 5.2 的别名对应关系

--------------------------------------------------------------------------------
⑥ Service 拿 userId 方式  ★ 这条最重要
--------------------------------------------------------------------------------
  建议：A. Controller 从 UserContext 取，传给 Service（**显式**）
  备选：B. Service 里直接 UserContext.getUser()（隐式）

  ★★ 选 A 的理由不是"分层干净"，而是**它直接决定你能不能写出纯单测**：

    ❌ 隐式：Service 内部读 ThreadLocal
       public void remove(Integer id) {
           Integer userId = UserContext.getUser().getUserId();  // 测试里怎么给？
       }
       ⇒ ThreadLocal 需要有 HTTP 线程才有值。想单测，得先手动
         UserContext.setUser(...) —— 那是**在测试里模拟框架**，脆。

    ✅ 显式：参数传进来
       public void remove(Integer userId, Integer id) { ... }
       ⇒ @Test 里直接：bookshelfService.remove(999, 1); 不需要任何环境

  ★★ 这一条直接关系到**判据 A**：
     11 测试体系现在 4/8，差的正是"Mockito 纯单测（Novel / User 各一个）"。
     决策点 6 选对了，判据 A 就顺路往前走一格；选错了，测试还是写不出来。

  备注：现有 UserService.getCurrentUser() 用的是 B。要不要统一你定 ——
        建议**新代码一律用 A**，老代码等下次改到时顺手改。

⑦ 定时任务配置
--------------------------------------------------------------------------------
  建议：5 分钟 + SCAN + last_read_time 幂等
  备选：1 分钟（更实时）/ 15 分钟（写压力小）
  ★ v1 建议"KEYS 标 TODO" —— 不建议。SCAN 的成本只是多写 5 行，

  备注：多实例问题已被幂等判断大幅缓解，分布式锁优先级降低。

  建议：合并成 1 条（MAX + COUNT 一次查完）

################################################################################
  十一、本轮不做（明确划出边界）
################################################################################

  □ 缓存（书架列表缓存、进度缓存）
    → 等有性能数据再说。当前 QPS 下加缓存是过度设计。

  □ 分布式锁（定时任务多实例冲突）
    → 有了 last_read_time 幂等判断后，重复刷不会导致数据错误，
      只是浪费。下一轮做 Redis 锁时一起。

  □ 书籍分组 / 标签（"在读"、"想读"、"读完"）
    → 需求里没有。加的话要再开一张表。

  □ 多设备进度冲突合并
    → Redis 里已存 updateTime 时间戳，但不做冲突算法（"取最新"就够了）。

  □ 前端（书架页 / api/bookshelf.js / 列表展示 author）
    → 后端只提供接口。★ 但注意：不做的后果是"author 字段加了没人用"，
      如果要展示，NovelListView / NovelDetailView 也要改。

  □ 并发双击加入书架的竞态处理
    → 撞唯一索引会抛异常。MVP 接受，前端按钮置灰即可。

  □ 进度上报改成 AOP 注解（@RecordProgress）
    → 会重蹈 CacheErrorHandler 的覆辙（绕过切面就静默失效）。
      显式调用丑但看得见。

  □ Flyway / Liquibase 迁移
    → 第三梯队。现在靠"改完实体记得同步 schema.sql"的人工纪律，
      这条纪律必然会忘 —— 所以它是技术债。
