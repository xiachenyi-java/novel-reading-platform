--------------------------------------------------------------------------------
亮点 1 · 双 Token 认证 + 黑名单 + 双向索引
--------------------------------------------------------------------------------
  【做了什么】
    · Access Token（JWT，2 小时）+ Refresh Token（UUID，7 天，存 Redis）
    · 刷新时做 Token 轮换（旧的立即作废）
    · 登出时把 Access Token 写进 Redis Hash 黑名单 + 删除 Refresh Token
    · 黑名单用 Hash 存（field=token，value=过期时间戳），读取时惰性清理
    · Refresh Token 做双向索引：
        正向 refresh_token:{token} → userId  （刷新时查用户）
        反向 user_refresh:{userId} → token   （登出时查要删哪个）

  【能深挖的问题】
    · 为什么 Refresh Token 要存 Redis 而不是也用 JWT？→ 服务端可控、能远程作废
    · 为什么黑名单用 Hash 不用 Set？→ 一个结构同时存 token 和过期时间，且能按用户分组
    · 为什么要双向索引？→ 刷新和登出两个方向都要查，只存单向登出就删不掉
    · 黑名单会不会无限增长？→ 惰性清理 + 建议给整个 key 加兜底 TTL
    · 有没有多设备问题？→ ★ 有！String 结构只存一个 token，多设备会互相覆盖

--------------------------------------------------------------------------------
亮点 2 · 注解式限流（AOP）
--------------------------------------------------------------------------------
  【做了什么】
    · 自定义 @RateLimit(key, limit, window) 注解
    · @Around 环绕通知拦截，用 Redis INCR 做固定窗口计数
    · 客户端真实 IP 提取（X-Forwarded-For 多级代理处理）
    · 超限抛 RateLimitException → 全局异常处理器返回 HTTP 429

  【能深挖的问题】
    · 为什么用 Redis 不用本地 Map？→ 多机部署时本地计数不准
    · 固定窗口有什么问题？→ ★ 临界突刺，第 59 秒 5 次 + 第 61 秒 5 次 = 2 秒 10 次
    · INCR 和 EXPIRE 分两步有什么风险？→ 中间崩溃 key 永不过期，应该用 Lua 合并
    · 为什么必须用 @Around？→ 只有环绕通知能阻止方法执行
    · X-Forwarded-For 能伪造吗？→ ★ 能！生产要由 Nginx 统一覆盖

--------------------------------------------------------------------------------
亮点 3 · Redis ZSet 排行榜
--------------------------------------------------------------------------------
  【做了什么】
    · 总榜 ranking:novel:total、日榜 ranking:novel:day:{yyyyMMdd}
    · 阅读章节时 incrementScore 累加热度
    · reverseRangeWithScores 取 TopN
    · 批量查询 + Map 保序组装（避免 N+1）
    · 日榜 key 设 2 天 TTL

  【能深挖的问题】
    · 为什么用 ZSet 不用数据库 ORDER BY？→ 跳表 O(log N) vs 全表扫描 O(N log N)
    · findAllById 返回的顺序能用吗？→ ★ 不能！顺序不保证，必须用 Map 重新保序
    · 日榜 key 加了 TTL 为什么安全？→ key 名带日期，过了今天不再被 touch
    · 排行榜怎么防刷？→ ★ 现在没做，方案是同一用户同一小说 N 分钟只计一次

亮点 4 · 动态条件查询（Specification）
--------------------------------------------------------------------------------
  【做了什么】
    · Repository 多继承 JpaSpecificationExecutor
    · 每个条件一个独立方法，条件为空返回 null（Spring Data 自动忽略）
    · Specification.allOf() 组合三个可选条件
    · 新增 GET /novels/categories 返回 DISTINCT 分类

  【能深挖的问题】
    · 为什么不用方法名推导？→ ★ 3 个条件 = 2³ = 8 个方法，组合爆炸
    · 为什么不用 @Query 判 null？→ SQL 冗长，参数为 null 时某些驱动报类型推断错误
    · Criteria API 的三个参数是什么？→ root（根实体）/ query（整个查询）/ cb（条件构造工厂）
    · 空条件返回 null 是野路子吗？→ 不是，是 Spring Data 官方约定

亮点 5 · 索引优化（有实测数据）
--------------------------------------------------------------------------------
  【做了什么】
    · 造 10 万条测试数据复现慢查询
    · EXPLAIN 定位：type=ALL + Using filesort
    · 用 @Table(indexes=...) 声明式加索引（不是手写 SQL）
    · novel: (last_update_time) + (category, last_update_time) 联合索引
    · chapter: (novel_id, chapter_number) 联合索引

  【实测数据】
    ------------------------------------------------------------------
    查询                              优化前      优化后     提升
    ------------------------------------------------------------------
    小说列表 ORDER BY last_update      136~210ms   0.1~0.6ms   约 300 倍
    章节目录 WHERE + ORDER BY          423ms       4ms         约 100 倍
    ------------------------------------------------------------------

  【能深挖的问题】
    · 为什么用 B+ 树？→ 非叶子只存索引 → 树矮 → IO 少；叶子链表 → 范围查询快
    · 什么是回表？→ 二级索引拿到主键后回聚簇索引查完整行
    · 最左前缀是什么？→ (a,b,c) 只能从 a 开始匹配，范围查询会中断后续列
    · 为什么 category 要建联合索引而不是单列？→ ★ 低区分度单列索引会被优化器忽略；
      联合索引还能顺带解决排序
    · 为什么联合索引不能替代 last_update_time 单列索引？→ ★ 最左前缀，
      不带 category 的纯列表查询用不上
    · ★ 搜索的 LIKE '%kw%' 为什么用不上索引？→ 以 % 开头，B+ 树有序性失效

  【加分项：声明式索引】
    "我没有手写 CREATE INDEX，而是用 @Table(indexes=...) 在实体上声明。
     好处是索引定义跟代码走，换台机器或重建表会自动创建，
     不会出现'本地有索引、服务器忘了建'的情况。"

亮点 6 · 缓存三大问题实战（穿透 + 击穿 + 雪崩 + 降级）★★ 最值钱的一条
--------------------------------------------------------------------------------
  【做了什么 · 全部已验证生效】
    · 空值缓存防穿透：用独立的 novel-null 缓存区（TTL 5 分钟）存
      "查过、但确实没有"的标记；findDetail 做三分支判断
      （命中 novel-null → 直接抛不存在 / 命中 novel → 返回 / 都未命中 → 查库）
    · addNovel 上加 @CacheEvict(value="novel-null", key="#result.id")
      —— 防止空表时把 id=1 缓存成"不存在"，导致新增第一本小说后
         5 分钟内查不到
    · TTL 随机抖动防雪崩：CacheConfig 用 TtlFunction（**每次 put 都求值**），
      TTL = 1500~2100 秒（基础 30 分钟 ± 5 分钟）。实测 novel::1 = 1832 秒
    · 本地互斥锁防击穿：findDetail 用 ConcurrentHashMap + synchronized
      + 双重检查，热点 key 过期瞬间只让一个线程查库，其余等锁后命中缓存。
      测压：同一热点 key 并发下查库 SQL 条数 10 → 1
      ★ 局限：是单机锁（多实例部署时会失效）；locks Map 需注意释放
    · 缓存降级：超时配置 + findDetail 4 处 try-catch

  【★★ 这段经历的价值在于"完整的闭环"：发现 → 定位 → 修复 → 复测】

    ── 起因：一次改动引入了回归 ──
    为了做空值缓存，我把 findDetail 从 @Cacheable 改成了手动
    cacheManager.getCache("novel").get(...) 调用。
    结果：CacheErrorHandler 静默失效了。

    原因：CacheErrorHandler 由 AbstractCacheInvoker 调用，
          而它是 CacheAspectSupport（AOP 拦截器）的父类。
          只有**注解驱动**的调用才经过拦截器；
          手动 cache.get() 直接进 RedisCache，没有人兜底。
    ★ 一句话：**"注解生效" = "框架的切面拦住了你"。**

    ── 发现（2026-10-05，docker stop redis 故障演练）──
      · GET /novels/{id}  →  挂起 60.0 秒，返回
                             {"code":500,"msg":"Redis command timed out"}
      · GET /novels       →  不受影响，正常 200（不走缓存）
      · 日志里 CacheErrorHandler 的 warn 一次都没触发

    ── ★★ 附带发现：比 500 更危险的是"挂起" ──
    项目没配 spring.data.redis.timeout，用的是 Lettuce 默认 60 秒命令超时。
    后果不是"快速失败"，而是每个请求占着 Tomcat 线程卡满 60 秒。
    200 线程 ÷ 60s = 3.3 req/s 就能打满线程池 →
    连不依赖 Redis 的列表接口也开始排队 → 级联故障。
    ★ 结论：**挂起（hang）几乎总是比报错（fail fast）更危险**，
      因为挂起会消耗资源并向上游传播，报错可以被隔离。

    ── 修复（两步，缺一不可）──
    第一级 · 止血：
      spring.data.redis.timeout=500ms
      spring.data.redis.connect-timeout=500ms
      （两个管的不是一回事：前者管命令响应，后者管建立 TCP 连接）
    第二级 · 治疗：findDetail 里 4 处 Redis 调用各包 try-catch
      读失败当"缓存未命中"继续走 DB，写失败吞掉异常

    ── ★★★ 复测数据（三阶段对比 —— 简历上就写这个）──
      ------------------------------------------------------------------
      阶段                  耗时        HTTP   body.code   接口可用性
      ------------------------------------------------------------------
      ① 改造前（60s 超时）  60.0s 挂起  200    500         ❌ 打不开
      ② 只加超时配置        0.51s       200    500         ❌ 打不开
      ③ 再加 try-catch      1.01s       200    200         ✅ 有数据
      ------------------------------------------------------------------
      并发压测（500 请求 / 100 并发 / Redis 挂）：
        P50 1.491s，P95 2.575s，最大 2.784s，0 个超 5 秒
        不依赖 Redis 的列表接口 P50 0.248s，全程 200，未被拖垮
      ★ ②→③ 的区分很重要：② 只是 fail fast（快速失败），
        ③ 才是 graceful degradation（优雅降级）。
        只做 ② 的话，用户体感只是"从一直转圈变成立刻报错"，还是不可用。

  【★ 附加收获：能解释每一个数字】
    Redis 挂时详情页耗时 1.01s = 两个 500ms 超时**串行叠加**
    （nullCache.get + novelCache.get），之后的查库 + 组装只花 9ms。
    → 进一步优化可以上熔断器（连续失败 N 次后直接跳过 Redis），
      能降到 ~10ms。★ 但这是优化不是 bug，别混着讲。

  【能深挖的问题】
    · 为什么不直接用默认的 CacheErrorHandler？→ ★ 默认 SimpleCacheErrorHandler
      直接抛异常，等于没降级
    · CacheErrorHandler 能保护手写的 Redis 调用吗？→ ★ 不能！
      它挂在 AOP 拦截器上，只保护注解驱动的调用
    · 那怎么修？→ 保留手动调用，在自己这层显式 try-catch 兜底；
      另外必须补 spring.data.redis.timeout，把 60 秒压下来
    · ★ 怎么判断降级到底生效了没有？→ **不能看 HTTP 状态码！**
      本项目 GlobalExceptionHandler.handleRuntimeException 没有
      @ResponseStatus，所有 RuntimeException 都返回 HTTP 200。
      必须看 body 里的 code 字段：code=200 才算真的成功
    · ★ 那判据本身怎么验证？→ 制造一个**必定失败**的场景，
      看判据会不会报错。假阳性判据比没有判据更危险 ——
      它让你以为已经验证过了。

亮点 7 · 修复前端"假分页"（问题定位能力）
--------------------------------------------------------------------------------
  【问题】
    原来的分类筛选是前端做的：后端只返回当前页 8 条，
    前端在这 8 条里 filter 分类。

  【三个具体错误】
    1. 数据缺失：选"玄幻"可能一条都不显示，但库里其实有 200 本
    2. total 撒谎：显示"共 100000 本"，实际翻 3 页就没了
    3. 翻页失效：翻到第 2 页，筛选条件就丢了

  【怎么修】
    把筛选条件下推到后端，前端只负责传参。

  【怎么验证修好了】
    SELECT COUNT(*) FROM novel WHERE category='玄幻';   -- 6
    GET /novels?category=玄幻          → totalElements = 6  ✓
    GET /novels?category=玄幻&page=2   → totalElements 仍是 6  ✓

  八、一句话总结你的项目
################################################################################

  面试官问"介绍一下你的项目"，用这段（背下来）：

  "这是一个小说阅读平台，前后端分离，后端 Spring Boot，
   前端 Vue3。我自己独立完成的，37 个类、2000 多行后端代码、16 个接口。

   功能上有用户认证、小说和章节的增删改查、搜索分类、
   阅读排行榜这几块。

   我觉得比较有意思的是三个地方：
   第一，认证我用的是双 Token，Access Token 短期、
   Refresh Token 存在 Redis 里可以远程作废，
   登出时把 Access Token 加进 Redis 黑名单，
   并且做了正反双向索引，保证登出能同时清掉两个 Token。

   第二，我做索引优化的时候造了 10 万条测试数据，
   用 EXPLAIN 发现列表查询是全表扫描加 filesort，
   加了索引之后 P99 从 136 毫秒降到 0.1 毫秒。

   第三，缓存这块我做过一次完整的故障演练，从发现到修复到复测。
   起因是我为了做缓存穿透防护，把详情接口从 @Cacheable
   改成了手动 cacheManager 调用，结果之前做好的降级静默失效了 ——
   因为 CacheErrorHandler 挂在 AOP 切面上，只保护注解驱动的调用。
   我用 docker stop redis 演练才发现：请求不是快速失败，
   是挂满 60 秒，而且会占满 Tomcat 线程、级联拖垮整个应用。
   修复分两步：先配 500 毫秒超时止血，再在业务代码里补 try-catch
   做真正的降级。复测后接口从"挂起 60 秒返回 500"变成
   "1 秒返回真实数据"；又压了 500 请求 100 并发，
   没有一个请求超过 5 秒，不依赖 Redis 的列表接口也没被拖垮。"

  ★ 这段话的结构：一句话定位 → 技术栈 → 功能范围 →
    三个亮点（每个都是"做了什么 + 怎么验证的"）
