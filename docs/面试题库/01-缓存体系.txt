################################################################################
  Q1　穿透 / 击穿 / 雪崩的区别？分别怎么防？　【其他】
################################################################################

- **考点**：三个概念的定义边界 + 各自的防御手段。高频八股，但答得好的关键是
  「说清触发条件的差异」而不是背方案清单。

- **追问链**：
  Q1「三者区别？」→ Q2「你说的空值缓存，存 null 行不行？」（转到 Q2）
  → Q3「TTL 抖动加多少合适？」（转到 Q7）
  → Q4「击穿和穿透最容易混在哪？」

- **参考答案**：
  三者都表现为"缓存没挡住请求，打到 DB"，但触发条件完全不同：

  | 问题 | 触发条件 | 涉及 key 数 | DB 里有吗 |
  |---|---|---|---|
  | 穿透 | 查一个不存在的 key | 单个/任意 | DB 里也没有 |
  | 击穿 | 单个热点 key 过期瞬间 | 单个 | DB 里有，缓存刚好不在 |
  | 雪崩 | 大量 key 同时过期 / Redis 宕机 | 大量 | 缓存层整体失效 |

  记忆法：
    穿透 = 光穿透玻璃（数据本来就不存在，缓存"没得挡"）
    击穿 = 砸穿一个洞（数据存在，但那个点的缓存刚好没了）
    雪崩 = 整片压倒（大片缓存同时失效）

  防御手段：
    穿透 → 空值缓存（短 TTL）/ 布隆过滤器 / 参数校验
    击穿 → 互斥锁只让一个线程查库 / 逻辑过期 / 热点数据永不过期
    雪崩 → TTL 加随机抖动 / 多级缓存 / 限流降级 / Redis 高可用

- **本项目的证据**：
  · 穿透 → 已做。`novel-null` 独立缓存区，TTL 5 分钟。
    实测：同一个不存在的 id 连查 5 次，SQL 只打 1 次。
  · 雪崩 → 已做。`CacheConfig.java:36-39` 用 TtlFunction 随机 TTL。
    实测：`novel::1` 的 TTL = 1832 秒（落在 1500~2100 区间）
  · 击穿 → 已做。`NovelServiceIml.findDetail` 用本地互斥锁
    （ConcurrentHashMap<Integer,Object> + synchronized + 双重检查）。
    实测：同一热点 key 并发下，查库 SQL 条数 10 → 1
    ★ 但它只是**单机锁**，多实例部署会失效；分布式锁仍未做（见 Q13）

- **坑**：
  ① 只说方案不说取舍 —— 面试官会追问"为什么不用布隆过滤器"
  ② 把三者讲混。最容易混的是**击穿和穿透**（都表现为"缓存没命中"），
     区别在 **DB 里到底有没有这条数据**
  ③ 把"Redis 宕机"归到雪崩 —— 对，但要说清它和"大量 key 同时过期"
     是**两种不同的雪崩成因**

- **关联**：docs/知识笔记/05-缓存体系.txt 第三节
             docs/实战笔记/05-缓存三大问题实战.txt 第二、三节


################################################################################
  Q2　防穿透为什么不能存 null？空值缓存还有什么坑？　【其他】
################################################################################

- **考点**：`Cache.get()` 的返回值语义 + 空标记的一致性处理。
  第二问是加分项，多数人只答得出前半段。

- **追问链**：
  Q1「为什么不能存 null？」→ Q2「那空标记的 TTL 设多久？」
  → Q3「新增的小说 id 恰好 = 之前查过的空 id，怎么办？」★ 关键
  → Q4「为什么不用布隆过滤器？」

- **参考答案**：
  因为 `Cache.get(key)` 返回 null 时，**分不清两种情况**：
    · 缓存里根本没有这个 key
    · 缓存里存了一个 null 值
  必须存非 null 的占位符（我用 `Boolean.TRUE`）才能当"存在标记"用。

  我用的是**独立缓存区**方案，不是往原缓存区里塞：

  | 缓存区 | key 形如 | TTL | 用途 |
  |---|---|---|---|
  | novel | `novel::{id}` | 25~35 分钟 | 真实数据 |
  | novel-null | `novel-null::{id}` | 5 分钟 | 空标记 |

  **为什么独立**：空值和真实数据的生命周期完全不同 ——
  真实小说可以缓存 30 分钟，空值只该缓存几分钟
  （万一数据后来又真的出现了）。

  **一致性尾巴**（★ 这是加分点）：
    T1  用户查 /novels/888 → DB 没有 → 写 novel-null::888（5 分钟）
    T2  管理员发新小说      → 自增 id 恰好 = 888
    T3  用户查 /novels/888 → 命中空标记 → 返回"不存在"  ❌
    T4  5 分钟后 TTL 过期   → 才正常
  修复：`addNovel` 上加
    `@CacheEvict(value = "novel-null", key = "#result.id")`

  · `#result` 是 SpEL 引用**方法返回值**，所以必须 `beforeInvocation=false`（默认）
  · 只有 addNovel 需要清 —— 它是唯一能把"不存在"变"存在"的入口
  · 不能用 `allEntries=true` —— 会清空整个 novel-null，误伤其他空标记

- **本项目的证据**：
  · `NovelServiceIml.java:207-241` 三分支判断逻辑
  · `NovelServiceIml.java` addNovel 上的 `@CacheEvict(value="novel-null", key="#result.id")`
  · 实测：`GET /novels/999999` → `{"code":500,"msg":"小说不存在"}`
    Redis 里出现 `novel-null::999999`，TTL = 300 秒 ✓
    连查 5 次，日志里 5 条 WARN、SQL 只有 1 条 ✓

- **坑**：
  ① 忘记一致性处理 —— 面试官一问"新增的 id 恰好是之前查过的怎么办"就答不上
  ② 把空标记和真实数据放同一个缓存区 —— TTL 就没法分开设了
  ③ 以为 `unless = "#result == null"` 能解决 —— 那只处理"返回 null"，
     处理不了"抛异常"（见 Q3）

             docs/实战笔记/05-缓存三大问题实战.txt 第二节


################################################################################
  Q3　@Cacheable 有什么语义盲区？　【其他】
################################################################################

- **考点**：对 Spring Cache **设计语义**的理解，不是 API 用法。
  能答出来说明你踩过坑或者认真读过文档。

- **追问链**：
  Q1「@Cacheable 什么时候不写缓存？」→ Q2「那有办法让它缓存异常吗？」
  → Q3「手动接管有什么代价？」（转到 Q8）

- **参考答案**：
  `@Cacheable` **只缓存方法正常 return 的返回值，方法抛异常时不写缓存**。

  这个语义本身是合理的（框架认为"抛异常"意味着这次调用失败，结果不可信），
  但它带来一个后果：**如果你的代码用异常表示"否定结果"，
  @Cacheable 就完全保护不了。**

  我的项目就是：
    ```java
    Novel novel = novelRepository.findById(novelId)
            .orElseThrow(() -> new BusinessException("小说不存在"));
    ```
    查不到 → 抛异常 → 不写缓存 → 下次相同请求还是打 DB → **缓存穿透**。

  ★ 推广：**任何"用异常表示否定结果"的场景，@Cacheable 都保护不了。**

- **本项目的证据**：
  · 改造前实测：`curl /novels/999999` 三次 → 日志里 3 条 SQL
  · 这也是我为什么放弃 `@Cacheable`、改成手动 `CacheManager` 双缓存的原因
  · ★ 但这次改动**引出了另一个 bug**（降级失效，见 Q8）——
    这是一个"修一个 bug 引入另一个"的真实案例

- **坑**：
  ① 以为 `unless` 能解决。`unless="#result == null"` 只处理"返回 null"的情况，
     处理不了"抛异常" —— 这两条代码路径完全不同
  ② 把 `@Cacheable` 的异常当成 bug。它不是 bug，是**设计如此**

- **关联**：docs/知识笔记/05-缓存体系.txt 5.1 节
             docs/实战笔记/05-缓存三大问题实战.txt 2.2 节


################################################################################
  Q4　加了缓存之后，Redis 挂了你的接口会怎样？★　【并发】
################################################################################

- **考点**：对"缓存让 Redis 从可选依赖变成强依赖"的认知 +
  能不能区分**快速失败**和**优雅降级**。这是个很有区分度的问题。

- **追问链**：
  Q1「会怎样？」→ Q2「那 60 秒是怎么来的？」
  → Q3「配了超时算修好了吗？」（转到 Q6）
  → Q4「还能更快吗？」→ Q5「那怎么验证它真的修好了？」（转到 Q5）

- **参考答案**：
  先说认知：加了缓存之后，Redis 从"可选依赖"变成了"**强依赖**"。
  没缓存时 Redis 挂了接口照样查库；加了缓存后 Redis 挂了接口可能直接 500。

  我的项目实际经历过三个阶段，都有实测数据：

  | 阶段 | 耗时 | HTTP | body.code | 接口可用性 |
  |---|---|---|---|---|
  | ① 改造前 | 60.0s 挂起 | 200 | 500 | ❌ 打不开 |
  | ② 只加超时配置 | 0.51s | 200 | 500 | ❌ 打不开 |
  | ③ 再加 try-catch | 1.01s | 200 | 200 | ✅ 有数据 |

  **① 为什么是 60 秒**：项目没配 `spring.data.redis.timeout`，
  Spring Boot 该配置默认值是 0（表示"用客户端默认值"），
  而 Lettuce 的命令超时默认 **60 秒**。
  → 不是"快速失败"，是**挂起**，占满 Tomcat 线程会造成级联故障。

  **② 加了配置**：
    ```
    spring.data.redis.timeout=500ms
    spring.data.redis.connect-timeout=500ms
    ```
  单请求从 60s 降到 0.51s。**但接口还是打不开** ——
  只是从"一直转圈"变成了"立刻报错"。

  **③ 在业务代码里补 try-catch**：
    读失败 → 降级为"缓存未命中"，继续走 DB
    写失败 → 吞掉异常，不影响主流程

- **本项目的证据**：
  · 三阶段数据（上表）来自 `docker stop demo2-redis` 故障演练，
    连测 3 次 0.509s / 0.517s / 0.510s，稳定贴着 500ms 配置
  · 1.01s 的拆解：`nullCache.get` 超时 500ms + `novelCache.get` 超时 500ms，
    之后的查库 + 组装只花 9ms
  · 并发压测（500 请求 / 100 并发 / Redis 挂）：
    P50 1.491s，P95 2.575s，最大 2.784s，**0 个超 5 秒**
    不依赖 Redis 的 `/novels` 列表 P50 0.248s，全程 200，未被拖垮

- **坑**：
  ① 说"我配了超时就好了" —— 一定要说清超时只是**止血**
  ② 只看 HTTP 状态码。本项目 RuntimeException 也返回 HTTP 200（见 Q5）

- **关联**：docs/实战笔记/05-缓存三大问题实战.txt 4.6 节
             docs/面试题库/01-缓存体系.txt Q5、Q6


################################################################################
  Q5　你说做了缓存降级，怎么证明它真的生效了？★★　【测试】
################################################################################

- **考点**：★ **这题是分水岭**。90% 的人答不上，因为大部分人从来没验证过。
  考的是"验证方法论"，不是缓存知识。

- **追问链**：
  Q1「怎么证明？」→ Q2「你怎么知道**判据本身**是对的？」★ 关键
  → Q3「如果日志里一条 warn 都没有，说明什么？」（转到 Q11）
  → Q4「中间态为什么要单独测？」

- **参考答案**：
  我的做法是**故障演练**：
    ```
    docker stop demo2-redis
    curl "http://localhost:8080/novels/1"
    docker start demo2-redis
    ```
  然后 —— ★ 关键在这里 —— **我看的不是 HTTP 状态码，是 body 里的 code 字段**。

  **为什么**：我的 `GlobalExceptionHandler.handleRuntimeException`
  没有 `@ResponseStatus` 注解，所有 RuntimeException 都返回 **HTTP 200**。
  所以按"HTTP 200 = 成功"判断，失败也会被读成成功，是个**假阳性判据**。

  正确判据：
    ```
    body {"code":200, ...有数据}                          → 降级有效
    body {"code":500,"msg":"Redis command timed out"}     → 降级失效
    ```
  补充判据：降级成功时应该有 warn 日志。
  如果日志里一条降级 warn 都没有，说明兜底逻辑压根没走到。

  ★ 而且 **"判据本身也要验证"**：
  制造一个**必定失败**的场景，看判据会不会报错。
  我第一次用"Redis 挂掉"就是这个作用 —— 如果判据说"成功"，那判据就是错的。
  **假阳性判据比没有判据更危险**，因为它让你以为已经验证过了。

- **本项目的证据**：
  · 我靠这个判据**发现了一个自己引入的 bug**：
    为了做空值缓存防穿透，把 findDetail 从 `@Cacheable` 改成手动调用
    → 降级打掉了，而且**没有任何报错**，HTTP 200 看起来一切正常。
  · 详见 Q8。
  · 三阶段对比（也是验证方法的一部分）：
    60.0s 挂起 / 0.51s 快速失败 / 1.01s 真正降级
    ★ 加上中间态 ② 才能区分"指标变好了"和"问题解决了"

- **坑**：
  ① 只看 HTTP 状态码 —— 最常见
  ② 只看接口返回，不看日志 —— 会漏掉"兜底逻辑没执行"这种情况
  ③ 用前后对比而不是三阶段对比 —— 会把"变快 60 倍"误当成"修好了"

             docs/面试题库/02-工程实践与排错.txt Q1


################################################################################
  Q6　只配超时不算修复吗？fail fast 和降级有什么区别？★　【其他】
################################################################################

- **考点**：能不能区分**面向系统**和**面向用户**的两种故障处理。
  这是"工作三年"和"刚毕业"的思维差异。

- **追问链**：
  Q1「有什么区别？」→ Q2「那挂起和报错哪个更危险？」★
  → Q3「超时设多少合适？」→ Q4「connect-timeout 和 timeout 什么区别？」（转到 Q9）

- **参考答案**：
  不算修复。这是两个层次的东西：

  | 手段 | 效果 | 用户体感 |
  |---|---|---|
  | 不配超时 | 挂起 60 秒 | 一直转圈 |
  | 只配超时 | 0.5 秒报错 | 立刻打不开 |
  | + try-catch 降级 | 1.0 秒返回真实数据 | ✅ 正常可用 |

  · **fail fast（快速失败）**：让故障快速暴露，别拖垮别人。
    解决的是"级联故障"问题 —— 这是**面向系统**的。
  · **graceful degradation（优雅降级）**：让功能继续可用。
    解决的是"接口还能不能用"问题 —— 这是**面向用户**的。

  只做前者，用户体感是"从一直转圈变成立刻报错"，**还是不可用**。

  ★ 而且 **挂起（hang）几乎总是比报错（fail fast）更危险**：
  因为挂起会**消耗资源并向上游传播** —— 200 个 Tomcat 线程全被占满
  卡 60 秒，连不依赖 Redis 的列表接口都开始排队。
  而报错可以被隔离（限流、熔断、快速返回）。

  算笔账（Tomcat 默认 200 线程）：
    ```
    改造前：200 线程 ÷ 60s  =  3.3   req/s   ← 超过就全排队
    改造后：200 线程 ÷ 1.5s =  133   req/s
    ```

- **本项目的证据**：
  · 三阶段实测数据（60.0s → 0.51s → 1.01s），
    ② 和 ③ 都是真实测出来的，不是推算
  · 并发压测证明了"挂起会传播"的反面：
    Redis 挂 + 100 并发时，不依赖 Redis 的列表接口 P50 仅 0.248s，
    **说明级联故障确实被切断了**

- **坑**：
  ① 以为"超时配短点"就是降级了
  ② 答不出"挂起比报错危险在哪" —— 只会说"挂起慢"

- **关联**：docs/知识笔记/05-缓存体系.txt 5.2 节
             docs/实战笔记/05-缓存三大问题实战.txt 4.3、4.4 节


################################################################################
  Q7　TtlFunction 和 entryTtl(Duration) 有什么区别？　【其他】
################################################################################

- **考点**：对 Spring Data Redis API 的理解深度 ——
  知不知道"配置时求值"和"每次调用时求值"的区别。

- **追问链**：
  Q1「区别是什么？」→ Q2「那能基于 key 算 TTL 吗？」
  → Q3「抖动范围加多少合适？」→ Q4「怎么验证抖动生效了？」

- **参考答案**：
  关键区别是**求值时机**：

  | 写法 | 随机数什么时候算 | 效果 |
  |---|---|---|
  | `entryTtl(Duration.ofMinutes(30))` | 配置时算一次 | 所有 key 都 30 分钟 |
  | `entryTtl((k, v) -> ...)` | **每次 put 都调用** | 每个 key TTL 都不同 |

  `TtlFunction` 是 Spring Data Redis 提供的函数式接口：
  ```java
  @FunctionalInterface
  public interface TtlFunction {
      Duration getTimeToLive(Object key, Object value);
  }
  ```
  ★ 它是**每次 put 时都执行一次**，不是配置时执行一次。
  所以可以基于 key / value 动态算 TTL —— 这就是防雪崩随机抖动的实现方式。

  我的配置：
  ```java
  .entryTtl((key, value) -> {
      int seconds = ThreadLocalRandom.current().nextInt(1500, 2101);
      return Duration.ofSeconds(seconds);
  })
  ```
  即 1500~2100 秒 = 25~35 分钟 = 基础 30 分钟 ± 5 分钟。

  ★ 规律：Spring Cache 的扩展点大多是**函数式接口 + 每次调用时求值**：
  `CacheResolver`、`KeyGenerator`、`CacheErrorHandler`、`TtlFunction` 都是。
  记住这个规律，能少背很多 API。

- **本项目的证据**：
  · `CacheConfig.java:36-39`
  · 实测：`novel::1` 的 TTL = **1832 秒**，落在 1500~2100 区间内 ✓
  · 验证方法：
    ```
    DEL novel::1 / novel::2 / novel::3
    分别 curl 三个详情接口
    TTL novel::1 / novel::2 / novel::3
    ```
    ★ 如果三个 TTL 是 1799/1798/1797 连着，说明抖动没生效
  · `novel-null` 区单独配 5 分钟，靠 `withInitialCacheConfigurations` 覆盖，
    没有被全局随机 TTL 冲掉 ✓（这点我专门验证过）

- **坑**：
  ① `nextInt(origin, bound)` 是**左闭右开**的，
     要取 [1500, 2100] 得写 `nextInt(1500, 2101)`
  ② ★ **单位事故**：我变量名叫 `seconds`，方法却一度写成
     `Duration.ofMinutes(seconds)` → TTL 变成 25~35 **小时**
     （实测 122769 秒 ≈ 34 小时）。
     单位敏感的 API（Duration / TimeUnit / BigDecimal），
     写完要盯着看两遍：变量名、方法名、单位三者一致吗？

             docs/实战笔记/05-缓存三大问题实战.txt 3.4、3.5 节


################################################################################
  Q8　@Cacheable 换成手写 CacheManager，会丢掉什么？★★　【其他】
################################################################################

- **考点**：考的是"**你知不知道注解背后是切面**"。
  这是 Spring 体系里最核心的一个认知，能迁移到 `@Transactional`、自定义注解。

- **追问链**：
  Q1「会丢什么？」→ Q2「那 `@Transactional` 呢？」★ 关键（考迁移能力）
  → Q3「什么情况下该用手写？」→ Q4「手写之后要自己补什么？」

- **参考答案**：
  会丢掉**缓存降级**。而且丢得**悄无声息**。

  原因：`CacheErrorHandler` 是 **`CacheInterceptor`（AOP 切面）的配置**，
  不是 `RedisCache` 的配置。

  ```
  走 @Cacheable：
    请求 → CacheInterceptor(切面) → RedisCache.get() → 出错
                                      ↓
                            CacheInterceptor 捕获 → CacheErrorHandler
                                      ↓
                              降级：跳过缓存，继续执行原方法

  手写 cacheManager.getCache()：
    请求 → Service → 直接调 RedisCache.get() → 出错
                                      ↓
                              直接往上抛 → GlobalExceptionHandler → 500
  ```

  ★ 一句话记住：**"注解生效" = "框架的切面拦住了你"。**
  一旦绕开切面（改用手写 API），切面提供的所有附加能力都会消失。

  **推广到项目里的其他注解**（★ 这张表值得背）：

  | 注解 | 底层切面 | 手写 API 后丢失什么 |
  |---|---|---|
  | `@Cacheable` | CacheInterceptor | 缓存降级 |
  | `@Transactional` | TransactionInterceptor | 事务回滚、传播、隔离 |
  | `@RateLimit`（自定义） | RateLimitAspect | 限流计数 |
  | `@RequireAdmin` | LoginInterceptor | 权限校验 |

- **本项目的证据**：
  · 这是我自己**改出来**的 bug：
    为了做空值缓存防穿透，把 findDetail 从 `@Cacheable` 改成
    `cacheManager.getCache("novel").get(...)` → 降级静默失效
  · 它最阴的地方在于：**没有任何报错**，接口 HTTP 200，
    看起来一切正常 —— 只有 Redis 真的挂掉那天才会暴露
  · 我是通过**故障演练**才发现的：期望"返回 200 + 数据"，
    实际是"挂起 60 秒 + body.code=500"
  · 修复后：4 处 Redis 调用各包 try-catch，1.01s 返回真实数据

- **坑**：
  ① 以为"手写更灵活，没有代价"。代价就是你要**自己补回切面提供的所有能力**
     （超时、降级、重试、监控）
  ② 只答"降级丢了"，答不出"为什么"（切面绕过）和"还有什么也丢了"

- **关联**：docs/知识笔记/05-缓存体系.txt 5.2 节
             docs/实战笔记/05-缓存三大问题实战.txt 4.2 节


################################################################################
  Q9　跨进程调用为什么必须显式配超时？　【并发】
################################################################################

- **考点**：对"默认值不可信"和"级联故障"的认知。
  【并发】标签 —— 这题本质是线程池耗尽问题。

- **追问链**：
  Q1「为什么要配？」→ Q2「connect-timeout 和 timeout 什么区别？」★
  → Q3「超时设多少合适？」→ Q4「知道超时预算吗？」★ 加分

- **参考答案**：
  因为**一个下游故障会拖垮整个上游服务**，而默认值往往很大。

  我项目里 Redis 没配超时时，用的是 Lettuce 默认 **60 秒**命令超时。
  Redis 一挂，200 个 Tomcat 线程全被占满卡 60 秒 →
  连不依赖 Redis 的列表接口也开始排队 → **级联故障**。

  ★ 关键：默认值是按"单机直连"的假设设的，一旦经过
  Docker 端口转发、Nginx、K8s Service 这些中间层，
  **连接挂起**会比**连接拒绝**常见得多 ——
  拒绝是立刻返回的，挂起会一直等到超时。

  **两个超时的区别，都要配**：

  | 配置 | 管什么 | 触发时机 |
  |---|---|---|
  | connect-timeout | 建立 TCP 连接的时间 | Redis 服务完全不在（端口不通） |
  | timeout | 发命令后等响应的时间 | 连接已建立但命令没响应（卡住/丢包） |

  **推荐值 500ms ~ 1s**：Redis 是内存操作，正常 p99 在 10ms 内，
  500ms 已经是 p99 的 25 倍以上 —— 500ms 没回它就已经不正常了。

  ★ **超时预算（timeout budget）**（加分项）：
  如果 A 调 B、B 调 C，每层都设 5 秒，A 最坏要等 15 秒。
  生产上一般要求「下游超时之和 < 上游自己的超时」。
  我这个项目是单体还用不上，但拆微服务会立刻遇到。

- **本项目的证据**：
  · `application-dev.properties` 最后两行：
    `spring.data.redis.timeout=500ms` / `spring.data.redis.connect-timeout=500ms`
  · 实测：配之前单请求挂起 **60.0 秒**；配之后 **0.51 秒**
  · 正常时 Redis 响应 6~20ms，500ms 是它的 25 倍以上

- **坑**：
  ① 只配 `timeout` 忘了 `connect-timeout`
  ② 超时配太长（5s）—— 用户要等 5 秒才看到错误页
  ③ 不配重试，或配了重试但没有退避 —— 重试会**放大流量**，
     Redis 挂时无脑重试等于雪上加霜

- **关联**：docs/实战笔记/05-缓存三大问题实战.txt 4.3 节
             docs/知识笔记/05-缓存体系.txt 5.2 节


################################################################################
  Q10　缓存和数据库的一致性怎么保证？　【其他】
################################################################################

- **考点**：Cache Aside 模式 + **能不能说清"哪些方法要清缓存"**。
  后半段是实践能力，前半段是背的。

- **追问链**：
  Q1「推荐哪种策略？」→ Q2「为什么是删除而不是更新？」
  → Q3「那**哪些方法**要加 @CacheEvict？」★ 关键（实践）
  → Q4「删缓存失败了怎么办？」→ Q5「延迟双删延迟多久？」

- **参考答案**：
  先给结论：**推荐"先更新数据库，再删除缓存"**（Cache Aside）。

  **为什么是"删除"而不是"更新"**：
    · 更新缓存可能写入一个计算复杂但根本没人读的值（浪费）
    · 并发更新时，两个线程可能以相反顺序写入缓存 → 脏数据
    · 删除是幂等的，多次删除结果一样
    · 缓存是懒加载的，删了自然会重建

  **为什么先操作数据库**：
    "先删缓存再更新库"在并发下更容易出问题：
      线程 A 删缓存 → 线程 B 读缓存未命中 → B 读库（旧值）→
      B 写缓存（旧值）→ A 更新库（新值）
      → 结果：数据库是新值，缓存是旧值，长期不一致

  ★ **怎么判断哪些方法要加 @CacheEvict**（这是实践考点）：
  把缓存对象（`NovelDetailVO`）的**所有字段列出来**，
  凡是会改变其中任何一个字段的方法，都必须加。

  `NovelDetailVO` 包含：
    id / title / summary / coverUrl / category / status
    / totalWords / lastUpdateTime / chapters

  所以：
    addChapter     改了 totalWords + chapters      → 必须 evict
    updateChapter  改了 totalWords                 → 必须 evict
    deleteChapter  改了 totalWords + chapters      → 必须 evict
    updateNovel    改了 title/summary/category/... → 必须 evict
    deleteNovel    整个对象没了                    → 必须 evict
    addNovel       要清 novel-null 的空标记        → 必须 evict

  ★ 最后要主动说：**没有 100% 的方案，只能做到最终一致**。
  极端情况用延迟双删（删缓存 → 更新库 → 延迟 500ms 再删一次），
  或者用 Canal 监听 MySQL binlog 异步刷新。

- **本项目的证据**：
  · 全项目 **6 个 @CacheEvict、0 个 @Cacheable**
  · ★ 踩过的坑：`deleteChapter` 的 key 一度写成 `#id`，
    但这个方法**没有叫 id 的参数**（参数是 `novelId` 和 `chapterId`）
    → SpEL 解析不到 → evict 一个不存在的 key → 真正的 `novel::1` 纹丝不动
    → 后果：删了章节，详情页目录还是旧的（最长 30 分钟）
  · ★ 万能自查法：**写完 `key = "#xxx"`，回头看方法签名里有没有这个参数名**
  · 注意 `deleteNovel(Integer id)` 的参数名**确实叫 id**，所以那里用 `#id` 是对的
    —— 两个方法别搞混

- **坑**：
  ① 只讲策略不讲"哪些方法要清"
  ② `@CacheEvict` 的 key 指向不存在的参数名（我踩过）
  ③ 用 `allEntries=true` 图省事 —— 会清空整个缓存区，误伤无辜

- **关联**：docs/知识笔记/05-缓存体系.txt 第四、5.1 节
             docs/项目笔记/05-缓存体系.txt


################################################################################
  Q11　缓存写失败为什么比读失败更难发现？★　【其他】
################################################################################

- **考点**：★ 这题来自一次意外发现，含金量很高。
  考的是"**同步 API 掩盖了异步现实**"这个认知。

- **追问链**：
  Q1「为什么更难发现？」→ Q2「那你怎么发现的？」（考实验设计）
  → Q3「缓冲满了会怎样？」→ Q4「那你还留着那个 catch 干什么？」

- **参考答案**：
  我的 findDetail 有 4 处 Redis 调用各包了 try-catch，其中两处是**写**。
  但故障演练时发现：**"详情缓存写入失败"这条日志一次都没出现**（grep = 0）。

  既然 Redis 挂了，put 为什么既不报错、也不记日志、还几乎不耗时？

  **我做的决定性实验**：
    ```
    docker start demo2-redis          ← 重启 Redis
    # ★ 关键：不发任何新请求
    docker exec demo2-redis redis-cli EXISTS "novel::1"
    → 1                                ← 它已经在那儿了
    ```

  **结论**：Lettuce 在断连期间把写命令**缓冲**了起来，重连后自动补发。

  **这意味着两件事**：
  1. 那个 put 的 catch 块在当前场景下**永远不会触发** ——
     不是写错了，是这层压根没抛异常。
     （保留它是对的，仍是防御其他故障模式的安全网。）
  2. ⚠️ 有个隐形风险：Lettuce 的 `disconnectedBufferSize` 默认 **64KB**。
     Redis 长时间挂 + 高频写 → 缓冲会**悄悄积压**，
     满了之后才真正开始失败。
     也就是说，「Redis 挂了」这件事，对**写操作**而言是**延迟暴露**的。

  ★ **本质认知**：这个现象的本质是**同步 API 掩盖了异步现实**：
  Lettuce 底层是异步的（Netty），Spring Data Redis 在外面包了一层
  同步 API，`connection.set()` 返回 **void**。
  **返回 void 的远程操作，你没法知道它到底成功没有。**

  💡 **"没有返回值的远程调用，等于没有错误处理。"**
  这也是为什么好的 RPC 框架都强制返回 Result 而不是 void。

- **本项目的证据**：
  · 完整实验过程见 `docs/实战笔记/05-缓存三大问题实战.txt` 4.5 节
  · 日志计数：`grep -c "详情缓存写入失败" logs/book-manager.log` → **0**
  · 重启 Redis 后未发任何请求，`novel::1` 已存在 → 排除"静默失败"，
    锁定"缓冲补发"
  · ★ 这次发现的方法是：**"日志里该出现的东西没出现"和"出现了不该出现的"
    一样是重要信号** —— 用 `grep -c` 让这种"缺席"变得可见

- **坑**：
  ① 以为"我包了 try-catch 就万事大吉" —— 包了 ≠ 异常真的会抛出来
  ② 看到"日志没有报错"就认为"操作成功了" —— 可能是**延迟暴露**

- **关联**：docs/实战笔记/05-缓存三大问题实战.txt 4.5 节
             docs/面试题库/02-工程实践与排错.txt Q3


################################################################################
  Q12　所有地方都该降级吗？　【其他】
################################################################################

- **考点**：能不能区分"业务功能"和"安全机制"。
  一刀切说"所有 Redis 调用都要 try-catch"是减分答案。

- **追问链**：
  Q1「所有地方都该降级吗？」→ Q2「那拦截器黑名单那个两难怎么选？」★
  → Q3「不降级的话，用户看到 'Unable to connect to Redis' 合适吗？」
  → Q4「那该怎么改？」

- **参考答案**：
  不是。**判断标准是：这次降级会不会破坏安全机制。**

  | 场景 | 该降级吗 | 降级方案 |
  |---|---|---|
  | 详情缓存（手动调用） | ✅ 该 | try-catch，读失败当未命中 |
  | 排行榜 | ✅ 该 | 返回空列表 |
  | 用户信息缓存 | ✅ 该 | 查数据库 |
  | 登录（写 refreshToken） | ❌ 不该 | ★ 安全机制不能降级，但应返回**友好提示** |
  | 登出（写黑名单） | ❌ 不该 | ★ 同上 |
  | 拦截器黑名单校验 | ⚠️ 看取舍 | 降级=跳过校验（有安全风险）<br>不降级=Redis 挂了全部接口 500<br>★ 折中：降级 + 记 error 日志 + 告警 |

  ★ 判断标准：**这次降级会不会破坏安全机制？**
    · 会 → 不降级，但要保证错误提示友好
    · 不会 → 降级，保证核心功能可用

- **本项目的证据**：
  · 详情缓存 → 已按"该降级"处理，4 处 try-catch，实测通过
  · 排行榜**读** → `findRankingByKey` 有 try-catch，异常返回空列表；
    实测 Redis 挂时 `code:200`、0.504s ✓
  · 排行榜**写**（`readChapter` 里三处 `incrementScore`）→
    ⚠️ **尚未加 try-catch**，这是 2026-10-06 排查时发现的遗漏
  · 拦截器黑名单 → 已按"折中方案"处理：try-catch 降级 + `log.warn`
  · 登录/登出 → 按"不该降级"处理，没有包 try-catch

- **坑**：
  ① 一刀切说"所有 Redis 调用都要 try-catch"
  ② 举不出"不该降级"的例子 —— 大部分人只会说"缓存挂了要降级"，
     但登录/登出这种涉及安全的地方降级 = 认证失效，是更严重的问题
  ③ 忘了"不降级也要给友好提示"这一半

- **关联**：docs/知识笔记/05-缓存体系.txt 5.2 节
             docs/项目笔记/05-缓存体系.txt "哪些地方该降级"


################################################################################
  Q13　缓存击穿你用互斥锁，为什么不用 synchronized 就完事？　【并发】
################################################################################

- **考点**：考"本地锁 vs 分布式锁"的边界意识，以及"锁的生命周期管理"。
  能主动说出自己方案的局限，比说"我完美解决了"更得分。

- **追问链**：
  Q1「你的互斥锁怎么实现的？」→ Q2「多实例部署还管用吗？」★ 关键
  → Q3「那用 Redis 分布式锁要注意什么？」→ Q4「你的 locks 会释放吗？」★ 关键

- **参考答案**：
  我用的是**本地互斥锁**：一个 ConcurrentHashMap<Integer,Object> 存
  每个 novelId 对应的锁对象，synchronized 住它，锁内**双重检查**
  （重读一次 nullCache / novelCache），只有第一个线程查库，其余等锁后
  直接命中缓存。
  ```
  Object lock = locks.computeIfAbsent(novelId, k -> new Object());
  synchronized (lock) {
      // 双重检查：可能已有别的线程重建好了
      ...
      novelRepository.findById(novelId);
      novelCache.put(novelId, vo);
  }
  ```

  ★ **但它有个硬边界：synchronized 只在单个 JVM 内有效。**
  多实例部署时，每个实例各有一把锁 → 每个实例仍会各查一次库，
  击穿防护退化成 N 倍。

  ★ **还有一个隐患：locks 只增不减。**
  访问过的每个 novelId 都永久留下一个锁对象 → 无界增长。
  而且不能简单地 finally 里 remove —— 那会重新引入竞态：
  remove 之后新到的线程会拿到一把新锁，和还在等旧锁的线程并发。

- **本项目的证据**：
  · 代码：NovelServiceIml.java:51 / 234（locks + synchronized 双重检查）
  · 测压：同一热点 key 并发下，查库 SQL 条数从 **10 → 1**（击穿防护生效）
  · ★ 但延迟反而升高（P50 1.578s）：19 个线程在等那 1 个加载线程 →
    这是互斥锁的**预期代价**（用延迟换 DB 压力），不是回归
  · ⚠ 该测压数据**条件不一致**（修复前 10 并发 / 修复后 20 并发），
    已标记待同条件复测

- **坑**：
  ① 以为 synchronized 就是"分布式锁" —— 单机锁跨不了 JVM
  ② 只测了"SQL 变少了"，没解释"延迟为什么变高了" ——
     互斥锁是 trade-off，面试官会追问这个
  ③ 锁对象 Map 忘了释放 / 或粗暴 remove 引入竞态
