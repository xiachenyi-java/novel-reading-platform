     ⇒ 完整分析见 docs/项目说明-给AI.txt 问题 21

【★ 实测优化效果（10 万条测试数据下）】

  ------------------------------------------------------------------
  查询                              优化前      优化后     提升
  ------------------------------------------------------------------
  小说列表 ORDER BY last_update      136~210ms   0.1~0.6ms   约 300 倍

P0 · 必须做
--------------------------------------------------------------------------------

  ✅ 已完成：novel 表加索引（2026-09）
    做法：不用手写 SQL，在实体上用注解声明 —— 重建表会自动创建
      @Table(name = "novel", indexes = {
          @Index(name = "idx_novel_last_update_time",
                 columnList = "lastUpdateTime"),
          @Index(name = "idx_novel_category_last_update_time",
                 columnList = "category,lastUpdateTime")
      })
    ★ Hibernate 会自动把 Java 属性名 lastUpdateTime 翻译成列名 last_update_time
    ★ 为什么联合索引 (category, last_update_time)：
      等值查询列在左、排序列在右，一个索引同时完成"筛选 + 排序"
    ★ 为什么 idx_novel_last_update_time 不能删：
      最左前缀 —— 不带 category 条件的纯列表查询用不上联合索引

  ✅ 已完成：用 EXPLAIN 验证
      EXPLAIN SELECT * FROM novel ORDER BY last_update_time DESC LIMIT 10;
      → type=index, key=idx_novel_last_update_time, Extra=Backward index scan
      EXPLAIN SELECT * FROM chapter WHERE novel_id = 1 ORDER BY chapter_number;
      → type=ref, key=idx_chapter_novel_number, Extra 为空（无 filesort）
    ★ 注意：数据量小（几十行）时优化器会忽略索引显示 ALL，这是正常的

  ✅ 已完成：Chapter 补 @Table(indexes=...) 声明
    问题：novel 的索引写在注解里，重建表会自动创建；chapter 没写，
          表一重建索引就丢了（曾只剩 PRIMARY）。
    做法：Chapter.java 已声明（实际索引名 idx_chapter_novel_number）
      @Table(name = "chapter", indexes = {
          @Index(name = "idx_chapter_novel_number",
                 columnList = "novelId,chapterNumber")
      })
    ★ 只建一个联合索引就够了 —— 最左前缀已覆盖单查 novelId 的场景，
      再建单列索引是冗余的。
    验证：重启后 SHOW INDEX FROM chapter; 应看到 2 行（PRIMARY + 联合索引）

【★ 动态查询 Specification（2026-09 新增）】
  位置：repository/NovelSpecifications.java（新建文件）
  用途：小说列表的搜索 + 分类筛选 + 状态筛选

  三个条件方法（条件为空时返回 null）：
    titleContains(keyword)      → cb.like(title, "%keyword%")
    categoryEquals(category)    → cb.equal(category, category)
    statusEquals(status)        → cb.equal(status, status)

  组装（NovelServiceIml.java:193）：
    Specification<Novel> spec = Specification.allOf(
            NovelSpecifications.categoryEquals(category),
            NovelSpecifications.statusEquals(status),
            NovelSpecifications.titleContains(keyword)
    );
    return novelRepository.findAll(spec, pageable);

  ★ 核心技巧：返回 null 的 Specification 会被 Spring Data 自动忽略，
    所以不需要写一堆 if (keyword != null) 来判断
  ★ 工具类加了私有构造器，防止被实例化
  ★ 参数顺序在 Controller / Service / Specification 三处必须一致
    （当前顺序：page, size, category, status, keyword）

  接口：
    GET /novels?page=1&size=8&category=玄幻&status=FINISHED&keyword=剑
    GET /novels/categories   → ["玄幻","都市",...]

  四、面试话术（可直接背）
################################################################################

【Q：你项目做过 SQL 优化吗？】
  "做过。小说列表接口原本是全表扫描加 filesort，
   我先造了 10 万条测试数据复现，用 EXPLAIN 看到 type=ALL、
   Extra=Using filesort，实测 136~210ms。

   分析后发现两个问题：
   novel 表按 last_update_time 排序但没有索引；
   chapter 表按 novel_id 查询并排序 chapter_number，也没有索引。

   我给 novel 加了 last_update_time 的单列索引，
   又加了一个 (category, last_update_time) 联合索引 ——
   因为分类筛选的查询是 WHERE category=? ORDER BY last_update_time，
   等值列放左边、排序列放右边，一个索引同时完成筛选和排序。
   单列索引不能删，因为不带分类的纯列表查询用不上联合索引（最左前缀）。

   优化后 type 变成 index + Backward index scan，filesort 消失，
   小说列表从 136ms 降到 0.1ms，章节目录从 423ms 降到 4ms。"

【Q：索引怎么维护的？】
  "我没有手写 CREATE INDEX，而是在实体上用 @Table(indexes=...) 声明。
   好处是索引定义跟着代码走，换台机器或者重建表会自动创建，
   不会出现'本地有索引、服务器上忘了建'的情况。"

【Q：为什么不直接写 SQL 查？】
  "列表要支持搜索、分类、状态三个可选条件，
   组合起来有 8 种情况。如果用方法名推导要写 8 个方法，
   用 @Query 拼 null 判断又不好维护。
   所以我用了 JpaSpecificationExecutor + Specification，
   每个条件一个独立方法，条件为空就返回 null 被自动忽略，
   以后再加筛选维度也不用改结构。"

【Q：搜索为什么不用索引？】
  "搜索用的是 LIKE '%关键词%'，
   用 EXPLAIN 验证过是 type=ALL 全表扫描 ——
   因为以 % 开头的 LIKE 无法利用 B+ 树的有序性。
   20 万数据下约 200ms 还能接受，
   但如果数据量再涨一个数量级，就要上全文索引或者 Elasticsearch。"
