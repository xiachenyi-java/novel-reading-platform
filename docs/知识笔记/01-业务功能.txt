【大类 01】业务功能
================================================================================
  对应项目笔记：docs/项目笔记/01-业务功能.txt

【定位】把一句模糊的需求，拆成一张能执行的清单。
        其他大类解决"怎么把代码写好"，只有这个解决"写什么代码"。


################################################################################
  一、这个大类在解决什么问题
################################################################################

  用餐厅比喻：
    顾客说"我想吃一碗牛肉面"        —— 这是需求
    厨师真的把面做出来端上桌        —— 这是业务功能落地
    至于厨房用什么锅、火候怎么控    —— 那是其他大类的事

  这个大类考验的是"需求 → 数据模型 → 接口 → 代码"的翻译能力。

  二、核心知识点
################################################################################

--------------------------------------------------------------------------------
2.1 实体识别：怎么从需求里找出"名词"
--------------------------------------------------------------------------------

  方法：把需求描述里的名词圈出来，能独立存在的就是实体。

  例："读者可以看小说，小说有很多章节，管理员发布章节"
      名词：读者 / 小说 / 章节 / 管理员
      → User（读者+管理员是同一个实体的不同角色）
      → Novel
      → Chapter

  【实体 vs 值对象】
    ------------------------------------------------------------------
    类型      判断标准                    例子
    ------------------------------------------------------------------
    实体      有唯一标识，生命周期独立    User / Novel / Chapter
    值对象    没有标识，依附于实体存在    地址、金额、章节大纲
    ------------------------------------------------------------------

  【坑】
    · 不要给所有名词都建表。"分类"如果只有几个固定值，
      用枚举或字符串字段就够了，建表反而增加 JOIN 成本。
    · 管理员和普通用户通常是同一张表 + role 字段，不是两张表。


--------------------------------------------------------------------------------
2.2 关系设计：一对多要不要用 ORM 的关联注解？
--------------------------------------------------------------------------------

  【三种关系】
    ------------------------------------------------------------------
    关系        实现方式                    例子
    ------------------------------------------------------------------
    一对一      外键 + 唯一索引              User ↔ UserProfile
    一对多      在多的一方加外键             Novel → Chapter
    多对多      中间表 + 联合唯一索引        User ↔ Novel（收藏）
    ------------------------------------------------------------------

  【★ 一对多的两种写法对比】

    写法A：用 JPA 的 @OneToMany
      @Entity
      public class Novel {
          @OneToMany(mappedBy = "novel", cascade = CascadeType.ALL)
          private List<Chapter> chapters;
      }

      优点：级联操作方便（保存小说时自动保存章节）
      缺点：
        · 懒加载 → 序列化时触发 N+1
        · 急加载 → 查小说标题时把 10 万字正文全查出来
        · 需要处理循环引用（@JsonIgnore / @JsonManagedReference）

    写法B：手动用外键字段（★ 推荐）
      @Entity
      public class Chapter {
          @Column(nullable = false)
          private Integer novelId;      // 就是个普通字段
      }

      优点：
        · 查询粒度完全可控 —— 要章节才查章节
        · 没有循环引用问题
        · 性能可预测
      缺点：
        · 级联删除要手写（deleteByNovelId）
        · 失去了一些 ORM 的便利

  【结论】
    生产项目里更常见的是写法B。
    原因：正文这类大字段，绝对不能在查列表时被连带加载。

  【坑】
    · 用 @OneToMany 时，@Data 生成的 toString() 会递归打印，导致栈溢出
      解法：@ToString.Exclude 或 @EqualsAndHashCode.Exclude
    · JSON 序列化双向关联会导致无限递归
      解法：@JsonIgnore 加在其中一边

2.3 冗余字段：用空间换时间的经典权衡
--------------------------------------------------------------------------------

  【问题场景】
    一本书的总字数 = 所有章节的 wordCount 求和。
    这是可以算出来的，为什么还要单独存一个字段？

  【分析】
    ------------------------------------------------------------------
    方案          查询成本                      写入成本
    ------------------------------------------------------------------
    实时计算      每次列表查询都要 JOIN + SUM    无
    冗余字段      直接读，零成本                每次增删改章节都要维护
    ------------------------------------------------------------------

  【决策原则】
    如果这个字段在"高频读、低频写"的接口里出现 → 冗余存储
    如果在"低频读"的场景里 → 实时计算

    列表页是最典型的"高频读"，所以总字数、评论数、点赞数
    这类字段通常都是冗余的。

  【代价：一致性维护清单】
    冗余字段一旦引入，所有会改变它的地方都要维护：
      · 新增章节   → totalWords += wordCount
      · 修改章节   → totalWords += (newWords - oldWords)
      · 删除章节   → totalWords -= wordCount

    ★ 漏一处，数据就不一致。这是冗余字段最大的风险。
    ★ 面试时能说出"代价是写入时手动维护一致性"就是满分答案。

  【更安全的做法】
    · 把维护逻辑封装在一个方法里，而不是散落在各处
    · 写定时任务定期校验（对账）
    · 或者在数据库层用触发器（不推荐，逻辑分散更难维护）


--------------------------------------------------------------------------------
2.4 排序字段与显示序号：什么时候该分离？
--------------------------------------------------------------------------------

  【问题】
    章节号要不要存数据库？

  【方案对比】
    ------------------------------------------------------------------
    方案          做法                          优缺点
    ------------------------------------------------------------------
    存实际序号    删除后重排所有后续记录        简单直观，但删除代价大
    存时间戳      按 create_time 排序           删除无代价，但显示要算序号
    显示序号分离  存 sort_order，显示时重排     灵活，适合拖拽排序场景
    ------------------------------------------------------------------

  【"删除后重排"的代价】
    有 500 章，删除第 2 章 → 后面 498 章的 chapter_number 都要 UPDATE。
    这是个 O(N) 的写操作，章节多了会明显变慢。

  【更优的做法】
    · 用 displayOrder 字段（可以有间隔，如 10, 20, 30），
      插入时取中间值，避免大规模重排
    · 或者干脆不存序号，用 create_time 排序，
      序号在展示时由前端算出来

  【延伸：排序字段的设计模式】
    ------------------------------------------------------------------
    模式            做法                      适用
    ------------------------------------------------------------------
    连续整数        1,2,3,4                   简单场景
    带间隔整数      10,20,30                  需要频繁插入
    小数排序        1.5（插在 1 和 2 之间）   多次插入后精度会不够
    字典序          用字符串做排序键          支持无限次插入（如 aab）
    ------------------------------------------------------------------

2.5 状态字段：用状态机管住流转
--------------------------------------------------------------------------------

  【问题】
    小说有"连载中/已完结"两种状态，怎么设计？

  【最小实现】
    @Column(nullable = false)
    private String status;        // "ONGOING" / "FINISHED"

  【进阶：状态机】
    当状态超过 3 个、且流转有规则时，就应该引入状态机思维：

      草稿(DRAFT) → 审核中(REVIEWING) → 已发布(PUBLISHED) → 已下架(OFFLINE)
                        ↓ 驳回
                    草稿(DRAFT)

    规则：
      · 只有草稿能提交审核
      · 只有审核中能被驳回
      · 只有已发布能下架

  【为什么要用状态机】
    不用状态机的代码长这样：
      if (novel.getStatus().equals("DRAFT")) {
          novel.setStatus("REVIEWING");
      } else if (...) {
          // 越来越长的 if-else，谁都不知道合法流转是什么
      }

    用状态机：
      stateMachine.fireEvent(novel, "SUBMIT");
      // 非法流转直接抛异常

  【实现方式】
    · 简单版：枚举 + switch 校验
    · 完整版：Spring StateMachine
    · 数据库版：单独一张状态流转表

  【坑】
    · 状态用字符串还是数字？
      字符串可读性好（"ONGOING" 一眼看懂），数字省空间。
      推荐字符串 + 枚举约束。
    · 状态值不要散落在各处硬编码，定义成枚举或常量。


--------------------------------------------------------------------------------
2.6 删除策略：物理删除 vs 逻辑删除
--------------------------------------------------------------------------------

  ------------------------------------------------------------------
  策略        做法                        优点            缺点
  ------------------------------------------------------------------
  物理删除    DELETE FROM               干净、省空间    无法恢复
  逻辑删除    加 deleted 字段，标记      可恢复、可审计  所有查询都要带条件
                                          关联数据不孤儿
  ------------------------------------------------------------------

  【逻辑删除的实现】
    @Column(nullable = false)
    private Boolean deleted = false;

    -- 查询时
    SELECT * FROM novel WHERE deleted = false;

  【★ 逻辑删除的三个坑】
    1. 所有查询都要带上 deleted = false，漏一个就查出已删数据
       → MyBatis-Plus 有 @TableLogic 自动处理，JPA 需要手写
    2. 唯一索引会失效
       → 删除了"剑来"后再创建同名小说会冲突
       → 解法：唯一索引改成 (title, deleted) 联合，或删除时改 title
    3. 数据表会越来越大
       → 需要定期归档

  【怎么选】
    · 用户、订单、文章等有业务价值的数据 → 逻辑删除
    · 日志、临时数据、中间表 → 物理删除
    · 级联删除时要考虑：删了小说，章节怎么办？
      · 物理级联删除
      · 或者章节也加 deleted，跟着小说一起标记


--------------------------------------------------------------------------------
2.7 接口设计的粒度：一个接口做一件事
--------------------------------------------------------------------------------

  【反例：一个接口干太多】
    POST /novel/saveAll
    body: { novel: {...}, chapters: [...], cover: {...} }
    → 创建小说 + 批量创建章节 + 上传封面，一次搞定

    问题：
      · 部分失败怎么办？事务要多大？
      · 前端只想改小说信息，却要传全部数据
      · 无法单独复用

  【正例：按资源拆分】
    POST   /novels                    创建小说
    POST   /novels/{id}/chapters      发布章节
    POST   /upload                    上传文件
    → 每个接口职责单一，可以独立复用和测试

  【什么时候可以"合并"】
    当多个操作在业务上必须原子完成时。
    比如"下单"要同时创建订单 + 扣库存 + 扣优惠券，
    这时候一个接口内部完成，但对外仍然是一个动作。

  【RESTful 的资源嵌套设计】
    ------------------------------------------------------------------
    场景                        推荐写法
    ------------------------------------------------------------------
    查小说的章节列表            GET /novels/{id}/chapters
    查某一章                    GET /novels/{id}/chapters/{cid}
    在小说下新建章节            POST /novels/{id}/chapters
    修改章节                    PUT /novels/{id}/chapters/{cid}
    删除章节                    DELETE /novels/{id}/chapters/{cid}
    ------------------------------------------------------------------

    ★ 注意：即使章节 ID 已经全局唯一，
      路径里仍然保留 novelId，因为这样能表达"归属关系"，
      也方便做水平越权校验。


--------------------------------------------------------------------------------
2.8 DTO / VO / Entity 的分层价值
--------------------------------------------------------------------------------

  ------------------------------------------------------------------
  名称      方向            职责                      特点
  ------------------------------------------------------------------
  Entity    后端 ↔ 数据库   表映射                    带 JPA 注解
  DTO       前端 → 后端     接收参数                  带校验注解
  VO        后端 → 前端     返回数据                  可裁剪、可脱敏
  ------------------------------------------------------------------

  【为什么不能直接用 Entity 接收参数】
    前端可能传进 id、status、totalWords 这些不该由它决定的字段，
    造成越权赋值（比如把别人的记录 id 传进来覆盖）。

  【为什么不能直接返回 Entity】
    · 会暴露敏感字段（passwordHash）
    · 会暴露内部结构（createdBy、deleted 标记）
    · 大字段会被连带返回（章节正文）

  【"正文脱敏"的典型场景】
    详情页需要章节目录，但不需要正文：

      public class NovelDetailVO {
          private Integer id;
          private String title;
          private List<ChapterOutline> chapters;    // 只有目录信息

          public static class ChapterOutline {
              private Integer id;
              private Integer chapterNumber;
              private String title;
              private Integer wordCount;
              // ★ 没有 content 字段
          }
      }

    ★ 一本 500 章的小说，如果详情接口把正文全返回，
      JSON 可能几十 MB。这不是形式主义，是真的省流量。


################################################################################
  三、通用的「坑」清单
################################################################################

  □ 不要给所有名词建表 —— 值对象用字段就够了
  □ 一对多关系慎用 @OneToMany —— 大字段会被连带加载
  □ 冗余字段要列全维护点 —— 漏一处就不一致
  □ 连续序号 + 删除重排 = O(N) 写操作，量大时改方案
  □ 状态值不要硬编码散落各处
  □ 逻辑删除会让唯一索引失效
  □ 一个接口只做一件事，除非它们必须原子完成
  □ 详情接口不要返回大字段（正文、图片二进制）
  □ 不要用 Entity 接参数，也不要返回 Entity


################################################################################
  四、面试会怎么问
################################################################################

  Q1：为什么总字数要冗余存一份，而不是实时算？
  A： 因为小说列表是最高频的接口，实时算需要 JOIN + SUM 聚合。
     冗余存储把查询成本降到零，代价是增删改章节时要手动维护一致性，
     一共三个维护点：新增 +、修改 +diff、删除 -。

  Q2：为什么章节和小说不用 @OneToMany？
  A： 两个原因。一是避免加载小说时把全部章节正文一起拉出来，
     正文可能有几十万字；二是避免 JSON 序列化的循环引用问题。
     用 novelId 手动关联虽然失去了级联便利，但查询粒度完全可控。

  Q3：删除章节后为什么要重排章节号？有没有更好的做法？
  A： 重排是为了读者体验（不然会出现 1、3、4、5 章）。
     但代价是 O(N) 的批量更新。
     更好的做法是把"显示序号"和主键分离，
     比如用带间隔的 sort_order，或者干脆用创建时间排序、
     序号在展示时算出来。

  Q4：详情接口为什么不返回章节正文？
  A： 一本 500 章的小说正文可能几十 MB，
     详情页只需要目录，正文在点击某一章时才单独查。
     这是 DTO/VO 分层的实际价值，不是形式主义。

  Q5：怎么做水平越权防护？
  A： 所有涉及"归属"的接口都要校验数据归属。
     比如删除章节时检查 chapter.novelId 是否等于路径里的 novelId。
     更彻底的做法是把归属条件直接写进 SQL，
     比如 deleteByIdAndUserId(id, userId)，天然防越权。

  Q6：物理删除还是逻辑删除？怎么选？
  A： 有业务价值的数据（用户、订单、文章）用逻辑删除，
     可以恢复、可审计、不会产生孤儿数据；
     日志和临时数据用物理删除。
     逻辑删除要注意三个坑：所有查询要带条件、唯一索引会失效、表会越来越大。
