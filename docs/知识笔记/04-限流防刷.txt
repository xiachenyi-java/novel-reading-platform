  对应项目笔记：docs/项目笔记/04-限流防刷.txt

################################################################################
  一、这个大类在解决什么问题
################################################################################

  你的服务上线后一定会遇到：
    · 用脚本疯狂试密码（撞库 / 暴力破解）
    · 写个循环刷你的接口，把数据库打挂
    · 爬虫把内容全爬走
    · 秒杀场景下的瞬时流量

  限流就是给服务装一个"闸门"，超过阈值的请求直接挡在门外。

  【限流的三个层次】
    ------------------------------------------------------------------
    层次        作用范围                      例子
    ------------------------------------------------------------------
    网关层      整个集群                      Nginx limit_req
    应用层      单个服务                      本大类讲的
    数据层      数据库连接 / 热点行           连接池限流
    ------------------------------------------------------------------


################################################################################
  二、四种限流算法 ★ 面试必问
################################################################################

【对比表】
  ------------------------------------------------------------------
  算法        原理                        优点            缺点
  ------------------------------------------------------------------
  固定窗口    时间切片 + 计数器           简单、省内存    ★ 临界突刺
  滑动窗口    记录每次请求的时间戳        精度高          内存占用大
  令牌桶      固定速率放令牌，请求取令牌  允许突发流量    实现稍复杂
  漏桶        请求入桶，固定速率流出      流量绝对平滑    不允许突发
  ------------------------------------------------------------------

【形象记忆】
  固定窗口 = 一节课 45 分钟，下课铃一响就重置
  滑动窗口 = 只看"最近 60 秒"这个滚动的区间
  令牌桶   = 有个桶按固定速度攒硬币，攒够了才能进（攒的可以一次花掉）
  漏桶     = 水龙头不管多快倒水，下面出水速度恒定

【选型建议】
  ------------------------------------------------------------------
  场景                          推荐算法
  ------------------------------------------------------------------
  一般接口保护                  固定窗口（够用且简单）
  登录等安全接口                滑动窗口（精度要求高）
  需要允许突发流量（API 平台）  令牌桶
  需要绝对平滑（消息队列削峰）  漏桶
  ------------------------------------------------------------------


--------------------------------------------------------------------------------
2.1 固定窗口计数器
--------------------------------------------------------------------------------

  【原理】
    把时间切分为固定窗口（如 1 分钟），每个窗口内允许 N 次请求。

  【实现：Redis INCR】
    Long count = redis.opsForValue().increment(key);
    if (count == 1) {
        redis.expire(key, window, TimeUnit.SECONDS);
    }
    if (count > limit) {
        throw new RateLimitException("请求过于频繁");
    }

  【★ 为什么用 Redis 而不是本地 Map】
    本地 Map 在多机部署时，每台机器各算各的，限流不准。
    Redis 是集中式的，所有机器共用一份计数 → 天然支持分布式限流。

  【★ 为什么 INCR 是原子的】
    Redis 单线程处理命令，INCR 是一个原子操作。
    对比 Java 的 count++ 是"读-改-写"三步，多线程下会丢更新。

  【★★ 临界突刺问题】
    假设限制：60 秒内最多 5 次

      时间轴： 0    10    20    30    40    50    60    70
      请求数：            5次（第59秒）        5次（第61秒）
                      ↑                       ↑
                    窗口1边界               窗口2开始

    第 59 秒发 5 次（窗口 1 的额度用光）
    第 61 秒发 5 次（窗口 2 的额度刚开始）
    → 实际在 2 秒内通过了 10 次请求，是限制值的 2 倍

    攻击者只要卡在窗口切换的瞬间，就能把限流效果翻倍。

  【★ 另一个坑：INCR 和 EXPIRE 分两步】
    如果 INCR 执行完、EXPIRE 执行前进程崩溃或 Redis 断开，
    这个 key 就永久存在 → 用户被永久限流。

    解法：
      · Lua 脚本把两步合并成原子操作
      · 或者用 SET key value EX 60 NX 的思路
      · 或者给 key 设一个兜底的过期时间


--------------------------------------------------------------------------------
2.2 滑动窗口
--------------------------------------------------------------------------------

  【原理】
    记录每次请求的时间戳，只统计"最近 N 秒"内的请求数。

  【实现：Redis ZSet】
    -- 1. 移除窗口外的记录
    ZREMRANGEBYSCORE key 0 (now - window)
    -- 2. 统计当前窗口内的请求数
    ZCARD key
    -- 3. 如果没超限，记录本次请求
    ZADD key now now
    -- 4. 设置过期时间
    EXPIRE key window

    ★ ZSet 的 score 用时间戳，member 也用时间戳（或加随机后缀防重复）

  【优点】解决了临界突刺，限流精度高
  【缺点】每个请求都要存一条记录，内存占用大
    → 优化：可以用 Redis 的 Bitmap 或者分片计数降低内存


--------------------------------------------------------------------------------
2.3 令牌桶
--------------------------------------------------------------------------------

  【原理】
    有一个桶，按固定速率往里面放令牌（token）。
    请求来了要先从桶里拿一个令牌，拿不到就限流。
    桶有容量上限，攒满就不再放了。

  【为什么允许突发流量】
    如果一段时间没有请求，桶会攒满令牌。
    突发流量来的时候，可以一次性消耗掉攒下的令牌。

  【实现】
    · 单机：Guava 的 RateLimiter
    · 分布式：Redisson 的 RRateLimiter

  【参数】
    · 令牌产生速率（rate）：每秒放几个
    · 桶容量（capacity）：最多攒几个


--------------------------------------------------------------------------------
2.4 漏桶
--------------------------------------------------------------------------------

  【原理】
    请求先进入桶里排队，然后以恒定速率流出处理。
    桶满了就拒绝新请求。

  【和令牌桶的区别】
    ------------------------------------------------------------------
    对比项        令牌桶              漏桶
    ------------------------------------------------------------------
    突发流量      允许（消耗攒的令牌） 不允许（流出速率恒定）
    限流对象      流入速率            流出速率
    典型应用      API 限流            流量整形、消息队列削峰
    ------------------------------------------------------------------


################################################################################
  三、AOP 注解式限流 ★ 工程实践的重点
################################################################################

【为什么要注解式】
  第一版：限流逻辑直接写在业务方法里 → 复用性差，10 个接口复制 10 遍
  第二版：自定义注解 + AOP 切面 → 任何接口加一行注解就能限流

【三步实现】

  1. 定义注解：
     @Target(ElementType.METHOD)          // 只能标记在方法上
     @Retention(RetentionPolicy.RUNTIME)  // 运行时保留，可被反射读取
     public @interface RateLimit {
         String key();                // 限流的业务标识
         int limit() default 5;       // 窗口内最大请求数
         int window() default 60;     // 窗口大小（秒）
     }

  2. 使用：
     @RateLimit(key = "login", limit = 5, window = 60)
     @PostMapping("/login")
     public Result<LoginVO> login(@RequestBody LoginDTO dto) { ... }

  3. 切面：
     @Aspect
     @Component
     public class RateLimitAspect {

         @Around("@annotation(rateLimit)")     // 匹配所有带 @RateLimit 的方法
         public Object around(ProceedingJoinPoint point, RateLimit rateLimit)
                 throws Throwable {
             String redisKey = "rate_limit:" + rateLimit.key() + ":" + getClientIp();

             Long count = redis.opsForValue().increment(redisKey);
             if (count != null && count == 1) {
                 redis.expire(redisKey, rateLimit.window(), TimeUnit.SECONDS);
             }
             if (count != null && count > rateLimit.limit()) {
                 throw new RateLimitException("请求过于频繁，请稍后再试");
             }

             return point.proceed();      // 放行目标方法
         }
     }

【★ 为什么必须用 @Around】
  ------------------------------------------------------------------
  注解            执行时机                    能阻止方法执行吗
  ------------------------------------------------------------------
  @Before         执行前                      不能
  @After          执行后（无论成功失败）      不能
  @AfterReturning 成功返回后                  不能
  @AfterThrowing  抛异常后                    不能
  @Around         包裹整个方法                ★ 能
  ------------------------------------------------------------------
  限流必须"拦住"请求不让它执行，所以只能用 @Around。

【★ AOP 的底层原理（面试考点）】
  Spring AOP 用动态代理实现：
    · 目标类实现了接口 → JDK 动态代理
    · 目标类没有接口   → CGLIB 生成子类

  ★ 由此推出的两个坑：
    · 同类内部方法调用，AOP 失效（走 this 不走代理）
    · final 方法不能被 CGLIB 代理


################################################################################
  四、限流维度与 IP 获取
################################################################################

【限流维度】
  ------------------------------------------------------------------
  维度        说明                        适用场景
  ------------------------------------------------------------------
  IP          按来源 IP 限流              防单机脚本
  用户ID      按登录用户限流              防单账号刷接口
  用户名      按尝试登录的账号限流        防针对某个账号撞库
  接口        按接口全局限流              保护核心接口
  全局        整个服务总量限流            防雪崩
  ------------------------------------------------------------------

  ★ 生产环境通常组合使用，比如：
    登录接口：IP + 用户名 双维度
    普通接口：用户ID 维度
    全站：全局 QPS 兜底

【★ 获取客户端真实 IP 的坑】

  如果服务前面有 Nginx / 负载均衡，
  request.getRemoteAddr() 拿到的是代理的 IP，不是真实用户 IP。

  真实 IP 在 X-Forwarded-For 请求头里（可能有多层，用逗号分隔）。

  private String getClientIp() {
      String ip = request.getHeader("X-Forwarded-For");
      if (isInvalid(ip)) ip = request.getHeader("Proxy-Client-IP");
      if (isInvalid(ip)) ip = request.getHeader("WL-Proxy-Client-IP");
      if (isInvalid(ip)) ip = request.getHeader("HTTP_CLIENT_IP");
      if (isInvalid(ip)) ip = request.getHeader("HTTP_X_FORWARDED_FOR");
      if (isInvalid(ip)) ip = request.getRemoteAddr();

      // 多层代理时取第一个
      if (ip != null && ip.contains(",")) {
          ip = ip.split(",")[0].trim();
      }
      return ip != null ? ip : "unknown";
  }

  【★ 安全隐患】
    X-Forwarded-For 是客户端可以伪造的！
    如果服务直接暴露公网，攻击者每次换个假 IP 就绕过限流了。

    正确做法：由 Nginx 统一设置这个头，并覆盖客户端传的值：
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      或者更严格：
      proxy_set_header X-Real-IP $remote_addr;

    然后应用只信任来自可信代理的 X-Forwarded-For。


################################################################################
  五、限流的响应规范
################################################################################

【HTTP 429 Too Many Requests】
  状态码必须是 429，不是 500 也不是 403。

【Retry-After 响应头】
  告诉客户端要等多久再试（秒数或 HTTP 日期）：
    Retry-After: 60
    Retry-After: Wed, 21 Oct 2026 07:28:00 GMT

  ★ 这是 HTTP 规范要求的，能提升 API 的专业度。

【响应体】
  {
    "code": 429,
    "msg": "请求过于频繁，请稍后再试",
    "data": null
  }

【★ 还有一个更友好的做法：排队而不是拒绝】
  对于非实时性要求高的接口，
  可以返回 202 Accepted + 任务 ID，让客户端轮询结果。
  （这属于削峰的范畴，见 docs/知识笔记/06-异步与消息.txt）


################################################################################
  六、分布式限流的思考
################################################################################

【单机 vs 分布式】
  ------------------------------------------------------------------
  对比项        单机限流                分布式限流
  ------------------------------------------------------------------
  实现          Guava RateLimiter       Redis / Sentinel
  精度          本机精确                全局精确
  性能          无网络开销              每次请求一次 Redis 往返
  适用          单实例部署              多实例部署
  ------------------------------------------------------------------

【★ Redis 限流的性能优化】
  每次请求都访问 Redis 会带来网络开销（约 0.5~1ms）。
  优化方案：
    · 本地预分配：一次从 Redis 取 100 个配额，用完再取
      （牺牲一点精度换性能）
    · 用 Pipeline 批量操作
    · 热点接口做多级限流（本地 + Redis）

【★ 限流与服务降级的关系】
  限流是"主动拒绝一部分请求，保护整体"
  降级是"牺牲非核心功能，保住核心功能"
  熔断是"下游服务挂了，不再调用它，直接返回兜底"

  三者共同构成"高可用三件套"，见 L7 架构部分。


################################################################################
  面试会怎么问
################################################################################

  Q1：你的限流是怎么实现的？
  A： Redis INCR 固定窗口计数 + 自定义 @RateLimit 注解 + AOP 环绕通知。
     用 Redis 是因为多机部署时本地计数不准，Redis 天然分布式。

  Q2：固定窗口有什么问题？
  A： 临界突刺。第 59 秒和第 61 秒各发 5 次，2 秒内过了 10 次。
     解法是滑动窗口（ZSet 存时间戳）。

  Q3：四种限流算法怎么选？
  A： 见上面的对比表。一般接口用固定窗口，
     登录等安全接口用滑动窗口，
     需要允许突发流量用令牌桶。

  Q4：为什么用 AOP 而不是直接在方法里写限流？
  A： 解耦和复用。注解式让业务代码保持干净，任何接口加一行就能限流。

  Q5：Redis 的 INCR 为什么是线程安全的？
  A： Redis 是单线程处理命令的，INCR 本身是原子操作。
     对比 Java 的 count++ 是非原子的（读-改-写三步）。

  Q6：INCR 和 EXPIRE 分两步有什么风险？
  A： 中间崩溃会导致 key 永不过期，用户被永久限流。
     解法是用 Lua 脚本合并成原子操作。

  Q7：怎么获取客户端真实 IP？
  A： 从 X-Forwarded-For 取，多层代理取第一个。
     ★ 但要强调：这个头可以伪造，
       生产环境必须由 Nginx 统一设置并覆盖客户端传的值。

  Q8：限流和熔断、降级有什么区别？
  A： 限流是主动拒绝部分请求保护整体；
     熔断是下游挂了就不调它了；
     降级是牺牲非核心功能保住核心功能。
