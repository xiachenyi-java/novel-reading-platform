================================================================================
【大类 13】安全加固
================================================================================
  对应项目笔记：docs/项目笔记/13-安全加固.txt

【定位】回答"别人能怎么搞我"。

【★ 先分清 auth 和 security】
  ------------------------------------------------------------------
  大类          回答的问题              关注点
  ------------------------------------------------------------------
  auth          你是谁？你能干什么？    认证、授权、会话
  security      别人能怎么攻击我？      漏洞、防御、加固
  ------------------------------------------------------------------

  auth 是"把门锁好，只让有钥匙的人进"。
  security 是"防止有人撬锁、翻墙、从窗户爬进来"。


################################################################################
  一、文件上传安全
################################################################################

【★ 五重校验（缺一不可）】

  ------------------------------------------------------------------
  序号  校验项              作用
  ------------------------------------------------------------------
  1     文件大小限制        防止磁盘打满和 DoS
  2     扩展名白名单        防止上传可执行脚本
  3     Content-Type 校验   基础校验（★ 可被伪造，不可单独依赖）
  4     文件头 magic number 真正确认文件类型 ★
  5     路径穿越校验        防止写到系统目录
  ------------------------------------------------------------------
  +     重命名（UUID）      防覆盖、防猜路径

【★ 为什么只校验 Content-Type 不够】
  Content-Type 是客户端发来的 HTTP 头，可以随意伪造。
  用 Postman 或 curl 就能传一个 .html 文件但声明 Content-Type: image/png。

【★ 扩展名白名单实现】
  private static final Set<String> ALLOWED_EXT =
          Set.of(".jpg", ".jpeg", ".png", ".gif", ".webp");

  String originalName = file.getOriginalFilename();
  String ext = originalName != null && originalName.contains(".")
          ? originalName.substring(originalName.lastIndexOf(".")).toLowerCase()
          : "";
  if (!ALLOWED_EXT.contains(ext)) {
      return Result.error("只支持 jpg/jpeg/png/gif/webp 格式");
  }

  ★ 必须 toLowerCase()，否则 .PNG / .JPG 会被误拒。

【★ 文件头 magic number 校验】
  private static final Map<String, String> MAGIC = Map.of(
      "jpg",  "FFD8FF",
      "png",  "89504E47",
      "gif",  "47494638",
      "webp", "52494646"
  );

  byte[] header = new byte[8];
  try (InputStream is = file.getInputStream()) {
      is.read(header);
  }
  String hex = bytesToHex(header);
  // 比对是否以某个魔数开头

  ★ 原理：文件内容的开头几个字节是固定的，改后缀名改不了真实类型。

【★ 路径穿越防护】
  Path baseDir = Paths.get(uploadPath).toAbsolutePath().normalize();
  Path fullPath = targetPath.toAbsolutePath().normalize();
  if (!fullPath.startsWith(baseDir)) {
      log.error("检测到非法路径穿越攻击！目标路径：{}", fullPath);
      return Result.error("上传失败：非法的文件存储路径");
  }

  【攻击原理】
    文件名传成 "../../../../etc/passwd"，
    不校验的话文件会写到系统目录里。

  【校验原理】
    先 normalize 把 ../ 解析掉，再判断最终路径是否还在允许目录内。

【★★ 存储型 XSS 的完整攻击链（重要）】
  如果满足这三个条件：
    ① 只校验 Content-Type（可伪造）
    ② 不校验扩展名
    ③ 上传目录可以匿名访问且被当作静态资源返回

  攻击流程：
    ① 攻击者准备一个 xss.html，内容是窃取 localStorage 的脚本
    ② 上传，手动设置 Content-Type: image/png
    ③ 后端校验通过，保存为 {uuid}.html
    ④ 攻击者访问 /uploads/{uuid}.html
    ⑤ 浏览器按 text/html 渲染并执行 JS
    ⑥ JS 读取 localStorage 里的 token → 发给攻击者
    ⑦ 攻击者拿到 token，完全接管账号

  【防御（四重）】
    · 扩展名白名单（第 2 项校验）
    · 文件头校验（第 4 项校验）
    · 响应头 X-Content-Type-Options: nosniff（禁止浏览器猜类型）
    · ★ 最彻底：上传到对象存储（OSS / S3）并使用独立域名，
      这样即使传了恶意文件，也在隔离域名下，拿不到主站的 localStorage

【★ 其他加固点】
  □ 上传目录不给执行权限（chmod 644 文件，755 目录）
  □ 图片二次压缩 / 重绘（用 Thumbnailator 重新生成，
    彻底消除恶意载荷，这是根治手段）
  □ 检查 polyglot 文件（既是图片又是 HTML 的构造）
  □ 限制单用户总上传量和频率


################################################################################
  二、越权控制
################################################################################

【两种越权】
  ------------------------------------------------------------------
  类型        含义                          例子
  ------------------------------------------------------------------
  垂直越权    低权限用户访问高权限接口      普通用户调管理员删除接口
  水平越权    同权限用户访问别人的数据      A 用户改 B 用户的订单
  ------------------------------------------------------------------

【垂直越权的防御】
  · 注解 + 拦截器检查角色（@RequireAdmin）
  · 或 Spring Security 的 hasRole()
  · 返回 403 而不是 401

【★ 水平越权的防御（更常见、更容易漏）】

  ✗ 错误做法：
    @DeleteMapping("/collect/{collectId}")
    public Result<Void> cancelCollect(@PathVariable Integer collectId) {
        collectService.deleteById(collectId);      // ← 别人能删你的收藏！
    }

  △ 及格做法：先查后判
    Collect c = collectService.findById(collectId);
    if (!c.getUserId().equals(currentUserId)) {
        throw new BusinessException("无权操作");
    }
    collectService.delete(c);

  ★ 更优做法：把权限条件写进 SQL
    collectService.deleteByIdAndUserId(collectId, currentUserId);
    → 天然防越权，没有并发窗口，性能也更好

【★ 通用防御原则】
  · 永远不要相信前端传来的"用户ID"，一律从上下文取（ThreadLocal）
  · 所有涉及"我的数据"的接口，查询条件必须带 userId
  · 优先"把权限条件写进 SQL"，而不是"先查后判"
  · 新增接口时，问自己："这个接口有没有校验数据归属？"

【★ 越权测试方法论】
  用两个账号 A 和 B：
    1. 用 A 登录，拿到 A 的数据 ID
    2. 用 B 的 token 去访问 A 的数据 ID
    3. 如果成功 → 存在水平越权


################################################################################
  三、敏感信息保护
################################################################################

【★ 三个泄露渠道】
  ------------------------------------------------------------------
  渠道            风险                          检查方法
  ------------------------------------------------------------------
  响应（接口返回）  返回了 passwordHash 等        抓包看响应体
  缓存（Redis）    缓存里存了敏感字段             打开 Redis 客户端看
  日志（log）      打印了整个对象                 搜索 log.info 里的对象
  ------------------------------------------------------------------

【★ 响应脱敏】
  · 返回 User 前 setPasswordHash(null)
  · 或者定义专门的 VO，只包含该给的字段
  · 不要在响应里包含内部 ID、创建人、deleted 标记等

【★ 缓存脱敏】
  从数据库查出来的对象直接序列化进缓存，会把所有字段都存进去。
  做法：
    · 缓存前置空敏感字段
    · 定义专门的 CacheVO
    · @JsonIgnore（★ 会影响所有序列化场景，改前要确认）

【★ 日志脱敏】
  · @Data 的 toString() 会打印所有字段
    → 密码哈希、token 会进日志
  · 解法：@ToString.Exclude 或只 log 需要的字段
  · token 只 log 前 8 位：token.substring(0, 8) + "..."

【★ 异常信息脱敏】
  ✗ 直接返回 e.getMessage()
    → 数据库异常的 message 会包含表名、字段名、SQL 片段
    → 这是给攻击者的情报

  ✓ 区分处理：
    · 可预期的业务异常 → 直接返回 message
    · 不可预期的系统异常 → 返回统一话术"系统繁忙"
    · 完整信息记在日志里（error 级别带堆栈）

【★ 配置脱敏】
  · 数据库密码、JWT secret 走环境变量，不提交 Git
  · ★ 不要留默认值，否则"忘配环境变量也能启动"
  · 可以用 @PostConstruct 校验生产环境是否真的配了
  · 更好的方案：用配置中心（Nacos / Apollo）便于集中管理和审计


################################################################################
  四、Web 常见攻击
################################################################################

--------------------------------------------------------------------------------
4.1 SQL 注入
--------------------------------------------------------------------------------

  【原理】
    用户输入被拼进 SQL，改变了原本的语义。
    例：' OR '1'='1   /   '; DROP TABLE user; --

  【防御】
    · ★ 参数化查询（PreparedStatement）—— 根本防御
    · ORM 框架（JPA / MyBatis）默认用参数化查询
    · 手写 SQL 时用占位符 :param 而不是字符串拼接
    · 动态排序字段必须白名单校验（无法参数化）

  ✗ @Query("SELECT n FROM Novel n WHERE n.title = '" + title + "'")
  ✓ @Query("SELECT n FROM Novel n WHERE n.title = :title")

  ★ 面试答法："我们全程用参数化查询，从根本上避免了 SQL 注入。
    唯一需要小心的是动态排序字段，我们做了白名单校验。"

--------------------------------------------------------------------------------
4.2 XSS（跨站脚本）
--------------------------------------------------------------------------------

  ------------------------------------------------------------------
  类型        原理                            存储位置
  ------------------------------------------------------------------
  存储型      恶意脚本存进数据库，别人看时执行  数据库 ★ 危害最大
  反射型      恶意脚本在 URL 里，诱导点击       URL 参数
  DOM 型      前端 JS 直接把不可信数据插入 DOM  —
  ------------------------------------------------------------------

  【防御】
    · ★ 输出编码（Vue/React 的 {{ }} 默认转义）
    · 富文本用白名单过滤（jsoup）
    · CSP（Content-Security-Policy）响应头
    · Cookie 加 HttpOnly（JS 读不到）
    · 文件上传的扩展名白名单（防"上传 HTML"这条路径）

  【★ Vue 场景】
    <div v-html="content"></div>    ✗ 危险（会执行 HTML）
    <div>{{ content }}</div>        ✓ 安全（自动转义）

--------------------------------------------------------------------------------
4.3 CSRF（跨站请求伪造）
--------------------------------------------------------------------------------

  【原理】
    诱导已登录用户在不知情的情况下发出请求。
    例：你登录了银行网站，然后访问恶意网站，
        它自动向银行发了一个转账请求，浏览器自动带上了 Cookie。

  【★ 成立的两个前提】
    1. 认证信息由浏览器自动携带（Cookie / Session）
    2. 攻击者能预测请求的全部参数

  【★ 为什么用 JWT 就不需要 CSRF 防护】
    Cookie 认证：浏览器自动带 Cookie → 攻击者能借用你的身份
    JWT 认证：token 存在 localStorage，需要 JS 手动加到 Header
             → 攻击者的网站读不到你域名下的 localStorage
             → CSRF 天然不成立

    ★ 但如果改成 Cookie 存 token，就必须重新开启 CSRF 防护。

  【防护手段（如果要用 Cookie）】
    · CSRF Token（服务端下发，请求时必须带上）
    · SameSite Cookie 属性（Lax / Strict）
    · 校验 Referer / Origin
    · 敏感操作二次验证

--------------------------------------------------------------------------------
4.4 其他攻击
--------------------------------------------------------------------------------

  【点击劫持】
    用透明 iframe 覆盖在页面上，诱导你点击。
    防御：X-Frame-Options: DENY 或 CSP 的 frame-ancestors 'none'

  【SSRF（服务端请求伪造）】
    服务端根据用户输入去请求 URL，攻击者构造内网地址探测内网。
    场景：通过 URL 导入图片、Webhook 回调。
    防御：白名单域名、禁止访问内网 IP、禁止重定向

  【暴力破解】
    防御：限流 + 失败次数锁定 + 验证码 + 异常登录检测

  【越权】
    见第二部分。

  【敏感信息泄露】
    见第三部分。

  【依赖漏洞】
    使用的第三方库有已知 CVE 漏洞。
    防御：定期扫描（OWASP dependency-check / Dependabot）


################################################################################
  五、认证安全加固
################################################################################

  ------------------------------------------------------------------
  项目              做法                              优先级
  ------------------------------------------------------------------
  密码强度策略      8 位以上 + 大小写 + 数字          P1
  登录失败锁定      Redis 计数，5 次锁定 15 分钟      P1
  密码修改后失效    删除该用户所有 refreshToken       P1
  JWT secret 强度   至少 32 字节 + 环境变量 + 轮换    P1
  HTTPS             生产必须（否则 token 明文传输）   P0
  敏感操作二次验证  改密码/删账号要重新验证           P2
  登录日志审计      记录 IP、时间、设备、结果         P2
  ------------------------------------------------------------------

【★ 登录失败锁定的副作用】
  攻击者可以用别人的用户名故意输错密码，把别人锁死（拒绝服务）。
  更完善的方案：
    · 按 IP + 用户名组合计数
    · 或用验证码代替硬锁定
    · 或锁定后允许通过邮箱/短信解锁

【★ 改密码后让所有 token 失效】
  方案一：删除该用户所有 refreshToken（需要反向索引 userId → token）
  方案二：★ 在 JWT 里加 pwdVersion 字段，用户表也存一个密码版本号。
          改密码时版本号 +1，校验时比对。
          优点：不用维护黑名单，天然支持"改密码后所有 token 失效"。

【★ 判断 JWT secret 强度】
  HMAC-SHA256 要求密钥至少 256 bit（32 字节）。
  太短 jjwt 会直接抛异常。
  生成方式：openssl rand -base64 32


################################################################################
  六、安全响应头
################################################################################

  ------------------------------------------------------------------
  响应头                            作用
  ------------------------------------------------------------------
  X-Content-Type-Options: nosniff  禁止浏览器猜测 MIME 类型
  X-Frame-Options: DENY            禁止被 iframe 嵌套（防点击劫持）
  Strict-Transport-Security        强制 HTTPS（HSTS）
  Content-Security-Policy          限制资源加载来源（防 XSS）
  Referrer-Policy: no-referrer     控制 Referer 泄露
  Permissions-Policy               限制浏览器特性（摄像头、定位等）
  ------------------------------------------------------------------

  ★ 一般在 Nginx 层统一配置，而不是在每个服务里配。

  七、OWASP Top 10（2021）
################################################################################

  ------------------------------------------------------------------
  排名    风险                                典型场景
  ------------------------------------------------------------------
  A01     权限控制失效（越权）                URL 直接改 ID 访问别人数据
  A02     加密机制失效                        密码明文、敏感数据传输不加密
  A03     注入（SQL / NoSQL / 命令注入）      字符串拼接 SQL
  A04     不安全设计                          业务逻辑漏洞
  A05     安全配置错误                        默认密码、暴露管理端点
  A06     使用含漏洞的组件                    第三方库有 CVE
  A07     身份认证失效                        弱密码、无失败锁定
  A08     软件和数据完整性失效                不安全的反序列化
  A09     安全日志和监控失效                  被攻击了不知道
  A10     服务端请求伪造 SSRF                 通过 URL 参数探测内网
  ------------------------------------------------------------------

  ★ 面试能说出前 3-5 个即可，最好结合自己的项目讲：
    "我对照检查过，注入这块因为用参数化查询是安全的，
     但权限控制和敏感信息保护还有改进空间。"


################################################################################
  八、安全自查清单
################################################################################

  【文件上传】
  □ 传一个 .html 改名成 .png 能传上去吗？
  □ 传一个假图片（内容不是图片）能传上去吗？
  □ 传超大文件，返回的是友好提示还是 500？
  □ 文件名里带 ../ 能穿越目录吗？
  □ 上传目录可以匿名访问吗？访问时是按什么类型渲染的？

  【认证授权】
  □ 不带 token 访问受保护接口 → 401？
  □ 普通用户调管理员接口 → 403？
  □ 登出后旧 accessToken 还能用吗？
  □ 登出后旧 refreshToken 还能换新 token 吗？
  □ 用伪造签名的 JWT 能通过吗？
  □ 改密码后其他设备的 token 失效了吗？

  【敏感信息】
  □ 接口返回里有 passwordHash 吗？
  □ Redis 里有敏感字段吗？
  □ 日志里有密码或完整 token 吗？
  □ 异常信息里有没有暴露表名 / SQL？
  □ 生产环境的 Actuator 端点有没有暴露 env / heapdump？

  【越权】
  □ 用 A 用户的 token 能操作 B 用户的数据吗？
  □ 所有涉及"我的数据"的接口都带了 userId 条件吗？

  【其他】
  □ CORS 白名单是精确配置的还是 *？
  □ 生产环境关了接口文档和 SQL 打印吗？
  □ 依赖库有没有已知漏洞？


################################################################################
  面试会怎么问
################################################################################

  Q1：你的项目做过哪些安全防护？
  A： ★ 结合真实做过的讲：
     "认证上，密码用 BCrypt 加密存储，登录接口做了限流防暴力破解，
     错误提示统一成'用户名或密码错误'防止账号枚举。
     权限上，用注解 + 拦截器做 RBAC，
     涉及数据归属的接口会校验，防止水平越权。
     文件上传上，做了路径穿越校验和 UUID 重命名。
     配置上，数据库密码和密钥都走环境变量，
     生产环境关闭接口文档和 SQL 打印。"

  Q2：文件上传怎么做安全校验？
  A： ★ 五重：文件大小、扩展名白名单、Content-Type、
     文件头 magic number、路径穿越校验，再加 UUID 重命名。
     ★ 必须强调："只校验 Content-Type 是不够的，客户端可以伪造。"

  Q3：什么是水平越权和垂直越权？怎么防？
  A： 垂直 = 低权限访问高权限接口（防法：注解 + 拦截器检查角色）
     水平 = 访问别人的数据（防法：把 userId 作为 SQL 查询条件）
     ★ 加分："更彻底的防法是不要先查后判，
       直接把 userId 写进查询条件，天然防越权。"

  Q4：为什么你的项目关闭了 CSRF？
  A： ★ 因为用的是 JWT 而不是 Cookie。
     Cookie 会被浏览器自动携带，所以需要 CSRF 防护；
     JWT 存在 localStorage，需要 JS 手动加到 Header，
     攻击者的网站读不到，CSRF 天然不成立。
     ★ 但如果改成 Cookie 存 token，就必须重新开启。

  Q5：XSS 怎么防？
  A： 输入过滤 + 输出编码。Vue/React 的 {{ }} 默认 HTML 转义，
     只要不用 v-html 就是安全的。
     富文本场景要用 jsoup 做白名单过滤。
     ★ 另外文件上传也要防（传 HTML 上去被当页面渲染）。

  Q6：用 ORM 还会有 SQL 注入吗？
  A： 不会。ORM 全部走 PreparedStatement 参数化查询。
     唯一要小心的是动态排序字段（无法参数化），需要白名单校验。
     手写 @Query 时也要用 :param 而不是字符串拼接。

  Q7：听说过 OWASP Top 10 吗？
  A： 能说出前 3-5 个：权限控制失效、加密机制失效、注入。
     ★ 然后结合自己项目说："我对照检查过，
       注入这块因为用参数化查询是安全的，
       但权限控制和敏感信息保护还有改进空间。"

  Q8：怎么防止密码被撞库？
  A： ① 密码用 BCrypt 加盐哈希（拖库后也难破解）
     ② 登录限流 + 失败次数锁定
     ③ 检测异常登录（异地、新设备）
     ④ 敏感操作二次验证
