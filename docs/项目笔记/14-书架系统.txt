     ★ 教训：**假阳性判据** —— 光看一眼、"应该加了吧"、只搜关键词，

       **制造一个必定失败的场景，看它会不会失败**。

     ★★ 更值钱的第二个教训（2026-10-10 补）：
       核查时我给的判据本身写错了 —— 我写"期望 1"，
       但 information_schema.statistics 是**一个索引的每列各占一行**，
       两列的 UK 产生 **2 行**。实测 COUNT(*)=2，COUNT(DISTINCT index_name)=1。
       ⇒ 按错判据验，**修好了也会被读成没修好**（假阴性）。
       正确写法：COUNT(DISTINCT index_name) = 1
       ⇒ 判据的两个方向都会骗你：假阳性让你以为修好了，
         假阴性让你去"修"一个已经正确的东西。

################################################################################
  三、★ 本轮踩过的坑（9 条，按发现顺序）
################################################################################

  ★ 全部是"能编译 / 能跑 / 但功能不生效或语义错"的类型 ——
    和项目里以前那个 @RequestParam vs @PathVariable 是**同一个病**。

  1. `@RequestBody @Valid Integer novelId` 不能直接反序列化成 Integer
     → 请求体 {"novelId": 123} 是个对象，不是整数。必须建 DTO。

  2. Controller 路径写了 /bookshelfs（复数），设计文档是 /bookshelf（单数）
     → 项目现有 /users /novels /upload 混着单复数，**按设计文档来**。
     ✅ 2026-10-10 已改：@RequestMapping("/bookshelf") 单数

  3. Service 方法漏了 @Transactional
     → 项目编码约定：所有写操作必须加。

  4. System.out.println("已在书架中")
     → 应改成 log.info，保持和现有服务类一致。

  5. ★ 复活分支漏了 createTime 重置（决策点 ②）
     → 后果：复活后按 create_time 排序会排最后，用户以为系统出 bug。

  6. 书架列表第一版漏了 userId 过滤 → 会查出所有用户的书架（越权）
  7. 书架列表第一版漏了 deleted=0 过滤 → 已移出的书也会出现

  8. `@Valid` 加在 `@RequestParam Integer page` 上
     → Integer 自己没有任何字段可校验，@Valid 什么也不做。
       真正校验范围要用 @Validated + @Min/@Max。

  9. ★★ Converter 忘加 @Component
     → 编译通过、启动不报错，但 Spring 根本不知道它存在。
       枚举转换还是走默认的 Enum.valueOf，大小写敏感、非法值 400。

  10. ★★（2026-10-10）导出 schema.sql 用了 PowerShell 的 > 重定向
     → **PowerShell 的 > / >> 默认写 UTF-16LE**，导出来的 .sql 是
       UTF-16 + BOM + CRLF，MySQL 客户端一读就报：
         "ASCII '\0' appeared in the statement, but this is not allowed
          unless option --binary-mode is enabled"
     → 后果：docker 首次建库执行失败 → app 撞 validate 起不来。
     → 这个坑**最阴的地方是判据会骗你**：
         grep -c "CREATE TABLE" 返回 **0**，看起来像"表根本没导进去"，
         实际内容是完整的 4 张表，只是编码不对。
       ⇒ **先 file 看编码，再看内容** —— 顺序反了会误诊。
     → 根因：Windows PowerShell 5.1 的历史包袱，不是 UTF-8。
     → 修法：用 mysqldump 的 --result-file=（让 dump 自己写文件），
             或 PowerShell 里显式 Out-File -Encoding utf8。
     ★ 三个回合的死法（拼接 → 缺表 → 编码），症状**一模一样**：
       都是"down -v 之后 app 起不来"。见问题清单 问题 20。

  ------------------------------------------------------------------
  【★ 贯穿性发现：这类坑的共同特征】
     · @PathVariable Integer 和 @RequestParam Integer 类型一样，编译器看不出
     · @Valid 加在不该加的地方，不报错但也不生效
     · @Component 忘加，整个类变成"死代码"
     · @Transactional 加在私有方法上，AOP 代理看不到
     · @RequireAdmin 加在 Service 上，拦截器看不到（项目已知问题）
     · @Cacheable 绕开切面手写调用，CacheErrorHandler 失效（问题 0）
     · ★ 唯一约束只在实体里声明、库里没有 —— 声明 ≠ 落地（问题 21）

    共同特征：**编译通过、能跑、不报错，但语义错 / 完全不生效。**
    应对方法：**每次写完先问一句"它怎么会被调用到？"**
    验证方法：**制造一个必定失败的场景，看判据会不会报错** ——
              这是项目"验证文化"第 3 条（假阳性判据比没有判据更危险）。

4.4 步骤 5（定时任务刷回 DB）
--------------------------------------------------------------------------------
  ✅ 完成（2026-10-10）—— task/ProgressFlushTask.java

  设计文档的三个坑全部避开：
    ✅ fixedDelay 不用 fixedRate（防任务重叠）
    ✅ SCAN 不用 KEYS（KEYS 会阻塞 Redis）
    ✅ Cursor 用 try-with-resources（它占一条 Redis 连接）
    ✅ 幂等版本号用 last_read_time，没用 update_time
    ✅ Demo2Application 已加 @EnableScheduling

  ★ 比设计多做的一处（值得记）：
    "关闭 Cursor 后再做数据库更新，避免数据库异常被外层 catch 吞掉"
    —— 设计文档没要求，是自己想到的 ✅

  ⚠ 三个小问题（见问题清单，不阻塞）：

  ① @Transactional 包住了整个 Redis 扫描（长事务）
       @Transactional(rollbackFor = Exception.class)
       public void flushProgress() {   ← 事务从这里开始，SCAN 也在里面
           ... 扫描 + 逐条解析（可能几秒到几十秒）...
           然后才做 DB 更新
       }
     · 扫描期间一直占着一条数据库连接
     · 某一条 UPDATE 抛异常 → 整轮已刷过的全部回滚，log.info 也不执行
     · ★ 原则：**事务只该包 DB 操作，不该包外部 IO**
     · 设计文档的写法里**没有** @Transactional

  ② 逐条 UPDATE，不是批量
       设计文档写"批量 UPDATE"，实现是 for 循环逐条调用。
       10 万个 key 就是 10 万次往返。
       ★ 学习项目无所谓；真要批量要用 JdbcTemplate.batchUpdate。

  ③ ZoneId.systemDefault() 和项目其他地方不一致
       日榜用的是 ZoneId.of("Asia/Shanghai")（写死），这里用 systemDefault()。
       prod 跑在 Docker 容器里，容器默认 TZ 通常是 UTC
       ⇒ 存进 last_read_time 的时间比真实时间差 8 小时。
       ★ 但**幂等不会因此出错** —— Redis 的 ts 是绝对时间戳，
         转换和比较用同一套基准，链路自洽。
         ⇒ 这是"显示不准"，不是"逻辑错"。

  ★★ 幂等 SQL（写得很准，和设计文档一字不差，还多一道保险）：
       UPDATE Bookshelf b SET b.lastReadChapterId = :chapterId,
              b.lastReadTime = :readTime, b.updateTime = :now
        WHERE b.userId = :userId AND b.novelId = :novelId AND b.deleted = 0
          AND (b.lastReadTime IS NULL OR b.lastReadTime < :readTime)
     · AND b.deleted = 0 是**自己加的**（设计文档没有）✅
       ⇒ 已移出的书不会被写进度
     · b.updateTime = :now 必须显式写 —— @Modifying 绕过 @PreUpdate

  【本轮学习到的关键判断】
    1. "三种排序走两条路" —— 排序列全在主表 → Sort；跨表 → 原生 SQL。
       判断标准不是"哪种更优雅"，是"排序列落在哪张表"。
    2. "显式传参 vs ThreadLocal" —— 显式传参让 Service 可单测，
       直接关联到判据 A 的"Mockito 纯单测"。
    3. "让数据库做安全检查" —— 归属校验写进 WHERE 子句
       （findByIdAndUserId / softDeleteByIds 的 userId 条件），
       比在 Java 里 if 判断更可靠。
    4. "能编译不生效" —— 一类坑的共同特征，
       验证方法：制造必失败场景，看判据会不会报错。
    5. ★ "声明 ≠ 落地" —— 实体里写了约束，不等于库里有了。
       ORM 的自动建表只管"新建表那一刻"，改已有表一律不补。
