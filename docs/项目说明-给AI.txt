################################################################################
  一、项目是什么
################################################################################

【一句话】
  基于 Spring Boot 的小说阅读平台，前后端分离。
  管理员发布小说和章节，读者浏览、搜索、阅读。

【性质】
  个人学习项目 / 简历项目。目标不是上线运营，是把 Java 后端知识点串成线。

【规模】（2026-10-10 实测核实；旧文档里的 37/2000/19/9 都是错的）
  · 后端：48 个 Java 类，2742 行代码，21 个 REST 接口
  · 前端：16 个 .vue（views 13 + components 2 + App.vue）
  · 数据库：4 张表（user / novel / chapter / bookshelf）
  · Redis：8 类 key + 2 个 Spring Cache 区域（novel / novel-null）
  · 测试：3 个测试类 12 个用例
          ⚠ 「连跑两遍全绿」是 2026-10-03 的结论，之后动过 readChapter → **必须重跑**
          ⚠ 书架系统 + 阅读进度目前**一个测试都没有**

【当前阶段】
  主体功能已完成，处于"从能跑 → 能讲"的收口阶段。

  【★ 三个必须知道的版本坑】

  1. Lombok 必须用 1.18.46（Spring Boot 4.1 管理的版本）
     × 1.18.36 及以下不支持 JDK 25，会报：
       ExceptionInInitializerError: com.sun.tools.javac.code.TypeTag :: UNKNOWN
     ★ 最佳做法：pom 里**不要写** <lombok.version>，让 Boot 的 BOM 管理
     ⚠ 现状不一致：pom.xml 第 35 行**确实写了** <lombok.version>1.18.46</lombok.version>。
       值恰好等于 BOM 管理的版本，所以目前无害；但 Boot 升级后它会把 Lombok
       钉死在 1.18.46。建议删掉这一行（annotationProcessorPaths 里的
       ${lombok.version} 仍能从 Boot 的 BOM 解析到）

  2. pom 里必须有 annotationProcessorPaths 配置
     JDK 23+ 默认不再自动运行 classpath 上的注解处理器，
     不配的话 Lombok 完全不生效，报一堆"找不到符号 getXxx()"
     ★ 本项目已配 ✅

  3. 本机 JAVA_HOME 必须指向 JDK 25
     ★ Windows 环境变量改动不会传播到已运行的进程，改完要重启终端 / IDEA


################################################################################
  三、关键设计决策（★ 改动前必读，这些是有意为之的）
################################################################################

--------------------------------------------------------------------------------
决策 1：Novel 和 Chapter 用 novelId 手动关联，不用 @OneToMany
--------------------------------------------------------------------------------
  【做法】Chapter 里就一个普通字段 `private Integer novelId;`
  【为什么】用 @OneToMany 的话，查小说时会把所有章节的正文一起加载出来 ——
            一本 500 章的小说正文可能几十 MB
  【代价】失去级联便利，删除小说要手写 chapterRepository.deleteByNovelId(id)
  【改的时候注意】不要"顺手"改成关联注解，会引发性能问题

--------------------------------------------------------------------------------
决策 2：novel.totalWords 是冗余字段
--------------------------------------------------------------------------------
  【做法】总字数单独存一列，而不是每次 SUM(chapter.word_count)
  【为什么】小说列表是最高频接口，实时算要 JOIN + 聚合
  【★ 代价】三个地方必须同步维护，漏一处就数据不一致：
            · addChapter    → totalWords += wordCount
            · updateChapter → totalWords += (新字数 - 旧字数)
            · deleteChapter → totalWords -= wordCount
  【改的时候注意】任何改变章节字数的操作，都要同步改 totalWords

--------------------------------------------------------------------------------
决策 3：Token 黑名单用 Redis Hash，不用 Set
--------------------------------------------------------------------------------
  【结构】blacklist:user:{userId}  →  Hash{ token: 过期时间戳 }
  【为什么不用 Set】Set 只存 token，没存过期时间，不知道何时能清理
  【清理机制】读取时惰性清理过期的 field
  【★ 遗留问题】整个 Hash key 没有兜底 TTL，用户登出后不再访问就永久驻留

--------------------------------------------------------------------------------
决策 4：Refresh Token 做双向索引
--------------------------------------------------------------------------------
  【正向】refresh_token:{token} → userId   用途：刷新时查是哪个用户
  【反向】user_refresh:{userId} → token    用途：登出时查要删哪个 token
  【为什么】两个方向都会用到，只存单向登出就删不掉 Refresh Token
  【★ 遗留问题】String 结构只存一个 token，**多设备登录会互相覆盖**（问题 9）

--------------------------------------------------------------------------------
决策 5：搜索/筛选用 Specification，不用方法名推导
--------------------------------------------------------------------------------
  【做法】NovelSpecifications 里每个条件一个静态方法，
          条件为空返回 null（Spring Data 自动忽略）
  【为什么】3 个可选条件用方法名推导要写 2³ = 8 个方法
  【★ 参数顺序】Controller → Service → Specifications 三处必须一致：
                page, size, category, status, keyword

--------------------------------------------------------------------------------
决策 6：索引用 @Table(indexes=...) 声明，不手写 SQL
--------------------------------------------------------------------------------
  【做法】实体类上 @Table(name="novel", indexes = {@Index(...)})
  【为什么】索引定义跟代码走，换机器 / 重建表会自动创建
  【注意】columnList 写 **Java 属性名**（如 lastUpdateTime），
          Hibernate 会自动翻译成列名（last_update_time）
  【★★ 边界：只管"新建表"，不管"改已有表"】（2026-10-08 实测）
    ddl-auto=update **建新表时会带上约束，但不会给已存在的表补约束**。
    ⇒ 实体里写了 ≠ 库里有了。bookshelf 的唯一约束就是这么丢的（问题 21）。
    ⇒ 表已经在库里时要改结构，只能手工 ALTER（或上 Flyway）。
    ★ 所以别把"实体里声明了"当成"索引/约束已落地"的判据 ——
      验证永远要去库里查（SHOW INDEX），或者更硬：制造场景看它会不会失败。

--------------------------------------------------------------------------------
决策 7：缓存降级 —— ★ 本项目最有价值的一次事故（2026-10-06）
--------------------------------------------------------------------------------
  【做法】CacheConfig 实现 CachingConfigurer，自定义 errorHandler；
          Redis 超时配 500ms（★ timeout 和 connect-timeout 都要配，
          前者管命令等待响应，后者管建立 TCP 连接）
  【为什么】@Cacheable 让 Redis 从"可选依赖"变成"强依赖"，Redis 一挂详情页打不开
  【★ 局限】CacheErrorHandler 只保护 @Cacheable/@CacheEvict 注解，
            **保护不了手写调用**（cacheManager.getCache() / stringRedisTemplate）
            ⇒ 手写的地方必须自己 try-catch
  【★ 一句话总结】**"注解生效" = "框架的切面拦住了你"**。
     绕开切面（改手写 API），切面提供的所有附加能力都会消失。
     推广（AOP 通用规律）：
       @Cacheable     → CacheInterceptor       → 丢失：缓存降级
       @Transactional → TransactionInterceptor → 丢失：事务回滚、传播
       @RateLimit     → RateLimitAspect        → 丢失：限流计数
       @RequireAdmin  → LoginInterceptor       → 丢失：权限校验

  ── 三阶段实测（★ 简历素材，判据一律看 body.code 不看 HTTP 状态码）──
     ------------------------------------------------------------------
     阶段                  耗时        HTTP   body.code   接口可用性
     ------------------------------------------------------------------
     ① 改造前（60s 超时）  60.0s 挂起  200    500         ❌ 打不开
     ② 只加超时配置        0.51s       200    500         ❌ 打不开
     ③ 再加 try-catch      1.01s       200    200         ✅ 有数据
     ------------------------------------------------------------------
     ★ ②→③ 才是真正的修复：② 只是 fail fast，③ 才是优雅降级。
       只做 ② 的话，用户体感是"从一直转圈变成立刻报错"，**还是不可用**。
     并发压测（500 请求 / 100 并发 / Redis 挂）：
       /novels/1    ：P50 1.491s，P95 2.575s，0 个超 5 秒
       /novels 列表 ：P50 0.248s，全程 200（不依赖 Redis，未被拖垮）
       ⇒ 级联故障被切断

  ── ★★ 两条通用教训（比事故本身值钱）──
     ① **挂起（hang）几乎总比报错（fail fast）更危险** ——
        挂起会占着 Tomcat 线程并向上游传播，报错可以被隔离。
     ② **判据本身也要验证** —— 旧判据"HTTP 200 = 降级有效"是错的，
        因为 RuntimeException 也返回 200，会把失败读成成功（假阳性）。

  ★ 完整复盘（Lettuce 断连会缓冲写命令的实验、根因推导、修复方案）
    → docs/实战笔记/05-缓存三大问题实战.txt 第四节

--------------------------------------------------------------------------------
决策 8：LoginInterceptor 三态设计
--------------------------------------------------------------------------------
  【第一态】OPTIONS 预检请求 → 直接放行
  【第二态】游客路径（GET + 路径以 /novels 开头）→ 宽松，有 token 就解析
  【第三态】其他所有路径 → 严格，无 token / 解析失败 / 在黑名单 → 401
  【★ 权限检查也在拦截器里】它比过滤器多一个能力：能拿到 HandlerMethod，
                            所以能读方法上的 @RequireAdmin 注解

--------------------------------------------------------------------------------
决策 9：@RequireAdmin 加在 Controller 方法上，不是 Service 上
--------------------------------------------------------------------------------
  【★ 重要】拦截器检查的是 HandlerMethod（Controller 方法），
            Service 方法上的注解它**看不到**。
            所以 Service 层加 @RequireAdmin 是无效的装饰品。

--------------------------------------------------------------------------------
决策 10：空值缓存防穿透 + 缓存三件套（2026-10-05 ~ 10-07 完成）
--------------------------------------------------------------------------------
  【要解决的问题】查一个不存在的 id（如 /novels/999999）时缓存永不命中，
                  每次请求都打到数据库 —— 这就是**缓存穿透**。

  【做法】用独立的缓存区域 novel-null 存"查过、但确实没有"的标记：
    · CacheConfig 里给 novel-null 单独设 **5 分钟** TTL
    · findDetail 改成三分支判断：
        ① 命中 novel-null → 直接抛"小说不存在"，不查库
        ② 命中 novel      → 直接返回
        ③ 都没命中        → 查库；库中也没有就写 novel-null 再抛异常
    · addNovel 上加 @CacheEvict(value = "novel-null", key = "#result.id")
        ★ 为什么需要这一手：空表时查过 /novels/1 会被缓存成 null，
          而新增的第一本小说正好拿到 id=1 —— 不清就会 5 分钟内显示"不存在"

  【为什么用独立区域，不混在 novel 里】
    空值和真实数据的生命周期完全不同：真实小说缓存 30 分钟，
    空值只该缓存几分钟（万一数据后来又真的出现了）。

  【★ 三件套完成情况（2026-10-07）】
    · 雪崩（大量 key 同时过期）→ TTL 随机抖动 ✓
      CacheConfig 的 TtlFunction（每次 put 求值），1500~2100 秒
    · 击穿（热点 key 失效瞬间，并发请求同时打 DB）→ 本地互斥锁 ✓
      findDetail：ConcurrentHashMap<Integer,Object> + synchronized + 双重检查
      ★ 遗留：① locks 只增不减（无界增长，内存泄漏隐患）
              ② 这是**单机锁**，多实例部署时每个 JVM 仍各查一次库
    详见 docs/项目笔记/05-缓存体系.txt


################################################################################
  四、编码约定（改代码时请遵守）
################################################################################

  【分层】
    · Controller 不碰数据库，Service 不感知 HTTP
    · 上层可以调下层，下层绝不能调上层
    · 依赖接口（INovelService）而不是实现

  【事务】
    · 所有写操作加 @Transactional(rollbackFor = Exception.class)
    · 查询方法加 @Transactional(readOnly = true)
    · ★ 同类内部方法调用会让 @Transactional 失效（AOP 代理问题）

  【参数校验】
    · DTO 上加 @NotBlank / @Size 等注解
    · Controller 参数上加 @Valid ← ★ 很容易漏！漏了校验完全不生效

  【权限】
    · 管理接口加 @RequireAdmin（★ 加在 Controller 方法上）
    · 涉及数据归属的接口要校验（如 deleteChapter 校验 chapter.novelId）

  【异常】
    · 业务异常抛 BusinessException（全局处理器返回 warn 级别）
    · 系统异常让全局兜底（error 级别带堆栈）

  【注释风格】
    · 中文注释
    · 类头写作者和日期：
        /**
         * 夏辰义
         * 2026/8/26 18:02
         */
    · 用 ========== 分隔大段逻辑

  【命名】
    · 类：大驼峰；方法/变量：小驼峰；包：全小写
    · Service 实现类命名是 NovelServiceIml（★ 注意是 Iml 不是 Impl，历史遗留）

  □ 不要提交 application-*.properties 里的真实密码

  【★★ 三条元教训（★ 这区最值钱的东西，"问题清单"里只有分散个案，综述只在这）】
    ① **判据本身也要验证 —— 两个方向都会骗你**：
       假阳性（HTTP 200 ≠ body.code=200）、
       假阴性（COUNT(*) ≠ COUNT(DISTINCT index_name)，
               会让"已经修好"被读成"没修好"）
    ② **"不报错" ≠ "正确"** —— 唯一约束缺失、建表脚本缺表、兜底缺失，
       这三样**一个都不报错**，但功能是坏的
    ③ **同一个状态存在两个地方时，两处的失效逻辑必须对齐** ——
       缓存降级 / 唯一约束 / 阅读进度，都是同一个病
