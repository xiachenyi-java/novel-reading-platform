【这份文件是什么】
  从《docs/系统提示词-给AI.txt》拆出的**两节流程性规则**。

  ★ 拆出理由：系统提示词的每一个字**每轮对话都在付费**，
    而这两节只在"改完代码"和"写完回答"这两个时刻才会用到。
    搬出来后提示词本体省下约 22%，**规则内容一字未减**。

【怎么用】
  系统提示词里保留了两行**触发指针 + 红线摘要**，命中就回来读对应章节：
    · 改完代码                → §一 文档同步授权
    · 抛面试题 / 末尾带小贴士 → §二 面试题库归档机制
  ★ 指针里的红线摘要足以兜底；本章节是**展开的执行细节**。

【★ 注意性质】
  这两节是**行为规则**（"AI 该怎么干活"），不是"现状描述"。
  ⇒ 不要拿"以代码为准"去改它们。判断标准永远是：
     这句话在说「现在是什么样」（状态/进度/事实）→ 才以代码为准
     这句话在说「应该是什么样」（规则/待办/缺陷）→ 一律不动


################################################################################
  一、文档同步授权（★ 代码与文档冲突时，以代码为准改文档）
################################################################################

## 边界
- ✅ 改**文档**：文档陈述与代码不符 → 直接改，不用问。
- ❌ 改**代码**：红线不变 —— 先说意图、列方案、等确认。
  ★ 发现代码有问题 → 「记进问题清单 + 报告他」，**不是**顺手改代码。

## ★ 三种冲突，三种处理（② 最容易搞错）
  ① 文档陈述的是「现状」，代码已变            → 文档过期   → ✅ 改文档
  ② 文档登记的是「缺陷/待办」，代码确实有该缺陷 → 不算冲突   → ⛔ 不动
  ③ 代码违反了文档的「关键设计决策」          → 代码有 bug → ⚠️ 报告，也不改文档

  ★★ ② 的反例（禁止，这叫**假同步**，比不同步危险得多）：
     文档说「问题 4：上传只校验 Content-Type，有 XSS 风险」，
     代码里 FileController **确实**只校验了 Content-Type。
       ✗ 错误：「以代码为准」→ 改成「上传已做校验」
          → 漏洞从清单上消失，但代码里的洞还在。
       ✓ 正确：不动。这条是对的，它是一条**待办**。

  ★ 一句话判据：这句话在说「**现在是什么样**」，还是「**应该是什么样**」？
     现在是什么样（状态 / 进度 / 事实）      → 以代码为准，改文档
     应该是什么样（设计意图/待办/缺陷/目标） → 一律不动

## 可自动改的内容（只限「现在是什么样」）
  · 问题清单里的状态标记（🔴 未解决 → ✅ 已解决）
  · 进度百分比、完成度数字
  · 「某文件里写了 X」这类事实描述
  · 已删除 / 已重命名的文件、方法、注解、配置项

  ★ 可改文件只有三个：
      docs/项目说明-给AI.txt（含其参考附录）、docs/项目笔记/*.txt、
      docs/前端说明-给AI.txt
        ↑ 2026-10-14 追加（他确认）：前端任务的"现状"全在这份里，
          不放进清单的话每轮改前端都得回来问一次

## ★ 一律不碰的文档（它们是历史记录，不是现状描述）
  · docs/知识笔记/  纯原理，与代码版本无关
  · docs/实战笔记/  「我当时的做法」—— 改了就是篡改实验记录
  · docs/面试题库/  已归档的答案
  · 各文件末尾的「完成度记录」表格（日期 + 变动）—— 那是流水账

## 留痕（★ 不许静默覆盖）
  每次改完，在回复里单独报告一行：
    📄 文档同步：<文件名> → <改了什么>
  改动必须走 git diff 可查。

## 存疑就停
  拿不准这是「现状陈述」还是「缺陷登记」→ **不改，先问**。
  问一句的成本，远低于把一条待办悄悄删掉。


################################################################################
  二、面试题库归档机制（★ 自动执行，不用问）
################################################################################

## 触发条件（满足任一即归档）
1. 他直接抛出一道面试题（"这题怎么答""面试官会怎么问"）
2. 他要求模拟面试 / 追问
3. 回答末尾的「🎓 面试小贴士」已经形成完整可答题
4. 做完实验、修完 bug 后自然浮现的考点

★ 只是顺嘴提一句、不成题的，不归档。宁缺毋滥。

## 分类规则（防污染）
1. 先 ls docs/面试题库/，**复用现有分类文件**
2. 现有分类都装不下的，先问一句：
   "这题建议新建 0X-xxx.txt，可以吗？" —— 禁止凭印象直接建
3. 归档时额外打一个短板标签（方便以后按标签集中刷）：
   【并发】线程池 / 锁 / 原子性 / 竞态
   【测试】验证方法论 / 压测 / 回归 / 单测
   【JVM】 内存 / GC / 类加载 / 调优     ← 目前 0 题，最需要补
   【其他】不属于上面三类的

## 每题固定格式（★ 与现有题目保持一致，别自创）
  · 用项目统一的「===== 横幅」分隔题目，**不要用 markdown 的 ###** ——
    全部文档都是 .txt，纯文本下 ### 没有视觉层级，和其余文档也不统一。
  · 标签写在题目行末尾（四类之一，见上）。
  · 六个字段：
      **考点**        这题在考什么**能力**（不是"考什么知识"）
      **追问链**      Q1「…」→ Q2「…」→ Q3「…」（面试官怎么一层层往下挖）
      **参考答案**    怎么组织语言
      **本项目的证据** 具体文件 / 实测数据 / 故障演练结论   ★ 最值钱
      **坑**          容易答错的地方
      **关联**        docs/知识笔记/xxx

## 去重
  写入前先搜题库关键词。已有同题 → **不新建**，
  改为在原题下补「追问链」或「项目证据」。

## 与红线的关系（★ 划清边界）
- 新建条目 / 追加新题：**默认执行，不用问**（他明确授权的）
- 修改、删除、重排已有条目：**必须先问**
- 每次写完回报一句：「已归档到 docs/面试题库/0X-xxx.txt → 第 N 节」
