################################################################################
  9.1 三层 / 四层架构
################################################################################

  Spring Boot 的三层架构是一种经典的分层设计模式，
  将应用按职责划分为三个独立层次，实现关注点分离和解耦。

【1. 表现层（Controller）】
  职责：接收和响应 HTTP 请求，处理用户交互
    · 用 @RestController 定义接口
    · 负责参数校验、数据转换（DTO ↔ Entity）
    · 调用 Service，不直接操作数据库
    · 返回统一的响应格式

  @RestController
  @RequestMapping("/users")
  public class UserController {
      private final UserService userService;      // 依赖接口

      @GetMapping("/{id}")
      public Result<UserVO> getUser(@PathVariable Long id) {
          return Result.success(userService.findById(id));
      }
  }

【2. 业务层（Service）】
  职责：封装核心业务逻辑，协调各组件完成业务流程
    · 用 @Service 标注
    · 事务控制（@Transactional）
    · 业务规则校验、复杂计算、流程编排
    · 调用 Repository 进行数据持久化
    · 不处理 HTTP，也不直接操作数据库连接

  @Service
  @RequiredArgsConstructor
  public class UserServiceImpl implements UserService {
      private final UserMapper userMapper;

      @Override
      @Transactional
      public UserVO findById(Long id) {
          User user = userMapper.selectById(id);
          return convertToVO(user);
      }
  }

【3. 数据访问层（DAO / Mapper / Repository）】
  职责：负责与数据库交互，执行 CRUD
    · @Mapper（MyBatis）或继承 JpaRepository（JPA）或 @Repository
    · 只关注 SQL，不含业务判断
    · 返回原始实体

  @Mapper
  public interface UserMapper {
      User selectById(Long id);
      int insert(User user);
  }

【调用关系】
  用户请求
      ↓
  Controller（表现层）   ← 接收请求、返回结果
      ↓
  Service（业务层）      ← 处理业务逻辑、事务
      ↓
  Mapper/DAO（数据层）   ← 执行 SQL、操作数据库
      ↓
  数据库

【分层的好处】
  ------------------------------------------------------------------
  优势        说明
  ------------------------------------------------------------------
  职责清晰    每层只关心自己的任务
  易于维护    修改数据库实现不影响上层业务
  方便测试    可单独对 Service 做单元测试，Mock 数据层
  可替换性    从 MyBatis 换为 JPA，只需改动数据层
  团队协作    前后端、各层可并行开发
  ------------------------------------------------------------------

【★ 两条铁律】
  1. Controller 不碰数据库，Service 不感知 HTTP
  2. 上层可以调下层，下层绝对不允许调上层

【四层版本】
  有些项目会把"模型层"单独提出来，变成四层：
    Controller：接收/返回 DTO/VO
    Service：处理业务，操作 Entity
    Mapper/DAO：持久化 Entity
    Model/Entity：数据实体定义

  核心思想不变：上层依赖下层，通过接口和依赖注入解耦。


################################################################################
  9.2 面向对象与依赖注入
################################################################################

【为什么 Controller 不能直接 new Service()】
  Service 里需要 Repository，
  而 Repository 是框架自动生成的代理对象
  （封装了数据库连接、事务、SQL 生成）。
  自己 new 出来的 Service，里面的 repository 是 null，一调用就空指针。

  ★ 框架的本质：一个"高级工厂"。
    你告诉它"我要这个对象"，它把已经配置好依赖关系的对象塞给你。
    这叫控制反转（IoC）—— 对象的创建权从你手里反转到了容器手里。

【依赖注入的三种方式】
  ------------------------------------------------------------------
  方式        写法                          推荐度
  ------------------------------------------------------------------
  字段注入    @Autowired private Xxx x;     ✗ 无法 final、难测试
  构造器注入  private final Xxx x; + 构造器 ★ 推荐
  Setter注入  @Autowired setter             △ 可选依赖时用
  ------------------------------------------------------------------

  ★ 构造器注入的好处：
    · 字段可以是 final（不可变，天然线程安全）
    · 依赖关系一目了然
    · 单元测试时可以直接 new，不需要容器
    · 循环依赖时启动就会报错，早暴露问题

【为什么 Entity 叫"实体"而不叫"数据库表"】
  因为 Novel 这个类不代表数据库表本身，
  它代表"一本小说这个业务概念"。只是 ORM 把它映射到了表上。

  解耦的意义：
    数据库表名叫 t_novel，但 Entity 类名叫 Novel
    数据库字段叫 create_time，但 Entity 字段叫 createdAt
    → 代码里的名字跟着业务走，数据库里的名字跟着 DBA 规范走


################################################################################
  9.3 Repository 的本质
################################################################################

  ------------------------------------------------------------------
  表面看    它是一个接口，只有方法签名，没有具体代码
  实际上    框架在启动时自动生成了实现类
            （你从来没见过，但它真实存在）
  本质上    它是你和数据库之间的"翻译官"
  ------------------------------------------------------------------

【★ save() 如何判断是 INSERT 还是 UPDATE】
  ------------------------------------------------------------------
  情况        save() 做什么       生成的 SQL
  ------------------------------------------------------------------
  id == null  认为是新数据        INSERT INTO novel (...) VALUES (...)
  id != null  认为是已有数据      UPDATE novel SET ... WHERE id = ?
  ------------------------------------------------------------------

  完整链路：
    你调用 save(novel)
        ↓
    自动生成的实现类接手
        ↓
    Hibernate 检查：novel.getId() 有值 → 更新操作
        ↓
    生成 SQL：UPDATE novel SET title='...' WHERE id=5
        ↓
    通过 JDBC 发送给 MySQL
        ↓
    MySQL 执行更新
        ↓
    返回给你：更新成功

【JPA 的三种查询方式】
  ------------------------------------------------------------------
  方式              例子                                    适用
  ------------------------------------------------------------------
  继承自带          save() / findById() / findAll()         基础 CRUD
  方法名推导        findByNovelIdOrderByChapterNumberAsc()  简单条件
  自定义 @Query     @Query("SELECT ...")                    复杂查询
  ------------------------------------------------------------------

  【★ 方法名推导的关键词】
    findBy / readBy / getBy / queryBy   查询
    And / Or                            条件组合
    Containing / Like                   LIKE
    GreaterThan / LessThan              >
    Between                             BETWEEN
    In                                  IN
    OrderByXxxAsc / Desc                排序
    countBy / deleteBy / existsBy       其他操作

【★ 一个必知的坑：@RequestParam 不传参数会怎样】

  情况1：写了 @RequestParam，前端不传
    抛异常 → HTTP 400 Bad Request

  情况2：不写 @RequestParam，前端不传
    不报错，参数变成 null → 继续执行 → 可能空指针或存进数据库

  ★ 为什么是 400 而不是 500？
    HTTP 协议规定：
      400 = 客户端请求有语法错误或参数缺失（客户端的锅）
      500 = 服务器内部错误（后端的锅）

  【可选参数的写法】
    @RequestParam(required = false) String keyword
    @RequestParam(defaultValue = "1") int page       ← 常用


################################################################################
  9.5 七个"为什么"
################################################################################

  【问题1：为什么 Controller 不能直接 new Service？】
    见 9.2。核心是 IoC —— 依赖对象由容器创建并注入。

  【问题2：为什么 Service 不能反过来调 Controller？】
    如果厨师想通知顾客，他不能冲出厨房直接找顾客，
    必须让服务员去传话。

    分层铁律：上层可以调下层，下层绝对不允许调上层。
    否则层与层之间缠成一团，改一个地方全崩。

  【问题3：为什么 Entity 叫"实体"？】
    见 9.2 末尾。核心是"代码名字跟业务走，数据库名字跟 DBA 规范走"。

  【问题4：为什么 Result.success() 要写成 static？】
    static 表示这个方法属于"Result 这个概念"，
    不属于"某一个 Result 对象"。

    好处：
      · 不用先 new 一个空对象
      · 强制规范：外部无法乱填 code，只能通过工厂方法
      · 命名即意图：Result.success(...) 读出来就是"我要一个成功的结果"

  【问题5：为什么用 @RestControllerAdvice 而不是 @ControllerAdvice？】
    @ControllerAdvice：默认返回页面（HTML），适合传统 MVC
    @RestControllerAdvice：默认返回 JSON，适合前后端分离

    用错的话，前端会收到一堆 HTML 标签而不是 {"code":500...}，解析直接报错。

  【问题6：ArithmeticException（1/0）会被兜底处理器捕获吗？】
    ★ 会！
    ArithmeticException 继承自 RuntimeException，
    所以会被 @ExceptionHandler(RuntimeException.class) 捕获。

    同理：NullPointerException、ArrayIndexOutOfBoundsException、
          ClassCastException、IllegalArgumentException 都是它的子类。

    但编译时异常（IOException、SQLException）抓不到，需要单独声明。

  【问题7：为什么校验放在 Controller 而不是 Service？】
    理由1：越早拦截越好
      空书名在 Controller 就被拦住，根本不用进 Service、不用查数据库。
      放在 Service 意味着代码跑了一大半才发现参数有问题。
    理由2：分层职责
      Controller：格式校验（非空、长度、格式）
      Service：业务校验（是否存在、库存够不够、余额足不足）

    否则 Service 会被一堆 if (xxx == null) 淹没，业务逻辑看不清。


################################################################################
  9.6 前后端交互
################################################################################

【★ 前端分页 vs 后端分页】
  ------------------------------------------------------------------
  对比项              前端分页                后端分页
  ------------------------------------------------------------------
  后端查多少数据      全部（100 条甚至 10 万）只查当前页
  网络传输量          巨大                    极小
  后端内存压力        大                      小
  前端内存压力        巨大                    几乎没有
  前端渲染压力        巨大                    几乎没有
  翻页体验            快（本地切数组）        稍慢（要发请求）
  ------------------------------------------------------------------

  ★ 结论：不是"谁更好"，而是"数据量大了前端分页根本不可用"。

【★★ 前端筛选 vs 后端筛选（比前端分页更隐蔽的坑）】

  前端分页至少"看起来"是对的（数据都在本地，切页没问题）。
  但"前端筛选 + 后端分页"这个组合，会产生**三个具体错误**：

  ------------------------------------------------------------------
  问题              表现                              原因
  ------------------------------------------------------------------
  1. 数据缺失       选"玄幻"可能一条都不显示，       只筛了当前页
                    但库里其实有 200 本               的 8 条
  ------------------------------------------------------------------
  2. total 撒谎     显示"共 100000 本"，              total 用的是
                    但用户翻 3 页就没数据了           后端全库计数
  ------------------------------------------------------------------
  3. 翻页失效       翻到第 2 页，筛选条件就没了       每页重新在前端
                                                      筛一次
  ------------------------------------------------------------------

  【为什么容易踩】
    因为代码"看起来"很合理：
      const res = await getList(page, size)
      let list = data.content.filter(n => n.category === selected)
    筛选逻辑确实生效了 —— 只是作用在**错误的数据集**上。

  【正确做法】
    筛选条件和分页参数一起传给后端，让数据库去筛：
      GET /novels?page=1&size=8&category=玄幻&keyword=剑

    后端返回的 totalElements 是"当前筛选条件的总数"，
    翻页时条件保持不变。

  【★ 一个判断标准】
    问自己："用户看到的总数，和实际能翻到的数据量一致吗？"
    不一致 → 筛选条件没下推到后端。

  【★ 怎么验证真的修好了】
    拿数据库的真实计数做对照：
      SELECT COUNT(*) FROM novel WHERE category = '玄幻';   -- 比如 6
      GET /novels?category=玄幻   →  totalElements 应该是 6
      GET /novels?category=玄幻&page=2  →  totalElements 仍然是 6  ★关键

    第 2 条是关键 —— 翻页后 total 不变，说明筛选条件真的保持住了。

【★ 前端搜索 10 万本书会发生什么】
  1. 网络层面
     后端返回几十 MB 的 JSON，用户等待几十秒
  2. 浏览器层面
     JS 把 10 万条加载进内存，filter 遍历 10 万次 → 页面卡死
  3. 用户体验
     输入"西"，等 30 秒才出结果

  正确做法：
    · 后端搜索：前端只传 keyword，数据库用 LIKE 查，只返回匹配的
    · 分页：即使结果有 1000 条，也分页显示

  ★ 同理：分类筛选也不能在前端做。
    如果后端只返回第 1 页的 8 条，前端在这 8 条里筛"玄幻"，
    用户就会以为"没有玄幻小说"，但数据库里其实有 200 本。

【HTTP 状态码语义】
  ------------------------------------------------------------------
  状态码    含义                    常见场景
  ------------------------------------------------------------------
  200       OK                      请求成功
  201       Created                 创建成功（RESTful 推荐）
  202       Accepted                已接受，异步处理中
  204       No Content              成功但无返回体
  301/302   重定向                  永久 / 临时
  304       Not Modified            缓存有效
  400       Bad Request             参数缺失或格式错误（客户端的锅）
  401       Unauthorized            未登录或 token 无效
  403       Forbidden               已登录但权限不足
  404       Not Found               资源不存在
  405       Method Not Allowed      方法不对
  408       Request Timeout         请求超时
  429       Too Many Requests       触发限流
  500       Internal Server Error   服务器内部错误（后端的锅）
  502       Bad Gateway             网关后面的服务挂了
  503       Service Unavailable     服务暂时不可用
  504       Gateway Timeout         网关超时
  ------------------------------------------------------------------

  【★ 401 vs 403 的区别（面试常问）】
    401 = 你没告诉我你是谁（认证失败，Authentication）
    403 = 我知道你是谁，但你没权限（授权失败，Authorization）

  【★ 400 vs 500 的区别】
    400 = 客户端的锅（参数错了）
    500 = 后端的锅（代码 bug）

【RESTful 风格约定】
  ------------------------------------------------------------------
  操作        方法        URL 示例            说明
  ------------------------------------------------------------------
  查询列表    GET         /novels             复数名词
  查询单个    GET         /novels/1           路径带 ID
  新增        POST        /novels             请求体传数据
  全量更新    PUT         /novels/1           路径带 ID + 请求体
  部分更新    PATCH       /novels/1           只传要改的字段
  删除        DELETE      /novels/1           路径带 ID
  ------------------------------------------------------------------

  【子资源嵌套】
    查小说的章节列表    GET    /novels/{id}/chapters
    查某一章            GET    /novels/{id}/chapters/{cid}
    新建章节            POST   /novels/{id}/chapters
    删除章节            DELETE /novels/{id}/chapters/{cid}

    ★ 即使章节 ID 全局唯一，路径里仍然保留 novelId，
      因为这样能表达"归属关系"，也方便做水平越权校验。

################################################################################
  面试会怎么问
################################################################################

  Q1：为什么要分层？不分层会怎样？
  A： 不分层的话，Controller 直接操作数据库，
     代码臃肿、无法复用、无法测试、改一处崩一片。
     分层的核心价值是"关注点分离"和"可替换性"。

  Q2：@RequestParam 和 @PathVariable 的区别？
  A： @RequestParam 取问号后面的参数（?page=1），
     @PathVariable 取路径里的参数（/novels/{id}）。
     @RequestParam 默认必填，不传会 400。

  Q3：为什么返回统一格式 Result？
  A： 前端只需要学一套解包流程，不用猜这次返回的是什么结构。
     成功看 data，失败看 msg。

  Q4：@ControllerAdvice 和 @RestControllerAdvice 的区别？
  A： 前者返回页面，后者返回 JSON。前后端分离用后者。

  Q5：HTTP 401 和 403 的区别？
  A： 401 是没认证（不知道你是谁），403 是没授权（知道你是谁但没权限）。

  Q6：前端分页和后端分页怎么选？
  A： 数据量小可以前端分页（翻页快），
     数据量大必须后端分页（否则网络和内存都爆炸）。

  Q7：ArithmeticException 能被 @ExceptionHandler(RuntimeException.class) 捕获吗？
  A： 能。它是 RuntimeException 的子类。
     但 IOException 这类编译时异常抓不到，需要单独声明。
