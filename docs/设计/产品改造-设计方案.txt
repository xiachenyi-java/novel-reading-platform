################################################################################
  二、★ 1000 人意味着什么（规模决定架构）
################################################################################

【这一节为什么在最前面】
  技术选型的答案，全都取决于规模。
  同一个问题，1000 人和 100 万人的答案**完全相反**。

【先把数字算清楚】

  ------------------------------------------------------------------
  指标          估算          说明
  ------------------------------------------------------------------
  注册用户      1000          上限
  日活（DAU）   50 ~ 100      个人项目，10% 已经很乐观了
  峰值并发      5 ~ 10        100 人不会同时点
  QPS           不到 10       跟一台家用电脑能扛的量级差不多
  数据量        百万行以内    书单/评论/笔记，几年也到不了千万
  ------------------------------------------------------------------

【★★ 结论：绝大部分"高大上"的技术，你都不需要】

  ------------------------------------------------------------------
  技术                      需要吗    原因
  ------------------------------------------------------------------
  单机部署（2核4G）          ✅ 够    10 QPS 用不满一个核
  单个 MySQL                 ✅ 够    百万行对 MySQL 是毛毛雨
  单个 Redis                 ✅ 够    你已经在用了
  数据库读写分离             ❌ 不要   主从延迟的复杂度 > 收益
  分库分表                   ❌ 不要   百万行分什么表
  消息队列（MQ）             ❌ 不要   没有削峰需求
  Elasticsearch              ❌ 不要   MySQL 全文索引够用
  微服务 / 服务拆分          ❌ 不要   一个人维护 8 个服务 = 灾难
  K8s / 容器编排             ❌ 不要   docker-compose 够了
  CDN                        ⚠️ 可选   静态资源多了再说
  对象存储                   ⚠️ 可选   封面/头像，本地磁盘先扛着
  ------------------------------------------------------------------

【★ 但有三件事，规模小也必须要】

  1. **备份** —— 1000 人的书单和笔记，丢了就是丢了，代码丢了能重写
  2. **监控告警** —— 你得知道服务挂了、AI 烧了多少钱
  3. **成本护栏** —— 见 7.5，规模小 ≠ 不会烧钱

【★ 一个反直觉的点：规模小 ≠ 简历价值低】

  你不能说"我做了百万级系统"（那是假的）。
  但你可以说：
    · "我做了完整的**冗余字段一致性**方案 + 定时对账"
    · "我做了**多级缓存降级**，演练过依赖服务宕机的真实行为"
    · "我做了 AI 调用的**成本模型**，把月成本从估算的 2000 元压到 77 元"

  ★ 简历上讲**深度**，不讲规模。1000 人的项目 + 讲得透 = 比"百万级"吹牛强。


################################################################################
  三、★ 三环架构：让项目能活 3 年
################################################################################

【为什么需要这一节】
  长期项目的真正死因不是"功能不够"，是**改不动了**。
  改一处崩三处 → 不敢动 → 只能往上加 → 烂尾。

  解法不是"少做功能"，是**按"能不能整块删掉"把模块分层**：

  ┌─ 内环（主干 · 永不动摇）─────────────────────────────────┐
  │  书库元数据 / 私人书房 / 书单 / 评分                        │
  │  要求：有测试 · 有事务 · 接口稳定 · 表结构慎改               │
  │  纪律：任何新功能都不许改这里的接口签名                       │
  └────────────────────────────────────────────────────────────┘
  ┌─ 中环（服务 · 可替换实现）─────────────────────────────────┐
  │  认证 / 缓存 / 限流 / 搜索 / AI网关 / 文件存储               │
  │  要求：先定义接口，实现可以整个换掉                           │
  │  例：AI 网关今天接 DeepSeek，明天接 Claude，调用方不改        │
  └────────────────────────────────────────────────────────────┘
  ┌─ 外环（实验 · 可整块删除）─────────────────────────────────┐
  │  AI读者 / AI听书 / 叙事特征 / AI分析工具                     │
  │  要求：独立目录 · 独立表 · 一个开关能关掉                     │
  └────────────────────────────────────────────────────────────┘

【★ 可证伪的架构判据】
  制造一个必定失败的场景，看判据会不会报错：

    把外环的整个目录删掉，然后跑测试

  期望：**内环测试全绿**（编译通过、测试通过）。
  如果编译不过 → 说明外环污染了主干，架构没做对。

  ★ 这个判据比"我觉得解耦了"强 100 倍，因为**它可以证伪**。
  ★ 这条建议写进项目的设计决策，当作硬性纪律。

【实现手段】
  后端：一个配置开关（如 @ConditionalOnProperty）控制外环是否加载
  前端：路由懒加载 + 菜单开关，关掉后入口直接不渲染
  数据库：外环的表放独立的迁移文件，方便整体回滚

【Trade-offs】
  ------------------------------------------------------------------
  方案            优点                      代价
  ------------------------------------------------------------------
  三环隔离        外环可随时推倒重来         前期多花时间设计接口
                  主干不被实验性代码污染
  不分环          想怎么写怎么写，快         3 个月后改不动
  ------------------------------------------------------------------

  ★ 对"毕业前时间紧"的诱惑，我的建议是：
    内环按三环纪律做，外环随便写 —— 因为它本来就是要被丢掉重写的。


################################################################################
  四、关键设计取舍（8 条，已定论）
################################################################################

--------------------------------------------------------------------------------
4.1 叙事特征从哪来 —— 【定论：本地提特征】
--------------------------------------------------------------------------------
  【问题】想按"叙事风格"找书，但库不存正文 —— 特征从哪来？

  【定论】两路并行：

    路线 A（自动 · 本地计算）：
      用户上传自己的 TXT → 浏览器本地解析（正文永不离开内存）
      → 本地算特征（段落长度方差 / 场景切换频率 / 对话占比 / 词频分布）
      → 只上传「特征向量」，不含一个字的原文
      → 建特征库 → 找叙事风格相似的书

      ★ 本质是**隐私计算 / 联邦学习的朴素版**，面试可讲。
      ★ 零版权风险：上传的是数字向量，不是正文。
      ⚠ 冷启动：特征库只覆盖"用户自己有的书"——
        但那些恰好是他关心的书，覆盖率低 ≠ 没用。

    路线 B（人工 · 零风险）：
      用户手动打叙事标签（"多线叙事""慢热""群像"）。
      ★ 建议 B 先行，A 后补 —— B 是 A 的兜底。

--------------------------------------------------------------------------------
4.2 试读怎么处理 —— 【定论：只做"用户自己粘贴"】
--------------------------------------------------------------------------------
  【问题】想提供试读，但爬取正文 = 侵权。

  【定论】删掉一切爬取。保留三种"阅读"用途：
    1. 用户自己粘贴的内容（用户自己负责）
    2. 用户本地 TXT（不上传）
    3. 跳转器：显示条目信息 + "前往正版平台"按钮

  ★ 三环架构救不了法律风险 —— 这不是架构问题，是底线问题。

--------------------------------------------------------------------------------
4.3 书摘和笔记存哪 —— 【定论：按"是不是原文"划线】
--------------------------------------------------------------------------------
  【问题】用户本地 TXT，但"阅读手账 / 书摘"要存哪？

  ------------------------------------------------------------------
  数据类型          例子                        存哪            理由
  ------------------------------------------------------------------
  书摘（原文引用）  "……他握紧了那把剑"          浏览器本地       是第三方正文
  感想（你写的）    "这段让我想起高中"          后端数据库       是你的原创
  进度（章节序号）  第 37 章 / 62%              后端数据库       不是内容
  私人评分          4.5 星                      后端数据库       是你的数据
  私人笔记          自定义文字                  后端数据库       是你的原创
  ------------------------------------------------------------------

  ★ 一句话：**"引用"留在本地，"感想"可以上云。**
  ⚠ 这条要写进代码注释，否则以后一定会有人图省事把书摘存进库。

--------------------------------------------------------------------------------
4.4 书房表：改造还是新建 —— 【定论：改造现有书架表】
--------------------------------------------------------------------------------
  现有书架表已有：用户 / 书籍 / 置顶 / 时间 / 进度
  书房只需要再加：状态（想读/在读/已读/弃坑）/ 笔记 / 分组

  ------------------------------------------------------------------
  方案              优点                    代价
  ------------------------------------------------------------------
  改造现有表（推荐） 省一半工作量，代码复用   表语义变宽
  新建表             语义干净                 数据迁移 + 两套代码路径，纯亏
  ------------------------------------------------------------------

  ★ 归属校验、唯一索引、软删复活这一整套**已经被验证过的逻辑可以原样复用**，
    这是改现有表最大的价值。

--------------------------------------------------------------------------------
4.5 AI 的动作写进哪张表 —— 【定论：物理隔离】
--------------------------------------------------------------------------------
  【问题】既想让 AI 和真人共用一套动作接口，又要求 AI 不进公共评论区。
  【定论】这两个要求打架，**用表级物理隔离，不用权限过滤**。

    公共评论 → comment 表（只有真人能写）
    AI 互动  → ai_interaction 表（AI 专属）

  ★ 理由：权限过滤是会漏的，表隔离不会。
  ★ 这不是"合规要求"，是**设计决策**（要求会被忘记，架构会挡住）。

--------------------------------------------------------------------------------
4.6 AI/真人识别 —— 【定论：只分析用户自己的 TXT】
--------------------------------------------------------------------------------
  【为什么不砍】有 4.1 的本地特征提取，技术基础是共用的，成本很低。
  【为什么不公开做】AI 检测误报率公认很高，判真人作者"疑似 AI"是伤害人。

  ------------------------------------------------------------------
                公开鉴定别人              私人分析自己的TXT
  ------------------------------------------------------------------
  风险          误伤真人，不可挽回          归零
  位置          公开功能                    书房里的一个工具
  正当用途      —                          想知道自己写的东西像不像AI
  ------------------------------------------------------------------
  ★ 输出必须是**可解释指标**（困惑度 / 突发性 / 句长方差），
    不是"这是AI写的"这种判定结论。

--------------------------------------------------------------------------------
4.7 冷启动：书库条目谁录入 —— 【定论：用户提交 + 事后审核】
--------------------------------------------------------------------------------
  【问题】库只存元数据，但条目从哪来？

  【定论】针对"自己和一小部分人"的规模：
    · **用户提交即入库**（不做事前审核）
      理由：朋友规模下，管理员不可能一直盯着审核队列
    · **事后审核**：被举报 / 发现问题 → 管理员下架
    · 管理员可以手工录"精选条目"当种子内容

  ⚠ 备选方案的风险提示：从公开数据源批量导入看起来省事，
    但主流读书平台**没有开放 API**，爬用户数据有法律风险。
    → 不做。冷启动慢一点没关系。

  ★ 这条同时也解决了"用户为什么留下"的第一层：
    用户能"建设"这个库，而不只是消费它。

--------------------------------------------------------------------------------
4.8 社区论坛 —— 【定论：推迟到有 10 个真实用户之后】
--------------------------------------------------------------------------------
  理由：论坛的技术含量 ≈ 又一个 CRUD，边际价值接近 0。
       真难点是"没人发帖"（产品问题），不是代码。
  ★ 在那之前建表 = 建一个永远空的表。

【内环（主干）】
  ------------------------------------------------------------------
  实体              用途                                    备注
  ------------------------------------------------------------------
  书库条目          书名/作者/封面/简介/来源链接/分类/标签    ★ 加 sourceUrl
  章节              平台自营试读内容                         定位见下方
  书房记录          用户 × 书籍 × 状态 × 笔记 × 分组          改造现有书架表
  书单              用户创建的主题书单                       含点赞/收藏/评论计数
  书单条目          书单 × 书籍 + 推荐语 + 排序位             多对多
  评分              用户对书的多维评分                       一人一书一条
  评论              短评 / 长评                              含点赞计数
  通知              站内消息                                 见 7.4
  ------------------------------------------------------------------

【外环（实验 · 可整块删除）】
  ------------------------------------------------------------------
  实体              用途                                    备注
  ------------------------------------------------------------------
  AI读者            人格定义（名字/头像/人设/性格标签）
  AI互动记录        AI 说了什么、用户回了什么                 物理隔离，见 4.5
  AI记忆            用于检索的历史片段                       见第六节
  叙事特征          ★ 只存向量，不存正文                     见 4.1
  阅读手账          心情标签 / 时间轴                        只存用户原创，见 4.3
  ------------------------------------------------------------------

【★ 章节表的定位 —— 需要你自己拍板】
  项目现在有章节表，存的就是正文。改造时要决定：
    (a) 删掉 —— 最干净，但要删掉现有阅读功能
    (b) 保留但限制为管理员独占，当"平台自营试读" —— 保守，但有版权灰区
    (c) 改造为"用户私密草稿" —— 只存用户自己写的东西
  ★ 我倾向 (b)，但这条你说了算，因为它直接决定留不留一个现有功能。

【★★ 冗余字段登记表 —— 本项目最大的历史包袱】

  ------------------------------------------------------------------
  字段                    由谁维护        同步时机
  ------------------------------------------------------------------
  书库条目.总字数          章节服务        章节增 / 删 / 改
  书库条目.平均分          评分服务        评分增删改
  书库条目.评分人数        评分服务        评分增删改
  书单.点赞数              点赞服务        点赞 / 取消
  书单.收藏数              收藏服务        收藏 / 取消
  书单.评论数              评论服务        评论增删
  评论.点赞数              点赞服务        点赞 / 取消
  ------------------------------------------------------------------

  ★ 这个项目里"冗余字段"是**第二次出现**了（第一次是总字数）。
    新方案会让它从 1 个变成 7 个 —— 靠人记是记不住的。

  ★★ 「计数类冗余字段三条纪律」：
    1. 所有写操作必须在一个事务里
    2. 增 / 删 / 改三处必须同步（不是"记得改"，是"三处都写"）
    3. 一个**定时对账任务**兜底

  ★ 对账怎么验（"判据本身也要验证"）：
    写一条 SQL 比对"冗余字段"和"实际统计值"。
    然后**先制造一条不一致的数据**，确认这条 SQL 能查出来 ——
    否则你永远不知道它是"真的没问题"还是"查询写错了"。

  ★ 顺带：现有系统里"软删除"字段在各表用法不一致，
    新表必须**统一软删约定**，并写进设计决策。


################################################################################
  六、★ 向量库是什么，你要不要用
################################################################################

【这一节专门讲你问的问题 —— 向量数据库】

--------------------------------------------------------------------------------
6.1 先理解问题：MySQL 能搜到"意思"吗？
--------------------------------------------------------------------------------
  场景：用户说 "我想找一本讲**蒸汽朋克和神秘学**的书"

  用 MySQL 的 LIKE：
    SELECT * FROM novel WHERE title LIKE '%蒸汽朋克%' OR summary LIKE '%神秘学%'
  → 能搜到，但**只能搜到字面有这几个词的**。
    一本书简介里写的是"维多利亚时代的工业幻想与克苏鲁神话"——
    明明很相关，但**一个关键词都没匹配上，搜不到。**

  ★ 问题本质：
    传统数据库按**字面**匹配，人找书按**意思**匹配。中间隔着一道墙。

--------------------------------------------------------------------------------
6.2 向量是什么（一个比喻）
--------------------------------------------------------------------------------

  比喻：把每段文字想象成**地图上的一个坐标点**。

    传统搜索：查"名字里带'蒸汽朋克'的书" → 只能精确匹配标签
    向量搜索：**把意思相近的书放在地图上相近的位置**

    比如这张"语义地图"上：
      《诡秘之主》        → 坐标 (3.2, 8.1)
      《钢铁火药和施法者》 → 坐标 (3.4, 7.9)   ← 很近！
      《霸道总裁爱上我》   → 坐标 (9.1, 1.2)   ← 很远

    你问"有没有像《诡秘之主》的" → 系统去找 (3.2, 8.1) **附近的点**
    → 即使那本书的简介里一个字都没提到"克苏鲁"，也能找到。

  ★ 这张地图的坐标，就是**向量**（一串数字，比如 1536 个浮点数）。

  ★ 谁负责把文字变成坐标？—— **Embedding 模型**（AI 模型的一种）。
    这是它干的活，不是你写的算法。你只需要调用它。

  ★ 关键性质：**意思相近 → 坐标相近**。这是模型训练出来的能力。

--------------------------------------------------------------------------------
6.3 向量数据库是什么
--------------------------------------------------------------------------------
  一句话：**一张"语义地图"的索引，专门用来快速找"离我最近的点"。**

  为什么不能直接用 MySQL 存这些坐标？
    · 假设有 100 万个向量，每个 1536 维
    · 找最近的 → 要跟 100 万个都算一遍距离 → **慢到不能用**
    · 向量数据库用**近似算法**（HNSW / IVF）：
      牺牲 1% 的准确度，换 1000 倍的速度

  ★ 所以向量库 = **"近邻搜索"专用索引**，就这一个用途。
    不是什么神秘的东西，你可以理解成"给语义地图建的 B+ 树"。

--------------------------------------------------------------------------------
6.4 你的 AI 读者为什么可能需要它
--------------------------------------------------------------------------------
  场景：你和 AI 读者"墨白"聊了半年，聊天历史有 3000 条。

    今天你说："上次我们聊到主角的师父，你觉得他..."

  【不用向量库】
    只能把"最近 20 条"塞给大模型 → **它不记得三个月前聊过什么**

  【用向量库】
    把你的问题变成坐标 → 在 3000 条历史里找**语义最近的 3 条**
    → 正好捞出来三个月前那次对话 → 塞给大模型 → AI 真的"记得"

  ★ 为什么不能用关键词搜索？
    "师父" / "老师" / "引路人" / "那个教他剑的人" ——
    字面完全不同，**关键词搜不到，向量能搜到**。

--------------------------------------------------------------------------------
6.5 ★ 所以你该不该用（我的建议：先不用）
--------------------------------------------------------------------------------

  ------------------------------------------------------------------
  方案                  怎么存记忆                什么时候用
  ------------------------------------------------------------------
  (a) 最近 N 条          只存最近 20~50 条         起步用这个 ✅
  (b) 关键词 + 最近N条   先关键词筛，再取最近的     觉得不够用再上
  (c) 向量库             语义检索                  真的"记不住事"了再上
  ------------------------------------------------------------------

  【★ 建议：从 (a) 起步】
    理由：
    1. 1000 人的规模，用户的 AI 对话历史**不会很长**（没人聊半年）
    2. 向量库要多一个组件（要么换 Redis 镜像，要么加 PostgreSQL）
    3. ★ 你还没到那个瓶颈 —— 别提前优化

  【什么时候该上】
    当你自己用的时候**明确感觉到**"它不记得我说过的事" ——
    那就是信号。到那时再上，半天就能加。

  【真要上，选哪个】
    · **Redis Stack** —— 有向量搜索能力，但需要 RedisJSON + RediSearch 模块，
      **普通的 redis 镜像不支持**，要换镜像
    · **pgvector** —— 需要 PostgreSQL，项目现在是 MySQL，要加一个库
    ★ 我倾向 Redis Stack（你已经有 Redis，换个镜像比加一个数据库轻）

  ★ 一句话总结：**向量库 = 给"语义地图"建的索引；
    你用得上，但不是现在。** 先记住这个概念，用的时候再回来看这节。

7.1 私人书房 + 本地 TXT 阅读器（路线图第 1 期）
--------------------------------------------------------------------------------
  【书房要做的】
    在现有书架基础上加：
      · 状态标记：想读 / 在读 / 已读 / 弃坑（用枚举，别用魔法数字）
      · 私人笔记（只存你自己写的话，见 4.3）
      · 自定义分组（可空）
      · 私人评分（不公开，只给自己看）
      · 阅读手账（心情标签 + 时间轴）

  【本地 TXT 阅读器 —— 纯前端，技术密度最高的一块】
    ★ 正文永不离开浏览器内存。四个技术点：

    【1】编码检测 ★ 中文 TXT 最大的坑
        GBK / GB2312 / UTF-8 / UTF-8-BOM 混杂。
        思路：先读前几字节判 BOM → 无 BOM 则按 UTF-8 试解码
              → 解出"替换字符"（乱码标志）就换 GBK 重试
        ⚠ 先别急着找第三方库，想想自己写要几行 —— 这题面试能讲。

    【2】大文件分片读取 ★ 一本小说 5～20MB
        用文件切片 API 分片读，或流式处理。
        ⚠ 一次性读整本 = 卡死浏览器

    【3】章节拆分（正则）
        常见格式：第X章 / 第X节 / 第X回 / Chapter N / 卷一 第X章
        ⚠ 坑：正文里也会出现"第一章"这种引用
          → 需要用"行首 + 行长上限"来约束，否则会误拆

    【4】虚拟列表 ★ 一章可能几万字，全渲染 DOM 会卡
        只渲染视口内的行。这是前端性能的经典题。

  【进度存储】
    章节序号 + 百分比 → 可以上后端（不是内容，见 4.3）

  ★ 这一期的技术密度最高，且**全部可测**（造各种编码的样本文件）

7.2 书单系统（路线图第 2 期）
--------------------------------------------------------------------------------
  【为什么书单是核心】
    · 天然产生 UGC，不碰版权
    · 比"单本推荐"更有组织性，用户可复用
    · 是"用户能建设这个站"的载体

  【表结构要点】
    书单：标题 / 简介 / 封面 / 创建者 / 是否公开 / 三个计数
    书单条目：书单 × 书籍 / 推荐语 / 排序位
    ★ 唯一约束：同一本书不能重复加进同一书单

  【★ 排序位怎么设计（真设计题）】
    "拖动排序"怎么做？三种方案：

    ------------------------------------------------------------------
    方案                  优点              缺点
    ------------------------------------------------------------------
    (a) 连续整数 1,2,3     直观              插一个要更新后面全部
    (b) 稀疏整数 10,20,30  插入平均 O(1)     间隙会用完，要定期重排
    (c) 链表 pre/next_id   插入 O(1)         查询要递归，SQL 难写
    ------------------------------------------------------------------

    ★ 建议 (b)：间隔 10，间隙用完时后台重排。
      理由：(a) 在书单有 200 本书时，拖一次要更新 199 行 —— 会长事务。
    ★ 这是"看起来很简单的功能里有真设计"的典型，面试可讲。

  【权限】
    isPublic = false 的书单，只有创建者本人可见。
    ⚠ 这是**资源级权限**（"这条是不是我的？"），
      比"角色级权限"（"你是不是管理员？"）难一层，见 8.3。

7.3 评分与评论（路线图第 2 期）
--------------------------------------------------------------------------------
  【多维评分】
    文笔 / 剧情 / 爽感 / 人物 → 四个维度
    总分 = 四项平均
    ★ 总分必须**计算后落库**，不要在查询时算 —— 否则无法索引 / 排序
    ★ 但算法只能有一处（写在实体的生命周期回调里，别在 Service 里手算）
    ★ 唯一约束：一人一书一评 —— 想改评分 = 修改，不是再插一条

  【一致性】见第五节的「冗余字段三条纪律」

  【防刷】
    · 限流（可以复用现有的限流注解）
    · 评分门槛：读完 X% 才能评分（进度已上后端，能查）
    · 异常检测：同一用户短时间给大量书评分 → 标记

7.4 社区论坛 + ★ 通知系统（路线图第 3 期）
--------------------------------------------------------------------------------
  【论坛：推迟，但下面是设计】
    按分类（玄幻/都市/言情）或话题（求书/推书/吐槽）划分
    可以关联书单或书籍条目
    ⚠ 需要内容审核机制（见 8.6）

  【★★ 通知系统 —— v2 漏了，但没有它 UGC 就是死的】

    为什么必须有：
      书单/评分是"一次性动作"（做完就走）。
      让人**回来**的是"我做的事有回应"。
      没有通知 = 用户不知道自己被回应了 = 不会回来。

    最小可行版（零成本）：
      · 一张通知表：接收者 / 类型 / 关联对象 / 是否已读 / 时间
      · 触发点：有人赞了你的书单、回复了你的评论、收藏了你的书单
      · 前端：顶部小红点 + 未读数
      · 不做邮件 / 不做 Push —— 站内信够了

    ★ 这一条是"产品能不能活"的关键，不是"锦上添花"。
    ★ 它属于内环（主干），不是外环。

7.5 ★ AI 阅读伴侣（路线图第 4 期 · 外环）
--------------------------------------------------------------------------------
  【技术栈】
    ★ 不需要引入 Python。
      Spring AI 2.0 已发布，官方声明即为 Spring Boot 4.0/4.1 设计。
      ⚠ 实际跑通前不要当成结论 —— 版本兼容要自己试一次。

  【★★ 成本模型】

    【真实价格 —— 2026-10 实测】
      DeepSeek 已改为峰谷分时计费，高峰（工作日 9-12 / 14-18 点）是闲时 2 倍。

      ------------------------------------------------------------------
      模型             输入(缓存命中)      输入(缓存未命中)
      ------------------------------------------------------------------
      deepseek-flash   空闲 0.02 元/M      空闲 1 元/M
      deepseek-v4-pro  空闲 0.15 元/M      空闲 4.5 元/M
      ------------------------------------------------------------------
      ⚠ 输出价格官网页面被截断，没拿到准确值。
        → 【待实测】自己去 DeepSeek 官网核一眼，这是必须自己验证的数字。

      ★ 注意那个 50 倍：缓存命中 0.02 vs 未命中 1 元。
        同一个模型、同一个 prompt，差 50 倍。这是所有省钱设计的核心。

    【一次"AI 读者说一句话"的消耗量】（估算，接上后要实测）
      人格设定 prompt    ~400 tokens   ← 固定不变
      记忆检索（近 N 条）  ~600 tokens   ← 每次不同
      当前剧情上下文      ~400 tokens   ← 每次不同
      输出                ~150 tokens
      ─────────────────────────────
      合计：输入 ~1400 / 输出 ~150

    【★★ 同一个功能，三种设计，差 1300 倍】
      ------------------------------------------------------------------
      设计                          用量              月成本（按日活100算）
      ------------------------------------------------------------------
      A 事件驱动 ✅                 1500 次/天        ≈ 77 元
      B 轮询式决策引擎 ❌           43 万次/天        ≈ 22000 元
      C 轮询 + Pro 模型 ❌❌        |                 ≈ 100000 元
      ------------------------------------------------------------------
      ★ B/C 在 1000 人规模下**直接烧穿预算**，不是"贵一点"的问题。

    【★★ 最重要的一句话】
      成本跟"AI 有几个"几乎无关，跟"谁触发它"完全相关。
      用户触发 → 可控；定时器触发 → 爆炸。

      ⚠ 特别警惕"决策引擎"这个词：
        如果做成"每分钟每个 AI 想一次我要不要发言"，
        99% 的回答是"不评论" —— **你花钱买了个"不"字。**

    【★★ 硬性成本上限（1000 人规模必须设）】
      · 每人每日 AI 调用上限（比如 50 次）
      · 全局每日预算上限（比如 10 元），超了**自动降级到台词池**
      · 没有这两条，某天一个用户刷起来就能烧掉你一个月预算

  【★ 五个省钱杠杆（按杠杆大小排序）】

    🥇 杠杆 1：让 prompt 缓存命中（50 倍）
      ⚠ 硬性工程约束（不是"优化建议"）：
        prompt 缓存是**前缀匹配** —— 开头那段一样才命中。

      ❌ 缓存永远不命中（时间戳在开头，每秒都在变）：
         你是书评人"墨白"，性格傲娇。
         当前时间：2026-10-13 15:23:47    ← 就这一行，废掉全部缓存
         用户正在读第 37 章...

      ✅ 缓存稳定命中：
         你是书评人"墨白"，性格傲娇。     ← 一字不变，永远放最前
         （然后才是）当前时间 / 当前章节    ← 动态内容全塞后面

    🥈 杠杆 2：事件驱动，绝不轮询（~280 倍）
      **唯一一条"不省就完蛋"的。**

    🥉 杠杆 3：规则前置，AI 后置（5～10 倍）
      先过便宜规则：
        if (人格.精力 < 阈值) return;
        if (随机数 > 0.3) return;          // 30% 概率发言
        if (上次发言 < 5 分钟前) return;    // 别刷屏
        // ↓ 只有走到这里才真的花钱
        调用AI(人格, 上下文);
      ★ 把"AI 有自主性"的产品感和成本解耦 ——
        用户觉得 AI 有性格，实际是概率。

    杠杆 4：检索而非全塞（避免 10 倍膨胀）
      只取最近的/最相关的几条。全塞进去 → 输入从 1400 涨到 14000。

    杠杆 5：四件顺手就能省的小事
      · 关掉"思考模式" —— 说句闲话不需要推理链
      · Embedding 用本地小模型 → 零成本
      · AI 相关定时任务挪到闲时（高峰是闲时 2 倍价）
      · AI 生成的内容也要过敏感词过滤（AI 也会说错话）

  【★ 成本护栏 = 中环的 AI 网关（四件套）】
    ------------------------------------------------------------------
    护栏        手段                          可复用的现成资产
    ------------------------------------------------------------------
    限流        每分钟每人 N 次               已有的限流注解
    缓存        相同输入 → 相同输出           已有的缓存管理器实战
    降级        AI 挂了 → 返回预设台词池      做过的缓存降级演练
    预算上限    每日 X 元，超了自动降级        新东西，但很简单
    ------------------------------------------------------------------

    ★★ "AI 服务突然挂了"是一个完美的**故障演练对象** ——
      你之前演练过依赖服务宕机看真实行为，
      现在可以故意改错 API 地址，看 AI 模块能不能优雅降级。

  【★ 起步路径（关键：先花 0 元验证设计）】
    阶段 1：**0 元** —— 预设台词池 + 规则调度
      3 个 AI，每个准备 50 句人设化台词，用规则/概率挑一句
      → 目的：验证「交互形态对不对」「用户会不会觉得有意思」
      → **如果这一步就没意思，接了大模型也一样没意思**

    阶段 2：接 API，**单** AI，事件驱动
      → 目的：验证技术链路 + 实测真实成本

    阶段 3：多 AI + 长期记忆
      ★ 多智能体是 1→N 的扩展，不是 0→1 的启动

  【人格设计】
    · 每个人格必须有**明确的语言习惯**（句长 / 口头禅 / 关注点）
    · 每个人格必须有**明确的立场倾向**（毒舌 / 温和 / 考据党）
    · 人格 prompt 必须放最前面且一字不变（见杠杆 1）

    ★ 人设一致性怎么测（很妙的测试点）：
      固定一个输入，让 3 个人格各说 10 句，
      人来判断"能不能分辨出是谁说的"。分不出 = 人格设计失败。
      ★ 这比"接口返回 200"有意义得多。

  【★★ 记忆的删除权（v2 漏了，但很重要）】
    用户必须能**一键清空 AI 记忆**。
    理由：AI 记忆里是用户的阅读偏好和聊天内容 —— 属于个人信息。
    ★ 这条在面试上是加分项（体现隐私意识）。

  【合规】
    · 显式标识：每条 AI 内容旁标 "AI生成 · 模拟读者观点"
    · 隐式标识：元数据中记录生成属性
    · 依据：《人工智能生成合成内容标识办法》（2025-09-01 施行）
    · ★ 物理隔离：AI 永不写进公共评论表（见 4.5）

8.1 ★ 数据库迁移工具（最紧急，比新功能紧急）
--------------------------------------------------------------------------------
  【现状】只有一个"初始化脚本"，只能建全新库，改字段它不管。

  【为什么不改它就行】
    本方案要加 10 张左右的表、改若干张表。
    · 本地库：手工改
    · 服务器库：手工改
    · 朋友想跑你的项目：不知道要执行哪些变更
    → 第 3 个月就会遇到"线上库和本地库结构不一致"

  【方案】引入数据库迁移工具（Flyway 之类）
    每个变更一个版本文件，按顺序自动执行，记录在案。
    ★ 【待实测】与当前框架版本的兼容性要试一次

8.2 决策日志 —— 建议新建一个文档
--------------------------------------------------------------------------------
  ★ 你**已经在做对的事了** —— 你维护的文档体系（总览 / 交接 / 操作细则）
    本质是给"未来的你和 AI"做 onboarding。别停。

  补一块：每次做重要技术选择，记 4 行：

    2026-10-20  书房表：改造 vs 新建
    决策：改造现有书架表，不新建
    原因：字段重叠 90%，迁移成本 vs 语义清晰度
    代价：表语义变宽，以后要拆需要迁移

  ★ 面试价值：面试官问"你做过什么技术决策"，这就是答案。

--------------------------------------------------------------------------------
8.3 ★ 权限模型升级
--------------------------------------------------------------------------------
  现状：只有"角色级"权限（你是不是管理员？）。

  新方案需要**资源级**权限：
    · 这条书单是不是我创建的？（改 / 删）
    · 这条笔记是不是我的？（看 / 改）
    · 这个 AI 会话是不是我的？
    · 这本私人书是不是在我的书房里？

  ★ 书架系统已经踩过这个坑（"必须校验归属"）。
    新模块有 4 个都要，需要**统一的归属校验模式**，不能每个 Service 各写各的。

  ⚠ 这是最容易漏的安全缺口：
    "查到了别人的数据"和"改掉了别人的数据"是两个不同严重度的问题。

--------------------------------------------------------------------------------
8.4 分页规范
--------------------------------------------------------------------------------
  书单列表 / 评论列表 / 帖子列表 / AI 会话列表 全都要分页。
  ★ 抽出统一的分页参数对象 + 上限兜底，别抄 4 遍。

--------------------------------------------------------------------------------
8.5 文件存储
--------------------------------------------------------------------------------
  封面（书单封面、AI 头像）存哪？
  现状：本地磁盘。
  ⚠ 换机器就丢。
  ★ 短期：保持本地磁盘，但**接口抽象好**（放中环），以后换对象存储不改调用方。
  ★ 长期：对象存储，有真用户再说。

--------------------------------------------------------------------------------
8.6 ★ 内容审核（UGC 上线必需）
--------------------------------------------------------------------------------
  一旦有真实用户，评论 / 书单简介 / 论坛帖就需要审核。
  ★ 最小可行版：
    · 敏感词过滤（本地词库，零成本）
    · 用户举报入口
    · 管理员下架能力（复用现有管理员权限）
  ⚠ 这一条不做，UGC 功能等于裸奔。

--------------------------------------------------------------------------------
8.7 用户数据权利
--------------------------------------------------------------------------------
  法律要求：用户可注销、可导出自己的数据。
  ★ 最小可行版：
    · 注销：软删用户 + 匿名化其 UGC（不要硬删，会破坏关联关系）
    · 导出：把该用户的笔记 / 评分 / 书单打成 JSON 给他
  ★ 和 7.5 的"一键清空 AI 记忆"是同一类需求，可以一起设计。

--------------------------------------------------------------------------------
8.8 ★ 备份（数据比代码宝贵）
--------------------------------------------------------------------------------
  代码丢了可以重写，用户的**书单和笔记**丢了就是丢了。
  ★ 最小可行版：定时导出数据库到另一个目录 + 保留最近 N 份。
  ⚠ 先确认现在数据库的数据实际存在哪里（容器卷？宿主机？）

--------------------------------------------------------------------------------
8.9 测试策略
--------------------------------------------------------------------------------
  ★ 你已经有基础（3 个测试类 / 12 个用例）。

  【目标】每加一个服务，同步加**至少 3 个用例**：
    正常 / 异常 / 边界
  ⚠ 不是"回头补覆盖率" —— 回头补 = 永远不会补。

  【本方案的测试重点】
    · 冗余字段一致性（平均分三处同步）
    · 归属校验（越权访问别人数据）
    · 软删复活（删掉再加回，旧数据不能残留）
    · AI：人格可区分性（见 7.5）
    · 前端：TXT 编码检测（用不同编码的样本文件）

--------------------------------------------------------------------------------
8.10 可观测性 + ★ 运营成本
--------------------------------------------------------------------------------
  【可观测性】
    ★ 最小可行版：结构化日志 + 关键指标（接口耗时、AI 调用次数与成本）
    ★ AI 成本监控尤其重要 —— 你必须在后台看到"今天花了多少钱"，
      否则 7.5 的成本模型就只是纸上谈兵。

  【★★ 运营成本（长期项目必须算这笔账）】
    ------------------------------------------------------------------
    项目                        月成本
    ------------------------------------------------------------------
    云服务器（2核4G）           ~50～100 元
    域名                        ~5 元（年均摊）
    对象存储（封面，可选）       ~0～5 元
    AI 调用（日活 100 人）       ~77 元
    ------------------------------------------------------------------
    合计                        **约 130～190 元/月**
    ------------------------------------------------------------------

    ★ 这个数字你要心里有数 —— 一年约 2000 元。
    ★ 三条省钱路径：
      · AI 是最大头 → 用好 7.5 的五个杠杆
      · 服务器可以先用最低配（10 QPS 用不了多少）
      · 前期可以只在自己电脑上跑，不买服务器

  【版权底线（重申）】
    · 不抓取、不缓存、不公开传播任何第三方正文

################################################################################
  十一、验证清单（期望值 → 判据 → 故障演练）
################################################################################

  ★ 本项目的验证文化：
    1. 先写期望值，再看结果 —— 否则会把任何结果都解释成成功
    2. 判据要选对地方 —— 异常也返回 HTTP 200 时，
       判断成败必须看响应体里的业务码，不能看 HTTP 状态码
    3. 判据本身也要验证 —— 制造一个必定失败的场景，看判据会不会报错
       ★ 假阳性和假阴性都会骗你，都比没有判据更危险
    4. 故障演练 > 看代码
    5. 用三阶段对比，不是前后对比
    6. 验证工具本身也要验证

--------------------------------------------------------------------------------
11.1 内环判据（每期都要跑）
--------------------------------------------------------------------------------
  · 冗余字段对账 → 期望 0 行不一致
    ★ 先制造一条不一致的数据，确认这条 SQL 真能查出来（判据自检）
  · 越权测试：A 用户改 B 用户的书单 / 笔记 / 评分 → 期望被拒
    ★ 注意：必须看响应体的业务码，不是 HTTP 状态码
  · 软删复活：删掉再加回 → 期望旧数据不残留
  · 分页兜底：页大小填 99999 → 期望被夹到上限
  · 通知：B 点赞 A 的书单 → 期望 A 的未读数 +1，B 自己不加

--------------------------------------------------------------------------------
11.2 外环判据（AI 专属）
--------------------------------------------------------------------------------
  · ★ 架构判据：删掉外环目录 → 期望内环测试全绿
  · 成本判据：连续调用 100 次，统计实际 token 消耗
    ★ 与 7.5 的估算对比 —— 差得多说明估算模型错了
  · 缓存判据：同一人格连续调用 10 次 → 期望后 9 次命中缓存
    ★ 验证方法：看返回的用量信息里"缓存命中"字段
  · 人格判据：3 个人格对同一输入各说 10 句 → 人能分辨出谁说的
  · 降级判据：故意把 API 密钥改错 → 期望返回预设台词，不是报错
  · 预算判据：把每日预算设成 1 分钱 → 期望第 2 次调用就走降级

--------------------------------------------------------------------------------
11.3 前端判据
--------------------------------------------------------------------------------
  · TXT 编码：准备 GBK / UTF-8 / UTF-8-BOM 三个样本 → 期望都正常显示
    ★ 再准备一个"混合编码"的坏样本，看它会不会**静默出错**
  · 大文件：20MB TXT → 期望不卡死（用浏览器开发者工具看内存）
  · 章节拆分：准备"正文里出现'第一章'字样"的样本 → 期望不误拆
