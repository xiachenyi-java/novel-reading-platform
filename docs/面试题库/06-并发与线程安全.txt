################################################################################
  Q1　双重检查锁为什么要判两次空？　【并发】
################################################################################

- **考点**：锁的粒度设计 + 竞态窗口 + 性能权衡。
  第二层考"为什么不用 synchronized(this)"，第三层考"锁对象怎么回收"。

- **追问链**：
  Q1「第一次都判空了，为什么进锁还要再判？」
  → Q2「为什么用 ConcurrentHashMap，不用 HashMap？」
  → Q3「computeIfAbsent 比 get + put 好在哪？」
  → Q4「锁对象什么时候回收？」★ 关键（项目里是已知缺陷）
  → Q5「多实例部署时这个锁还有用吗？」

- **参考答案**：
  第一次判空是**快速路径**：绝大多数请求能直接命中缓存，
  只付出一次 Map 查找的代价，根本不进锁。
  第二次判空是因为**等锁期间别人可能已经查完库写进缓存了**——
  不判的话，锁一释放就重复查库，互斥锁白加了。

  锁按 novelId 分，不用 synchronized(this)：
  this 是全局锁，查 A 书会把查 B 书的请求一起堵住；
  按 key 分锁，只有同一本书的请求才排队。

- **本项目的证据**：
  · `NovelServiceIml.java:264-265`：findDetail 的防击穿双重检查锁
    `locks.computeIfAbsent(novelId, ...)` + `synchronized(lock)`
  · 压测数据：同一热点 key 并发下，查库 SQL 条数 **10 → 1**
  · `NovelServiceIml.java:85-87`：addChapter 也复用了这把按书分的锁

- **坑**：
  ① 只答"防止重复查库"，不答"第一次判空是为了不进锁"——漏了性能这层
  ② 用 synchronized(this) 做按 key 分锁——变成全局串行
  ③ **锁对象不回收**：`locks` 只增不减（项目已知问题），
     被问"什么时候回收"要能答"目前没回收，方案是 remove / Guava Striped"
  ④ 忘了它是**单机锁**，多实例部署时无效（要靠分布式锁或 DB 唯一约束）

- **关联**：docs/知识笔记/10-并发与线程安全.txt 10.3「项目实战：按 key 分锁」


################################################################################
  Q2　volatile 能保证 i++ 线程安全吗？　【并发】
################################################################################

- **考点**：可见性 vs 原子性 的边界。并发最经典的一个坑，
  答错直接暴露基础不牢。

- **追问链**：
  Q1「volatile 保证什么？」→ Q2「那 i++ 安全吗？为什么？」
  → Q3「i++ 编译后是几条指令？」
  → Q4「那用什么修？」→ Q5「AtomicInteger 怎么做到原子的？」（CAS）
  → Q6「LongAdder 为什么比 AtomicInteger 快？」

- **参考答案**：
  **不安全。** volatile 只保证两件事：可见性 + 禁止指令重排，
  **不保证原子性**。

  `i++` 实际是三步：读 → 加 → 写回。
  两个线程可能同时读到 100，各自加 1 后都写回 101 —— 少加一次。

  修复三选一：
    · synchronized —— 最简单，高竞争下最慢
    · AtomicInteger —— CAS 自旋，中等
    · LongAdder —— 分段累加，超高并发下最快

- **本项目的证据**（2026-10-21 本机实测，JDK 25 Temurin）：
  · 10 线程 × 10000 次（期望 100,000）：
      无锁      33764 / 24807 / 99626 / 100000 / 32279   ← 5 次错 4 次
      synchronized / AtomicInteger / LongAdder           ← 全部正确
  · 100 线程 × 100000 次（期望 10,000,000）：
      synchronized  ~500 ms
      AtomicInteger ~145 ms
      LongAdder      ~10 ms      ← 约 50 倍（vs synchronized）

- **坑**：
  ① 答"volatile 保证可见性所以线程安全"——最典型的错误
  ② 只答结论不答 i++ 的三步，面试官会继续追问
  ③ 不知道 LongAdder 的代价：`sum()` 是近似值，强一致场景不能用
  ④ 实测时**跑一次没出错就以为没问题**——并发 bug 是概率性的

################################################################################
  Q3　你怎么证明并发代码是安全的？　【测试】
################################################################################

- **考点**：验证方法论。这题不考知识，考的是"你会不会自己骗自己"。
  ★ 这是他的强项，项目里有三阶段对比和故障演练。

- **追问链**：
  Q1「跑一次通过，能证明没问题吗？」
  → Q2「那怎么制造一个必定失败的场景？」
  → Q3「为什么你第二轮的失效率反而更低？」（JIT 预热）
  → Q4「可见性实验复现不出来，是不是就没问题？」★ 关键

- **参考答案**：
  跑一次通过**不能**证明，并发 bug 是概率性的。

  我的做法：
    ① **先写期望值再跑** —— 不然任何结果都能被解释成成功
    ② **多轮运行** —— 不是看一次，是看 5 次里错几次
    ③ **放大规模** —— 线程数、循环次数都往上加
    ④ **对比修复前后** —— 同一套判据，看结果是否稳定变对
    ⑤ **制造必错场景** —— 先验证"我的判据能不能抓住错误"

  ★ 最关键的一句：**并发 bug 复现不出来 ≠ 没有 bug。**

- **本项目的证据**：
  · 2026-10-21 原子性实验：无锁 10 线程×1 万，**5 次里错 4 次**
  · 100 线程×10 万反而只有第 1 次错 —— 原因是 JIT 预热改变了竞态窗口，
    说明"用第一轮数据下结论"本身就是错的
  · 可见性实验：不加 volatile **5/5 卡死**，加 volatile **5/5 正常退出**
  · 缓存降级三阶段：60.0s → 0.51s → 1.01s，body.code 500 → 200
    （★ 判据看 body.code，不看 HTTP 状态码）

- **坑**：
  ① 用"跑通了"当判据 —— 假阳性
  ② 只在一种规模下测 —— 规模变了结论可能反过来
  ③ 不验证测量工具本身 —— 比如计时用整数除法，1ms 以下全显示 0
  ④ 把 JIT 冷启动的第一轮数据直接拿来当结论
