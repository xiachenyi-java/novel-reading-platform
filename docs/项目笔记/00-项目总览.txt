################################################################################
  一、项目定位
################################################################################

【一句话】
  基于 Spring Boot + JPA + Redis + JWT 的小说发布与阅读平台，
  后端 + Vue3 前端的完整前后端分离项目。

【这是什么性质的项目】
  学习项目 / 简历项目。目标不是上线运营，而是：
    · 把 Java 后端的核心知识点串成一条线
    · 简历上有东西可写、面试时有东西可讲

【当前阶段】
  主体功能已完成，处于"从能跑 到 能讲"的收口阶段。

################################################################################
  七、整体路线图 · 双轨制
################################################################################

【模型变了：线性 → 双轨】
  以前是"线性四阶段，走完就结束"。
  现在是"两条轨道并行，永不结束"：

      轨道 A · 学习轨（持续，永不结束）
      ------------------------------------
      13 个大类 + Java 学习路线的 15 阶段
      按 A0 / A1 / A2 版本号持续推进

                    ^
                    |  互相喂
                    v

      轨道 B · 运营轨（上线后开启，持续）
      ------------------------------------
      服务器 / 备案 / 监控 / 备份 / 内容 / 用户 / 值班

                    ^
                    |
              上线 = 两条轨道的交汇点，不是终点

  【为什么这么改】
    · 学习不会"学完"，给学习设终点只会制造焦虑
    · 上线不是奖励，是第二段路的起点
    · ★ 运营中遇到的"真问题"，是最好的学习课题（见七·三）

  【只锚三个时间点，不定死日期】
    ① 判据 A/B/C 达标  →  开始部署演练
    ② 部署链路跑通     →  正式上线
    ③ 上线之后         →  运营轨开启，学习轨照常推进

  ~~缓存降级失效~~ —— ★ 2026-10-05 发现，2026-10-06 修复 ✅

    【问题】findDetail 为了做空值缓存，从 @Cacheable 改成了手动
      cacheManager.getCache("novel").get(...) 调用。
      结果：CacheErrorHandler 静默失效 —— 它由 AbstractCacheInvoker 调用，
      而那是 AOP 拦截器 CacheAspectSupport 的父类，只保护注解驱动的调用；
      手动 cache.get() 直接进 RedisCache，没有 try/catch 兜底。
      ★ 一句话：**"注解生效" = "框架的切面拦住了你"。**

    【当时的实测】（docker stop demo2-redis，5/5 次可复现）
      · GET /novels/{id} → 挂起 60.0 秒 → HTTP 200 +
                           {"code":500,"msg":"Redis command timed out"}
      · GET /novels      → 不受影响，正常 200
      · 日志里 CacheErrorHandler 的 warn 一次都没触发

    【★ 为什么"挂起"比"500"更糟】
      项目当时没配 spring.data.redis.timeout，用 Lettuce 默认 60 秒命令超时
      → 每个请求占满一条 Tomcat 线程卡 60 秒 → Redis 一挂 + 请求量稍大
      就级联拖垮整个应用（连不依赖 Redis 的接口也开始排队）。

    【★★★ 判据修正（这个认知比 bug 本身值钱）】
      旧判据"HTTP 200 = 降级有效"是**错的**。
      GlobalExceptionHandler.handleRuntimeException 没有 @ResponseStatus，
      所有 RuntimeException 都返回 HTTP 200。
      必须看 **body 的 code 字段**：code=200 才算真的成功。
      ★ 通用教训：**判据本身也要验证** —— 假阳性判据比没有判据更危险。

    【✅ 修复（2026-10-06）】
      第一级 · 超时（止血）—— application-dev.properties
        spring.data.redis.timeout=500ms
        spring.data.redis.connect-timeout=500ms
      第二级 · try-catch（治疗）—— NovelServiceIml.findDetail
        4 处 Redis 调用各包 try-catch：两次 get、两次 put
        · 读失败 → 当"缓存未命中"，继续走 DB（**不要 rethrow**）
        · 写失败 → 吞掉异常，不影响主流程

    【✅ 三阶段实测数据】
      ------------------------------------------------------------------
      阶段                  耗时        HTTP   body.code   接口可用性
      ------------------------------------------------------------------
      ① 改造前（60s 超时）  60.0s 挂起  200    500         ❌ 打不开
      ② 只加超时配置        0.51s       200    500         ❌ 打不开
      ③ 再加 try-catch      1.01s       200    200         ✅ 有数据
      ------------------------------------------------------------------
      ★ ②→③ 才是真正的修复。② 只是 fail fast（快速失败），
        ③ 才是 graceful degradation（优雅降级）。
      并发压测（500 请求 / 100 并发）：P50 1.491s，0 个超 5 秒；
      不依赖 Redis 的 /novels 列表 P50 0.248s，未被拖垮。

    【★ 附带发现：Lettuce 断连时会缓冲写命令】
      演练时"详情缓存写入失败"的 warn 一次都没触发。
      重启 Redis 后**不发任何请求**，novel::1 就已经存在了
      → Lettuce 在断连期间缓冲写命令，重连后自动补发。
      ★ 影响：put 的 catch 在当前场景不会触发；disconnectedBufferSize
        默认 64KB，缓冲满了才真正失败 → 写失败是**延迟暴露**的。
      ★ 本质：同步 API 掩盖了异步现实。connection.set() 返回 void，
        **"没有返回值的远程调用，等于没有错误处理。"**

  【★ 2026-10-06 · 进度表事故（不是代码 bug，是度量方式的问题）】

    【现象】同一批 13 个大类，两张进度表有 5 处对不上：
            02 / 04 / 06 / 08 / 11。
            更糟的是，项目笔记首行还有第三套数字 —— **三处都不一致**。
            例：11 测试体系  说明表 50% / 总览表 34% / 笔记首行 4/8 = 50%
                04 限流防刷  说明表 55% / 总览表 100% / 笔记首行 约 54%

    【根因 1 · 判据不可证伪】
      "11 测试体系 34%" 这句话，没有任何操作能证明它是错的。
      一个不能被反驳的数字，不是判据，是安慰剂。
      ★ 和缓存降级那次是同一类错 —— 用 HTTP 200 判成败（其实
        RuntimeException 也返回 200）。**假阳性判据比没有判据更危险。**
      ★ 识别方法只有一句：**「什么样的结果会证明我错了？」** 答不上来就是安慰剂。

    【根因 2 · 数据冗余】
      两张表是"复制粘贴 + 局部更新"的关系（13 个里 8 个一致，
      说明是同源的），某次改动只更新了其中一个 → 漂移。
      ★ 这和 novel.totalWords 是**同一个病**（决策 2：三个地方必须同步维护）。
        区别：代码那边有性能收益，值得付同步成本；
              文档这边没有任何约束 ⇒ **消除冗余**才是对的解。

    【根因 3 · 口径没定义】
      "完成度"到底是"主体步骤"还是"含进阶项"？每个文件各自理解：
        04「7/7 约 54%（含进阶项共 13 项）」  ← 7/7 和 13 自相矛盾
        06「3/8 主体步骤（含扩展项约 20%）」   ← 3/8=37.5% 和 20% 矛盾
        08「7/9 约 41%（含新发现共 17 项）」   ← 9 和 17 矛盾
        03 干脆没有分母（只有"14 版走完"）
        13「0/8 官方清单，但已有 10 项安全实践」← 双口径
      ⇒ 5 处待定口径（见第六节）。

    【✅ 解法（2026-10-06 已实施）】
      1. 定唯一权威源 = docs/项目笔记/XX-xxx.txt 首行的【完成度】
      2. 删掉 docs/项目说明-给AI.txt 里的重复表，改成指针
      3. 本文件第六节的表改成**只抄不算**的派生视图 + "下一个动作"列
      4. 判据 A 只跟踪需要的 6 个大类（其余 7 个记百分比没有决策价值）

    【★ 这事的价值（面试可讲）】
      不是"我们文档没维护好"，而是**"我们删掉了一个不可证伪的指标"**。
      判断一个指标该不该留，只问一句：
        **「这个数字变化了，会改变我下一步做什么吗？」**
      不会 → 删掉它，换成"下一个动作"。
      ★ 05 缓存体系已于 2026-10-07 从 9/14 = 64% 做到 10/14 = 71% 过线 ——
        这就是数字该有的用法：驱动一个具体的动作。
