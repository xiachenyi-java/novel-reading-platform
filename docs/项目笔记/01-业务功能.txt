  ✅ 已完成：日榜写入（2026-09）
    修法：readChapter() 里在总榜加分旁边，给当天的日榜 key 也加一次分
      String today = LocalDate.now(ZoneId.of("Asia/Shanghai"))
                          .format(DateTimeFormatter.ofPattern("yyyyMMdd"));
      String dailyRankKey = "ranking:novel:day:" + today;
      stringRedisTemplate.opsForZSet().incrementScore(dailyRankKey, novelId, 1);
      stringRedisTemplate.expire(dailyRankKey, 2, TimeUnit.DAYS);
    ★ 时区统一用 Asia/Shanghai，和 findDailyRanking() 的读法一致

  □ 排行榜防刷
    问题：readChapter() 每调用一次就 +1，用户按 F5 刷新 100 次就是 100 热度。
    后果：写个脚本一分钟就能把垃圾小说刷到榜首。
    位置：NovelServiceIml.readChapter()
    修法（由简到繁）：
      方案一：同一用户对同一小说 N 分钟内只计一次
              key = rank:lock:{userId}:{novelId}，SETNX + 5分钟过期
      方案二：只有登录用户才计入热度（游客不计）
      方案三：登录用户权重 1，游客权重 0.1，加时间衰减

P1 · 应该做（性能和数据正确性）
--------------------------------------------------------------------------------

  ✅ 已完成：日榜 key TTL（2026-09）
    做法：每次写入后 expire(dailyRankKey, 2, TimeUnit.DAYS)
    ★ 澄清一个问题：每次 incrementScore 后都调 expire 会不断推迟过期时间吗？
      —— 这个场景下不会。因为 key 名里带了日期，
      过了今天就不会再被 touch，TTL 自然到期。
      代价只是每次阅读多一次 Redis 往返，可接受。

  ✅ 已完成：分类筛选下推到后端（2026-09）
    做法：
      后端：GET /novels?page=&size=&category=&status=&keyword=
            用 JpaSpecificationExecutor + Specification 动态拼条件
            新增 GET /novels/categories 返回 DISTINCT 分类
      前端：loadNovels() 删掉所有客户端 filter，改为传参给后端
            分类列表从接口动态加载，不再硬编码
    效果：total 变成真实值，翻页时筛选条件保持（实测验证过）
    详见：项目笔记/07-数据访问.txt

  □ readChapter 的 Redis 写入移出只读事务
    问题：readChapter() 标了 @Transactional(readOnly = true)，
          但里面在写 Redis。Redis 不受数据库事务保护。
    后果：数据库回滚了热度已加上；高并发下热点 key 竞争激烈。
    位置：NovelServiceIml.readChapter()
    修法：移到事务提交后（TransactionSynchronizationManager），
          或者改成异步批量累加。

  四、面试话术（可直接背）
################################################################################

【Q：你的搜索和筛选功能怎么做的？】
  "列表接口支持分页、关键词搜索、分类筛选、状态筛选四个参数，
   都可以自由组合。

   后端用 JpaSpecificationExecutor + Specification 动态拼查询条件 ——
   每个条件写一个独立方法，条件为空时返回 null，
   Spring Data 会自动忽略。这样加新筛选维度不用改已有代码，
   也避免了方法名推导的组合爆炸（3 个条件就是 8 个方法）。

   分类列表我没有写死在前端，而是加了一个
   GET /novels/categories 接口，
   用 SELECT DISTINCT category 返回库里实际存在的分类，
   这样新分类会自动出现。"

【★ Q：这个功能你修过什么 bug？（这是加分回答）】
  "原来的分类筛选是前端做的 —— 后端只返回当前页的 8 条，
   前端在这 8 条里 filter 分类。

   问题有两个：一是如果第 1 页没有'玄幻'，用户会以为没有玄幻小说，
   但库里其实有；二是 total 显示的是全库数量，和实际展示的条数对不上；
   三是翻页之后筛选就失效了。

   我把筛选条件下推到后端，前端只负责传参。
   改完之后 total 是当前筛选条件的真实数量，翻页时条件也保持住了。
   我用 45 本真实数据验证过：选'玄幻'返回 totalElements=6，
   和 SELECT COUNT(*) WHERE category='玄幻' 完全一致，
   翻到第 2 页 total 仍然是 6。"

  ★ 这个回答的价值在于：能说出"我发现了什么问题、怎么定位、
    怎么验证修好了"，比只说"我做了搜索功能"高一个档次。
