          · 实验组 —— 同样内容存 UTF-16LE + BOM：
              printf '\xff\xfe' > u16.sql

                "ASCII '\0' appeared in the statement, but this is not

        ⇒ 只要用 PowerShell 的 `>` 导 mysqldump，就一定会中这一招。
        ★ 用 `cmd` 的 `>`、或者 mysqldump 自己的 `--result-file=` 都不会。

      ── 修法（推荐第一个）──
        ① 让 mysqldump 自己写文件（不经过 shell 重定向）：
             mysqldump -uroot -p****** --no-data --databases book_db \
               --result-file=docker/mysql/init/01-schema.sql
        ② 或者转码现有的（内容已经对了，只差编码）：

        ③ PowerShell 里想用重定向的话要显式指定：

  21. ✅【2026-10-08 发现 · 2026-10-10 已修】bookshelf 的唯一约束没进库

      ── 当时的现象 ──
        SHOW INDEX FROM book_db.bookshelf 只有 PRIMARY + 2 个普通索引，
        **一个唯一约束都没有**。功能性判据更硬：
        事务内连续插入两条 (user_id, novel_id) 完全相同的记录
        → **两条都成功**，COUNT = 2 ⇒ 约束在功能上确实不存在。

      ── 为什么当时没进库 ──
        Hibernate 的 ddl-auto=update **建新表时会带上约束，
        但不会给已经存在的表补约束**。这张表是先跑起来建出来的，
        之后才把 @UniqueConstraint 加进实体 —— 于是约束永远差一步。
      ★ 这是决策 6 那句话的第二次验证：
        "索引定义跟代码走"**只在建表那一刻成立**，表已在库里就不成立。

      ── ✅ 现状（2026-10-10 复核）──
        uk_bookshelf_user_novel (user_id, novel_id) 已在库里。
        SHOW INDEX → 13 行 = PRIMARY + uk_bookshelf_user_novel(2列)
                    + idx_bookshelf_top_create(5列) + idx_bookshelf_top_read(5列)

      ── ★★ 顺带修正：我第一次给的判据本身是错的（假阴性判据）──
        我写的是：
          SELECT COUNT(*) FROM information_schema.statistics
          WHERE ... AND non_unique=0 AND index_name<>'PRIMARY';   → 期望 1
        **这个"期望 1"是错的。** information_schema.statistics 是
        **一个索引的每一列各占一行**，两列的 UK 会产生 **2 行**。
        实测：COUNT(*) = 2，而 COUNT(DISTINCT index_name) = 1。
        ⇒ 按我原来的判据验，**修好了也会被读成"没修好"**。
        正确写法：
          SELECT COUNT(DISTINCT index_name) FROM information_schema.statistics
          WHERE table_schema='book_db' AND table_name='bookshelf'
            AND non_unique=0 AND index_name<>'PRIMARY';           → 期望 1
        ★ 教训：验证文化第 3 条说的是"假阳性判据比没有判据更危险"，
          但**假阴性判据同样有害** —— 它会让你以为没修好，
          然后跑去"修"一个已经正确的东西。判据的两个方向都要验。

      ── 为什么它是 🔴（留个记录，面试用）──
        约束缺失的代价不只是"多一条脏数据"：
        `findByUserIdAndNovelId` 返回 Optional，Spring Data 单结果查询
        遇到两行会抛 `IncorrectResultSizeDataAccessException`
        ⇒ 一旦真的出现重复行，**「加入书架」接口会从此永久 500**，
          连正常复活逻辑都走不了。而且是在某次并发之后才开始坏，
          之前所有测试都是绿的。

  23. ✅【2026-10-10 发现 · 2026-10-14 已修（提交 dc8f67a）】软删掉的记录还能被置顶

      ── 现象 ──
        BookshelfServiceIml.top() / remove() 用的是 findByIdAndUserId，

          Optional<Bookshelf> findByIdAndUserId(Integer id, Integer userId);
        ⇒ 对一条已经移出（deleted=1）的记录调 PUT /bookshelf/{id}/top
          会返回 200，并把 is_top 设成 1。

      ── 为什么是问题 ──
        虽然 remove() 会把 isTop 清 0，但**顺序反了就有洞**：
          移出一本 → 用它的 id 调置顶（成功，is_top=1）
          → 重新加入书架（复活分支只改 deleted，**不动 isTop**）
          → 这本书莫名其妙排在最前面（is_top DESC 排第一）
        ★ 用户视角：我明明没置顶它。
        ★ 更隐蔽的是：这条路径**每一步都返回 200**。

      ── 修法（二选一，1~3 行）──
        ① 把 top / remove 的查询换成带 deleted 条件的：

        ② 或者在复活分支里把 isTop / topTime 一起重置
        ★ 建议 ① —— 和 softDeleteByIds 的 WHERE 里带 userId 是同一个思路：
          **让数据库替你做状态校验**，比在 Java 里 if 判断可靠。

  24. 🟡【2026-10-10 发现 · 未修】移出书架后再重新加入，旧阅读进度会被写回来

      ── 现象（代码层面可确认，接口层判据待跑）──
        BookshelfServiceIml.remove() 特意把两个进度字段清空了：
          bookshelf.setLastReadChapterId(null);
          bookshelf.setLastReadTime(null);
        **但 Redis 里的 progress:{userId}:{novelId} 没人删**（TTL 7 天）。

      ── 于是 "清空" 这个动作会被另一个组件撤销 ──
        ① 读到第 5 章      → Redis: progress:1:100 = {chapterId, number=5, T1}
        ② 定时任务刷回     → DB: last_read_chapter_id=…, last_read_time=T1
        ③ 移出书架         → DB 清成 null（本意：干净记录）
                             ⚠ Redis 的 key 还在
        ④ 重新加入         → 复活分支只改 deleted，两个字段仍是 null
        ⑤ 下一轮定时任务    → WHERE deleted=0 AND lastReadTime IS NULL → **匹配**
                            → 把 Redis 里的旧进度写回 DB
        ⇒ "读到第 5 章"又回来了

      ── 最难受的是表现依赖时序 ──
        · 7 天内重新加入 → 进度回来
        · 超过 7 天（TTL 过期）→ 进度不回来
        ⇒ 用户完全没法理解为什么有时候回来、有时候不回来。

      ── 本质 ──
        **同一个状态存在两个地方（DB + Redis），两处的失效逻辑没对齐。**
        和"缓存与数据库一致性"是同一类问题 —— 只是这次不是缓存不一致，
        是"清空"被另一个写入方覆盖。

      ── 修法（1 行）──
        remove() 里顺手删 key：
          stringRedisTemplate.delete("progress:" + userId + ":" + novelId);
        ★ 注意：remove() 是 @Transactional。如果删了 Redis 之后事务回滚，
          Redis 已经删了 —— 又是不一致。但**这个方向是安全的**：
          最坏结果是"进度没了"（可重读），比"进度错乱"轻。
        ★ 也可以反过来想：如果本意就是"重新加入时恢复进度"，
          那 remove() 里就不该清空那两个字段 —— **两者必须二选一**。

      ── ⚠ 现状（2026-10-14 复核代码）—— 代码补了，但**走不到** ──
        remove() 里确实加上了删 key（BookshelfServiceIml.java:170-177），还带 try/catch：
          stringRedisTemplate.delete("progress:" + userId + ":" + novelId);
        ★ 但 remove() 第一步的查询传了 deleted=1（见新条目 25），
          对**在架的**记录必然 orElseThrow ⇒ 根本执行不到删 key 那几行。
        ⇒ 本条在"代码层面"补上了，"行为层面"依旧没修好 —— 等 25 修完再回头看它。
        ★ 顺带记一笔：这段 try/catch 的思路是对的（Redis 抖动不该让"移出"失败），
          修 25 的时候**别顺手把它删了**。
        ★★ 另一个缺口（2026-10-14 一并发现）：**批量移出没删 key**。
          batchRemove() 只调 softDeleteByIds（一条 UPDATE），
          **完全没有碰 progress:*** —— 所以就算 25 修好了，
          走"批量移出"这条路进来的书，旧进度照样会被写回。
          ⇒ 修 24 时两条路径都要覆盖（remove + batch-remove），
            别只修单条那条。

      ── 判据 ──
        □ 读到第 5 章 → 等一轮刷回 → 移出书架 → 重新加入 → 等一轮
          → 期望 last_read_chapter_id = null
          → 现在会变成原来的 chapterId
        □ 顺带验幂等：不读书等两个周期，日志期望"扫描 N 条，更新 0 条"

  18. ✅【2026-10-07 实测发现 · 当天已解决】Docker 里的 prod 撞上空库

      ── 现象 ──
      demo2-app 启动即 Exited(1)：
        SchemaManagementException: Schema validation: missing table [chapter]
      ★ 注意：报的是 chapter，但它只是**第一个被检查到的** ——
        三张表其实都缺。

      ── 根因：三件事叠加，缺一不发生 ──
        ① compose 里 SPRING_PROFILES_ACTIVE=prod
        ② prod 的 ddl-auto=validate  → **只校验、绝不建表**（设计正确）
        ③ compose 的 MYSQL_DATABASE   → **只建库、绝不建表**
      ＋ 项目里**没有任何 .sql 文件**（find 过）
      ⇒ 开发库的表是 dev 的 update 模式**悄悄长出来的**，
        只存在于本机硬盘上。**validate 在向一份不存在的合同对账。**
      ⇒ 只要 volume 为空（新机器 / 删过 volume），**100% 复现**，不是偶发。

      ── ✅ 修法（方案 A：MySQL 官方 initdb 机制）──
        ① mysqldump -uroot -p****** --no-data --databases book_db \
             > docker/mysql/init/01-schema.sql
        ② docker-compose.yml 的 mysql 加挂载：
             - ./docker/mysql/init:/docker-entrypoint-initdb.d:ro
        ③ docker compose down -v && docker compose up --build

      ── ★★ 两个必须记住的坑 ──
        · init 脚本**只在数据目录为空时执行一次**。
          不 `down -v` 就 up，脚本根本不会跑，你会得到**一模一样的报错**。
        · 导出的 schema **必须验索引在不在**：
            SHOW INDEX FROM book_db.novel;
          应看到 3 行（PRIMARY + idx_novel_last_update_time
          + idx_novel_category_last_update_time）。
          漏了的话，"索引优化有实测数据"这条简历优势在线上等于零。

      ── ★ 深层认知（面试可讲）──
        **@Table(indexes=...)（决策 6）在 prod 的 validate 模式下
        不产生任何 DDL。** 它在 dev 的 update 下会自动建索引，
        但 prod 只校验不创建 —— 索引必须由 schema.sql / 迁移脚本显式创建。
        ⇒ "索引定义跟代码走"这句话**只在 dev 成立**。

      ── 已实测（2026-10-07）──
        容器 3 个全 Up；GET /novels → body code=200；
        chapter / novel / user 三张表齐全；novel 的 3 个索引齐全。
        ★ 注意 content 为空数组 —— 导出用的是 --no-data，只带结构不带数据。
        ★ 2026-10-08 回看：当时只有 3 张表（bookshelf 还没建），
          所以那时的脚本是对的。现在有了 Bookshelf 实体，
          这份"只有 3 张表"的脚本会让 prod 启动失败 —— 见问题 20。

      ── 遗留待办 ──
        · mysql 仍无 healthcheck（七·二 B1 待办）——
          init 脚本会让 MySQL 首次启动多花 20-40 秒，
          depends_on 只等 service_started ⇒ 更容易撞上"没就绪"
        · 没有 .dockerignore：构建上下文 129M，其中 126M(98%) 是
          novel-frontend/node_modules —— Dockerfile 一个字节都没用到
        · 没有 schema 版本管理（Flyway/Liquibase）—— 第三梯队
        · 前端不在 compose 里（见 七·二 B1：Nginx 托管 dist/）
