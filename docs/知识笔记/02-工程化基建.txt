################################################################################
  第 1 课：Service 层抽离
################################################################################

【餐厅比喻】
  服务员（Controller）不能直接炒菜，必须交给厨师（Service）。

【四层架构对照表】
  ------------------------------------------------------------------
  层级          餐厅角色      职责                      代码
  ------------------------------------------------------------------
  前端页面      顾客          看菜单、点菜、吃菜        index.html
  Controller    服务员        接待、记菜单、端菜上桌    XxxController
  Service       厨师          决定怎么做菜、把控口味    XxxService
  Repository    仓库管理员    去冰箱取食材、清点库存    XxxRepository
  Entity        食材清单      定义"食材长什么样"        Xxx
  数据库        冰箱          真正存放食材的地方        MySQL
  ------------------------------------------------------------------

【两条铁律】
  1. 顾客不能直接冲进厨房喊"给我拿块肉"
     → Controller 不碰数据库
  2. 厨师不能直接去冰箱翻东西
     → Service 不感知 HTTP

  更本质的表述：上层可以调下层，下层绝对不允许调上层。

【控制反转（IoC）】
  问题：为什么 Controller 不能直接 new Service()？
  答案：Service 里依赖 Repository，
        而 Repository 是框架自动生成的代理对象（封装了连接、事务、SQL 生成）。
        自己 new 出来的对象，依赖字段是 null，一调用就空指针。

  本质：框架是一个"高级工厂"，
        你告诉它"我要这个对象"，它把已经配置好依赖关系的对象塞给你。
        对象的创建权从你手里反转到了容器手里 —— 这就是控制反转。

【依赖注入的三种方式】
  ------------------------------------------------------------------
  方式        写法                          推荐度
  ------------------------------------------------------------------
  字段注入    @Autowired private Xxx x;     ✗ 不推荐（无法 final、难测试）
  构造器注入  private final Xxx x; + 构造器 ✓ 推荐
  Setter注入  @Autowired setter             △ 可选依赖时用
  ------------------------------------------------------------------

  ★ 构造器注入的好处：
    · 字段可以是 final（不可变）
    · 依赖关系一目了然
    · 单元测试时可以直接 new，不需要容器

【坑】
  · Java 包名规范是全小写。Entity（大写 E）能跑但不规范，应该叫 entity。


################################################################################
  第 2 课：统一返回格式（Result）
################################################################################

【快递包裹比喻】
  你现在的"病"：前端每次收快递，包裹形状都不一样

    GET  /list     → 一摞书直接扔过来        [{...},{...}]
    POST /add      → 一张纸条                "添加成功，ID=5"
    DELETE /del    → 一张纸条                "删除成功"
    出错了         → 一张皱巴巴的报错单      Tomcat 错误页面

  前端的心情：我永远不知道这次打开包裹，里面是什么，得每次都猜。

【目标：所有包裹用"同一个纸箱"】
  {
    "code": 200,        // 物流状态：200=成功，500=出问题
    "msg": "success",   // 快递员留言
    "data": ...         // 真正的货物
  }

【Result<T> 的解剖】
  public class Result<T> {
      private Integer code;
      private String msg;
      private T data;     // ← 这个 T 是"占位符"
  }

  Result    是外卖盒
  <T>       是盒子里装什么菜的标记
  code/msg  是盒子上的标签（固定不变）
  data      是盒子里装的菜（随 T 变化）

【T 的四种变身】
  ------------------------------------------------------------------
  调用方式                  T 变成什么      实际用途
  ------------------------------------------------------------------
  Result<List<Novel>>       List<Novel>     装一摞（查询列表）
  Result<Novel>             Novel           装一个（查询单个）
  Result<Page<Novel>>       Page<Novel>     装一页（分页查询）
  Result<Void>              Void            什么都不装（删除）
  ------------------------------------------------------------------

【★ 为什么是 Void 不是 void？】
  ------------------------------------------------------------------
                  void                        Void
  ------------------------------------------------------------------
  身份            Java 关键字                 java.lang 包里的一个类
  能用在泛型里吗  ✗ 不能                      ✓ 能
  实际值          没有值                      永远是 null
  ------------------------------------------------------------------
  泛型 <T> 只接受类，不接受关键字。

【★ 为什么 success() 要写成 static？】

  假设不写 static（错误示范）：
    Result<List<Novel>> r = new Result<>();   // 先造一个空盒子
    r = r.success(novelList);                 // 用对象去调用方法

  问题：success() 和具体哪个盒子没关系，它只是一个"造盒子的工厂"。
        你却必须先 new 一个空盒子才能用 ——
        就像去工厂买手机，工厂说"你先买一部，我再给你生产一部"。

  写成 static 之后：Result.success(novelList)   // 直接通过"工厂名"生产

  三个好处：
    1. 不用先造空对象，类名直接调用
    2. 强制规范：外部无法 new Result<>() 乱填 code，
       只能通过工厂方法，保证"成功=200，失败=500"
    3. 命名即意图：Result.success(...) 读出来就是"我要一个成功的结果"

  口诀：static 表示这个方法属于"Result 这个概念"，
        不属于"某一个 Result 对象"。

【坑】
  · 不要直接返回 Entity（会暴露不该暴露的字段）
  · 不要裸抛异常给前端（会返回 HTML 错误页）
  · 分页场景建议单独定义 PageResult，而不是直接返回 Page 对象
    （Page 的字段名和结构会随框架版本变化，前端容易被绑死）


################################################################################
  第 3 课：全局异常处理
################################################################################

【大楼消防系统比喻】
  老办法：每个房间自备灭火器 —— 每个 Controller 方法里写 try-catch
  新办法：大楼装总控喷淋系统 —— 一个 GlobalExceptionHandler 全覆盖

  老办法的三个问题：
    · 100 个房间就要写 100 次
    · 有的房间忘了放灭火器 → 火就烧穿楼顶，返回 HTML 错误页
    · 每个房间灭火方式不一样 → 前端要处理 N 种格式

【三个核心零件】
  ------------------------------------------------------------------
  零件          代码                                  作用
  ------------------------------------------------------------------
  总控开关      @RestControllerAdvice                 监听所有 Controller
  烟雾传感器    @ExceptionHandler(XxxException.class) 声明触发条件
  喷淋头        Result.error(...)                     包装成标准信封
  ------------------------------------------------------------------

【@RestControllerAdvice vs @ControllerAdvice】
  ------------------------------------------------------------------
  注解                    返回什么    适用场景
  ------------------------------------------------------------------
  @ControllerAdvice       页面(HTML)  传统网站，后端渲染页面
  @RestControllerAdvice   JSON        前后端分离
  ------------------------------------------------------------------

【★ 异常分流策略（推荐模板）】
  ------------------------------------------------------------------
  异常类型                          处理方式              日志级别
  ------------------------------------------------------------------
  BusinessException（自定义）       Result.error(msg)     warn
  MethodArgumentNotValidException   取第一个校验消息       warn
  RateLimitException                429 + 提示            warn
  MaxUploadSizeExceededException    文件过大提示           warn
  RuntimeException                  业务异常兜底           error
  Exception                         系统繁忙，请稍后再试   error
  ------------------------------------------------------------------

  Spring 会自动选择"最具体"的处理器。
  BusinessException 同时匹配 RuntimeException 的处理器，
  但 Spring 会优先选 BusinessException 那个。

【★ 三个坑】

  坑1：@ExceptionHandler 的方法参数类型必须和声明的异常类型兼容
    ✗ @ExceptionHandler(MaxUploadSizeExceededException.class)
      public Result<Void> handle(MethodArgumentNotValidException e)
      → Spring 塞不进参数，处理器自己崩，用户看到 500

    ✓ @ExceptionHandler(MaxUploadSizeExceededException.class)
      public Result<Void> handle(MaxUploadSizeExceededException e)

  坑2：log.error 必须带异常对象
    ✗ log.error(e.getMessage());        // 只有一句话，没有堆栈
    ✓ log.error("描述", e);             // 有堆栈，能定位到行

  坑3：编译时异常抓不到
    @ExceptionHandler(RuntimeException.class) 抓不到 IOException / SQLException。
    ArithmeticException、NullPointerException、ClassCastException
    都是 RuntimeException 子类，能被兜底捕获 ✓

【★ 兜底异常必须用 error 级别】
  兜底处理器是"不该发生的事发生了"，属于系统故障。
  用 warn 会导致告警规则漏掉真正的线上问题。


################################################################################
  第 4 课：Lombok
################################################################################

【自动代笔秘书比喻】
  你写的（清爽）：
    @Data
    public class Novel {
        private Integer id;
        private String title;
    }

  编译后的（完整）：
    public class Novel {
        private Integer id;
        private String title;
        public Integer getId() { return id; }
        public void setId(Integer id) { this.id = id; }
        public String getTitle() { return title; }
        public void setTitle(String title) { this.title = title; }
        public String toString() { ... }
        public boolean equals(Object o) { ... }
        public int hashCode() { ... }
    }

  关键：.java 里看不到这些方法，但 .class 里全都有。
        框架运行时读的是 .class。

【核心注解】
  ------------------------------------------------------------------
  注解                      作用                          适用
  ------------------------------------------------------------------
  @Data                     getter+setter+toString+       Entity / DTO
                            equals+hashCode
  @Slf4j                    生成 log 对象                  Service / Controller
  @RequiredArgsConstructor  为所有 final 字段生成构造器   Service
  @Getter / @Setter         只生成其中一个                需要精细控制时
  @Builder                  建造者模式                     参数多的对象
  @NoArgsConstructor        无参构造器                     JPA 实体必需
  @AllArgsConstructor       全参构造器                     配合 @Builder
  @ToString.Exclude         排除某个字段                   ★ 脱敏
  ------------------------------------------------------------------

【为什么 @RequiredArgsConstructor 只给 final 字段生成构造器？】
  final 表示"赋值后不能改"。
  Lombok 的设计哲学：只有必须初始化的字段，才需要放进构造器。
  非 final 字段可以在对象创建后再赋值，不需要强制注入。

【★ 坑】
  · Entity 上慎用 @Data
    equals/hashCode 基于所有字段，两个内容相同但 id 不同的对象会被判等，
    业务上通常不对。
    推荐：@Getter + @Setter + @EqualsAndHashCode(of = "id")
  · @Data 的 toString() 会打印所有字段
    → 密码哈希、token 会进日志
    解法：@ToString.Exclude
  · 双向关联的 toString() 会递归 → 栈溢出
  · @Value + @RequiredArgsConstructor 混用时，@Value 字段不能是 final


################################################################################
  第 5 课：参数校验
################################################################################

【机场安检比喻】
  老做法：恐怖分子已经上飞机了才被发现
    → 前端传空书名，后端照单全收，直到数据库报 NOT NULL 才失败

  新做法：在登机口设安检门
    → 空书名直接拒绝，根本不用进 Service、不用查数据库

【三层校验体系】
  ------------------------------------------------------------------
  层级            作用                          代码
  ------------------------------------------------------------------
  前端校验        提升体验，减少无效请求        if (!name) return
  Controller 校验 拦截非法数据，保护后端        @Valid + @NotBlank
  数据库校验      最后一道防线                  @Column(nullable = false)
  ------------------------------------------------------------------

  ★ 前端校验可以被绕过（用 Postman 直接调接口），后端校验绝对不能省。

【三个校验注解的区别】
  ------------------------------------------------------------------
  注解         能用在哪                    检查内容
  ------------------------------------------------------------------
  @NotNull     任何类型                   不能是 null
                                           null ✗  "" ✓  " " ✓
  @NotEmpty    String/集合/数组/Map       不能 null 且长度>0
                                           null ✗  "" ✗  " " ✓
  @NotBlank    只能 String                不能 null、""、全空格
                                           null ✗  "" ✗  " " ✗
  ------------------------------------------------------------------

【常用校验注解速查】
  ------------------------------------------------------------------
  注解                     用途
  ------------------------------------------------------------------
  @NotBlank / @NotNull     非空
  @Size(min, max)          长度范围（String / 集合）
  @Min / @Max              数值范围
  @Email                   邮箱格式
  @Pattern(regexp)         正则
  @Positive / @Negative    正数 / 负数
  @Past / @Future          时间范围
  @Valid                   嵌套对象校验 ★
  ------------------------------------------------------------------

【★ @Valid 的作用】
  @PostMapping
  public Result<Novel> add(@RequestBody @Valid NovelDTO dto)

  @RequestBody：把前端 JSON 转成 DTO 对象
  @Valid：启动校验，检查 DTO 里所有带校验注解的字段

  没有 @Valid：Spring 看到 @NotBlank 也不会检查，直接放行。

【MethodArgumentNotValidException 拆解】
  @ExceptionHandler(MethodArgumentNotValidException.class)
  public Result<Void> handleValid(MethodArgumentNotValidException e) {
      String msg = e.getBindingResult()      // 安检报告
                    .getFieldErrors()        // 所有违规字段
                    .get(0)                  // 第一个违规
                    .getDefaultMessage();    // @NotBlank(message="...") 里的文字
      return Result.error(msg);
  }

【★ 坑】
  · @NotBlank 不能用在 Integer 上（只接受 String）
  · 嵌套对象校验，内部字段也要加 @Valid
  · 校验放 Controller 还是 Service？
    Controller 管"格式校验"（非空、长度、格式）
    Service    管"业务校验"（是否存在、库存够不够、余额足不足）
  · @Validated 支持分组校验（不同场景用不同规则）


################################################################################
  第 6 课：DTO 分离
################################################################################

【访客登记表比喻】
  老做法：让访客直接填人事档案
    → 他本来只该填"姓名"，但你把档案摊在他面前，
      他顺手把"工号""入职日期"也填了，甚至乱填

  新做法：只给访客一张登记表，上面只有该填的字段

【DTO / VO / Entity 三者职责】
  ------------------------------------------------------------------
  名称      方向            职责                      特点
  ------------------------------------------------------------------
  DTO       前端 → 后端     接收参数                  带校验注解
  Entity    后端 ↔ 数据库   表映射                    带 JPA 注解
  VO        后端 → 前端     返回数据                  可裁剪、可脱敏
  ------------------------------------------------------------------

  数据流：
    DTO → Service 转成 Entity → 数据库 → 转成 VO → 前端

【DTO 里不该有什么】
  ✗ id（数据库 ID 不该由前端决定）
  ✗ status（状态是后端业务决定的）
  ✗ totalWords（字数是后端算出来的）
  ✗ lastUpdateTime（时间是后端生成的）
  ✗ role（权限不该由前端指定）★ 越权风险

【核心价值】
  这不只是"规范"，而是真实的越权防护 ——
  防止前端通过传 id 来覆盖别人的数据，
  或者通过传 role=ADMIN 给自己提权。

【VO 的价值】
  · 脱敏：去掉 passwordHash
  · 裁剪：详情页不给正文，只给目录
  · 组合：把多个表的数据组装成一个前端好用的结构
  · 稳定：内部字段改名不影响前端契约


################################################################################
  第 7 课：后端搜索
################################################################################

【图书馆查书比喻】
  老做法：把图书馆 10 万本书搬到前台，让顾客自己一本本翻
  新做法：告诉管理员书名，他直接去书架拿

【JPA 方法名推导】
  findBy      → 查询
  Title       → 按 title 字段
  Containing  → 包含，自动生成 LIKE %keyword%
  → SELECT * FROM novel WHERE title LIKE '%关键词%'

【常用后缀】
  ------------------------------------------------------------------
  后缀                      生成的 SQL
  ------------------------------------------------------------------
  Containing / Like         LIKE %x%
  StartingWith              LIKE x%
  EndingWith                LIKE %x
  GreaterThan / LessThan    > / <
  Between                   BETWEEN
  In                        IN (...)
  IsNull / IsNotNull        IS NULL / IS NOT NULL
  OrderByXxxAsc/Desc        排序
  And / Or                  组合条件
  ------------------------------------------------------------------

【★ 坑】
  · LIKE '%keyword%' 前面有通配符 → 不走索引
  · 数据量大时要上 Elasticsearch 或全文索引
  · 如果是 LIKE 'keyword%'（前缀匹配）则可以用上索引
  · 组合条件的方法名过长时，应该改用 @Query 手写


################################################################################
  第 8 课：分页查询
################################################################################

【餐厅点菜比喻】
  老做法：厨房一次做 100 道菜全端上来
    · 厨房累瘫（生成巨大 JSON）
    · 传菜员跑断腿（网络传输）
    · 桌子堆不下（渲染 100 行 DOM）

  新做法：每次只上 8 道，吃完再点

【★ 前端分页 vs 后端分页】
  ------------------------------------------------------------------
  对比项              前端分页                后端分页
  ------------------------------------------------------------------
  后端查多少数据      全部（100 条甚至 10 万）只查当前页
  网络传输量          巨大                    极小
  后端内存压力        大                      小
  前端内存压力        巨大                    几乎没有
  前端渲染压力        巨大                    几乎没有
  翻页体验            快（本地切数组）        稍慢（要发请求）
  ------------------------------------------------------------------

  ★ 不是"谁更好"的问题，而是"数据量大了前端分页根本不可用"。

【Page 对象的结构】
  {
    "content": [ ... ],       // 当前页数据
    "totalElements": 100,     // 总条数
    "totalPages": 20,         // 总页数
    "number": 1,              // 当前页（★ 从 0 开始）
    "size": 8,                // 每页大小
    "first": false,           // 是否首页
    "last": false             // 是否末页
  }

  前端只需要三个字段：
    content       → 表格数据
    totalElements → "共 X 条"
    totalPages    → 分页按钮数量

【★ 坑】
  · Spring Data 页码从 0 开始，前端通常从 1 开始 → Service 层要 page - 1
  · 必须限制 size 最大值（如 100），防止前端传 99999 拖垮数据库
  · 深分页问题：LIMIT 1000000, 10 会先扫 1000010 行再丢弃前 1000000 行
    解法：游标分页（WHERE id > lastId ORDER BY id LIMIT 10）
  · 排序字段要加索引，否则每次分页都要 filesort


################################################################################
  第 9 课：事务控制
################################################################################

【结婚誓词比喻】
  delete 方法里有两件事：删小说 + 重排章节号
  老问题：小说删了，重排到一半数据库断了 → 小说没了，章节还是乱的
        就像戒指戴了一半，司仪问"你愿意吗"，你说"算了"。
        这算结了还是没结？

  @Transactional 就像结婚誓词："无论好坏，要么一起过，要么不过。"

【ACID 四大特性】
  ------------------------------------------------------------------
  字母  英文          中文    含义
  ------------------------------------------------------------------
  A     Atomicity     原子性  操作不可分割，要么全成功，要么全失败
  C     Consistency   一致性  数据始终保持合法状态
  I     Isolation     隔离性  多个事务互不干扰
  D     Durability    持久性  成功后就永久保存
  ------------------------------------------------------------------

【@Transactional 的关键参数】
  ------------------------------------------------------------------
  参数            作用
  ------------------------------------------------------------------
  rollbackFor     指定哪些异常触发回滚（默认只回滚 RuntimeException）
  readOnly        只读事务，优化性能（查询方法加）
  propagation     传播行为，默认 REQUIRED
  timeout         超时时间（秒）
  isolation       隔离级别，默认用数据库的
  ------------------------------------------------------------------

  ★ 推荐写法：@Transactional(rollbackFor = Exception.class)
    表示"任何异常都回滚"，比默认行为更严格。

【★ 五个必知的大坑】

  坑1：同类内部方法调用 @Transactional 会失效
    @Service
    public class Svc {
        public void methodA() {
            methodB();        // ← 直接调用走 this，绕过代理，methodB 的事务失效
        }
        @Transactional
        public void methodB() { ... }
    }
    原因：Spring 事务基于 AOP 代理。外部调用走代理，内部调用走 this。
    解法：注入自己 / AopContext.currentProxy() / 拆分到另一个类

  坑2：默认只回滚 RuntimeException
    受检异常（IOException 等）默认不回滚，必须写 rollbackFor

  坑3：catch 吃掉异常 = 回滚失效
    try {
        ...
    } catch (Exception e) {
        log.error("出错了", e);    // ← 异常被吃掉，Spring 以为成功了
    }
    要么不 catch，要么 catch 后重新 throw

  坑4：事务方法必须是 public
    非 public 方法上的 @Transactional 不生效

  坑5：事务里做耗时操作 = 长事务
    事务里调用外部 API、发消息、处理大文件，
    会长时间占用数据库连接，导致连接池耗尽。
    解法：把耗时操作挪到事务外，或提交后再做

【传播行为（7 种，知道前两个即可）】
  ------------------------------------------------------------------
  传播行为        含义
  ------------------------------------------------------------------
  REQUIRED（默认） 有事务就加入，没有就新建
  REQUIRES_NEW    总是新建事务，挂起当前事务
  NESTED          嵌套事务（保存点）
  SUPPORTS        有就用，没有就非事务执行
  NOT_SUPPORTED   非事务执行，挂起当前事务
  MANDATORY       必须在事务中，否则抛异常
  NEVER           必须不在事务中，否则抛异常
  ------------------------------------------------------------------


################################################################################
  第 10 课：日志规范
################################################################################

【行车记录仪比喻】
  出事故时，行车记录仪是唯一能还原真相的东西。
  线上出问题时，日志是唯一的线索。

【System.out.println vs SLF4J】
  ------------------------------------------------------------------
  对比项        System.out.println        SLF4J + @Slf4j
  ------------------------------------------------------------------
  输出          仅控制台                  控制台 + 文件
  级别控制      无                        DEBUG < INFO < WARN < ERROR
  性能          强制字符串拼接            占位符 {} 延迟拼接
  生产环境      重启即丢失                文件持久保存，自动切割
  ------------------------------------------------------------------

【★ 日志级别使用策略】
  ------------------------------------------------------------------
  级别    什么时候用                            要不要堆栈
  ------------------------------------------------------------------
  DEBUG   开发调试，生产环境关闭                否
  INFO    关键业务节点（登录、发布、删除）      否
  WARN    业务异常、可预期的错误（参数错、限流）否
  ERROR   系统异常、不可预期的错误（NPE、SQL错） ★ 必须带
  ------------------------------------------------------------------

【占位符 vs 字符串拼接】
  ✗ log.debug("用户 " + name + " 登录");     // 无论级别高低都会拼接
  ✓ log.debug("用户 {} 登录", name);         // 级别不够时不执行 toString

【配置】
  logging.level.com.example=INFO
  logging.file.name=logs/app.log
  logging.logback.rollingpolicy.max-file-size=50MB
  logging.logback.rollingpolicy.max-history=30

【★ 坑】
  · 只配 file.name 不配 max-file-size，日志会无限膨胀占满磁盘
  · log.error(e.getMessage()) 是错的 —— 没有堆栈，线上查不到行号
  · 日志里绝对不能出现密码、完整 token、身份证号、手机号
    @Data 的 toString() 会打印所有字段，log 整个对象 = 泄露
  · 异步日志（AsyncAppender）能提升高并发性能，
    但队列满了会丢日志

【进阶：traceId】
  并发场景下，日志文件里多条请求的日志是交错的。
  给每个请求分配一个 traceId 打到每一行，就能 grep 出完整链路。
  实现：MDC（本质是 ThreadLocal）+ Filter，在 finally 里清理。

【自动试菜机比喻】
  老做法：厨师做完菜自己尝
    · 太慢：改一行测一次要 2 分钟
    · 易漏：忘了测边界情况

  ------------------------------------------------------------------
  @SpringBootTest   启动整个 Spring 容器        Service 是 null

【测试金字塔】
  ------------------------------------------------------------------
  类型          启动容器  耗时    测什么              数量
  ------------------------------------------------------------------
  纯单元测试    否        毫秒    Service 业务逻辑    多 ★

  E2E           否        分钟    UI 全流程           极少
  ------------------------------------------------------------------

【★ 什么代码值得测】
  ------------------------------------------------------------------
  值得测 ✓                          不值得测 ✗
  ------------------------------------------------------------------
  业务逻辑（计算、状态流转）         Getter / Setter
  边界条件（空值、极值、越界）       纯 DTO 定义
  异常分支（不存在、无权限）         框架自带功能
  算法（排序、聚合）                 简单的一行委托
  ------------------------------------------------------------------

################################################################################
  第 12 课：API 文档（Knife4j）
################################################################################

【使用说明书比喻】
  API 文档就是系统的"使用说明书"，告诉前端：
    有哪些接口？地址是什么？要传什么参数？会返回什么数据？

  Knife4j 是 Swagger/OpenAPI 的"增强皮肤"。

【解决的核心问题】
  ------------------------------------------------------------------
  没有 Knife4j                          有 Knife4j
  ------------------------------------------------------------------
  手写文档，改代码就过时                注解写代码里，自动同步
  前端问"这个接口传啥参数"              前端自己打开 /doc.html 看
  联调时口头对字段                      在线调试，点一下发请求
  ------------------------------------------------------------------

【常用注解】
  ------------------------------------------------------------------
  注解                          用在哪
  ------------------------------------------------------------------
  @Tag(name = "小说管理")        Controller 类
  @Operation(summary = "创建小说") 方法
  @Parameter(description = "页码")  参数
  @Schema(description = "书名")      DTO/VO 字段
  @SecurityRequirement             声明需要 token
  @SecurityScheme                  配置类里定义认证方案
  ------------------------------------------------------------------

【★ 坑】
  · 生产环境必须关掉（knife4j.enable=false）
    否则把全部接口暴露给外人，等于给攻击者一张地图
  · 文档要和代码同步更新，过时的文档比没有文档更糟


################################################################################
  第 13 课：多环境配置（Profile）
################################################################################

【三家餐厅比喻】
  开发店（dev）：你家的厨房，随便折腾，锅糊了没事
  测试店（test）：朋友来试吃，规矩一点
  生产店（prod）：正式开门迎客，绝对不能出错

  问题：三家店的"运营手册"能一样吗？

【核心概念对照表】
  ------------------------------------------------------------------
  概念                            餐厅比喻                    代码
  ------------------------------------------------------------------
  application.properties          所有门店通用的规矩          公共配置
  application-dev.properties      家厨房专用手册              开发配置
  application-prod.properties     正式门店手册                生产配置
  spring.profiles.active=dev      今天在家厨房试做            激活开发环境
  --spring.profiles.active=prod   今天正式营业                命令行切换
  ${DB_PASSWORD}                  保险柜密码不写进手册        环境变量
  ddl-auto=update                 随便改装修                  开发自动改表
  ddl-auto=validate               只检查消防规范              生产只校验
  ------------------------------------------------------------------

【典型差异】
  ------------------------------------------------------------------
  配置项            dev                      prod
  ------------------------------------------------------------------
  数据库地址        localhost                ${DB_URL}
  数据库密码        明文                     ${DB_PASSWORD}
  ddl-auto          update                   validate
  show-sql          true                     false
  日志级别          INFO                     WARN
  接口文档          true                     false
  server.port       8080                     80 或 443
  ------------------------------------------------------------------

【★ 三个"绝对不能"（保命规则）】

  规则1：数据库密码绝对不能提交到 Git
    ✗ spring.datasource.password=123456
    ✓ spring.datasource.password=${DB_PASSWORD}
    ★ 而且不要留默认值，否则"忘配环境变量也能启动"

  规则2：生产环境绝对不能 ddl-auto=update
    想象：正式营业时厨师说"我觉得灶台位置不对"，当场拆墙改布局？
    正确做法：validate（只检查，不动手），改表走 Flyway / Liquibase

  规则3：配置文件名字绝对不能写错
    正确：application-prod.properties
    错误：application_prod.properties（下划线）
          prod-application.properties（顺序反了）

【配置优先级（从高到低）】
  命令行参数 > 环境变量 > application-{profile}.properties
            > application.properties > 默认值

【坑】
  · 生产数据库不要用 root 账号，要建只有必要权限的专用账号
  · 敏感配置建议用配置中心（Nacos / Apollo）而不是环境变量，
    便于集中管理和审计
  · Spring Boot 2.4+ 引入了 spring.config.import，
    配置文件的加载方式有变化


################################################################################
  第 14 课：Docker 打包
################################################################################

【最佳实践清单】
  ------------------------------------------------------------------
  要点              做法                              作用
  ------------------------------------------------------------------
  基础镜像          用 alpine / slim 精简版           减小体积和攻击面
  多阶段构建        builder 阶段 + runtime 阶段       最终镜像不含编译工具
  非 root 运行      创建 appuser，USER appuser        降低容器逃逸危害
  敏感信息          环境变量注入，不写进镜像          镜像层可被任何人拉取
  健康检查          HEALTHCHECK 指令                  配合编排工具自动恢复
  镜像标签          语义化版本 v1.2.3                  避免只用 latest 无法回滚
  .dockerignore     排除 .git / target / logs         加速构建，减小层体积
  ------------------------------------------------------------------

【两阶段构建模板（Java）】
  # 第一阶段：构建
  FROM maven:3.9-eclipse-temurin-21-alpine AS builder
  WORKDIR /app
  COPY pom.xml .
  RUN mvn dependency:go-offline -B      # ★ 先下依赖，利用缓存层
  COPY src ./src
  RUN mvn clean package -DskipTests

  # 第二阶段：运行
  FROM eclipse-temurin:21-jre-alpine
  WORKDIR /app
  COPY --from=builder /app/target/*.jar app.jar
  EXPOSE 8080
  ENTRYPOINT ["java", "-jar", "app.jar"]

【为什么分两阶段？】
  构建需要 Maven + JDK + 全部源码（几百 MB）
  运行只需要 JRE + 一个 jar（几十 MB）
  → 体积小、启动快、攻击面小

【★ 坑】
  · EXPOSE 只是文档性质的声明，不影响实际运行
    要和 server.port 保持一致，否则会误导人
  · 没有 .dockerignore 会把 target / .git / node_modules 都复制进去
  · 镜像层里的敏感信息删了也还在（分层存储），
    所以密码必须用环境变量注入，绝不能 COPY 进去
  · docker-compose 的端口映射是"宿主机:容器"，
    容器内端口要和 server.port 一致


################################################################################
  面试会怎么问
################################################################################

  Q1：@Transactional 什么情况下会失效？
  A： 五个坑：同类内部调用、默认不回滚受检异常、
     catch 吃掉异常、方法非 public、长事务。
     ★ 重点讲前三个。

  Q2：前端分页和后端分页怎么选？
  A： 数据量小可以前端分页（翻页快），
     数据量大必须后端分页（否则网络和内存都爆炸）。

  Q3：全局异常处理怎么做的？
  A： @RestControllerAdvice + @ExceptionHandler 分流。
     业务异常 warn 级别返回友好提示，
     系统异常 error 级别带堆栈，兜底返回统一话术。

  Q4：为什么用 DTO 而不是直接用 Entity 接收参数？
  A： 防越权赋值（前端传 id 覆盖别人数据、传 role 提权），
     同时让校验规则和数据库解耦。

  Q5：生产环境和开发环境的配置怎么隔离？
  A： Spring Profile。敏感信息走环境变量，
     生产 ddl-auto=validate + show-sql=false + 关闭接口文档。

  Q6：Spring 的 IoC 和 AOP 是什么？
  A： IoC 是把对象创建权交给容器（为什么要注入而不是 new）。
     AOP 是把横切逻辑（事务、日志、限流）从业务代码里抽出来。
     ★ 这是框架原理，详见 L5 框架部分。

  Q7：Docker 为什么要多阶段构建？
  A： 最终镜像里不含编译工具和源码，体积小、启动快、攻击面小。

  Q8：为什么不能在配置类里随便定义 Bean？
  A： ★ 结合自动配置的"退避机制"讲：
     Spring Boot 的自动配置类大多带 @ConditionalOnMissingBean，
     你一旦自己声明了同类型的 Bean，自动配置就会退避，
     可能丢掉框架预置的重要配置。
     正确做法是用 XxxCustomizer 扩展，而不是直接替换。
