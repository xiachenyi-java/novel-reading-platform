【★ 漏洞 1 详情：存储型 XSS 的完整攻击链】

  你的代码：
    FileController：
      String contentType = file.getContentType();
      if (contentType == null || !contentType.startsWith("image/")) {
          return Result.error("只能上传图片文件");
      }
      String ext = originalName.substring(originalName.lastIndexOf("."));
      String newName = UUID.randomUUID() + ext;        // ← ext 没校验！
      Files.copy(file.getInputStream(), targetPath);

    WebConfig：
      registry.addResourceHandler("/uploads/**")
              .addResourceLocations("file:" + uploadPath + "/");
      .excludePathPatterns("/uploads/**")              // ← 匿名可访问

  攻击流程：
    ① 攻击者准备一个 xss.html，内容是窃取 localStorage 的脚本
    ② 用 Postman 上传，手动设置 Content-Type: image/png
    ③ 后端校验通过，保存为 {uuid}.html
    ④ 攻击者访问 /uploads/{uuid}.html
    ⑤ 浏览器按 text/html 渲染并执行 JS
    ⑥ JS 读取 localStorage 里的 token → 发给攻击者
    ⑦ 攻击者拿到 token，完全接管账号

  ★ 注意：Content-Type 是客户端发来的 HTTP 头，可以随意伪造。
    只校验它等于没校验。

【★ 漏洞 2 详情（✓ 已修复）：异常处理器会崩】

  位置：common/GlobalExceptionHandler.java
    @ExceptionHandler(MaxUploadSizeExceededException.class)
    public Result<Void> handleFileSizeException(MethodArgumentNotValidException e)
                                                                    ↑ 类型不匹配

  为什么崩：
    Spring 要把抛出的 MaxUploadSizeExceededException 塞进
    MethodArgumentNotValidException 类型的参数 → 类型不兼容
    → 抛 IllegalArgumentException → 处理器自己失败
    → 用户看到默认的 500 错误页

  验证方法：
    上传一个 15MB 的文件（超过配置的 10MB），
    看返回的是"文件不能超过 10MB"还是 500。

  ✓ 已修复（GlobalExceptionHandler）：
    @ExceptionHandler(MaxUploadSizeExceededException.class)
    public Result<Void> handleFileSizeException(MaxUploadSizeExceededException e) {
        log.warn("传输文件过大: {}", e.getMessage());
        return Result.error("上传失败：文件大小不能超过 10MB");
    }
    参数类型已匹配，返回友好提示，不再 500。

P1 · 应该做
--------------------------------------------------------------------------------

  □ 文件头 magic number 校验
    位置：controller/FileController.java
    做法：读文件前几个字节，比对图片格式的魔数
      jpg  → FFD8FF
      png  → 89504E47
      gif  → 47494638
      webp → 52494646（RIFF 开头）
    意义：只改后缀名改不了真实文件类型，这是真正的"是不是图片"校验。

  □ 给 passwordHash 脱敏
    ① 缓存脱敏：UserService.getCurrentUser() 里缓存前 setPasswordHash(null)
    ② 日志脱敏：检查有没有 log.info("user={}", user)
       （@Data 的 toString 包含 passwordHash）
    ★ 和项目笔记/05-缓存体系.txt 的 P0 是同一件事

  □ 上传接口加权限和限流
    位置：controller/FileController.java
    改动：
      · 加 @RateLimit(key = "upload", limit = 10, window = 60)
      · 考虑是否要加 @RequireAdmin（取决于业务：只有管理员发小说→加；
        如果用户能传头像→不加，但要有其他限制）

  □ 上传响应头加固
    方案一：给 /uploads/** 加 X-Content-Type-Options: nosniff
    方案二：图片走独立的域名/端口，与主站隔离
    方案三：图片二次重绘（用 Thumbnailator 重新生成，彻底消除恶意载荷）
    ★ 方案三是根治，方案一二是缓解。

  □ 区分业务异常和系统异常
    位置：common/GlobalExceptionHandler.java
    问题：handleRuntimeException 直接返回 e.getMessage()，
          如果是数据库异常（SQLGrammarException），
          message 会包含表名、字段名、SQL 片段 → 泄露内部结构。
    改法：明确区分可预期的业务异常（直接返回 message）
          和不可预期的系统异常（返回统一话术）。

  □ CorsConfig 白名单配置化
    位置：config/CorsConfig.java + application-*.properties

【Q：你的项目做过哪些安全防护？】
  ★ 直接用上面那 10 条真实做过的，这是你最强的部分：
  "主要有几个方面：
   认证上，密码用 BCrypt 加密存储，登录接口做了 IP 限流防暴力破解，
   错误提示统一成'用户名或密码错误'防止账号枚举。

   权限上，用自定义注解 + 拦截器做 RBAC，
   普通用户访问管理员接口返回 403；
   涉及数据归属的接口会校验，比如删除章节时会检查
   这个章节是否属于该小说，防止水平越权。

   文件上传上，做了路径穿越校验（normalize + startsWith）
   和 UUID 重命名，避免文件覆盖和目录遍历。

   配置上，数据库密码和 JWT 密钥都走环境变量，
   生产环境关闭接口文档和 SQL 打印。"

【Q：文件上传只校验 Content-Type 够吗？】
  "不够。Content-Type 是客户端发来的 HTTP 头，可以随意伪造。
   要配合扩展名白名单和文件头 magic number 校验，
   才能真正确认是不是图片。
   另外如果上传目录可以匿名访问，
   要防止传一个 HTML 文件进去造成存储型 XSS。"

  ★ 这是一个很好的"我知道我项目的问题在哪"的回答，
    比假装完美更加分。前提是你要真的知道。

【Q：为什么你的项目关闭了 CSRF？】
  "因为用的是 JWT 而不是 Cookie。
   Cookie 会被浏览器自动携带，所以需要 CSRF token 防护；
   JWT 存在 localStorage，需要 JS 手动加到请求头，
   攻击者的网站读不到，CSRF 天然不成立。
   但如果哪天改成 Cookie 存 token，就必须重新开启。"
