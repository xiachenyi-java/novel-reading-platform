【✅ 已修复：登出后 refreshToken 依然有效（2026-10-05 复核）】

  原问题：
    登录时只写正向索引 refresh_token:{token} → userId，没写反向索引
    user_refresh:{userId} → token；登出时反查永远拿到 null → 删不掉 refreshToken。
    后果：登出只拉黑了 accessToken，攻击者（或用户自己）在 7 天内
    仍能用旧 refreshToken 换出新的 accessToken，等于"登出没登干净"。

  修复后的实现：
    · 登录（UserService.login）：同时写正向 + 反向索引，都是 7 天
    · 刷新（UserService.refresh）：先删旧的正向 + 反向索引（令牌轮换），
      再写入新 refreshToken 的正向 + 反向索引
    · 登出（UserController.logout）：用 user_refresh:{userId} 反查出
      refreshToken，把两个 key 一起删除；accessToken 进黑名单

  为什么需要双向索引：
    正向 refresh_token:{token} → userId ：刷新时用 token 查是哪个用户
    反向 user_refresh:{userId} → token ：登出时用 userId 查要删哪个 token
    两个方向都要用，所以两个都要存。

  验证方式：登出后，用旧 refreshToken 调 /users/refresh
            应返回"刷新令牌已过期或不存在"

  □ 登录失败次数限制
    现状：只有 IP 维度的限流（5次/60秒），攻击者换 IP 就能绕过。
    修法：Redis 计数，key = login:fail:{username}
          失败时 INCR，首次设置 15 分钟过期；达到 5 次抛"账号已锁定"

    修法：加一个 @PostConstruct 校验，prod profile 下发现是默认值就抛异常终止启动

  三、关键实现速查
################################################################################

【JWT Payload 结构】
  sub          → userId
  username     → 用户名
  role         → 角色（USER / ADMIN）
  iat / exp    → 签发时间 / 过期时间
  算法：HS256，密钥来自 jwt.secret

【拦截器三态逻辑】
  ------------------------------------------------------------------
  情况                              处理
  ------------------------------------------------------------------
  OPTIONS 预检请求                  直接放行
  游客路径（GET /novels/**）        有 token 就解析+查黑名单，没 token 也放行
  其他所有路径                      无 token → 401
                                    解析失败 → 401
                                    在黑名单 → 401
                                    @RequireAdmin 且非 ADMIN → 403
  ------------------------------------------------------------------

【黑名单数据结构】
  key   : blacklist:user:{userId}
  type  : Hash
  field : token 本身
  value : 过期时间戳（毫秒）
  ★ 没有整体 TTL，靠读取时惰性清理过期的 field

【MySQL user 表】
  id, username(unique), password_hash(BCrypt, length=60), role(默认 USER)
