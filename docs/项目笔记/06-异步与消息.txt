【技术亮点（面试可以主动讲）】

  ✓ ZSet 选型正确：跳表实现，插入和查询都是 O(log N)，
    比数据库 ORDER BY 的 O(N log N) 快几个数量级
  ✓ 用 findAllById 批量查库，避免了 N+1 问题（1 次查询而不是 N 次）
  ✓ 用 Map 保序组装：
     findAllById 返回的 List 顺序不保证和传入的 id 列表一致，
     所以用 novelIds（有序）遍历 + novelMap（O(1) 查找）来保序。
     ★ 这个细节很多人会踩坑，是很好的面试素材。
  ✓ 小说被删时跳过（novelMap.get(id) == null 就 continue），防止 NPE
  ✓ 热度用 Double 存、Long 返回，前端看到的是整数

【★ 缺口 3：排行榜无防刷】

  readChapter() 每调用一次就 +1，用户按 F5 刷新 100 次就是 100 热度。
  写个脚本一分钟就能把垃圾小说刷到榜首。

【★ 缺口 5：@Async 和 MQ 完全没开始】

  这个包叫"异步"，但异步的部分（第 4-8 步）一步都没做。

################################################################################
  三、关键实现速查
################################################################################

【排行榜读取流程】
  1. reverseRangeWithScores("ranking:novel:total", 0, top-1)
     → 返回 Set<TypedTuple<String>>，按 score 降序
  2. 拆成两个容器：
       List<Integer> novelIds   （保持顺序）
       Map<Integer, Double> scoreMap（存热度）
  3. findAllById(novelIds) 批量查库
     → 转成 Map<Integer, Novel> novelMap
  4. 按 novelIds 顺序遍历，从 novelMap 取详情、从 scoreMap 取热度
     → 组装 NovelRankVO
     → novelMap.get(id) == null 时 continue（小说已删）

【Redis Key】
  ranking:novel:total            ZSET  总榜，无 TTL
  ranking:novel:day:{yyyyMMdd}   ZSET  日榜，写入后 expire 2 天

【热度写入点】
  NovelServiceIml.readChapter()：
    总榜、日榜都写：
      stringRedisTemplate.opsForZSet()
              .incrementScore("ranking:novel:total", String.valueOf(novelId), 1);
      stringRedisTemplate.opsForZSet()
              .incrementScore(dailyRankKey, String.valueOf(novelId), 1);
      stringRedisTemplate.expire(dailyRankKey, 2, TimeUnit.DAYS);

【接口】
  GET /novels/ranking?top=10&type=total|daily
  top 上限被限制为 100（硬编码）
  ★ 注意：前端 api/novel.js 的 getRanking 只接受一个参数，
    第二个参数 type 被丢弃了，所以日榜切换实际不生效（前端 bug）
    位置：novel-frontend/src/api/novel.js
