################################################################################
  一、ORM 选型：JPA vs MyBatis-Plus
################################################################################

【两种设计哲学】
  ------------------------------------------------------------------
  维度            JPA / Hibernate        MyBatis-Plus
  ------------------------------------------------------------------
  核心思想        面向对象，对象即表       SQL 可控，半自动
  写代码          几乎不写 SQL            简单 CRUD 自动生成，
                                          复杂查询手写 SQL
  学习曲线        陡（要懂 JPA 规范）      平缓（会 SQL 就会用）
  复杂查询        痛苦（Criteria 难用）    友好
  自动建表        支持（ddl-auto）        不支持（推荐 Flyway）
  国内流行度      中等                    ★ 主流
  ------------------------------------------------------------------

【国内为什么 MyBatis-Plus 更主流】
  1. 复杂查询友好 —— 业务查询千奇百怪，JPA 的 Criteria 很难写
  2. SQL 可控 —— DBA 能 Review 到每一条 SQL，方便优化
  3. 团队上手快 —— 会 SQL 就能用
  4. 分页插件成熟

【★ 面试标准答案（背下来）】
  "两者的选择取决于场景。
   JPA 适合领域模型清晰、CRUD 为主的系统，开发效率高、类型安全；
   MyBatis-Plus 适合复杂查询多、SQL 需要精细优化的场景，可控性强。
   国内互联网业务查询复杂、迭代快，所以 MyBatis-Plus 更主流。"

【★ JPA 的三个痛点（面试可讲）】
  1. findAllById 不保证返回顺序，要手动用 Map 重排
  2. 复杂关联查询要写 Criteria API，可读性差
  3. 关联对象的加载策略（懒加载 / 急加载）容易踩坑

【MyBatis-Plus 常用能力】
  ------------------------------------------------------------------
  能力                    说明
  ------------------------------------------------------------------
  BaseMapper              单表 CRUD 不用写
  IService / ServiceImpl  Service 层也帮你写好了
  LambdaQueryWrapper      ★ 字段名有编译期检查（比字符串写法好）
  PaginationInnerInterceptor  分页插件
  @TableLogic             逻辑删除自动处理
  自动填充                @TableField(fill = FieldFill.INSERT)
  ------------------------------------------------------------------


################################################################################
  一·补充、动态查询 —— 多条件组合怎么拼
################################################################################

【问题场景】
  列表接口要支持"搜索 + 分类 + 状态"三个可选条件，
  用户可能只传一个、传两个、或全都不传 —— 组合起来 2³ = 8 种情况。

  如果每种组合写一个方法，方法名会爆炸：
    findByCategory(...)
    findByTitleContaining(...)
    findByCategoryAndTitleContaining(...)
    ... 一共 8 个

【三种解法对比】
  ------------------------------------------------------------------
  方案                代码量    扩展性    适用
  ------------------------------------------------------------------
  方法名推导          爆炸      差        条件固定 1-2 个
  @Query + null 判断  少        差        条件少且不常变
  Specification       中        好 ★      条件可选、会持续增加
  QueryDSL            多        好        重度使用（要引依赖）
  ------------------------------------------------------------------

--------------------------------------------------------------------------------
方案一：方法名推导（组合爆炸）
--------------------------------------------------------------------------------
  List<Novel> findByCategory(String category, Pageable p);
  List<Novel> findByTitleContaining(String kw, Pageable p);
  List<Novel> findByCategoryAndTitleContaining(String c, String kw, Pageable p);
  ... 3 个条件 = 8 个方法

  ★ 只适合 1-2 个固定条件。条件一多就是灾难。

--------------------------------------------------------------------------------
方案二：@Query + null 判断（简洁但脆弱）
--------------------------------------------------------------------------------
  @Query("SELECT n FROM Novel n WHERE " +
         "(:category IS NULL OR n.category = :category) AND " +
         "(:keyword IS NULL OR n.title LIKE %:keyword%)")
  Page<Novel> search(String category, String keyword, Pageable p);

  优点：一个方法搞定所有组合
  缺点：
    · 条件一多 SQL 就长得没法看
    · 参数为 null 时，某些数据库/驱动会报类型推断错误
    · 加新条件要改 SQL 字符串，容易改错

--------------------------------------------------------------------------------
方案三：Specification（★ 推荐）
--------------------------------------------------------------------------------

  【第一步：Repository 多继承一个接口】
    public interface NovelRepository extends JpaRepository<Novel, Integer>,
                                              JpaSpecificationExecutor<Novel> { }

  【第二步：每个条件写一个独立方法】
    public class NovelSpecifications {
        private NovelSpecifications() {}     // 工具类，禁止实例化

        public static Specification<Novel> titleContains(String keyword) {
            return (root, query, cb) ->
                    StringUtils.hasText(keyword)
                            ? cb.like(root.get("title"), "%" + keyword + "%")
                            : null;
        }

        public static Specification<Novel> categoryEquals(String category) {
            return (root, query, cb) ->
                    StringUtils.hasText(category)
                            ? cb.equal(root.get("category"), category)
                            : null;
        }
    }

  【第三步：用 allOf 组合】
    Specification<Novel> spec = Specification.allOf(
            NovelSpecifications.titleContains(keyword),
            NovelSpecifications.categoryEquals(category),
            NovelSpecifications.statusEquals(status)
    );
    return novelRepository.findAll(spec, pageable);

  【★ 核心技巧：返回 null 的 Specification 会被自动忽略】
    这是 Spring Data 的官方约定，不是野路子。
    所以不需要写一堆 if (keyword != null) —— 空条件直接"消失"。

  【老版本写法（allOf 不可用时效果一样）】
    Specification<Novel> spec = Specification
            .where(NovelSpecifications.titleContains(keyword))
            .and(NovelSpecifications.categoryEquals(category));

  【★ 三个参数是什么】
    root   —— 查询的根实体，root.get("title") 相当于 SQL 里的列名
    query  —— 整个查询对象（可用来加 order by / distinct）
    cb     —— CriteriaBuilder，工厂类，cb.like / cb.equal / cb.and 都从这来

    这就是 Criteria API —— JPA 的"用 Java 代码拼 SQL"。

  【优点】
    · 每个条件独立、可单独测试
    · 条件任意组合，加新维度不用改已有代码
    · 类型安全（字段名写错编译期就报错）
    · 天然防 SQL 注入（框架生成 PreparedStatement）

  【缺点】
    · 复杂查询（多表 JOIN + 子查询）写起来很啰嗦，这种场景手写 SQL 更清楚
    · 比方法名推导多一层概念

  【★ 什么时候不该用它】
    条件固定的 1-2 个 → 方法名推导更简单
    复杂多表查询 → @Query 手写 SQL 更直观

--------------------------------------------------------------------------------
MyBatis-Plus 的对应方案：QueryWrapper
--------------------------------------------------------------------------------
  LambdaQueryWrapper<Novel> wrapper = new LambdaQueryWrapper<>();
  wrapper.like(StringUtils.hasText(keyword), Novel::getTitle, keyword)
         .eq(StringUtils.hasText(category), Novel::getCategory, category);

  ★ 注意第一个参数是 boolean —— 条件为 false 时这个条件不拼接。
    这是 MyBatis-Plus 版的"空条件自动忽略"，思路和 Specification 返回 null 一样。

  ★ 面试对比可以这么答：
    "JPA 用 Specification + Criteria API，MyBatis-Plus 用 QueryWrapper，
     核心思路都是'把每个条件独立出来、按需拼接'，
     区别是 JPA 走对象模型、MP 走 SQL 片段。"


################################################################################
  二、索引原理 ★★★ 面试必问
################################################################################

--------------------------------------------------------------------------------
2.1 为什么是 B+ 树
--------------------------------------------------------------------------------

  ------------------------------------------------------------------
  数据结构    为什么不用
  ------------------------------------------------------------------
  数组        插入删除要移动元素，O(N)
  链表        查询要遍历，O(N)
  哈希表      不支持范围查询（> < BETWEEN ORDER BY）
  二叉树      数据量大时树太高，磁盘 IO 次数多
  B 树        非叶子节点也存数据，一个节点能放的索引项少 → 树更高
  B+ 树       ✓ 非叶子只存索引 → 能放更多 → 树更矮 → IO 更少
              ✓ 叶子节点用链表连接 → 范围查询高效
  ------------------------------------------------------------------

  【★ 关键：为什么树矮很重要】
    MySQL 一次磁盘 IO 读一页（16KB）。
    树高 3 层 → 最多 3 次 IO 就能找到数据。
    3 层的 B+ 树大约能存 2000 万条记录（假设主键 bigint）。

--------------------------------------------------------------------------------
2.2 聚簇索引 vs 二级索引
--------------------------------------------------------------------------------

  ------------------------------------------------------------------
  类型          说明                          叶子节点存什么
  ------------------------------------------------------------------
  聚簇索引      主键索引，一张表只有一个      完整行数据
  二级索引      自己建的索引，可以有多个      主键值
  ------------------------------------------------------------------

  【★ 回表】
    用二级索引查到主键值后，还要再去聚簇索引查一次完整数据。
    两次查询 = 回表。

  【★ 覆盖索引】
    如果查询需要的字段都在索引里，就不用回表。
      SELECT id, title FROM novel WHERE title = 'xx'
      （建了 title 索引，id 是主键自动带在二级索引的叶子节点里）
    → EXPLAIN 的 Extra 列显示 "Using index"

  ★ 这也是为什么"不要写 SELECT *"—— 会让覆盖索引失效，强制回表。

--------------------------------------------------------------------------------
2.3 最左前缀原则
--------------------------------------------------------------------------------

  联合索引 (a, b, c) 相当于建了三个索引： (a) (a,b) (a,b,c)

  ------------------------------------------------------------------
  WHERE 条件                          能否用上索引
  ------------------------------------------------------------------
  a = 1                               ✓ 用上 a
  a = 1 AND b = 2                     ✓ 用上 a, b
  a = 1 AND b = 2 AND c = 3           ✓ 全部用上
  a = 1 AND c = 3                     ✓ 只用上 a（c 用不上）
  b = 2                               ✗ 跳过了最左的 a
  b = 2 AND c = 3                     ✗
  a = 1 AND c = 3 AND b = 2           ✓ 优化器会自动重排
  a > 1 AND b = 2                      △ a 用范围，b 用不上
  ------------------------------------------------------------------

  ★ 范围查询会中断后续列的使用。

--------------------------------------------------------------------------------
2.4 索引失效的常见场景
--------------------------------------------------------------------------------

  □ 在索引列上做运算或函数
    ✗ WHERE YEAR(create_time) = 2026
    ✓ WHERE create_time >= '2026-01-01' AND create_time < '2027-01-01'

  □ 隐式类型转换
    ✗ WHERE phone = 13800000000   （phone 是 varchar）
    ✓ WHERE phone = '13800000000'

  □ LIKE 以 % 开头
    ✗ WHERE title LIKE '%剑来'
    ✓ WHERE title LIKE '剑来%'

  □ OR 连接非索引列
    ✗ WHERE title = 'x' OR summary = 'y'  （summary 无索引）

  □ 违反最左前缀原则

  □ 使用 != 或 NOT IN（视情况可能全表扫）

  □ IS NULL / IS NOT NULL（视情况）

  □ 索引列参与计算：WHERE id + 1 = 10

--------------------------------------------------------------------------------
2.5 EXPLAIN 执行计划解读 ★★
--------------------------------------------------------------------------------

  EXPLAIN SELECT * FROM novel ORDER BY last_update_time DESC LIMIT 10;

  ------------------------------------------------------------------
  列        重点看什么
  ------------------------------------------------------------------
  id        查询序号，越大越先执行
  select_type  查询类型（SIMPLE / PRIMARY / SUBQUERY / UNION）
  table     表名
  type      ★ 访问类型，从好到坏：
              system > const > eq_ref > ref > range > index > ALL
            ★ 出现 ALL 就是全表扫描，必须优化
  possible_keys  可能用到的索引
  key       ★ 实际使用的索引。NULL 表示没走索引
  key_len   索引使用的字节数（可以判断用了联合索引的几列）
  ref       索引列的比较对象
  rows      ★ 预估扫描行数，越小越好
  filtered  按条件过滤后剩余的百分比
  Extra     ★ 额外信息：
              "Using index"      → 覆盖索引 ✓ 很好
              "Using where"      → 在存储引擎层过滤
              "Using filesort"   → 需要额外排序 ✗ 要优化
              "Using temporary"  → 用了临时表 ✗ 要优化
  ------------------------------------------------------------------

--------------------------------------------------------------------------------
2.6 索引设计原则
--------------------------------------------------------------------------------

  【该建索引的字段】
    ✓ 频繁出现在 WHERE / ORDER BY / GROUP BY / JOIN ON 的字段
    ✓ 区分度高的字段（如 user_id，而不是 gender）
    ✓ 主键、外键

  【不该建索引的字段】
    ✗ 区分度低的（性别、状态只有几个值）
    ✗ 频繁更新的（每次更新都要维护索引）
    ✗ 很少查询的
    ✗ 大文本字段（TEXT / BLOB）

  【★ 索引不是越多越好】
    · 每个索引占磁盘空间
    · 每次 INSERT/UPDATE/DELETE 都要维护所有索引 → 写入变慢
    · 一般单表索引不超过 5-6 个

  【联合索引的字段顺序】
    原则：区分度高的放左边，等值查询放左边，范围查询放右边。
    例：(category, last_update_time)
        WHERE category = '玄幻' ORDER BY last_update_time DESC
        → 一个联合索引同时满足筛选和排序，避免 filesort

  【★ 怎么判断区分度】
    SELECT COUNT(DISTINCT column) / COUNT(*) FROM table;
    结果越接近 1 越好（一般 > 0.1 才考虑建索引）


################################################################################
  三、事务与锁
################################################################################

【ACID】
  ------------------------------------------------------------------
  字母  英文          中文    含义
  ------------------------------------------------------------------
  A     Atomicity     原子性  要么全成功，要么全失败
  C     Consistency   一致性  数据始终保持合法状态
  I     Isolation     隔离性  多个事务互不干扰
  D     Durability    持久性  成功后就永久保存
  ------------------------------------------------------------------

【四种隔离级别】
  ------------------------------------------------------------------
  级别                    脏读    不可重复读  幻读    说明
  ------------------------------------------------------------------
  读未提交(READ UNCOMMITTED) ✓      ✓          ✓     几乎不用
  读已提交(READ COMMITTED)   ✗      ✓          ✓     Oracle 默认
  可重复读(REPEATABLE READ)  ✗      ✗          ✗★    ★ MySQL 默认
  串行化(SERIALIZABLE)       ✗      ✗          ✗     性能差
  ------------------------------------------------------------------
  ★ MySQL 在可重复读级别下通过 MVCC + 间隙锁基本解决了幻读。

  【三种读问题的定义】
    脏读      读到了其他事务未提交的数据
    不可重复读 同一事务内两次读同一行，结果不同（别人 UPDATE 了）
    幻读      同一事务内两次范围查询，结果行数不同（别人 INSERT 了）

【★ MVCC（多版本并发控制）】
  核心：每一行数据有多个版本，读操作读快照，写操作读最新。
  实现：
    · 隐藏字段：DB_TRX_ID（最后修改的事务ID）、DB_ROLL_PTR（回滚指针）
    · undo log 版本链
    · ReadView（读视图，记录当前活跃的事务ID列表）

  【RC 和 RR 的区别就在 ReadView 的生成时机】
    RC：每次 SELECT 都生成新的 ReadView → 能读到别人已提交的新数据
    RR：只在第一次 SELECT 时生成 ReadView → 整个事务读到的都是一致的快照

【★ 锁的分类】
  ------------------------------------------------------------------
  分类维度    类型                    说明
  ------------------------------------------------------------------
  粒度        表锁 / 行锁 / 间隙锁    行锁并发高，表锁开销小
  模式        共享锁(S) / 排他锁(X)    读锁 / 写锁
  思想        悲观锁 / 乐观锁         先锁再操作 / 版本号 CAS
  ------------------------------------------------------------------

  【间隙锁（Gap Lock）】
    锁住一个范围，防止其他事务在这个范围内插入数据。
    ★ 这是 MySQL 在 RR 级别下防幻读的手段。
    ★ 副作用：间隙锁会降低并发，也更容易死锁。

  【乐观锁的实现】
    UPDATE novel SET status = 'FINISHED', version = version + 1
    WHERE id = 1 AND version = 5;
    → 如果返回影响行数为 0，说明被别人改过了


################################################################################
  四、SQL 优化实践
################################################################################

--------------------------------------------------------------------------------
4.1 慢 SQL 排查流程
--------------------------------------------------------------------------------

  1. 开启慢查询日志
     slow_query_log = 1
     long_query_time = 1

  2. 找出慢 SQL（mysqldumpslow / pt-query-digest）

  3. EXPLAIN 分析执行计划
     关注 type（是否 ALL）、key（是否 NULL）、rows、Extra

  4. 优化手段
     · 加合适的索引
     · 改写 SQL（避免索引失效的写法）
     · 减少回表（用覆盖索引）
     · 分页优化（深分页改游标）
     · 大表拆分

--------------------------------------------------------------------------------
4.2 N+1 问题
--------------------------------------------------------------------------------

  【什么是 N+1】
    查 1 次拿到 N 条记录，然后循环 N 次去查关联数据 → 总共 N+1 次查询。

    // ✗ 错误示范
    List<Novel> novels = novelRepo.findAll();
    for (Novel n : novels) {
        List<Chapter> cs = chapterRepo.findByNovelId(n.getId());   // N 次查询
    }

    N=100 时，就是 101 次数据库往返。

  【解法】
    · 批量查询 + Map 组装（最通用）
      List<Novel> novels = novelRepo.findAllById(ids);        // 1 次
      Map<Integer, Novel> map = novels.stream()
              .collect(Collectors.toMap(Novel::getId, Function.identity()));
    · JPA 的 JOIN FETCH
      @Query("SELECT n FROM Novel n JOIN FETCH n.chapters WHERE n.id = :id")
    · JPA 的 @EntityGraph
    · MyBatis 的 <collection> 嵌套映射
    · 配置 hibernate.default_batch_fetch_size

  【怎么发现 N+1】
    · 开 show-sql，看日志里有没有循环执行的 SQL
    · 用 Druid 的 SQL 监控
    · 用 p6spy

--------------------------------------------------------------------------------
4.3 深分页优化
--------------------------------------------------------------------------------

  【问题】
    LIMIT 1000000, 10 会先扫描前 1000010 行，再丢弃前 1000000 行。
    越翻到后面越慢。

  【方案一：游标分页 ★ 推荐】
    SELECT * FROM novel WHERE id > #{lastId} ORDER BY id LIMIT 10
    ★ 要求：排序字段唯一且有序（通常是主键或创建时间）
    ★ 缺点：不支持跳页，只能上一页/下一页

  【方案二：子查询先定位主键】
    SELECT * FROM novel
    WHERE id >= (SELECT id FROM novel ORDER BY id LIMIT 1000000, 1)
    LIMIT 10
    ★ 子查询走覆盖索引，比直接 LIMIT 快很多

  【方案三：业务上限】
    限制最大页码（业务上通常没人翻到 10 万页）

--------------------------------------------------------------------------------
4.4 其他优化点
--------------------------------------------------------------------------------

  □ 避免 SELECT *（用覆盖索引，减少回表和网络传输）
  □ 用 JOIN 代替子查询（视情况，MySQL 优化器会转换）
  □ 用 EXISTS 代替 IN（子查询结果集大时）
  □ 批量插入用 INSERT INTO ... VALUES (...), (...), (...)
  □ 用 UNION ALL 代替 UNION（不需要去重时）
  □ 大事务拆小事务（减少锁持有时间）
  □ 用 COUNT(*) 而不是 COUNT(column)（后者不统计 NULL）


################################################################################
  五、连接池
################################################################################

【HikariCP vs Druid】
  ------------------------------------------------------------------
  对比项       HikariCP                Druid
  ------------------------------------------------------------------
  性能         更快（Spring Boot 默认） 稍慢
  监控         无内置                  有内置监控页面 ★
  SQL 防火墙   无                      有
  SQL 监控     无                      ★ 有
  适用         追求性能                需要监控审计
  ------------------------------------------------------------------

【连接池核心参数】
  ------------------------------------------------------------------
  参数                  说明
  ------------------------------------------------------------------
  maximum-pool-size     最大连接数 ★ 不是越大越好
  minimum-idle          最小空闲连接
  connection-timeout    获取连接超时时间（默认 30s）
  idle-timeout          空闲连接存活时间
  max-lifetime          连接最大生命周期（要小于数据库的 wait_timeout）
  ------------------------------------------------------------------

  【★ 最大连接数怎么定】
    经验公式：连接数 = CPU核心数 × 2 + 磁盘数
    常见误区：设成几百上千，以为越大越好。
    实际上连接太多会导致数据库端线程切换开销剧增，反而更慢。

  【★ 连接泄漏】
    借了连接忘了还（没关流 / 没关事务），连接池很快耗尽。
    排查：Druid 监控页面的"连接泄漏"功能，或看活跃连接数是否持续升高。


################################################################################
  面试会怎么问
################################################################################

  Q1：JPA 和 MyBatis 怎么选？
  A： 见上面的标准答案。关键是要说"取决于场景"而不是"哪个更好"。

  Q2：MySQL 索引的底层数据结构是什么？为什么用它？
  A： B+ 树。非叶子节点只存索引 → 树更矮 → 磁盘 IO 少；
     叶子节点链表连接 → 范围查询高效。

  Q3：什么是回表？什么是覆盖索引？
  A： 回表 = 二级索引查到主键后，再回聚簇索引查完整数据。
     覆盖索引 = 查询的字段都在索引里，不用回表。

  Q4：什么是最左前缀原则？
  A： 联合索引 (a,b,c) 只能从最左列开始匹配。
     WHERE b=2 用不上，WHERE a=1 AND c=3 只用得上 a。

  Q5：索引失效的场景有哪些？
  A： 索引列做运算/函数、隐式类型转换、LIKE '%x'、
     OR 连接非索引列、违反最左前缀。

  Q6：怎么优化慢 SQL？
  A： ① EXPLAIN 看执行计划
     ② 加合适的索引，避免索引失效的写法
     ③ 避免 SELECT *，用覆盖索引
     ④ 深分页改游标分页
     ⑤ 大表拆分 / 读写分离

  Q7：什么是 N+1 问题？怎么解决？
  A： 循环里查数据库。用批量查询 + Map 组装，
     或 JOIN FETCH / @EntityGraph。

  Q8：索引越多越好吗？
  A： 不是。索引占空间，且每次写入都要维护，会拖慢写操作。
     一般单表不超过 5-6 个。

  Q9：MySQL 的默认隔离级别是什么？为什么？
  A： 可重复读（REPEATABLE READ）。
     MySQL 通过 MVCC + 间隙锁在这个级别下基本解决了幻读，
     所以在保证较高隔离性的同时性能可接受。

  Q10：乐观锁和悲观锁怎么选？
  A： 冲突少用乐观锁（版本号 CAS，性能好），
     冲突多用悲观锁（SELECT FOR UPDATE，简单可靠）。

  Q11：连接池的最大连接数是不是越大越好？
  A： 不是。连接太多会导致数据库端线程切换开销剧增。
     经验公式：CPU核数 × 2 + 磁盘数。

  Q12：列表要支持多个可选条件，你怎么实现？
  A： 用 JpaSpecificationExecutor + Specification。
     每个条件写一个独立方法，条件为空时返回 null ——
     Spring Data 会自动忽略返回 null 的 Specification，
     所以不需要写一堆 if (keyword != null)。
     组合用 Specification.allOf(...) 或 where().and() 链式调用。
     ★ 为什么不用方法名推导：3 个条件就是 2³=8 个方法，组合爆炸。
     ★ 为什么不用 @Query 判 null：SQL 会很长，而且参数为 null 时
       某些驱动会报类型推断错误。

  Q13：搜索为什么用 LIKE 会慢？怎么优化？
  A： LIKE '%关键词%' 以 % 开头，无法利用 B+ 树索引的有序性，
     只能用 type=ALL 全表扫描。
     优化方向：
       ① 改成前缀匹配 LIKE '关键词%'（能用索引，但搜索体验差）
       ② MySQL 全文索引 FULLTEXT + ngram 分词器（支持中文）
       ③ 上 Elasticsearch（分词、高亮、相关性排序都有）
     ★ 数据量小的时候 LIKE 够用，但要知道它的上限在哪。
