【大类 05】缓存体系
================================================================================
  对应项目笔记：docs/项目笔记/05-缓存体系.txt

【定位】回答"怎么少查几次数据库"。面试最高频的八股之一。


################################################################################
  一、为什么需要缓存
################################################################################

  数据库是磁盘 IO，一次查询几毫秒到几百毫秒。
  Redis 是内存操作，一次查询几十微秒。

  差 100 倍。

  所以只要有"读多写少"的数据，就应该考虑放缓存。

  【但缓存带来的问题比它解决的还多】
    · 缓存和数据库不一致怎么办？
    · 缓存挂了数据库会不会被打爆？
    · 缓存穿透、击穿、雪崩怎么防？
    · 内存满了怎么办？
    · 缓存和数据库的双写顺序？

  这个大类就是解决这些问题。


################################################################################
  二、Redis 基础
################################################################################

--------------------------------------------------------------------------------
2.1 五种基本数据结构 + 三种高级结构
--------------------------------------------------------------------------------

  ------------------------------------------------------------------
  结构        底层实现              典型用途
  ------------------------------------------------------------------
  String      简单动态字符串        缓存对象(JSON)、计数器、分布式锁
  Hash        哈希表 / 压缩列表     存对象字段、购物车、黑名单
  List        双向链表 / 压缩列表   消息队列、时间线、最新列表
  Set         哈希表 / 整数集合     去重、共同关注、抽奖
  ZSet        跳表 + 哈希表         排行榜、延迟队列、滑动窗口
  ------------------------------------------------------------------
  Bitmap      字符串                签到统计、布隆过滤器、活跃用户
  HyperLogLog 稀疏算法              基数统计（UV），有 0.81% 误差
  GEO         有序集合              附近的人、地理位置
  ------------------------------------------------------------------

  【★ 为什么 ZSet 用跳表而不是红黑树】
    · 跳表实现简单，代码可维护性好
    · 跳表的范围查询更高效（链表天然有序）
    · 并发环境下跳表更容易做无锁化

--------------------------------------------------------------------------------
2.2 为什么 Redis 快
--------------------------------------------------------------------------------

  1. 纯内存操作 —— 不涉及磁盘 IO
  2. 单线程处理命令 —— 避免锁竞争和线程上下文切换
  3. IO 多路复用（epoll）—— 单线程处理大量连接
  4. 高效的数据结构 —— 跳表、压缩列表、整数集合

  【★ 单线程为什么还能扛高并发】
    单线程指的是"命令执行"是单线程的，
    网络 IO 用了多路复用，而且内存操作本身极快。
    瓶颈通常在网络带宽而不是 CPU。

  ★ 补充：Redis 6.0 引入了多线程 IO（处理网络读写），
    但命令执行仍然是单线程。

--------------------------------------------------------------------------------
2.3 过期策略与内存淘汰
--------------------------------------------------------------------------------

  【过期删除策略】
    ------------------------------------------------------------------
    策略        做法                          优缺点
    ------------------------------------------------------------------
    惰性删除    访问时才检查是否过期          省 CPU，但可能内存泄漏
    定期删除    每秒随机抽查一批              折中
    ------------------------------------------------------------------
    ★ Redis 用的是"惰性删除 + 定期删除"组合。

  【内存淘汰策略（8 种）】
    ------------------------------------------------------------------
    策略                      说明
    ------------------------------------------------------------------
    noeviction（默认）        不淘汰，写入报错
    allkeys-lru               所有 key 中淘汰最久未使用的 ★ 常用
    allkeys-lfu               所有 key 中淘汰使用频率最低的
    allkeys-random            所有 key 中随机淘汰
    volatile-lru              设了过期时间的 key 中 LRU
    volatile-lfu              设了过期时间的 key 中 LFU
    volatile-random           设了过期时间的 key 中随机
    volatile-ttl              淘汰即将过期的
    ------------------------------------------------------------------

  【LRU vs LFU】
    LRU（Least Recently Used）—— 淘汰最久未使用的
    LFU（Least Frequently Used）—— 淘汰使用次数最少的
    ★ 热点数据用 LFU 更准（避免偶发的一次访问把冷数据留在内存里）

2.4 持久化
--------------------------------------------------------------------------------

  ------------------------------------------------------------------
  方式    原理                        优点            缺点
  ------------------------------------------------------------------
  RDB     定时生成内存快照            恢复快、文件小  可能丢数据
  AOF     记录每条写命令              数据安全        文件大、恢复慢
  混合    两者结合（Redis 4.0+）      兼顾            ★ 推荐
  ------------------------------------------------------------------

  【AOF 的三种刷盘策略】
    ------------------------------------------------------------------
    策略            说明                    安全性
    ------------------------------------------------------------------
    always          每条命令都 fsync        最高，性能最差
    everysec        每秒 fsync              折中 ★ 默认
    no              交给操作系统            最快，可能丢 30 秒数据
    ------------------------------------------------------------------


################################################################################
  三、缓存三大问题 ★★★ 面试必背
################################################################################

  ------------------------------------------------------------------
  问题      原因                        后果              解决方案
  ------------------------------------------------------------------
  穿透      查一个不存在的数据，缓存和  每次请求都打到    1. 缓存空值（短TTL）
            数据库都没有                数据库，等于没    2. 布隆过滤器
                                        有缓存            3. 参数校验拦截
  ------------------------------------------------------------------
  击穿      某个热点 key 突然过期，     大量请求同时涌    1. 互斥锁（只让一个
            大量请求同时打过来          向数据库          线程去查库）
                                                          2. 热点数据永不过期
                                                          3. 逻辑过期
  ------------------------------------------------------------------
  雪崩      大量 key 同一时间过期，或   数据库瞬间被打爆  1. TTL 加随机值
            Redis 整个挂了                                2. 多级缓存
                                                          3. 限流降级
                                                          4. 集群高可用
  ------------------------------------------------------------------

  【★ 记忆技巧】
    穿透 = 数据"不存在"，缓存挡不住（像光线穿透玻璃）
    击穿 = 数据存在，但缓存"过期了"，请求砸穿到数据库
    雪崩 = 大片缓存同时失效，像雪崩一样压倒数据库


--------------------------------------------------------------------------------
3.1 缓存穿透的详细方案
--------------------------------------------------------------------------------

  【方案一：缓存空值】
    if (novel == null) {
        redis.set(key, "NULL", 60, TimeUnit.SECONDS);   // 短 TTL
        return null;
    }
    优点：实现简单
    缺点：如果攻击者用大量随机 ID 攻击，会缓存大量空值占内存
          → 所以要设短 TTL

  【方案二：布隆过滤器（Bloom Filter）】
    原理：一个位数组 + 多个哈希函数。
          写入时把多个位置置 1；查询时如果有一位是 0，说明一定不存在。

    优点：空间极小（1 亿数据约 100MB），查询快
    缺点：
      · 有误判率（说存在但实际不存在），但不会漏判
      · 不支持删除元素（可以用 Counting Bloom Filter）

    实现：Redisson 的 RBloomFilter，或 Guava 的 BloomFilter

  【方案三：参数校验】
    比如 ID 必须 > 0，格式必须合法，直接在入口拦截明显非法的请求。


--------------------------------------------------------------------------------
3.2 缓存击穿的详细方案
--------------------------------------------------------------------------------

  【方案一：互斥锁】
    public Novel getNovel(Integer id) {
        String key = "novel:" + id;
        Novel cached = getFromCache(key);
        if (cached != null) return cached;

        // 只让一个线程去查库
        String lockKey = "lock:novel:" + id;
        try {
            if (redis.setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS)) {
                Novel novel = loadFromDb(id);
                setToCache(key, novel, 30, TimeUnit.MINUTES);
                return novel;
            } else {
                Thread.sleep(50);             // 等其他线程查完
                return getFromCache(key);     // 重试读缓存
            }
        } finally {
            redis.delete(lockKey);
        }
    }

    ★ 缺点：其他线程要等待，吞吐量下降

  【方案二：逻辑过期（永不过期）】
    缓存里存的不是数据本身，而是 {data, expireTime}。
    发现逻辑过期时，异步开一个线程去更新缓存，当前请求返回旧数据。
    优点：不阻塞任何请求
    缺点：会有一段时间返回旧数据，需要业务能接受

  【方案三：热点数据预热 + 永不过期】
    提前把热点数据加载进缓存，并且不设 TTL，
    通过后台定时任务或数据变更时主动更新。


--------------------------------------------------------------------------------
3.3 缓存雪崩的详细方案
--------------------------------------------------------------------------------

  【TTL 加随机值】
    int ttl = 30 * 60 + ThreadLocalRandom.current().nextInt(300);   // 30分钟 ± 5分钟
    redis.set(key, value, ttl, TimeUnit.SECONDS);

  【多级缓存】
    本地缓存（Caffeine） → Redis → 数据库
    本地缓存扛住大部分请求，即使 Redis 挂了也还有一层。

    ★ 代价：本地缓存多机之间不一致，只适合对一致性要求不高的数据。

  【限流降级】
    Redis 挂了时，用限流保护数据库不被压垮，
    非核心功能直接降级返回兜底数据。

  【Redis 高可用】
    主从复制 + 哨兵，或 Cluster 集群。


################################################################################
  四、缓存与数据库的一致性 ★★ 面试高频
################################################################################

【四种更新策略对比】
  ------------------------------------------------------------------
  策略                          一致性    并发安全    推荐度
  ------------------------------------------------------------------
  先更新数据库，再更新缓存      差        有并发问题  ✗
  先更新缓存，再更新数据库      差        有并发问题  ✗
  先删除缓存，再更新数据库      较差      有并发问题  △
  先更新数据库，再删除缓存      好        概率极低    ★ 推荐
  ------------------------------------------------------------------

【为什么推荐"先更新数据库，再删除缓存"】

  1. 为什么是"删除"而不是"更新"？
     · 更新缓存可能写入一个计算复杂但根本没人读的值（浪费）
     · 并发更新时，两个线程可能以相反顺序写入缓存 → 脏数据
     · 删除是幂等的，多次删除结果一样
     · 缓存是懒加载的，删了自然会重建

  2. 为什么先操作数据库？
     "先删缓存再更新库"在并发下更容易出问题：
       线程 A 删缓存 → 线程 B 读缓存未命中 → B 读库（旧值）→
       B 写缓存（旧值）→ A 更新库（新值）
       → 结果：数据库是新值，缓存是旧值，长期不一致

     "先更新库再删缓存"的异常窗口极小：
       线程 A 更新库 → 线程 B 读缓存（旧值，但这发生在 A 删缓存之前）
       → A 删缓存 → 后续请求会读到新值
       只有当"读请求恰好在更新库和删缓存之间读到了旧缓存并写回"时才有问题，
       而这个窗口极短。

【延迟双删（应对极端并发）】
    1. 删除缓存
    2. 更新数据库
    3. 延迟 500ms 后再删除一次缓存

  目的：删掉在"步骤 1 和步骤 2 之间"被其他线程写进去的旧值。
  延迟时间要大于一次读请求的耗时。

【★ 更彻底的方案】
  · Canal 监听 MySQL binlog，异步刷新缓存
  · 业务层用消息队列保证顺序

【★ 一个重要的认知】
  缓存一致性没有 100% 的方案。
  要么接受"最终一致"（延迟双删、binlog 同步），
  要么对强一致要求高的数据干脆不用缓存。


################################################################################
  五、Spring Cache 声明式缓存
################################################################################

【三个核心注解】
  ------------------------------------------------------------------
  注解          作用                          触发时机
  ------------------------------------------------------------------
  @Cacheable    查缓存，有就返回，没有就执行  方法执行前查缓存
                方法并缓存结果
  @CachePut     总是执行方法，并把结果更新到  方法执行后更新缓存
                缓存（不检查缓存）
  @CacheEvict   删除缓存                      方法执行后删缓存
  ------------------------------------------------------------------

  【记忆】
    @Cacheable = 先看缓存，有就不干了
    @CachePut   = 照常干，干完更新缓存
    @CacheEvict = 干完把缓存删了（下次自然会重建）

【配置】
  @Configuration
  @EnableCaching                                  // 开启缓存注解支持
  public class CacheConfig {
      @Bean
      public RedisCacheManager cacheManager(RedisConnectionFactory factory) {
          RedisCacheConfiguration config = RedisCacheConfiguration.defaultCacheConfig()
                  .entryTtl(Duration.ofMinutes(30))                        // 默认 TTL
                  .serializeKeysWith(                                      // key 序列化
                          RedisSerializationContext.SerializationPair
                                  .fromSerializer(new StringRedisSerializer()))
                  .serializeValuesWith(                                    // value 序列化
                          RedisSerializationContext.SerializationPair
                                  .fromSerializer(RedisSerializer.json()));
          return RedisCacheManager.builder(factory).cacheDefaults(config).build();
      }
  }

【@Cacheable 常用参数】
  @Cacheable(
      value = "novel:detail",         // 缓存名称（Redis key 前缀）
      key = "#novelId",               // 缓存 key，支持 SpEL
      condition = "#novelId > 0",     // 满足条件才缓存
      unless = "#result == null"      // 结果为 null 时不缓存（防穿透）
  )

  SpEL 表达式：
    #novelId            → 方法参数
    #result             → 返回值（只在 unless 里可用）
    #root.methodName    → 方法名
    'list'              → 字符串常量（★ 要加单引号）

【★ 坑】
  · @Cacheable 同类内部调用会失效（和 @Transactional 一样的 AOP 代理问题）
  · 缓存对象必须可序列化
  · key 的设计要唯一，避免不同参数命中同一个 key
  · 缓存 null 值可以防穿透，但 TTL 不能太长
  · 缓存和数据库的 TTL 要匹配业务的一致性要求

--------------------------------------------------------------------------------
5.1 ★ 哪些方法必须加 @CacheEvict？（一个容易漏的点）
--------------------------------------------------------------------------------

  【判断方法】
    把缓存的对象（比如 NovelDetailVO）的所有字段列出来，
    凡是会改变其中任何一个字段的方法，都必须 @CacheEvict。

    例：NovelDetailVO 包含
      id / title / summary / coverUrl / category / status
      / totalWords / lastUpdateTime / chapters

    那么：
      addChapter     改了 totalWords + chapters      → 必须 evict
      updateChapter  改了 totalWords                 → 必须 evict
      deleteChapter  改了 totalWords + chapters      → 必须 evict
      updateNovel    改了 title/summary/category/... → 必须 evict
      deleteNovel    整个对象没了                    → 必须 evict

  【★ 漏掉会怎样】
    改了数据但缓存没清 → 前端看到旧数据，直到 TTL 过期。
    这是"看起来功能正常、实际数据不对"的典型 bug，很难发现。

  【★★ 一个极易犯的错：@CacheEvict 的 key 指向不存在的参数】

    @CacheEvict(value = "novel", key = "#id")        ← #id 是什么？
    public void deleteChapter(Integer novelId, Integer chapterId) { ... }

    这个方法**没有叫 id 的参数**！
    SpEL 解析不到 → 缓存 key 算出来是空 →
    evict 的是一个不存在的 key，真正的 novel::1 纹丝不动。

    ★ 万能自查法：
      写完 key = "#xxx"，回头看方法签名里**有没有这个参数名**。
      名字对不上，就一定是 bug。

    对比：
      deleteChapter(Integer novelId, Integer chapterId) → key = "#novelId"  ✓
      deleteNovel(Integer id)                          → key = "#id"       ✓
      （两个方法参数名不同，别搞混）


################################################################################
  5.2 ★★ 缓存降级 —— 缓存不能成为单点故障
################################################################################

【问题：加了缓存，反而更脆弱】

  没加缓存时：Redis 挂了 → 接口照样查数据库 → 正常  ✅
  加了缓存后：Redis 挂了 → @Cacheable 抛异常 → 接口 500  ❌

  ★ 也就是说，@Cacheable 让 Redis 从"可选依赖"变成了"强依赖"。
    你享受了缓存的好处，同时也把缓存的故障风险收下了。

【为什么会抛异常】

  Spring 的 CacheInterceptor 在缓存读写失败时，
  会交给 CacheErrorHandler 处理。

  默认实现是 SimpleCacheErrorHandler —— 它的做法是：
      public void handleCacheGetError(...) { throw exception; }   // 直接往上抛

  所以默认行为就是"缓存挂了，接口跟着挂"。

【解决方案：自定义 CacheErrorHandler】

  @Slf4j
  @Configuration
  @EnableCaching
  public class CacheConfig implements CachingConfigurer {   // ★ 实现这个接口

      @Override
      public CacheErrorHandler errorHandler() {
          return new CacheErrorHandler() {
              @Override
              public void handleCacheGetError(RuntimeException e, Cache cache, Object key) {
                  log.warn("缓存读取失败，降级直查数据库。cache={}, key={}",
                           cache.getName(), key);
                  // ★ 什么都不抛，方法继续执行 → 直接查数据库
              }

              @Override
              public void handleCachePutError(RuntimeException e, Cache cache,
                                              Object key, Object value) {
                  log.warn("缓存写入失败，忽略。cache={}, key={}", cache.getName(), key);
              }

              @Override
              public void handleCacheEvictError(RuntimeException e, Cache cache, Object key) {
                  log.warn("缓存清除失败，忽略。cache={}, key={}", cache.getName(), key);
              }

              @Override
              public void handleCacheClearError(RuntimeException e, Cache cache) {
                  log.warn("缓存清空失败，忽略。cache={}", cache.getName());
              }
          };
      }
  }

  ★ 核心：把"抛异常"改成"只记日志"，请求就降级直查数据库了。

【★ 怎么验证降级真的生效】

  ★ 故障演练 —— 这是最有说服力的验证方式：

    1. docker stop redis        （或直接关掉 Redis 服务）
    2. curl "http://localhost:8080/novels/1"
    3. 期望：正常返回数据（而不是 500）
    4. 看日志：应该有 "缓存读取失败，降级直查数据库" 的 WARN

  【★★★ 2026-10-05 实测：期望没实现 —— 降级曾失效（2026-10-06 已修复）】

    ★ 这是一个非常重要的**反例**，别跳过去：

      findDetail 为了做空值缓存，从 @Cacheable 改成了手动
      cacheManager.getCache("novel").get(...) 调用，
      而 CacheErrorHandler 由 AbstractCacheInvoker 调用
      （它是 AOP 拦截器 CacheAspectSupport 的父类），
      只保护**注解驱动**的调用 —— 手动 cacheManager 调用绕过了它。

    ★ 当时的实测（docker stop demo2-redis，5/5 次可复现）：
      · GET /novels/{id} → 挂起 60.0 秒 → 返回 HTTP 200
        + body {"code":500,"msg":"Redis command timed out"}
      · GET /novels      → 不受影响，正常 200
      · 日志里没有任何降级 WARN，CacheErrorHandler 一次都没触发

    ★ 根因还有一层：项目没配 spring.data.redis.timeout，
      用的是 Lettuce 默认 60 秒命令超时 → 不是快速失败而是挂起，
      占满 Tomcat 线程会造成级联故障。

    ★★ 判据修正：判断降级是否生效**不能看 HTTP 状态码** ——
      GlobalExceptionHandler.handleRuntimeException 没有 @ResponseStatus，
      所有 RuntimeException 都返回 HTTP 200，必须看 body 的 code 字段。
      ★ 通用教训：**判据本身也要验证** ——
        假阳性判据比没有判据更危险，因为它让你以为已经验证过了。

  【✅ 2026-10-06 修复：手动调用必须自己补降级】

    第一级 · 超时（止血）—— application-dev.properties
      spring.data.redis.timeout=500ms
      spring.data.redis.connect-timeout=500ms
      ★ 两个都要配：connect-timeout 管建立 TCP 连接，
        timeout 管命令发出后等响应

    第二级 · try-catch（治疗）—— 4 处 Redis 调用各包一层
      · 读失败 → 当"缓存未命中"，继续走 DB（**不要 rethrow**）
      · 写失败 → 吞掉异常，不影响主流程
      · catch 里打 log.warn，只打 message 不打堆栈（避免刷屏）

    ★★ 只做第一级是不够的：
      ------------------------------------------------------------------
      手段              效果                     用户体感
      ------------------------------------------------------------------
      不配超时          挂起 60 秒               一直转圈
      只配超时          0.5 秒报错               立刻打不开
      + try-catch 降级  1.0 秒返回真实数据       ✅ 正常可用
      ------------------------------------------------------------------
      · fail fast（快速失败）= 让故障**快速暴露**，别拖垮别人 → 面向系统
      · graceful degradation（优雅降级）= 让功能**继续可用** → 面向用户

    ★ 实测数据（docker stop demo2-redis，请求 GET /novels/1）：
      ① 改造前 60.0s 挂起 / body.code=500
      ② 只加超时 0.51s / body.code 仍是 500
      ③ 加 try-catch 1.01s / body.code=200 ✅ 有数据
      并发压测 500 请求 / 100 并发：P50 1.491s，0 个超 5 秒；
      不依赖 Redis 的列表接口 P50 0.248s，未被拖垮。

  ★ 面试时能说出"我做过故障演练，据此发现降级其实没生效，
    然后修好并复测"，比只说"我加了缓存降级"有说服力得多。

【★★ 一个重要局限（很多人不知道）】

  CacheErrorHandler **只能保护 Spring Cache 的注解**
  （@Cacheable / @CacheEvict / @CachePut），
  **保护不了手写的 Redis 调用**。

    @Cacheable                              → 走 CacheInterceptor → 被保护  ✅
    stringRedisTemplate.opsForZSet()...     → 直接调 Redis 客户端 → 异常直接抛出  ❌

  ★ 所以只有 @Cacheable 是不够的，手写 Redis 的地方也要单独处理：

    // 排行榜：Redis 挂了返回空列表，而不是 500
    try {
        Set<TypedTuple<String>> tuples = stringRedisTemplate.opsForZSet()
                .reverseRangeWithScores(rankKey, 0, top - 1);
        ...
    } catch (Exception e) {
        log.warn("排行榜查询失败，降级返回空列表", e);
        return new ArrayList<>();
    }

  【哪些地方该降级、哪些不该】

    ------------------------------------------------------------------
    场景                  该降级吗      降级方案
    ------------------------------------------------------------------
    详情缓存（手动调用）   ✅ 该        需 try-catch；★ 已按此法修复 ✓
    排行榜                 ✅ 该        返回空列表
    用户信息缓存           ✅ 该        查数据库
    登录（写 refreshToken）❌ 不该      ★ 安全机制不能降级，
                                       但应返回友好提示而不是技术错误
    登出（写黑名单）       ❌ 不该      ★ 同上是安全机制
    拦截器黑名单校验       ⚠️ 看取舍    降级=跳过校验（有安全风险）
                                       不降级=Redis 挂了全部接口 500
                                       ★ 折中：降级 + 记 error 日志 + 告警
    ------------------------------------------------------------------

  ★ 判断标准：**这次降级会不会破坏安全机制？**
    会 → 不降级，但要保证错误提示友好
    不会 → 降级，保证核心功能可用


################################################################################
  六、序列化
################################################################################

【问题】
  默认的 RedisTemplate 用 JDK 序列化，
  在 Redis 里看到的是 \xac\xed\x00\x05 这样的乱码，没法调试。

【解决方案】
  · Key 用 StringRedisSerializer（可读）
  · Value 用 GenericJackson2JsonRedisSerializer 或 RedisSerializer.json()（JSON）

  ★ 用 StringRedisTemplate 可以省掉 Key 的配置。

【★ 坑】
  · JDK 序列化要求类实现 Serializable，且类结构变化会导致反序列化失败
  · JSON 序列化不存储类型信息（除非开启 @class 字段），
    反序列化复杂对象（泛型、多态）可能出问题
  · 缓存里存的类要加 serialVersionUID


################################################################################
  七、其他高频考点
################################################################################

【大 key 问题】
  ------------------------------------------------------------------
  判断标准     String > 10KB，集合元素 > 5000
  危害         阻塞 Redis、网络拥塞、删除时卡顿
  排查         redis-cli --bigkeys
  解决         拆分、压缩、改用 Hash 分片
  ------------------------------------------------------------------

【热 key 问题】
  ------------------------------------------------------------------
  判断标准     单 key QPS 极高（如秒杀商品）
  危害         单节点压力过大
  排查         redis-cli --hotkeys、monitor 采样
  解决         本地缓存、key 加随机后缀打散到多节点
  ------------------------------------------------------------------

【Pipeline】
  一次发多条命令，减少网络往返（RTT）。
  ★ 注意：Pipeline 不是原子的，命令之间可能插入其他客户端的命令。

【Lua 脚本】
  Redis 保证脚本原子执行，适合"判断 + 操作"的复合逻辑。
  典型场景：分布式锁的释放、限流的原子计数。

【主从复制】
  全量同步（RDB）+ 增量同步（replication backlog）。
  ★ 主从延迟是读写分离下"读到旧数据"的根源。

【哨兵（Sentinel）】
  监控主节点，挂了自动选一个新主。
  优点：高可用；缺点：单主写入能力有限。

【Cluster 分片】
  16384 个哈希槽，每个节点负责一部分。
  ★ CRC16(key) % 16384 决定 key 落在哪个槽。


################################################################################
  面试会怎么问
################################################################################

  Q1：Redis 有哪些数据结构？分别用在哪？
  A： String（缓存对象、计数器）、Hash（存对象、黑名单）、
     List（消息队列）、Set（去重）、ZSet（排行榜）、
     Bitmap（签到）、HyperLogLog（UV 统计）。
     ★ 结合自己项目讲最好。

  Q2：缓存穿透、击穿、雪崩的区别？
  A： 见上面的对比表。关键是能说清楚"为什么会发生"和"怎么防"。

  Q3：怎么保证缓存和数据库的一致性？
  A： 推荐"先更新数据库，再删除缓存"。
     极端情况用延迟双删，或 Canal 监听 binlog 异步刷新。
     ★ 要强调：没有 100% 的方案，只能做到最终一致。

  Q4：Redis 为什么快？
  A： 纯内存 + 单线程避免锁竞争 + IO 多路复用 + 高效数据结构。

  Q5：Redis 单线程为什么还能扛高并发？
  A： 单线程指命令执行，网络 IO 用多路复用，
     内存操作本身极快，瓶颈通常在网络带宽。

  Q6：Redis 内存满了怎么办？
  A： 配置 maxmemory-policy 淘汰策略。
     常用 allkeys-lru 或 volatile-lru。

  Q7：Redis 持久化怎么选？
  A： RDB 恢复快但可能丢数据，AOF 安全但文件大。
     Redis 4.0+ 推荐混合持久化。

  Q8：怎么用 Redis 实现分布式锁？
  A： SETNX + 过期时间 + 唯一 value，删除用 Lua 保证原子性。
     ★ 详见 docs/知识笔记/06-异步与消息.txt

  Q9：@Cacheable 失效的场景？
  A： 同类内部调用（AOP 代理问题）、方法非 public、
     缓存对象不可序列化、key 设计冲突。

  Q10：怎么处理大 key 和热 key？
  A： 大 key 拆分成多个小 key，或压缩；
     热 key 加本地缓存，或加随机后缀打散到多个节点。

  Q11：加了缓存之后，Redis 挂了怎么办？
  A： ★ 这是个很有区分度的问题，能答好说明你真的想过生产环境。
     ★★ 关键是能区分"快速失败"和"优雅降级" —— 这是两个层次的东西。

     "先说认知：加了缓存之后，Redis 从'可选依赖'变成了'强依赖'，
      Redis 一挂接口就会 500。

      我的项目实际经历过三个阶段，都有实测数据：
        ① 改造前     ：Redis 挂 → 挂起 60 秒 → body.code=500 → ❌ 不可用
        ② 只加超时   ：0.51 秒 → body.code 仍是 500  → ❌ 还是不可用
        ③ 加 try-catch：1.01 秒 → body.code=200 + 真实数据 → ✅ 可用

      ② 和 ③ 是两个层次：
        · fail fast（快速失败）—— 让故障快速暴露，别拖垮别人，**面向系统**
        · graceful degradation（优雅降级）—— 让功能继续可用，**面向用户**
      只做 ② 的话，用户体感只是从'一直转圈'变成'立刻报错'，还是打不开。

      ★ ① 的 60 秒怎么来的：项目没配 spring.data.redis.timeout，
        走的是 Lettuce 默认 60 秒命令超时。不是快速失败而是**挂起** ——
        每个请求占满一条 Tomcat 线程卡 60 秒，200 线程 ÷ 60s = 3.3 req/s
        就能打满线程池，连不依赖 Redis 的列表接口都开始排队 → 级联故障。
        加超时后：200 线程 ÷ 1.5s ≈ 133 req/s。
        ★ 结论：**挂起（hang）几乎总是比报错（fail fast）更危险**，
          因为挂起会消耗资源并向上游传播，报错可以被隔离。

      ★ ② 的配置（两个都要配，管的不是一回事）：
        spring.data.redis.timeout=500ms          ← 命令发出后等响应
        spring.data.redis.connect-timeout=500ms  ← 建立 TCP 连接
        ★ 推荐值 500ms~1s。Redis 是内存操作，正常 p99 在 10ms 内，
          500ms 已经是 p99 的 25 倍以上 —— 500ms 没回它就已经不正常了。

      ★ ③ 为什么必须手写 try-catch：
        这里踩过一个坑 —— 我为了做空值缓存防穿透，把 findDetail
        从 @Cacheable 改成了手动 cacheManager.getCache("novel").get(...)，
        结果 CacheErrorHandler 静默失效了。因为它挂在 AOP 拦截器
        （CacheAspectSupport / AbstractCacheInvoker）上，只保护**注解驱动**
        的调用，手动调用绕过了它。
        ★ 一句话：**"注解生效" = "框架的切面拦住了你"。**
        修法就是在那 4 处 Redis 调用（两次 get、两次 put）各包一层 try-catch：
        读失败当'缓存未命中'继续走 DB，写失败吞掉异常。

      ★ 判据：不能看 HTTP 状态码（本项目 RuntimeException 也返回 HTTP 200），
        要看 body 的 code 字段。★ 判据本身也要验证 ——
        假阳性判据比没有判据更危险，因为它让你以为已经验证过了。

      ★ 并发验证：500 请求 / 100 并发 / Redis 挂，
        P50 1.491s，0 个超 5 秒；不依赖 Redis 的列表接口 P50 0.248s 未被拖垮。

      ★ 另一个局限：CacheErrorHandler 只能保护注解，
        手写的 stringRedisTemplate 调用也要单独 try-catch。"

  ★ 延伸追问：还能更快吗？
     能。1 秒是两个 500ms 超时**串行叠加**的结果。
     加**熔断器**（连续失败 N 次后直接跳过 Redis，过 30 秒再试探放一个请求）
     能降到 ~10ms。可用 Sentinel 或 Resilience4j。
     ★ 这是优化，不是 bug —— 别把优化当修复讲。

  Q12：所有地方都该降级吗？
  A： 不是。判断标准是"这次降级会不会破坏安全机制"。
     · 详情缓存、排行榜、用户信息缓存 → 该降级，保证核心功能可用
     · 登录、登出（双 Token、黑名单）→ 不该降级，
       因为这是安全机制，降级会让认证失效；
       但要保证返回的是友好提示，而不是 "Unable to connect to Redis"
     · 拦截器黑名单校验 → 两难：降级有安全风险，不降级则全部接口 500
       折中方案：降级 + 记 error 日志 + 告警
