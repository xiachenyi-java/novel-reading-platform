================================================================================
【大类 06】异步与消息
================================================================================
  对应项目笔记：docs/项目笔记/06-异步与消息.txt

【定位】回答"能不能别让用户等"。三个关键词：异步、解耦、削峰。


################################################################################
  一、这个大类在解决什么问题
################################################################################

  ------------------------------------------------------------------
  同步：用户点"发布章节"
        → 后端存库
        → 给 1000 个订阅者发通知（等 30 秒）
        → 返回"发布成功"
        用户等了 30 秒，只为了看一句"发布成功"
  ------------------------------------------------------------------
  异步：用户点"发布章节"
        → 后端存库
        → 往消息队列扔一条消息
        → 立刻返回"发布成功"（0.1 秒）
        → 后台慢慢发通知
  ------------------------------------------------------------------

  【三大价值】
    ------------------------------------------------------------------
    价值    说明                                    例子
    ------------------------------------------------------------------
    异步    主流程不阻塞                            发通知不阻塞发布
    解耦    生产者不需要知道谁在消费                发布方不用知道有多少订阅者
    削峰    瞬时流量存进队列，后端按自己节奏消费    秒杀 10 万请求 → 慢慢处理
    ------------------------------------------------------------------


################################################################################
  二、@Async 异步任务
################################################################################

【为什么不用 new Thread()】
  · 每次创建/销毁线程开销大
  · 无法控制线程数量，高并发下会 OOM
  · 无法管理任务队列、拒绝策略

【@Async 的用法】
  1. 开启异步支持：
     @Configuration
     @EnableAsync
     public class AsyncConfig { }

  2. 标记异步方法：
     @Async
     public void sendNotification(Integer userId, String content) {
         // 这个方法会在独立的线程里执行
     }

  3. 调用方立即返回，不等待

【★ 必须自己配线程池】

  Spring 默认用 SimpleAsyncTaskExecutor，
  它每次调用都新建一个线程，不复用 —— 高并发下会创建海量线程导致 OOM。

  正确做法：
    @Configuration
    @EnableAsync
    public class AsyncConfig implements AsyncConfigurer {

        @Override
        public Executor getAsyncExecutor() {
            ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
            executor.setCorePoolSize(8);         // 核心线程数
            executor.setMaxPoolSize(16);         // 最大线程数
            executor.setQueueCapacity(200);      // 队列容量
            executor.setKeepAliveSeconds(60);    // 空闲线程存活时间
            executor.setThreadNamePrefix("app-async-");   // ★ 线程名前缀
            executor.setRejectedExecutionHandler(
                    new ThreadPoolExecutor.CallerRunsPolicy());   // 拒绝策略
            executor.initialize();
            return executor;
        }
    }

  ★ setThreadNamePrefix 很重要：出问题时 jstack 一看就知道是哪个线程池的线程。

【★ 四个坑】
  坑1：@Async 同类内部调用失效（和 @Transactional 一样的 AOP 代理问题）
  坑2：@Async 方法必须是 public
  坑3：返回 void 时，方法内抛的异常不会传播到调用方，必须自己 try-catch
  坑4：ThreadLocal 会失效（子线程拿不到主线程的 ThreadLocal）
       ★ 这就是为什么 @Async 里取不到当前登录用户。
       解法见下。

【★ @Async 里怎么拿到当前用户】
  三种解法：
    1. 把用户信息作为方法参数传进去（最简单）
    2. 用 TransmittableThreadLocal（阿里的 TTL）
    3. 用 TaskDecorator 手动复制上下文：
       @Bean
       public TaskDecorator taskDecorator() {
           return runnable -> {
               UserContextDTO user = UserContext.getUser();   // 主线程里取
               return () -> {
                   try {
                       UserContext.setUser(user);              // 子线程里放
                       runnable.run();
                   } finally {
                       UserContext.remove();
                   }
               };
           };
       }


################################################################################
  三、线程池 ★★ 面试必问第一名
################################################################################

【★ 七大参数（必须背下来）】
  public ThreadPoolExecutor(
      int corePoolSize,                   // 1. 核心线程数（常驻）
      int maximumPoolSize,                // 2. 最大线程数
      long keepAliveTime,                 // 3. 非核心线程空闲存活时间
      TimeUnit unit,                      // 4. 时间单位
      BlockingQueue<Runnable> workQueue,  // 5. 任务队列
      ThreadFactory threadFactory,        // 6. 线程工厂
      RejectedExecutionHandler handler    // 7. 拒绝策略
  )

  口诀：核心、最大、存活时间、时间单位、队列、工厂、拒绝策略

【★ 任务提交后的完整流程（面试必考）】

  提交任务
      ↓
  ① 核心线程池满了吗？
     没满 → 创建核心线程执行
     满了 ↓
  ② 队列满了吗？
     没满 → 放进队列等待
     满了 ↓
  ③ 线程数达到 maximumPoolSize 了吗？
     没达到 → 创建非核心线程执行
     达到了 ↓
  ④ 执行拒绝策略

  ★ 关键点：先排队，再扩容到最大线程数。
    很多人记反，以为"核心满了就直接创建到最大"。
    正确顺序：核心 → 队列 → 最大 → 拒绝

【四种拒绝策略】
  ------------------------------------------------------------------
  策略                        行为                          风险
  ------------------------------------------------------------------
  AbortPolicy（默认）         抛 RejectedExecutionException 调用方要处理
  CallerRunsPolicy            让提交任务的线程自己执行      ★ 降级不丢任务
  DiscardPolicy               静默丢弃                      ✗ 任务静默丢失
  DiscardOldestPolicy         丢弃队列最老的                ✗ 老任务被丢
  ------------------------------------------------------------------

  ★ 生产推荐 CallerRunsPolicy：它会拖慢提交速度形成"背压"，避免任务丢失。

【★ 为什么不推荐 Executors】
  ------------------------------------------------------------------
  方法                    问题
  ------------------------------------------------------------------
  newFixedThreadPool      队列无界（LinkedBlockingQueue）→ 任务堆积 OOM
  newSingleThreadExecutor 队列无界 → OOM
  newCachedThreadPool     最大线程数 Integer.MAX_VALUE → 无限创建线程 OOM
  newScheduledThreadPool  队列无界 → OOM
  ------------------------------------------------------------------

  ★ 阿里 Java 开发手册明确禁止用 Executors，
    必须手动 new ThreadPoolExecutor，让你清楚每个参数的含义。

【线程数怎么设】
  ------------------------------------------------------------------
  任务类型              推荐线程数            理由
  ------------------------------------------------------------------
  CPU 密集型            核心数 + 1            线程太多反而增加切换开销
  IO 密集型             核心数 × 2            等待 IO 时不占 CPU，可多开
  ------------------------------------------------------------------

  更理论的公式：
    线程数 = 核心数 × 目标CPU利用率 × (1 + 平均等待时间 / 平均计算时间)

  ★ 生产环境要压测调优，公式只是起点。

  获取核心数：Runtime.getRuntime().availableProcessors()

【线程池监控】
  继承 ThreadPoolExecutor 覆写 beforeExecute / afterExecute：
    · 已完成任务数
    · 队列积压数
    · 活跃线程数
    · 拒绝任务数
  ★ 配合 Micrometer 暴露成指标。

【动态调参】
  ThreadPoolExecutor 提供了 setCorePoolSize / setMaximumPoolSize，
  可以配合配置中心实现运行时动态调整。


################################################################################
  四、分布式锁
################################################################################

【为什么需要】
  单机用 synchronized（JVM 内的锁）。
  但你有 3 台服务器时，synchronized 只能锁住自己那台，
  另外两台完全不受影响 → 锁失效。

  分布式锁 = 所有机器都去抢同一把"公共的锁"。

【★ 手写 Redis 分布式锁的四个要素】

  要素1：SETNX 实现互斥
    SET key value NX PX 30000
    NX = 不存在才设置（保证只有一个线程成功）
    PX = 毫秒级过期时间

  要素2：必须设置过期时间
    ★ 不设的话，拿到锁的线程崩了，锁永远不释放 → 死锁

  要素3：唯一 value 防误删
    ★ 场景：
      · 线程 A 拿到锁，业务超时，锁自动过期
      · 线程 B 拿到同一把锁
      · 线程 A 执行完，执行 DEL key → 删掉了 B 的锁！
    ★ 解法：value 存 UUID（标识"这是我加的锁"），删除前先判断

  要素4：判断 + 删除必须原子
    if redis.call("get", KEYS[1]) == ARGV[1] then
        return redis.call("del", KEYS[1])
    else
        return 0
    end
    ★ 用 Lua 脚本保证原子性，因为"判断"和"删除"之间如果被打断，
      还是会误删别人的锁。

【完整实现】
  public boolean tryLock(String key, String value, long expireMs) {
      Boolean success = redis.opsForValue()
              .setIfAbsent(key, value, expireMs, TimeUnit.MILLISECONDS);
      return Boolean.TRUE.equals(success);
  }

  public void unlock(String key, String value) {
      String script = "if redis.call('get', KEYS[1]) == ARGV[1] " +
                      "then return redis.call('del', KEYS[1]) else return 0 end";
      redis.execute(new DefaultRedisScript<>(script, Long.class),
                    Collections.singletonList(key), value);
  }

【★ 手写锁的经典问题】
  业务执行时间 > 锁过期时间怎么办？
    线程 A 拿到锁（30 秒），业务要跑 60 秒。
    30 秒后锁自动过期，线程 B 拿到锁开始执行。
    此时 A 和 B 同时在跑 → 锁失效。

  解法：
    方案一：把过期时间设得足够长（治标不治本）
    方案二：起一个"看门狗"线程，定时给锁续期
    方案三：用 Redisson（内置看门狗）

【Redisson 的看门狗机制】
  Redisson 加锁时默认 30 秒过期。
  如果业务还没执行完，看门狗每隔 10 秒（1/3 过期时间）给锁续期。
  业务执行完释放锁，看门狗停止续期。

  RLock lock = redissonClient.getLock("lock:" + id);
  try {
      boolean locked = lock.tryLock(10, 30, TimeUnit.SECONDS);
      if (locked) {
          // 业务逻辑
      }
  } finally {
      if (lock.isHeldByCurrentThread()) {
          lock.unlock();
      }
  }

【★ 三种分布式锁实现对比】
  ------------------------------------------------------------------
  实现        优点                    缺点
  ------------------------------------------------------------------
  Redis       性能高、实现简单        主从切换时可能丢锁
  ZooKeeper   强一致性、可靠性高      性能较低
  数据库      实现简单                性能差、有单点
  ------------------------------------------------------------------

  【Redis 锁的"主从切换丢锁"问题】
    线程 A 在 master 拿到锁 → master 挂了 → 数据还没同步到 slave
    → slave 升为新 master → 线程 B 也能拿到同一把锁
    解法：RedLock（向多数节点加锁），但 RedLock 本身也有争议。

【★ 一个重要的认知】
  如果你的业务能接受"偶尔两个线程同时执行"（比如重复发一条通知），
  那用 Redis 锁就够了。
  如果绝对不能（比如扣款），应该用 ZooKeeper 或数据库的唯一约束兜底。


################################################################################
  五、消息队列（RabbitMQ）
################################################################################

【核心概念】
  ------------------------------------------------------------------
  概念          说明                              类比
  ------------------------------------------------------------------
  Producer      消息生产者                        寄信人
  Consumer      消息消费者                        收信人
  Exchange      交换机，决定消息路由              邮局分拣中心
  Queue         队列，存储消息                     收件人的信箱
  RoutingKey    路由键，交换机据此决定去向        信封上的地址
  Binding       绑定关系                          邮局的投递规则
  ------------------------------------------------------------------

  流转：Producer → Exchange → (RoutingKey + Binding) → Queue → Consumer

【四种 Exchange 类型】
  ------------------------------------------------------------------
  类型      路由规则                        适用场景
  ------------------------------------------------------------------
  Direct    精确匹配 RoutingKey             点对点
  Topic     通配符匹配（* 一个词 # 多个）   按类别订阅 ★
  Fanout    广播到所有绑定的队列            通知所有订阅者
  Headers   按消息头匹配                    很少用
  ------------------------------------------------------------------

  【Topic 通配符】
    *  匹配一个单词       novel.*.update  →  novel.chapter.update ✓
    #  匹配零个或多个     novel.#         →  novel.a.b.c ✓

【★ 消息不丢失的三个环节】

  ------------------------------------------------------------------
  环节          风险                    解决方案
  ------------------------------------------------------------------
  生产者 → MQ   网络抖动，消息没发出去  1. 生产者确认（publisher confirm）
                                        2. 事务消息
                                        3. 本地消息表
  ------------------------------------------------------------------
  MQ 内部       Broker 宕机，内存中丢失 1. 队列持久化（durable）
                                        2. 消息持久化（deliveryMode=2）
                                        3. 镜像队列 / 仲裁队列
  ------------------------------------------------------------------
  MQ → 消费者   消费者拿到就崩了         1. 手动 ACK（消费成功才确认）
                                        2. 消费失败重试
                                        3. 重试多次后进死信队列
  ------------------------------------------------------------------

【死信队列（DLX）】
  死信 = 无法被正常消费的消息。三种情况：
    1. 消息被拒绝（basicReject / basicNack）且不重新入队
    2. 消息过期（TTL 到期）
    3. 队列达到最大长度

  死信会被路由到"死信交换机" → "死信队列"，等待人工处理。
  ★ 意义：消息不会凭空消失，可以事后排查和补偿。

【★ 消息幂等（面试高频）】

  问题：网络抖动导致消息重复投递，消费者处理了两次。

  为什么 MQ 保证不了"只投一次"？
    因为"投递"和"确认"是两个动作，
    如果消费者处理完但确认时网络断了，MQ 会重投。
    所以只能做到"至少一次"，需要消费者自己保证幂等。

  幂等的实现方式：
    · 唯一索引（数据库层兜底）
    · Redis 记录消息 ID（处理前先查，处理完写入）
    · 状态机（只允许特定状态流转）
    · 乐观锁（version 字段）

  示例：
    String msgId = message.getMessageProperties().getMessageId();
    Boolean first = redis.opsForValue()
            .setIfAbsent("mq:consumed:" + msgId, "1", 24, TimeUnit.HOURS);
    if (Boolean.FALSE.equals(first)) {
        return;     // 已经处理过，直接返回
    }
    // 处理业务

【★ 顺序消息】
  问题：同一个订单的"创建 → 支付 → 完成"三条消息，
        如果被不同消费者并发处理，顺序就乱了。

  解法：
    · 把同一业务 ID 的消息路由到同一个队列（RabbitMQ 用 hash routing key）
    · 消费者单线程消费该队列
    · 或者用 RocketMQ 的顺序消息特性

【★ 延迟消息】
  场景：下单后 30 分钟未支付自动取消。

  实现：
    · RabbitMQ：TTL + 死信队列组合
    · RocketMQ：内置延迟消息（支持固定延迟级别）
    · Redis：ZSet 存时间戳，定时任务轮询
    · 定时任务：XXL-Job / Quartz

【★ 三种 MQ 选型对比】
  ------------------------------------------------------------------
  对比项        RabbitMQ        RocketMQ        Kafka
  ------------------------------------------------------------------
  吞吐量        万级            十万级          百万级
  延迟          微秒级          毫秒级          毫秒级
  可靠性        高              高              高
  顺序消息      不支持          支持            分区内有序
  事务消息      不支持          支持 ★          支持
  延迟消息      需组合实现      原生支持 ★      不支持
  适用场景      中小项目        电商/金融 ★     日志/大数据
  ------------------------------------------------------------------


################################################################################
  六、削峰填谷
################################################################################

  【场景】秒杀活动，10 万请求瞬间涌入，数据库扛不住。

  【方案】请求先写入 MQ，后端按自己的处理能力消费。

    用户请求 → 网关限流（挡掉大部分）→ MQ（存起来）→ 消费者（按能力消费）

  【★ 三个要点】
    1. 前端要限流 + 按钮置灰，从源头减少无效请求
    2. 队列长度要有限制（否则消息堆积也会 OOM）
    3. 要给用户即时反馈（"排队中，请稍候"），而不是让页面一直转圈

  【★ 队列积压了怎么办】
    · 增加消费者实例（水平扩容）
    · 提高单个消费者的并发（线程池）
    · 临时丢弃非核心消息
    · 降级：直接返回"系统繁忙"，不再接收新消息


################################################################################
  面试会怎么问
################################################################################

  Q1：你们项目为什么用消息队列？
  A： 三个理由：解耦、削峰、异步。
     ★ 要结合具体场景：发布章节后要给订阅用户发通知，
       同步做用户要等几十秒，用 MQ 后立刻返回。

  Q2：怎么保证消息不丢失？
  A： 分三个环节：生产者用 confirm，Broker 用持久化，
     消费者用手动 ACK，最后加死信队列兜底。

  Q3：消息重复消费怎么办？
  A： 保证消费端幂等。用唯一索引 / Redis 去重 / 状态机 / 乐观锁。

  Q4：Redis 分布式锁怎么实现？
  A： SETNX + 过期时间 + 唯一 value，删除用 Lua 保证原子性。
     ★ 要能说出"为什么要唯一 value"（防误删别人的锁）
       和"为什么要 Lua"（判断和删除要原子）。

  Q5：手写分布式锁有什么问题？Redisson 怎么解决的？
  A： 问题是业务执行时间超过锁过期时间，导致锁提前释放。
     Redisson 用看门狗线程定时续期解决。

  Q6：线程池核心参数有哪些？怎么设置？
  A： 七大参数。线程数按 CPU 密集 / IO 密集分别设，
     生产环境要压测调优。

  Q7：@Async 有什么坑？
  A： 同类内部调用失效、方法必须 public、
     返回 void 时异常不传播、默认线程池会无限创建线程、
     ThreadLocal 会失效。

  Q8：MQ 选型怎么考虑？
  A： RabbitMQ 适合中小项目、延迟低；
     RocketMQ 支持事务消息和延迟消息，适合电商金融；
     Kafka 吞吐量最高，适合日志和大数据场景。

  Q9：怎么保证消息顺序？
  A： 同一业务 ID 的消息路由到同一个队列，消费者单线程消费。

  Q10：延迟消息怎么实现？
  A： RabbitMQ 用 TTL + 死信队列组合；
     RocketMQ 原生支持；
     Redis 用 ZSet + 定时轮询。
