################################################################################
  Q1　JWT 是无状态的，用户登出后 token 怎么失效？　【其他】
################################################################################

- **考点**：能不能识破"JWT 是无状态的"这句半真半假的话。
  无状态指的是**服务端不为每个会话存一份数据**（对比 Session），
  但"能登出"这件事天然需要服务端记一笔状态 —— 考的是你知不知道
  这笔状态该**记什么、记在哪、记多久、记不下了怎么办**。

- **追问链**：
  Q1「JWT 为什么不学 Session 做成有状态的？」→
  Q2「黑名单为什么用 Redis Hash，不用 Set 或 String？」→
  Q3「黑名单 key 会不会一直涨？」→
  Q4「Redis 挂了黑名单查不了，你放过还是拒绝？」
  （★ 转到 01-缓存体系 Q12：哪些地方该降级、哪些不该）→
  Q5「多设备同时登录，一个设备登出会不会把别的设备踢掉？」
  （★ 本项目真有这个问题，见下面的「坑」）

- **参考答案**：
  先纠正前提：JWT 的"无状态"指**服务端不存会话数据**，
  所以 JWT 一旦签发，在过期之前**一直有效** —— 这正是它不能天然登出的原因。
  "过期"是**自然到期**，"登出"是**主动作废**，两回事。

  要能登出，就得补一笔"已作废"的状态，主流两种做法：

  | 方案 | 怎么存 | 优点 | 缺点 |
  |---|---|---|---|
  | 黑名单（本项目） | 登出时把当前 token 记进 Redis，拦截器每次校验查一下 | 改动小，签发逻辑不动 | 每个请求多一次 Redis 查询 |
  | 版本号 / 白名单 | 用户表存 tokenVersion，签发时写进 JWT，登出 +1，校验时比对 | 不随 token 数量膨胀 | 要改签发逻辑 + 每次都查库/缓存 |

  关键细节，面试官最爱挖这三条：
    · **存什么** —— 不能只存 token 本身，要连"它什么时候自然过期"一起存，
      否则黑名单只能等整条 key 过期，白占内存
    · **用什么结构** —— 用 Hash（field = token，value = 过期时间戳）而不是 Set：
      **Set 存不了每条 token 各自的过期时间**
    · **记多久** —— 只要覆盖 access token 的剩余寿命就够，之后它自己就过期了，
      再留在黑名单里没意义

- **本项目的证据**：★ 全都有，能说出类名和行号
  · 接口：`UserController.logout`（`POST /users/logout`，需登录）
    从 `Authorization` 头取 token → 剥掉 `Bearer ` → 从 `UserContext` 取 userId
  · 拉黑：`UserServiceIml.logout`（约 194–215 行）两步走 ——
    1) 先删双 Token 的正反向索引：`user_refresh:{userId}` 取出 refreshToken
       → 删 `refresh_token:{refreshToken}` 和 `user_refresh:{userId}`
    2) access token 进黑名单：key = `blacklist:user:{userId}`（**Hash**），
       field = access token，value = 当前毫秒 + 120 分钟的时间戳；
       另外 `expire(key, 120, MINUTES)` 给整条 key 也兜了 120 分钟的底
  · 校验：`LoginInterceptor.isBlacklisted`（约 158 行起）
    `opsForHash().get("blacklist:user:" + userId, token)`；命中再比时间戳，
    顺手把已过期的记录惰性删掉
  · 为什么用 Hash：`AGENTS.md` 关键设计决策 3 —— Set 存不了过期时间
  · 降级取舍：黑名单查询包了 try/catch，Redis 异常时只 `log.warn` 然后**放过**
    （可用性优先，代价是那段窗口内旧 token 还能用）→ 对照 01-Q12
  · ⚠ **未验证**：登出后拿旧 token 再请求、期望 HTTP 401 —— **这条判据我从没跑过**。
    面试前建议真跑一遍（判据：登出 → 用旧 token 请求 `GET /bookshelf` → 期望 401）
  · ⚠ **前端现状**（2026-10-14 实测代码）：`useAuth.logout()` 只删本地 localStorage，
    **没有调 `POST /users/logout`** ⇒ 在浏览器里点"退出登录"，
    服务端那份 token 并没有被拉黑，直到自然过期前都还有效

- **坑**：
  · 答成"JWT 自带过期，所以能登出" —— 过期 ≠ 作废，这是最容易翻车的一句
  · 只删 refreshToken、不拉黑 accessToken —— accessToken 才是在用的那把钥匙
  · 以为"要给黑名单设 TTL 就得给每条 field 设" ——
    Redis 的 Hash **不支持给单个 field 设 TTL**，所以只有两条路：
    (a) 给整条 key 设 TTL，(b) value 里存时间戳靠惰性删除。**本项目两个都做了**
  · ⚠ 本项目已经踩到、但**还没修**的三处（被追问时主动说，比被挖出来强）：
    - 问题 9：`user_refresh:{userId}` 是 **String**，只能存一个 refreshToken，
      ⇒ A 设备登出会顺手删掉 B 设备的（登出行为错）
    - N1：`LoginInterceptor` 里过期判断边界不一致（游客路径 `>=`、严格路径 `>`，约 69 / 116 行）
    - N3：游客路径有个空 catch 把异常吞了 —— 连"有人拿伪造 token 扫描"都发现不了
