【技术亮点（面试可以主动讲）】

  ✓ 自定义 @RateLimit 注解 + @Around 环绕通知，限流逻辑与业务代码完全解耦
  ✓ 用 Redis INCR 做计数，天然支持分布式（多机部署时本地 Map 会算不准）
  ✓ 客户端真实 IP 提取：依次尝试 X-Forwarded-For、Proxy-Client-IP、
    WL-Proxy-Client-IP、HTTP_CLIENT_IP、HTTP_X_FORWARDED_FOR，最后回退 getRemoteAddr
  ✓ 多级代理时取 X-Forwarded-For 的第一个 IP
  ✓ RateLimitException 走全局异常处理器，返回 HTTP 429

【★ 缺口 2：固定窗口的临界突刺没处理】

  假设限流 5 次/60 秒：
    第 59 秒发 5 次（窗口 1 的额度用光）
    第 61 秒发 5 次（窗口 2 的额度刚开始）
    → 2 秒内实际通过了 10 次，是限制值的 2 倍

  攻击者卡在窗口切换瞬间就能把限流效果翻倍。

【★ 缺口 3：INCR 和 EXPIRE 分两步，非原子】

  代码：
    Long count = stringRedisTemplate.opsForValue().increment(redisKey);
    if (count != null && count == 1) {
        stringRedisTemplate.expire(redisKey, window, TimeUnit.SECONDS);
    }

  风险：如果 INCR 执行完、EXPIRE 执行前进程崩溃或 Redis 断开，
        这个 key 就永久存在 → 用户被永久限流。

【★ 缺口 4：X-Forwarded-For 可伪造】

  如果服务直接暴露公网，客户端可以自己加一个假的 X-Forwarded-For 头，
  每次换一个假 IP 就绕过限流了。
  生产环境应该由 Nginx 统一设置这个头，并覆盖客户端传的值。

################################################################################
  三、关键实现速查
################################################################################

【注解定义】
  @Target(ElementType.METHOD)
  @Retention(RetentionPolicy.RUNTIME)
  public @interface RateLimit {
      String key();
      int limit() default 5;
      int window() default 60;
  }

【切面核心逻辑】
  @Around("@annotation(rateLimit)")
  public Object around(ProceedingJoinPoint point, RateLimit rateLimit) throws Throwable {
      String redisKey = "rate_limit:" + rateLimit.key() + ":" + getClientIp();
      Long count = stringRedisTemplate.opsForValue().increment(redisKey);
      if (count != null && count == 1) {
          stringRedisTemplate.expire(redisKey, rateLimit.window(), TimeUnit.SECONDS);
      }
      if (count != null && count > rateLimit.limit()) {
          throw new RateLimitException("请求过于频繁，请稍后再试");
      }
      return point.proceed();
  }

【Redis Key 格式】
  rate_limit:{业务key}:{ip}
  例：rate_limit:login:192.168.1.100

【异常处理链路】
  RateLimitAspect 抛 RateLimitException
      → GlobalExceptionHandler.handleRateLimit()
      → @ResponseStatus(HttpStatus.TOO_MANY_REQUESTS)  → HTTP 429
      → Result.error(429, "请求过于频繁，请稍后再试")
