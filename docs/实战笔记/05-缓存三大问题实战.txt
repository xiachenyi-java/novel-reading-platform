################################################################################
  二、任务一：缓存穿透
################################################################################

--------------------------------------------------------------------------------
2.1 问题：不存在的 id 每次都打 DB
--------------------------------------------------------------------------------

  复现：
    curl "http://localhost:8080/novels/999999"   # ×3

  日志里：
    select n1_0.id,... from novel n1_0 where n1_0.id=?   （×3）
    WARN GlobalExceptionHandler : 用户问题: 小说不存在     （×3）

  三次请求 → 三条 SQL。缓存完全没挡住。

--------------------------------------------------------------------------------
2.2 根因：@Cacheable 的语义盲区 ★ 核心知识点
--------------------------------------------------------------------------------

  @Cacheable 只缓存"方法正常 return"的返回值。
  方法抛异常时，它不写缓存。

  findDetail 查不到小说时：
    Novel novel = novelRepository.findById(novelId)
            .orElseThrow(() -> new BusinessException("小说不存在"));   // ← 抛异常

  → 方法没正常返回 → @Cacheable 不写缓存 → 下次相同请求回到原点。

  ★★ 推广：任何"用异常表示否定结果"的场景，@Cacheable 都保护不了。
     这不是 bug，是语义设计 —— 框架认为"抛异常"意味着"这次调用失败了，
     结果不可信，不该缓存"。

--------------------------------------------------------------------------------
2.3 方案：空值缓存（双 cache + 独立 TTL）
--------------------------------------------------------------------------------

  【核心思路】
    查不到时，也往缓存写一个"非 null 占位符"（空标记），
    用较短的 TTL 让它自然过期。

  【为什么不能存 null】
    Cache.get(key) 返回 null 时，分不清两种情况：
      · 缓存里根本没有这个 key
      · 缓存里存了一个 null 值
    必须存非 null 的占位符（如 Boolean.TRUE）才能当"存在标记"用。

  【为什么空标记要用短 TTL】
    · 占内存 —— 被恶意刷 10 万个不存在的 id，就是 10 万个 key
    · 是"推测性"数据 —— 可能被新增数据推翻（新小说可能撞上这个 id）
    短 TTL 既省内存，也缩小数据不一致的窗口。

  【为什么不用布隆过滤器】
    · 有误判率（可能把存在的误判成不存在）
    · 无法删除元素（新增数据后不能更新）
    学习项目优先选简单方案。布隆过滤器列为后续优化。

--------------------------------------------------------------------------------
2.4 代码改动
--------------------------------------------------------------------------------

  改动 1：CacheConfig.java —— 给 novel-null 单独配 5 分钟 TTL

    return RedisCacheManager.builder(connectionFactory)
            .cacheDefaults(config)                                    // 默认 25~35 分钟
            .withInitialCacheConfigurations(Map.of(
                    "novel-null", config.entryTtl(Duration.ofMinutes(5))   // 覆盖为 5 分钟
            ))
            .build();

    ★ 关键 API：withInitialCacheConfigurations(Map<String, RedisCacheConfiguration>)
    ★ 关键概念：RedisCacheConfiguration 是**不可变对象**，
               config.entryTtl(...) 返回的是新对象，不会污染原 config。

  改动 2：NovelServiceIml.findDetail —— 去掉 @Cacheable，改手动双缓存

    Cache novelCache = cacheManager.getCache("novel");
    Cache nullCache  = cacheManager.getCache("novel-null");

    // ① 查空标记（优先，命中直接抛）
    Object nullMark = nullCache.get(novelId);
    if (nullMark != null) {
        throw new BusinessException("小说不存在");
    }

    // ② 查真数据
    NovelDetailVO cached = novelCache.get(novelId, NovelDetailVO.class);
    if (cached != null) {
        return cached;
    }

    // ③ 查 DB
    Optional<Novel> opt = novelRepository.findById(novelId);
    if (opt.isEmpty()) {
        nullCache.put(novelId, Boolean.TRUE);   // ★ 关键：写空标记
        throw new BusinessException("小说不存在");
    }
    Novel novel = opt.get();

    // ④ 组装 VO（原逻辑不变）+ ⑤ 写缓存
    ...
    novelCache.put(novelId, vo);
    return vo;

  【★ 为什么先查 novel-null 再查 novel】
    正常情况两者互斥。但如果数据结构不一致，"不存在"应该优先 ——
    宁可返回"不存在"，也不要返回可能过期的数据。
    顺带还能省一次 Redis 往返（命中空标记就直接抛）。

--------------------------------------------------------------------------------
2.5 尾巴：空标记和"新增数据"的一致性
--------------------------------------------------------------------------------

  场景：
    T1  用户查 /novels/888   → DB 没有 → 写 novel-null::888（5 分钟 TTL）
    T2  管理员发新小说        → DB 新增一本，自增 id 恰好 = 888
    T3  用户查 /novels/888   → 命中空标记 → 返回"不存在"  ❌
    T4  5 分钟后 TTL 过期     → 才正常

  修复：addNovel 加 @CacheEvict

    @CacheEvict(value = "novel-null", key = "#result.id")
    public Novel addNovel(NovelDTO dto) { ... }

  ★ 关键 API：#result 是 SpEL 引用**方法返回值**
  ★ 它要求 beforeInvocation = false（默认值），
    因为方法执行前 #result 还不存在。
  ★ key = "#result.id" 精确清新书的空标记，不误伤其他空标记。

  【为什么只有 addNovel 需要清】
    updateNovel / deleteNovel / 章节操作，都不会把"不存在的 id"变成"存在"。
    deleteNovel 是反向变化（存在 → 不存在），不涉及空标记。
    ★ 唯一能把"不存在"变"存在"的入口，只有 addNovel。

  【为什么不用 allEntries = true】
    会清空整个 novel-null 区，误伤其他所有空标记 ——
    等于一次性放弃全部穿透防护。图省事的代价。

--------------------------------------------------------------------------------
2.6 验证
--------------------------------------------------------------------------------

  docker exec -it demo2-redis redis-cli
  > DEL novel-null::999999

  curl "http://localhost:8080/novels/999999"   # ×5

  预期与实测：
    · SQL 只打 1 次（第 1 次查库 + 写标记，后 4 次命中空标记直接抛）  ✅
    · WARN "小说不存在" 出现 5 次（每次都要告诉用户"没有"，正常）    ✅
    · Redis 里：
        novel::1              → TTL ≈ 1800s
        novel-null::999999    → TTL = 300s
      两个 TTL 不同 → 独立配置生效                                    ✅

  日志形态（★ 这个是"生效了"的视觉特征）：
    SQL       ← 第 1 次：查库、没查到、写标记、抛异常
    WARN      ← 第 1 次响应
    WARN      ← 第 2 次：命中空标记，不查库
    WARN      ← ...
    WARN
    WARN

    ★ 5 条 WARN 密集出现（间隔 1s），中间一条 SQL 都没有，只有最前面 1 条。


################################################################################
  三、任务二：缓存雪崩
################################################################################

--------------------------------------------------------------------------------
3.1 问题：大量 key 同时过期
--------------------------------------------------------------------------------

  典型场景：系统凌晨 3 点被预热脚本灌了 5000 个 novel 进缓存，
  它们同一秒写入（TTL 都 30 分钟），也同一秒过期。
  第二天下午流量高峰期恰好到点 → 5000 个请求同时打 DB。

--------------------------------------------------------------------------------
3.2 ★ 穿透 / 击穿 / 雪崩的区别（最容易混）
--------------------------------------------------------------------------------

  ------------------------------------------------------------------
  问题   触发条件                  涉及 key 数   DB 里有吗
  ------------------------------------------------------------------
  穿透   查一个不存在的 key        单个/任意      DB 里也没有
  击穿   单个热点 key 过期瞬间     单个           DB 里有，缓存刚好不在
  雪崩   大量 key 同时过期         大量           缓存层整体失效
         / Redis 宕机
  ------------------------------------------------------------------

  【记忆法】
    穿透 = 光穿透玻璃 —— 数据本来就不存在，缓存"没得挡"
    击穿 = 砸穿一个洞 —— 数据存在，但那个点的缓存刚好没了
    雪崩 = 整片压倒   —— 大片缓存同时失效

--------------------------------------------------------------------------------
3.3 方案：TTL 加随机抖动
--------------------------------------------------------------------------------

  核心思路：写缓存时 TTL = 基础值 ± 随机量，让过期时间错开。

--------------------------------------------------------------------------------
3.4 ★ 关键 API：TtlFunction
--------------------------------------------------------------------------------

  Spring Data Redis 提供了 RedisCacheConfiguration.entryTtl(TtlFunction) 重载：

    @FunctionalInterface
    public interface TtlFunction {
        Duration getTimeToLive(Object key, Object value);
    }

  ★★ 关键理解：TtlFunction 是**每次 put 时都执行一次**，
     不是配置时执行一次。这是它和 entryTtl(Duration) 的根本区别。

  ------------------------------------------------------------------
  写法                              随机数什么时候算    效果
  ------------------------------------------------------------------
  entryTtl(Duration.ofMinutes(30))  配置时算一次        所有 key 都 30 分钟
  entryTtl((k, v) -> ...)           每次 put 都调用     每个 key TTL 都不同
  ------------------------------------------------------------------

  ★ 这个"每次调用时求值"的特性和 CacheErrorHandler、CacheResolver、
    KeyGenerator 是一致的 —— Spring Cache 的扩展点大多是函数式接口，
    都是"每次调用时求值"。记住这个规律，能少背很多 API。

--------------------------------------------------------------------------------
3.5 代码改动（CacheConfig.java）
--------------------------------------------------------------------------------

  RedisCacheConfiguration config = RedisCacheConfiguration.defaultCacheConfig()
          .entryTtl((key, value) -> {
              int seconds = ThreadLocalRandom.current().nextInt(1500, 2101);
              return Duration.ofSeconds(seconds);          // ★ 秒，不是分钟
          })
          .serializeKeysWith(...)
          .serializeValuesWith(...);

  参数含义：
    · nextInt(origin, bound) 是**左闭右开**区间
      → 取 [1500, 2101) 才能包含 2100
    · 1500~2100 秒 = 25~35 分钟 = 基础 30 分钟 ± 5 分钟
    · 抖动范围经验值：基础 TTL × (1 ± 10~20%)

--------------------------------------------------------------------------------
3.6 验证
--------------------------------------------------------------------------------

  docker exec -it demo2-redis redis-cli
  > DEL novel::1
  > DEL novel::2
  > DEL novel::3

  curl ".../novels/1" ; curl ".../novels/2" ; curl ".../novels/3"

  > TTL novel::1
  > TTL novel::2
  > TTL novel::3

  预期：三个 TTL 互不相同，都落在 1500~2100 秒。
        ★ 如果三个是 1799 / 1798 / 1797 连着，说明抖动没生效。

  进一步验证"每次 put 都随机"：
    DEL novel::1 → 再 curl /novels/1 → 新 TTL 又不一样。

  ★ 2026-10-06 实测：novel::1 的 TTL = 1832 秒，落在区间内  ✅


################################################################################
  四、任务三：缓存降级失效 ★★★ 本次最有价值的一段
################################################################################

--------------------------------------------------------------------------------
4.1 问题：改了缓存实现，降级悄悄失效了
--------------------------------------------------------------------------------

  背景：上午为了做空值缓存（任务一），把 findDetail 从 @Cacheable
        改成了手动 cacheManager 调用。

  后果：Redis 挂掉时，/novels/1 返回
        HTTP 200 + {"code":500,"msg":"Redis command timed out"}

  ★ 为什么改造前没事：
    @Cacheable 由 CacheInterceptor 切面管理，
    Redis 出错时会被 CacheErrorHandler 兜底降级。
    改成手写 cacheManager.getCache(...).get(...) 后，绕过了切面，
    CacheErrorHandler 不再生效。

--------------------------------------------------------------------------------
4.2 ★★ 根因：CacheErrorHandler 是"切面的配置"，不是"RedisCache 的配置"
--------------------------------------------------------------------------------

  走 @Cacheable：
    请求 → CacheInterceptor(切面) → RedisCache.get() → 出错
                                        ↓
                              CacheInterceptor 捕获 → CacheErrorHandler
                                        ↓
                                降级：跳过缓存，继续执行原方法

  手写 cacheManager.getCache()：
    请求 → Service.findDetail → 直接调 RedisCache.get() → 出错
                                        ↓
                                直接往上抛 → GlobalExceptionHandler → 500

  ★★ 一句话记住：
     注解生效 = 框架的切面拦住了你。
     一旦绕开切面（改用手写 API），切面提供的所有附加能力都会消失。

  【推广到项目里其他注解】（★ AOP 通用规律）

    ------------------------------------------------------------------
    注解                底层切面                手写 API 后丢失什么
    ------------------------------------------------------------------
    @Cacheable          CacheInterceptor        缓存降级
    @Transactional      TransactionInterceptor  事务回滚、传播、隔离
    @RateLimit(自定义)  RateLimitAspect         限流计数
    @RequireAdmin       LoginInterceptor        权限校验
    ------------------------------------------------------------------

    ★ 这张表值得背下来 —— 它解释了为什么"手写版"总是比"注解版"要操心更多。

--------------------------------------------------------------------------------
4.3 第一级修复：加超时（止血）
--------------------------------------------------------------------------------

  【问题】Redis 挂掉时单请求挂起 60 秒。

  为什么是 60 秒：Spring Boot 的 spring.data.redis.timeout 默认值是 0
  （含义是"用客户端默认值"），而 Lettuce 的命令超时默认 **60 秒**。

  【为什么"挂起"比"报错"更危险】
    Redis 挂 + 请求量稍大 → 200 个 Tomcat 线程全被占满卡 60 秒 →
    连**不依赖 Redis** 的列表接口也开始排队 → 级联故障。

    算笔账（Tomcat 默认 200 线程）：
      改造前：200 线程 ÷ 60s  =  3.3   req/s   ← 超过就全排队
      改造后：200 线程 ÷ 1.5s =  133   req/s

  【修复】application-dev.properties 加两行

    spring.data.redis.timeout=500ms
    spring.data.redis.connect-timeout=500ms

  【★ 两个超时的区别（容易混）】

    ------------------------------------------------------------------
    配置                管什么                      触发时机
    ------------------------------------------------------------------
    connect-timeout     建立 TCP 连接的时间         Redis 服务完全不在
                                                    （端口不通）
    timeout             发出命令后等响应的时间      连接已建立但命令没响应
                                                    （Redis 卡住 / 网络丢包）
    ------------------------------------------------------------------

  【推荐值】500ms ~ 1000ms
    Redis 是内存操作，正常 p99 都在 10ms 内，500ms 已经很宽容了。
    ★ 本项目实测正常响应 6~20ms，500ms 是 p99 的 25 倍以上 ——
      只要 Redis 500ms 没回，它就已经不正常了，没必要再等。

--------------------------------------------------------------------------------
4.4 第二级修复：手写 try-catch（治疗）
--------------------------------------------------------------------------------

  核心思路：把 CacheErrorHandler 原本要做的兜底，手动补上。

  【修复原则】
    · 读失败 → 降级为"缓存未命中"，继续往下走（**不要 rethrow**）
    · 写失败 → 吞掉异常，不影响主流程（缓存是加速器，不是必需品）
    · catch 里打 log.warn（不用 error，避免刷屏；不打印堆栈）

  代码改动：findDetail 里 **4 处** Redis 调用各包 try-catch

    // ① 读空标记
    Object nullMark = null;
    try {
        nullMark = nullCache.get(novelId);
    } catch (Exception e) {
        log.warn("空标记读取失败，降级。novelId={}, err={}", novelId, e.getMessage());
    }

    // ② 读真数据
    NovelDetailVO cached = null;
    try {
        cached = novelCache.get(novelId, NovelDetailVO.class);
    } catch (Exception e) {
        log.warn("详情缓存读取失败，降级。novelId={}, err={}", novelId, e.getMessage());
        // ★ 不 rethrow，cached 保持 null，继续走
    }

    if (nullMark != null) { throw new BusinessException("小说不存在"); }
    if (cached != null) { return cached; }

    // ③ 查 DB
    Optional<Novel> opt = novelRepository.findById(novelId);
    if (opt.isEmpty()) {
        try {
            nullCache.put(novelId, Boolean.TRUE);
        } catch (Exception e) {
            log.warn("空标记写入失败，忽略。novelId={}, err={}", novelId, e.getMessage());
        }
        throw new BusinessException("小说不存在");
    }

    Novel novel = opt.get();
    // ... 组装 VO 逻辑不变 ...

    // ④ 写真数据
    try {
        novelCache.put(novelId, vo);
    } catch (Exception e) {
        log.warn("详情缓存写入失败，忽略。novelId={}, err={}", novelId, e.getMessage());
    }
    return vo;

  ★ 注意变量声明位置：nullMark / cached 必须声明在 try **外面**，
    否则 catch 块外看不见（Java 作用域规则）。

--------------------------------------------------------------------------------
4.5 ★★ 意外发现：Lettuce 断连时会缓冲写命令
--------------------------------------------------------------------------------

  【现象】
    修完降级后做故障演练，行为对了，但日志里
    "详情缓存写入失败" **一次都没出现**（grep 结果 = 0）。

    既然 Redis 挂了，put 为什么既不报错、也不记日志、还几乎不耗时？

  【决定性实验】
    docker start demo2-redis     ← 重启 Redis
    # ★ 关键：不发任何新请求！
    docker exec demo2-redis redis-cli EXISTS "novel::1"
    → 1        ← 它已经在那儿了

  【结论】
    Lettuce 在断连期间把写命令**缓冲**了起来，重连后自动补发。

  【这意味着两件事】

    1. 那个 put 的 catch 块，在当前场景下**永远不会触发**。
       ——不是写错了，是这层压根没抛异常。
       保留它是对的，仍是防御其他故障模式的安全网。

    2. ⚠️ 有个隐形风险：Lettuce 的 disconnectedBufferSize 默认 **64KB**。
       Redis 长时间挂 + 高频写 → 缓冲会**悄悄积压**，
       满了之后才真正开始失败。
       也就是说，「Redis 挂了」这件事，对**写操作**而言是**延迟暴露**的。

  【★ 为什么这个发现值得记录】
    因为它来自"验证到底"的习惯 —— 如果只看接口返回 200 就收工，
    永远不会知道底层其实是另一回事。

--------------------------------------------------------------------------------
4.6 验证（三阶段对比）★★ 简历素材
--------------------------------------------------------------------------------

  同样是 `docker stop demo2-redis` 后请求 `GET /novels/1`：

  ------------------------------------------------------------------
  阶段                  耗时          HTTP   body.code   接口可用性
  ------------------------------------------------------------------
  ① 改造前（60s 超时）  60.0s 挂起    200    500         ❌ 打不开
  ② 只加超时配置        0.51s         200    500         ❌ 打不开
  ③ 再加 try-catch      1.01s         200    200         ✅ 有数据
  ------------------------------------------------------------------

  ★ ①→② 是"止血"，②→③ 才是"治疗"。这个区分很重要 ——
    只做 ② 的话，接口是"快速失败"，不是"降级"。

  【③ 的耗时拆解】（日志时间戳）

    49.819  空标记读取失败    ← 500ms 超时
    50.322  详情缓存读取失败  ← 500ms 超时
    50.331  返回响应          ← 只花 9ms（查库 + 组装）
    合计 ≈ 1.01s（两个 500ms 串行叠加）

  【边界情况】

    ------------------------------------------------------------------
    请求                    结果                                  判定
    ------------------------------------------------------------------
    /novels/1（存在）       code:200 + 真实数据，1.012s           ✅
    /novels/999999（不存在）code:500 "小说不存在"，1.018s        ✅
    ------------------------------------------------------------------

    ★ 注意第二个：Redis 挂了，业务逻辑依然正确 ——
      该报"不存在"还是报"不存在"，只是走了 DB。

  【并发压测：500 请求 / 100 并发 / Redis 挂】

    ------------------------------------------------------------------
    指标                  /novels/1        /novels 列表（不依赖 Redis）
    ------------------------------------------------------------------
    最小                  0.503s           0.006s
    P50                   1.491s           0.248s
    P95                   2.575s           —
    最大                  2.784s           2.162s
    平均                  1.526s           —
    超过 5 秒的           0 个             —
    超过 60 秒的          0 个             —
    HTTP 状态             全程 200         全程 200
    ------------------------------------------------------------------

    结论：Redis 挂了不影响不依赖 Redis 的接口，**级联故障被切断**。

  【两个未深挖的观察（留作后续课题）】
    · P50 (1.491s) 是单请求 (0.51s) 的 3 倍
      → 100 并发间有互相影响（Lettuce 共享连接争用 / JVM GC / 连接重试）
    · 列表接口最大 2.162s（基线 0.011s）
      → 100 线程高频异常可能引发小 GC，但整体未崩

  【★ 验证过程本身踩的坑 —— 值得单独记一笔】
    第一次压测跑出 1000 条记录，其中 500 条耗时 0.0003s。
    一度以为是"应用有快速失败的路径"。

    真相是**我的测试脚本写错了**：
      seq 1 100 | xargs -P 100 -n1 curl ... "http://localhost:8080/novels/1"
    xargs -n1 把序号**追加**到了命令末尾，于是 curl 收到两个 URL：
      /novels/1 和 1（被当成 http://1/）
    → 每个 curl 发两次请求，第二次瞬间失败，多打了 500 行噪声。

    ★ 教训：**验证工具本身也要验证**。
      看到"0.0003 秒完成一次 HTTP 请求"就该警觉 —— 那物理上不可能。


################################################################################
  五、踩坑清单汇总
################################################################################

  ------------------------------------------------------------------
  #   坑                                教训
  ------------------------------------------------------------------
  1   @Cacheable 不缓存异常              缓存"否定结果"必须手动接管
  2   空标记存 null                     分不清"没存"和"存了 null"，
                                         必须存非 null 占位符
  3   get 写成 put                      get 是读、put 是写；
                                         get(key, Class<T>) 第二参必须是 Class
  4   缓存读取结果没用                   变量拿了不用等于白读，
                                         命中率归零
  5   entryTtl 单位错                   变量名 seconds + 方法 ofMinutes
                                         → TTL 差 60 倍（25~35 小时！）
  6   nextInt 生成了没接住               生成的随机数必须赋值或直接使用
  7   catch 里 rethrow                  catch 里只要出现 throw，
                                         就等于没降级
  8   缓存降级失效                      CacheErrorHandler 是切面的配置，
                                         手写 API 会绕过切面
  9   Redis 超时 60s                    跨进程调用必须显式配超时
  10  变量声明位置                      try 里声明的变量，catch 外看不见
  11  deleteNovel 也要清空标记？         ❌ 只有"不存在→存在"的转变才需要清
  12  allEntries=true 图省事            会清空整个 cache，误伤无辜
  13  压测脚本把序号当第二个 URL        验证工具本身也要验证
  ------------------------------------------------------------------

  【★ 第 5 条展开 —— 单位事故的通用教训】
    现象：TTL 变成 25~35 小时（实测 122769 秒 ≈ 34 小时）

    单位敏感的 API 写完要盯着看两遍：**变量名、方法名、单位三者一致吗**。
    同类高危 API：
      · Duration（ofSeconds / ofMinutes / ofHours / ofMillis）
      · TimeUnit（SECONDS / MINUTES / MILLISECONDS）
      · BigDecimal 的 scale
      · ByteBuffer 的字节序
    Duration 相关的 bug，十有八九是单位。


################################################################################
  六、贯穿三个任务的核心认知
################################################################################

--------------------------------------------------------------------------------
认知 1：注解 vs 手写 API 的能力差异
--------------------------------------------------------------------------------

  "注解生效" = "切面拦住了你"。手写 API 会丢掉：

  ------------------------------------------------------------------
  手写对象                              丢掉的能力
  ------------------------------------------------------------------
  cacheManager.getCache(...).get(...)   缓存降级
  transactionTemplate.execute(...)      事务回滚、传播、隔离
  手写限流计数                          计数、过期
  ------------------------------------------------------------------

--------------------------------------------------------------------------------
认知 2：三个缓存问题的解法对比
--------------------------------------------------------------------------------

  ------------------------------------------------------------------
  问题   核心思路                        本项目解法
  ------------------------------------------------------------------
  穿透   让"不存在"也进缓存              空值缓存 + 独立 TTL
                                         + addNovel 清标记
  雪崩   让大量 key 不要同时过期         TtlFunction 随机抖动
  击穿   让单个热点 key 过期瞬间          ✓ 本地互斥锁（单机）
         只查一次 DB                              ★ 多实例失效
                                                 （分布式锁未做）
  降级   Redis 挂了不影响主流程          超时配置 + 手写 try-catch
  ------------------------------------------------------------------

--------------------------------------------------------------------------------
认知 3：跨进程调用必须设超时 ★★
--------------------------------------------------------------------------------

  任何跨进程调用都必须设超时，否则一个下游故障会拖垮整个上游服务。

  · 默认值往往很大或很"宽容"（如 Lettuce 60s），必须显式覆盖
  · connect-timeout 和 timeout 是两回事，**都要配**
  · 推荐值：Redis 500ms；MySQL 可类推（如 3~5s）

  【★ 超时预算（timeout budget）】
    如果 A 调 B、B 调 C，每层都设 5 秒，A 最坏要等 15 秒。
    生产上一般要求「下游超时之和 < 上游自己的超时」。
    本项目是单体用不上，但拆微服务会立刻遇到。

--------------------------------------------------------------------------------
认知 4：fail fast ≠ graceful degradation ★★
--------------------------------------------------------------------------------

  ------------------------------------------------------------------
  手段              效果                     用户体感
  ------------------------------------------------------------------
  不配超时          挂起 60 秒               一直转圈
  只配超时          0.5 秒报错               立刻打不开
  + try-catch 降级  1.0 秒返回真实数据       ✅ 正常可用
  ------------------------------------------------------------------

  ★ 这是两个层次的东西，很多人分不清：
    · fail fast（快速失败）= 让故障**快速暴露**，别拖垮别人
    · graceful degradation（优雅降级）= 让功能**继续可用**
    只做前者，接口从"一直转圈"变成"立刻报错" —— 还是不可用。

################################################################################
  八、可延伸的知识点（面试延伸）
################################################################################

  · 布隆过滤器 vs 空值缓存
      内存更省，但有误判率、无法删除元素

  · @Cacheable 的 unless 属性
      可以在方法返回 null 时也不缓存（另一种防穿透思路）

  · 多级缓存
      Caffeine（本地）+ Redis（分布式）

  · 逻辑过期
      不用 Redis TTL，用业务字段标记过期时间，后台线程异步刷新

  · 单飞（singleflight）
      让并发请求只查一次 DB，其他请求等结果

  · 分布式锁
      Redisson、SETNX + EXPIRE、Redlock

  · Spring Cache 扩展点
      CacheResolver / KeyGenerator / CacheErrorHandler 都是函数式接口，
      都是"每次调用时求值"

  · Tomcat 线程池
      默认 200 线程；被下游占满会级联故障

  · AOP 切面绕过
      手写 API 会丢失注解式编程的附加能力

  · Lettuce 断连缓冲
      disconnectedBufferSize 默认 64KB，写失败是延迟暴露的
      ★ 本质是"同步 API 掩盖了异步现实" ——
        Lettuce 底层是异步的（Netty），Spring Data Redis 在外面
        包了一层同步 API（connection.set() 返回 void）。
        **返回 void 的远程操作，你没法知道它到底成功没有。**
