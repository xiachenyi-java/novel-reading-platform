################################################################################
  一、实验 A：无锁 i++ 丢数据
################################################################################

【目的】
  用同一份数据规模，对比四种写法：
    无锁 i++ / synchronized / AtomicInteger / LongAdder

【代码】
  public class AtomicDemo {
      static int plainCount = 0;
      static int syncCount = 0;
      static final AtomicInteger atomicCount = new AtomicInteger(0);
      static final LongAdder adderCount = new LongAdder();

      static int THREADS = 10;        // 第二轮改成 100
      static int ITERS   = 10000;     // 第二轮改成 100000
      static int EXPECTED = THREADS * ITERS;

      interface Task extends Runnable { }   // ★ 必须是 Runnable

      public static void main(String[] args) throws Exception {
          // 方案 0：无锁
          for (int round = 1; round <= 5; round++) {
              plainCount = 0;
              long t0 = System.nanoTime();
              runThreads(() -> { for (int j = 0; j < ITERS; j++) plainCount++; });
              double ms = (System.nanoTime() - t0) / 1_000_000.0;
              System.out.printf("第%d次：期望 %d，实际 %d，耗时 %.2f ms%n",
                      round, EXPECTED, plainCount, ms);
          }
          // 方案 1：synchronized（每次自增都进同步块）
          // 方案 2：AtomicInteger.incrementAndGet()
          // 方案 3：LongAdder.increment()
          // 具体写法同上，这里省略重复代码
      }

      static void runThreads(Task task) throws InterruptedException {
          Thread[] ts = new Thread[THREADS];
          for (int i = 0; i < THREADS; i++) { ts[i] = new Thread(task); ts[i].start(); }
          for (Thread t : ts) t.join();
      }
  }

【实测数据】

  ── 规模一：10 线程 × 每线程 10000 次（期望 100,000）──
  ------------------------------------------------------------------
  方案              5 次实际值                              耗时
  ------------------------------------------------------------------
  无锁 i++      33764 / 24807 / 99626 / 100000 / 32279  0.58 ~ 4.76 ms
  synchronized  全部 100000                              5.55 ~ 14.51 ms
  AtomicInteger 全部 100000                              1.15 ~ 6.25 ms
  LongAdder     全部 100000                              0.63 ~ 7.25 ms
  ------------------------------------------------------------------

  ── 规模二：100 线程 × 每线程 100000 次（期望 10,000,000）──
  ------------------------------------------------------------------
  方案              5 次实际值                              耗时
  ------------------------------------------------------------------
  无锁 i++      6467182 / 10M / 10M / 10M / 10M          5.34 ~ 66.90 ms
  synchronized  全部 10M                                 483.99 ~ 526.48 ms
  AtomicInteger 全部 10M                                 143.17 ~ 160.93 ms
  LongAdder     全部 10M                                   9.45 ~ 50.06 ms
  ------------------------------------------------------------------

【三个反直觉的结论】

  1. 无锁不是"每次"都错
     规模一 5 次错 4 次；规模二 5 次只错第 1 次。
     ★ 并发 bug 是概率性的：跑一次没出错，不代表没问题。

  2. 规模二"更安全"是 JIT 预热在骗你
     第 1 次运行时还是解释执行，单次 count++ 更慢，
     两个线程同时处在"读-改-写"窗口里的时间占比更大 → 更容易丢更新。
     JIT 编译成本地代码后窗口变窄，后 4 次碰巧全对。
     ★ 所以"用第一轮数据下结论"本身就是错的。

  3. 高竞争下 LongAdder 完胜
     synchronized  ~500 ms
     AtomicInteger ~145 ms   ← CAS 在 100 线程下大量自旋失败
     LongAdder      ~10 ms   ← 分段累加，各打各的 Cell
     ★ 约 50 倍（vs synchronized）、14 倍（vs AtomicInteger）
     ★ 但 sum() 是近似值，强一致场景不能用。

【坑】
  · interface Task { void run(); } 不是 Runnable，new Thread(task) 直接编译失败
    → 必须写 interface Task extends Runnable { }
  · 计时用整数除法 (nanoTime - t0) / 1_000_000，1ms 以下全显示 0
    → 必须用 double + %.2f，否则看不出方案 2/3 的差距
  · 5 轮里第 1 轮是 JIT 冷启动，直接取平均会失真


################################################################################
  二、实验 B：while(!flag) 卡死
################################################################################

【目的】
  证明"一个线程改了变量，另一个线程不一定看得到"。

【代码】
  public class VisibilityDemo {
      static boolean flag = false;          // 不加 volatile

      public static void main(String[] args) throws Exception {
          Thread t = new Thread(() -> {
              long i = 0;
              while (!flag) { i++; }
              System.out.println("子线程看到 flag 变了，退出，i=" + i);
          });
          t.start();
          Thread.sleep(1000);
          flag = true;
          System.out.println("主线程已把 flag 改成 true");
          t.join(3000);
          System.out.println("子线程还活着吗：" + t.isAlive());
          System.exit(0);   // ★ 死循环线程是非守护线程，不强制退出 JVM 会一直挂着
      }
  }

  对照组：把 static boolean flag 改成 static volatile boolean flag。

【实测数据】
  ------------------------------------------------------------------
  flag 修饰        5 次结果
  ------------------------------------------------------------------
  不加 volatile    5/5 卡死（join 超时后 isAlive() = true）
  加  volatile      5/5 正常退出
  ------------------------------------------------------------------

【坑】
  · 这个实验不是所有 JVM 都能 100% 复现。JIT、CPU 缓存、
    甚至循环体里多一句 System.out.println 都可能让线程"碰巧"读到新值。
    ★ 复现不出来 ≠ 没有可见性问题。
  · 不加 volatile 的版本，主线程 join 超时退出后 JVM 不会结束，
    因为自旋线程是非守护线程 → 必须 setDaemon(true) 或 System.exit(0)。
    ★ 这本身是个考点：JVM 退出的条件是"所有非守护线程结束"。


################################################################################
  三、这两个实验怎么用进面试
################################################################################

  Q1「volatile 能保证 i++ 线程安全吗？」
    → 不能。volatile 只保证可见性 + 禁止重排，不保证原子性。
      i++ 是"读-改-写"三步。

  Q2「你怎么证明并发代码是安全的？」
    → 跑一次通过不算。我的做法是：
      先写期望值 → 多轮运行 → 放大规模 → 对比修复前后 → 制造必错场景。
      而且要知道：JIT 预热会让第一轮结果失真。

  Q3「你项目里的双重检查锁为什么判两次空？」
    → 第一次判空是快速路径（不进锁），
      第二次是因为等锁期间别人可能已经写好缓存了。

  ★ 三题的完整答案见 docs/面试题库/06-并发与线程安全.txt
